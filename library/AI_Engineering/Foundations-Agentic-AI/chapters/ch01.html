Part I · What Is an Agent? — Chapter 1

From Cybernetics to Language Agents

The idea of a machine that perceives, decides and acts is as old as computing. For seventy years it kept running into the same wall: nobody could tell the machine enough about the world. This chapter tells how that wall came down, and what new walls stood behind it.

Why this chapter

Ask a modern coding assistant to fix a failing test and watch what it does. It does not simply print an answer. It lists the files in the repository, opens the test, reads the function under test, forms a hypothesis, edits a line, runs the test suite, reads the error message it gets back, and tries again. Five minutes and forty model calls later it reports that the test passes and explains the change. Nothing in that sequence was scripted in advance. At every step a language model looked at everything that had happened so far and chose what to do next. That is what we mean by an agent, and since about 2023 such systems have moved from research demonstrations to products used by millions of people.

The word "agent" is older than the products, and it carries baggage. It has meant a thermostat, a theorem-proving planner, a robot that avoids obstacles, a software process that negotiates with other processes, and a neural network that plays Go. Each of these traditions solved part of the problem and left a precise, nameable part unsolved. Understanding those traditions is not antiquarianism. The questions an interviewer asks about a language agent (how does it recover from errors, how do you know when it is done, why does it loop, how do you keep it safe, why not just train it with reinforcement learning) were all asked before, about other kinds of agents, and the answers then shape the answers now.

This chapter therefore tells the history of agents as a chain of bottlenecks, in the same style as the companion book Introduction to LLM Engineering. We start with feedback control, move through symbolic planning, situated robotics and the agent-oriented software of the 1990s, then through reinforcement learning's triumphs and its appetite for experience. We then see how large language models supplied the missing ingredient, a broad prior over the world and an interface to it written in natural language, and how the first language agents of 2021–2023 worked and failed. Along the way we derive the single most important formula for anyone building agents, the compounding of per-step errors over a long task, and we define the measurements that the rest of the book uses.

1.1 What is an agent?

Before telling a history we need to know what it is a history of. The most useful definition is also the oldest and the plainest: an agent is anything that perceives its environment through sensors and acts on that environment through actuators, and does so repeatedly, so that what it perceives next depends partly on what it did. Russell and Norvig built their textbook around exactly this definition[1]. The definition is deliberately broad. A thermostat is an agent: it senses temperature and switches a heater. So is a chess program, a self-driving car and the coding assistant of the opening paragraph. What distinguishes them is not whether they are agents but how good their decisions are, how rich their actions are, and how much of the world they must cope with.

The essential feature is the loop. A function that maps an input to an output, once, is not an agent; a classifier that labels an image does not see the consequences of its label. An agent's output changes the world, and the changed world becomes its next input. This closure is what makes agents both powerful and difficult. It is powerful because the agent can gather information it did not have at the start, try something, observe the result and adjust. It is difficult because errors are no longer independent: a wrong action at step three changes every observation from step four onwards, and an agent that misreads the situation can dig itself deeper with every step.

Figure 1.1 draws the loop in the form we will use throughout the book. At step \(t\) the environment is in some state \(s_t\), which the agent usually cannot see directly. It receives an observation \(o_t\): a file's contents, a web page, a customer's message, the output of a test. The agent's decision rule, its policy \(\pi\), maps what it knows to an action \(a_t\): open a file, click a link, issue a refund, run a command. The environment responds by moving to a new state and emitting a new observation, and the loop repeats until the task is done, abandoned or out of budget. Chapter 2 makes this precise as a partially observable Markov decision process; for now the picture is enough.

Look at where the difficulty sits in Figure 1.1. The arrows are easy to draw and, for software environments, easy to build: an observation is a string, an action is a function call. All the intelligence lives in the box labelled "policy". For seventy years the central problem of building agents was how to fill that box. One can write the policy by hand, as a table of rules or a program; one can derive it by searching a model of the world, as planners do; or one can learn it from experience, as reinforcement learning does. Each approach demanded something that was in short supply. Hand-written policies needed programmers to anticipate every situation. Planners needed a complete, correct model of the world written in logic. Learned policies needed millions of trials. The history that follows is the history of those three shortages, and of the moment in 2022 when a fourth approach (borrow a policy from a model that has read most of the internet) briefly seemed to remove all three at once.

It is worth fixing the running examples in the vocabulary of Figure 1.1 now, since we will lean on them throughout. For the coding agent, the environment is a repository plus a shell; observations are file contents, command outputs and test results; actions are commands such as "open this file", "replace these lines", "run pytest"; the hidden state is everything about the code base the agent has not yet read. For the support agent, the environment is a booking database plus a human customer; observations are the customer's messages and the results of database queries; actions are messages to the customer and tool calls such as "look up reservation" or "issue refund"; the hidden state includes the customer's true intent. For the research agent, the environment is the web; observations are search results and page contents; actions are searches, page fetches and, finally, the written report. Three very different worlds, one loop.

Definition — agent, policy, episode

An agent interacts with an environment in discrete steps \(t=1,2,\dots\). At each step it receives an observation \(o_t\in\mathcal O\) and emits an action \(a_t\in\mathcal A\). Its history is \(h_t=(o_1,a_1,\dots,a_{t-1},o_t)\). A policy is a rule, possibly random, that maps histories to distributions over actions, \(a_t\sim\pi(\cdot\mid h_t)\). An episode is one run of the loop from an initial observation to termination, at most \(H\) steps later; the sequence of observations and actions it produces is a trajectory \(\tau\).

The definition leaves out one thing on purpose: a goal. A thermostat has one (a set temperature) and so does the coding agent (make the test pass), but the goal is not part of the loop; it is part of how we judge the loop. In reinforcement learning the goal is encoded as a reward signal; in classical planning, as a logical formula that the final state must satisfy; in a language agent, usually as a sentence in the first message. How the goal is communicated, and whether the agent's behaviour actually serves it, will turn out to be one of the deepest questions in the book, the subject of the alignment discussion in Chapter 20. With the loop defined, we can ask how the earliest engineers filled the policy box.

1.2 Feedback: the cybernetic agent (1943–1960)

The first scientific theory of agents came not from computer science, which barely existed, but from wartime control engineering. In 1943 Arturo Rosenblueth, Norbert Wiener and Julian Bigelow published a short paper, "Behavior, Purpose and Teleology", arguing that purposeful behaviour, in animals or machines, could be explained by negative feedback: the system measures the gap between where it is and where it wants to be, and acts to reduce the gap[2]. Wiener had been working on anti-aircraft fire control, where a gun must aim at the predicted position of a manoeuvring aircraft, and he saw the same structure in a hand reaching for a glass. His 1948 book Cybernetics named the field and made "feedback" a household word[3].

The cybernetic agent is the thermostat, generalised. It has a set point, a sensor, a comparator and an actuator. Its policy is a fixed mathematical function of the error, often linear, and its intelligence lies entirely in the choice of that function and its gains. Mathematically it is a dynamical system with a control input, and the theory of such systems (stability, overshoot, the trade-off between responsiveness and oscillation) became one of the great successes of twentieth-century applied mathematics. Autopilots, industrial process control and the guidance computers of the Apollo programme were all cybernetic agents in this sense.

For the mathematician — a controller is a policy

Consider the discrete-time linear system \(s_{t+1}=As_t+Ba_t+w_t\) with noise \(w_t\), and a quadratic cost \(\sum_t (s_t^\top Q_c s_t + a_t^\top R_c a_t)\). The optimal policy is linear, \(a_t=-Ks_t\), where \(K\) is obtained from the discrete algebraic Riccati equation: this is the linear–quadratic regulator. When \(s_t\) is observed only through noisy measurements, the optimal policy feeds a Kalman-filter estimate of \(s_t\) into the same gain (the separation principle). Every element of a modern agent is already here: a state, an observation model, a belief (the Kalman estimate), a policy and a cost. What the linear–quadratic world lacks is everything that makes language agents hard: discrete, combinatorial actions, an environment with no known equations, and goals that cannot be written as a quadratic form.

The cybernetic tradition left two permanent contributions. The first is the loop itself, and the insight that robust behaviour comes from correcting errors rather than from never making them. A language agent that runs the tests after every edit, and fixes what the tests report, is a feedback controller in exactly Wiener's sense; Chapter 7 is about this idea. The second is the vocabulary of state, observation and estimation that reinforcement learning later inherited. Its limitation was equally clear. A feedback controller works when we can write down the dynamics and the goal as equations of a few variables. It has nothing to say about how to fix a bug, book a flight or write a report, tasks whose "state" is a code base, a database or the web. For those, the pioneers of the next generation turned from differential equations to symbols and search.

1.3 Search and symbols: the planning agent (1956–1985)

In 1956, at the Dartmouth workshop that named artificial intelligence, Allen Newell and Herbert Simon demonstrated the Logic Theorist, a program that proved theorems from Principia Mathematica by searching through sequences of inference steps. Their next program, the General Problem Solver (GPS, 1959), generalised the idea into what they called means–ends analysis: compare the current state with the goal, find an operator that reduces the difference, and if that operator cannot yet be applied, make satisfying its preconditions a sub-goal[4]. This was the first explicit theory of how an agent could act purposefully in a symbolic world, and its recursive structure (achieve a goal by achieving sub-goals) reappears, almost unchanged, in the "plan-and-execute" agents of Chapter 6.

The planning tradition reached its classic form at the Stanford Research Institute between 1966 and 1972, with Shakey, the first mobile robot to reason about its own actions. Shakey's planner, STRIPS[5], represented the world as a set of logical facts, such as At(Robot, Room1) and Closed(Door2), and each action as an operator with preconditions, facts it adds and facts it deletes. A plan is a sequence of operators that transforms the initial set of facts into one satisfying the goal. Finding a plan is a search problem in the space of fact sets, and the same project produced the A* algorithm (Hart, Nilsson and Raphael, 1968)[6], which finds a shortest path in a graph when given an admissible heuristic: an estimate of the remaining distance that never overestimates it.

Definition — a STRIPS planning problem

Let \(F\) be a finite set of propositions. A state is a subset \(s\subseteq F\). An operator is a triple \((\mathrm{pre},\mathrm{add},\mathrm{del})\) of subsets of \(F\); it is applicable in \(s\) if \(\mathrm{pre}\subseteq s\), and then yields \(s'=(s\setminus\mathrm{del})\cup\mathrm{add}\). Given an initial state \(s_0\) and a goal \(\mathcal G\subseteq F\), a plan is a sequence of operators whose successive application is defined and produces a state containing \(\mathcal G\). Deciding whether a plan exists is PSPACE-complete in general (Bylander, 1994), because the state space has \(2^{\lvert F\rvert}\) elements and plans can be exponentially long.

The planning agent fills the policy box of Figure 1.1 in a principled way: the policy is "search a model of the world for a plan, then execute it". When the model is right, this is enormously powerful. A planner can solve problems it has never seen, guarantee optimality with A*, and explain its decisions by pointing to the plan. Its descendants run logistics, schedule spacecraft and control factory robots to this day, and in Chapter 6 we will see language models used to write planning problems in the PDDL language that grew out of STRIPS, so that a classical planner can solve them.

Three problems stopped symbolic planning from producing general agents, and each will reappear in modern form. The first is the frame problem, posed by McCarthy and Hayes in 1969[7]: describing what an action changes is easy, but describing everything it does not change (moving a box does not change the colour of the walls, the time zone, or the price of bread) requires either a vast number of axioms or a closed-world assumption that breaks as soon as the world surprises you. The second is combinatorial explosion: realistic problems have so many facts that unguided search is hopeless, and good heuristics must be hand-crafted for each domain. The third, and decisive, is the knowledge-acquisition bottleneck. Someone had to write the facts and the operators, by hand, in logic, and keep them consistent with a world that changes. The expert systems of the late 1970s and 1980s, such as MYCIN for diagnosing infections and XCON for configuring computers, ran into the same wall at commercial scale: they worked impressively inside their narrow domains and failed abruptly at the edges, and maintaining their rule bases became more expensive than the value they produced.

The planning agent's lesson for us is therefore double-edged. Search over a model is a superb way to choose actions, and modern agents that plan, back-track and verify are drawing on it. But a policy is only as good as the model it searches, and nobody can write by hand a model of a code base, a customer or the web. The next generation of researchers drew the conclusion that perhaps agents should not need a model at all.

1.4 Situated, rational and software agents (1986–2000)

In 1986 Rodney Brooks, building robots at MIT, argued that the planning tradition had the problem backwards[8]. Shakey spent minutes thinking between movements because it maintained a symbolic model of the world and replanned whenever the model changed. Brooks's robots had no central model at all. Their subsumption architecture stacked simple reactive behaviours ("avoid obstacles", "wander", "follow walls") in layers, each mapping sensor readings directly to motor commands, with higher layers able to suppress lower ones. "The world is its own best model," he wrote: rather than represent the world, look at it again. His insect-like robots walked over rough terrain that would have paralysed a planner, and the approach later reached millions of homes in the Roomba vacuum cleaner.

Reactive agents traded deliberation for robustness. They respond quickly and degrade gracefully, but they cannot pursue a goal that requires a long sequence of non-obvious steps, because nothing in them looks ahead. The 1990s spent much of their effort reconciling the two traditions. The most influential synthesis was the belief–desire–intention (BDI) model, grounded in Michael Bratman's philosophy of practical reasoning and turned into an architecture by Anand Rao and Michael Georgeff[9]. A BDI agent maintains beliefs about the world, a set of desires (goals it might pursue), and intentions: the goals and partial plans it has committed to. The crucial idea is commitment. A BDI agent does not replan from scratch at every step, which would be slow and erratic; it sticks with its intentions until they succeed, become impossible, or are overtaken by something more important, and it fills in the details of its plans only as it goes.

BDI agents were deployed in air-traffic management and telecommunications, and the decade also produced the idea of multi-agent systems: populations of software agents with their own goals, communicating through agent communication languages and negotiating with protocols borrowed from economics. Wooldridge and Jennings's 1995 survey[10] listed the properties such agents should have, and the list reads like a product brief for 2025: autonomy (operating without direct human intervention), social ability (interacting with other agents and humans), reactivity (responding to changes in a timely way) and pro-activeness (taking the initiative in pursuit of goals). Russell and Norvig's 1995 textbook[1] reorganised the whole of AI around the rational agent, one that acts to maximise its expected performance measure given what it has perceived, and that framing is the one this book adopts.

What the 1990s did not solve was the knowledge problem. A BDI agent's plans came from a hand-written plan library; a multi-agent marketplace needed hand-written ontologies so that agents could understand each other's messages. The vision was right and the architecture was sensible, but filling the policy box still required people to write down, in advance, what to do in every circumstance that mattered. The obvious alternative, which had been developing quietly alongside, was to let the agent learn what to do from experience.

1.5 Learning to act: reinforcement learning (1989–2019)

Reinforcement learning (RL) replaces the hand-written policy with a learned one. The agent is given a scalar reward \(r_t\) after each step and must learn a policy that maximises the expected sum of rewards, without being told which actions are good. The mathematical foundation is Bellman's dynamic programming of the 1950s; the learning algorithms came later. Sutton's temporal-difference learning (1988) and Watkins's Q-learning (1989) showed how to learn the value of states and actions from sampled experience alone, by nudging each estimate towards the reward just received plus the estimated value of where the agent ended up[11]. For the first time an agent could improve itself without anyone writing a model of the world or a rule for each situation.

The first spectacular success was Gerald Tesauro's TD-Gammon (1992–1995), a small neural network that learned backgammon by playing against itself and reached the level of the best human players[12]. Then, for almost two decades, progress was steady but unspectacular, because the tabular and linear methods of the time could not handle large observation spaces. The breakthrough came when RL was combined with deep networks. DeepMind's Deep Q-Network (DQN), announced in 2013 and published in Nature in 2015, learned to play 49 Atari games from raw pixels and the score alone, reaching at least three-quarters of a professional human tester's score on 29 of them, with one architecture and one set of hyperparameters[13]. AlphaGo defeated Lee Sedol at Go in March 2016[14], combining a learned policy and value network with Monte Carlo tree search (the planning tradition again, now guided by learned heuristics). AlphaGo Zero (2017) learned Go with no human games at all, and OpenAI Five and AlphaStar reached professional level in the team video games Dota 2 and StarCraft II by 2019.

These systems were agents in the full sense of Figure 1.1, and they were superhuman. Why did they not lead directly to agents that could fix bugs or book flights? Three walls stood in the way, and each one is a precise statement about what a policy needs.

The first wall is sample efficiency. DQN was trained on 50 million frames for each game, which its authors equate to about 38 days of continuous play, to reach a level a human reaches in a couple of hours. OpenAI Five played the equivalent of about 45,000 years of Dota 2 over ten months of training. Such numbers are affordable in a simulator that runs thousands of times faster than real time; they are unthinkable for an agent whose every action costs real money, touches a real customer or modifies a real code base. The second wall is reward specification. A game comes with a score. Most useful tasks do not, and an agent that maximises a carelessly written reward will find and exploit every loophole in it, a phenomenon known as reward hacking that we will meet again in Chapter 18. The third wall, and the deepest, is the absence of priors. A deep RL agent starts as a randomly initialised network. It does not know that doors open, that text on a screen means something, or that a failing test suggests a bug in the function it tests. Everything must be learned from the reward signal, in each new environment, from scratch.

Put the three walls together and the problem of the policy box looks like this. Symbolic AI could not write down enough knowledge about the world; reinforcement learning could not gather enough experience of it. What was needed was a source of broad, general knowledge about the world (what things are, how they work, what people usually do next) that an agent could start from, so that learning or search would only have to fill in the details. Between 2018 and 2020 such a source appeared, from a direction almost nobody in the agents community was watching.

1.6 Language models as priors (2018–2022)

A language model is trained to predict the next token of text, and nothing more. The companion book tells the story of how that objective, applied with the Transformer architecture to ever larger corpora, produced models of startling generality; here we need only the consequence. To predict the next word of a recipe, a stack-overflow answer, a legal contract, a bug report and its fix, a model must represent, implicitly, an enormous amount about the world those texts describe: that ovens are preheated before baking, that a KeyError means a dictionary lacks a key, that a refund usually requires a booking reference. Pre-training on trillions of tokens is, among other things, a way of compressing the accumulated written experience of humanity into a conditional distribution \(p_\theta(x_i\mid x_{<i})\).

The moment this mattered for agents was GPT-3 in 2020[15]. Brown and colleagues showed that a 175-billion-parameter model could perform tasks it was never trained on, given only a description and a few examples in its prompt: translate, answer questions, unscramble words, write simple code. They called this in-context learning. For anyone thinking about policies the implication was immediate. Here was a function that, given a description of a situation in words, produced a plausible next step in words, with no task-specific training at all. If the situation could be described as text and the action expressed as text, the language model was a policy, and it came with the broad prior that reinforcement learning lacked. It knew roughly what doors, files, flights and functions are.

Two further developments made the prior usable. The first was instruction tuning and reinforcement learning from human feedback. InstructGPT (Ouyang et al., 2022)[16] fine-tuned GPT-3 on demonstrations of following instructions and then optimised it against a reward model trained on human preferences, and a 1.3-billion-parameter InstructGPT was preferred by human raters over the 175-billion-parameter GPT-3. A raw pre-trained model continues text; an instruction-tuned model does what it is asked, which is what a policy must do. Chapter 3 explains both stages, and Chapter 17 derives the mathematics. The second development was chain-of-thought prompting (Wei et al., January 2022)[17]: asking the model to write out intermediate reasoning before its answer substantially improved accuracy on multi-step problems. A policy that can deliberate in words before choosing an action is far more capable than one that must answer in a single step, and Chapter 5 is devoted to why.

It is important to be precise about what the language model did and did not supply. It supplied a prior over behaviour: given a description of a situation, a distribution over sensible things to do next, drawn from everything humans have written about similar situations. It did not supply grounding. A model trained on text has never run a command or seen the result; it can only guess what a file contains, and when it guesses wrong it does so fluently. It did not supply memory beyond its context window, nor reliability: a model that is right 90% of the time on each step is, as §1.8 shows, nearly useless over a long task. The first language agents were attempts to supply grounding by closing the loop of Figure 1.1, letting the model act, and writing the results back into its context.

1.7 The first language agents (2021–2023)

The earliest systems that used a language model as the policy of an agent all appeared within about eighteen months, from several laboratories at once, which is usually the sign that an idea's time has come. Each solved the grounding problem for one kind of environment.

WebGPT (OpenAI, December 2021)[18] fine-tuned GPT-3 to answer questions by operating a text-based web browser. The model's actions were commands such as Search, Click on link, Quote and Scroll, emitted as text; the browser's responses were written back into the prompt. It was trained first by imitating human demonstrations and then with rejection sampling against a learned reward model, and its answers, which cited the pages they quoted, were preferred to human-written answers more than half the time. It is the direct ancestor of the research agent in this book. SayCan (Google, April 2022)[19] grounded a language model in a robot: the model scored how useful each of the robot's pre-trained skills would be for an instruction such as "I spilled my drink, can you help?", and a learned value function scored how likely each skill was to succeed from the robot's current state. Multiplying the two, "say" times "can", chose the action. MRKL (AI21, May 2022)[20] proposed a modular architecture in which a language model routes sub-problems to external "experts" such as a calculator, a database or a weather API, the conceptual seed of tool calling.

The design that unified these threads and became the template for nearly everything since was ReAct, by Shunyu Yao and colleagues at Princeton and Google, released in October 2022[21]. ReAct's insight is to interleave two kinds of output in a single text stream: thoughts, free-form reasoning that does not affect the environment, and actions, structured commands that do. After each action the environment's response is appended as an observation, and the model continues. Reasoning helps the model decide what to do and keep track of what it has learned; acting lets it gather the information that reasoning alone would have to hallucinate. On the question-answering benchmark HotpotQA, chain-of-thought alone often invented facts, and acting alone often wandered; the combination, with a simple Wikipedia search tool, did markedly better on fact verification and was far more interpretable. Figure 1.2 shows the shape of a ReAct trajectory for the research agent.

Figure 1.2 repays a careful reading, because three features of every modern agent are already visible in it. First, the policy is the language model conditioned on the whole history: the second thought ("confirm Shakey was built there") is only possible because the first observation is in the context. The context is the agent's entire working memory, a point Chapter 2 formalises and Chapter 4 turns into an engineering discipline. Second, the program around the model, which we will call the harness (or scaffold), does real work: it parses the action out of the text, executes it, formats the result and decides when to stop. Third, the context grows with every step, and every later model call must read all of it. In Figure 1.2 this is harmless; in a coding episode of forty steps that reads large files, it dominates the cost, as §1.10 computes.

Within months the remaining pieces arrived. Toolformer (Meta, February 2023)[22] showed that a model could teach itself when to call APIs (a calculator, a search engine, a calendar) by inserting candidate calls into text and keeping those that made the following tokens more predictable, the beginning of training models to use tools rather than prompting them to. Reflexion (March 2023)[23] had the agent write a verbal post-mortem after a failed attempt and condition its next attempt on it, a form of learning that changes the context rather than the weights (Chapter 7). Generative Agents (Park et al., April 2023)[24] populated a simulated village with 25 language agents that remembered, reflected and planned their days, and introduced a memory architecture that Chapter 13 dissects. Voyager (May 2023)[25] played Minecraft by writing code for new skills, testing them, and storing the working ones in a growing library, an agent that accumulated competence. By mid-2023 the basic vocabulary of the field (reasoning, tools, observations, reflection, memory, skills) was in place.

1.8 The 2023 moment, and the arithmetic of long tasks

In late March 2023, days after GPT-4's release, an open-source project called Auto-GPT appeared on GitHub. It wrapped GPT-4 in a loop: given a high-level goal such as "grow my business", the model would write itself a task list, choose a task, execute it with tools (web search, file writing, code execution), record the result in a memory, and continue indefinitely. A similar project, BabyAGI, appeared the same week. Auto-GPT became one of the fastest-growing repositories in GitHub's history, and for a few weeks "autonomous agents" were the most discussed topic in technology. The demonstrations were exciting. The results, for almost everyone who tried to use them for real work, were disappointing. The agents looped, repeating the same search; they lost track of the goal; they declared success on tasks they had not done; and they consumed a great deal of money in API calls doing so.

Why did a system built from the most capable model of its day fail so reliably? The simplest model of the answer is also the most important formula in this book. Suppose a task requires \(H\) steps, each step must be done correctly for the task to succeed, and the agent gets each step right with probability \(\rho\), independently of the others. Then

\[ \Pr[\text{task succeeds}] \;=\; \rho^{H} \;=\; e^{H\ln\rho} \;\approx\; e^{-H(1-\rho)} \quad\text{for } \rho \text{ near } 1. \]

The approximation uses \(\ln\rho\approx-(1-\rho)\) and shows what really matters: success decays exponentially in the product of the horizon and the per-step error rate \(1-\rho\). An agent that is right 95% of the time on each step, a figure that sounds excellent, succeeds on a 10-step task with probability \(0.95^{10}\approx0.60\) and on a 50-step task with probability \(0.95^{50}\approx0.077\). The horizon at which success falls to one half is \(H_{1/2}=\ln 2/(-\ln\rho)\approx 0.69/(1-\rho)\): about 14 steps at \(\rho=0.95\), 69 steps at \(\rho=0.99\) and 693 steps at \(\rho=0.999\). Every factor of ten in reliability buys a factor of ten in the length of task the agent can complete. Figure 1.3 plots the curves.

Figure 1.3 explains the Auto-GPT experience. A goal such as "research the market and write a business plan" requires dozens of steps, and the GPT-4 of early 2023, operating through an untested harness with no recovery mechanism, was perhaps 90% reliable per step on such work. The blue curve (\(\rho=0.95\)) is already below 10% by fifty steps; the orange curve (\(\rho=0.90\)) is below 1%. No amount of cleverness in the task list could rescue an exponential.

The model is crude, and Chapter 2 refines it, but its crudeness is instructive because each of its assumptions points to a remedy. The model assumes every step must be right, so a single error is fatal; real agents can detect and recover from errors (run the test again, notice the search returned nothing useful), which converts some failures into a few extra steps rather than a failed task, and Chapter 2 shows that recovery changes the exponential decay into something much gentler. It assumes \(\rho\) is fixed; better models, better tools and better context raise \(\rho\), and since \(H_{1/2}\) scales as \(1/(1-\rho)\), improving per-step reliability from 95% to 99% multiplies the feasible horizon by five. It assumes the task needs \(H\) steps; good tool design and decomposition shorten \(H\), for example a single "run the test suite and summarise failures" tool in place of five separate commands. And it assumes independence; in reality errors are correlated (an agent that misunderstood the task gets every step wrong), which is why verification against the goal, by tests, by checkers or by a human, matters so much. Almost every technique in Parts II–IV of this book can be classified by which of these four levers it pulls.

Drill 1.1 — How reliable must each step be?

You want the coding agent to complete a 50-step task with probability at least 90%, with no error recovery. What per-step reliability is needed? Solve \(\rho^{50}\ge0.9\): \(\rho\ge0.9^{1/50}=e^{\ln 0.9/50}=e^{-0.10536/50}=e^{-0.002107}\approx0.99789\). Each step must succeed 99.79% of the time: about one error in 475 steps. If instead the agent can detect and fix any error at the cost of two extra steps, the requirement is completely different; Chapter 2 computes it. The lesson: without recovery, long-horizon reliability demands per-step accuracy far beyond what any 2023 model offered.

1.9 Making agents work (2023–2026)

The years after Auto-GPT were spent pulling the four levers of §1.8, and the result was a sequence of genuinely useful agents. It is easiest to understand as a chain of bottlenecks.

Bottleneck: parsing. Early agents asked the model to write actions in an ad-hoc text format and parsed them with regular expressions; a misplaced bracket was a failed step. In June 2023 OpenAI added function calling to its API: the developer declares tools as JSON schemas, and the model, fine-tuned for the purpose, emits a structured call that the harness can execute directly. Anthropic, Google and the open-model ecosystem followed, and constrained decoding later made schema-valid output guaranteed rather than merely likely (Chapter 8). A whole class of per-step errors disappeared, raising \(\rho\).

Bottleneck: measurement. In October 2023 Jimenez and colleagues released SWE-bench[26]: 2,294 real GitHub issues from twelve popular Python repositories, each paired with the tests that the human fix made pass. A system is given the repository and the issue text and must produce a patch; it succeeds if the hidden tests pass. At release the best system resolved under 2% of issues. The benchmark gave the field what Atari had given deep RL, a hard, realistic, automatically scored target, and its curated 500-task subset, SWE-bench Verified (August 2024), became the standard yardstick for coding agents. Figure 1.4 below tracks it.

Bottleneck: the interface. In May 2024 the SWE-agent paper[27] showed that the design of the tools themselves, which it called the agent–computer interface, mattered as much as the model: a file viewer that shows a hundred lines with line numbers, an editor that rejects edits that break the syntax, and a search command with concise output raised GPT-4's resolution rate several-fold compared with a raw shell. Tools designed for models, not for humans, shorten \(H\) and raise \(\rho\) at once (Chapter 10).

Bottleneck: reasoning per step. In September 2024 OpenAI released o1, the first widely available reasoning model, trained with reinforcement learning to think at length before answering; DeepSeek-R1 (January 2025)[28] showed openly how such training works with rewards that can be checked automatically. Spending more computation on each decision raises per-step reliability on hard steps (Chapter 5), and training on whole agentic tasks with verifiable rewards (Chapter 18) teaches recovery behaviours that prompting never produced.

Bottleneck: reach. In October 2024 Anthropic released computer use, letting a model operate a desktop through screenshots, mouse and keyboard, and benchmarks such as OSWorld measured how far such agents had to go (Chapter 11). In November 2024 it published the Model Context Protocol (MCP)[29], an open standard for connecting models to tools and data sources, which was adopted across the industry within months (Chapter 12). Agents could now act on almost any software a person could.

Bottleneck: horizon. Through 2025, coding agents that run in a terminal or a cloud sandbox for minutes to hours (Claude Code, OpenAI's Codex, Cursor's agent mode, Devin and others) and deep research agents that read hundreds of pages before writing a report became everyday tools. Making them work required managing a context that overflows (compaction, notes, sub-agents; Chapter 14) and keeping them safe while they act with real permissions (Chapter 20).

Figure 1.4 shows the outcome of pulling all the levers together on a single benchmark: from about a third of real issues resolved in mid-2024 to more than three-quarters a year later. Two cautions are needed when reading such a chart, and an interviewer will expect you to give them. First, the points are developer-reported numbers with different scaffolds, sampling settings and occasionally different task subsets; they show the trend, not a controlled comparison (Chapter 19 discusses how to compare agents properly). Second, a benchmark that is heavily optimised against saturates, and its remaining failures are often ambiguous or under-specified tasks rather than hard ones; SWE-bench Verified was itself created because human annotators found that a large fraction of the original tasks had under-specified issue texts or tests that rejected valid fixes.

A more general measure was proposed in March 2025 by Kwa and colleagues at METR[30]. They timed skilled humans on a suite of software and research tasks ranging from seconds to many hours, ran AI agents on the same tasks, and for each model computed its 50% time horizon: the length of task, measured in human time, that the model completes with probability one half. Figure 1.5 plots their estimates on a logarithmic axis. The striking finding is how straight the line is: the time horizon of frontier models doubled roughly every seven months between 2019 and 2025, from a few seconds for GPT-2 to around an hour for the best models of early 2025 and over two hours by the second half of the year.

How should a mathematician read Figure 1.5? A straight line on a log scale is exponential growth, and seven-month doubling is a growth factor of about \(2^{12/7}\approx3.3\) per year. Extrapolations of such curves are dangerous (the measurement is noisy, the task suite is specific, and the 50% threshold says nothing about the 99% reliability a production system needs), but the figure makes one point unarguable: the horizon over which agents are useful has been growing fast and steadily, and it is the horizon, through \(\rho^H\), that decides whether an agent is a toy or a tool. Note also that the time horizon at 80% success, which METR also reports, is several times shorter than at 50%. The gap between "sometimes works" and "reliably works" is exactly the gap between the curves of Figure 1.3.

By 2025 the typical language agent had settled into a recognisable anatomy, drawn in Figure 1.6. Its policy is a language model; the harness builds the context for each call from a system prompt, the task, tool definitions, memory and the history; the model's output is parsed into tool calls that act on the environment; results return as observations; and an outer layer decides when to stop, when to ask a human, and what to remember. Every chapter of this book zooms into one part of this picture.

Figure 1.6 deserves one more observation: only the orange box is the model. The rest is ordinary software, and a large part of the progress described in this section came from improving that software rather than the model. This is good news for an engineer. When an agent fails, the cause is as often a badly assembled context, an ambiguous tool, a missing check or an absent stopping rule as it is a lack of model capability, and those causes are within the engineer's control. Anthropic's widely read 2024 guide Building Effective Agents[31] made the same point from practice: the most successful deployments it saw used simple, composable patterns, not elaborate frameworks, and added autonomy only where it measurably helped.

1.10 Measuring an agent

Every claim in the history above was a claim about measurement: a success rate on a benchmark, a time horizon, a cost. Before we can improve agents we need to say precisely what we measure, and the measures for agents differ in important ways from those for models that answer a single question. Four quantities matter, and every design decision in this book trades among them: how often the agent succeeds, how consistently it succeeds, what an episode costs, and how long it takes.

Success, once and repeatedly

The basic measure is the success rate: the fraction of tasks in an evaluation set on which the agent's final state satisfies the goal, as judged by a test suite, a database check or a grader. For a single task, let \(p\) be the probability that one attempt succeeds. Two derived quantities answer two different questions, and confusing them is a common interview mistake.

The first question is: if I may try \(k\) times and keep the best, how likely am I to succeed? This is pass@\(k\), introduced for code generation by Chen et al. (2021)[32]. With independent attempts, \(\text{pass@}k = 1-(1-p)^k\), which rises towards one as \(k\) grows. It is the right measure when a cheap, reliable check can pick out a successful attempt, for example a hidden test suite at development time, or a human reviewing several candidate patches. The second question is: if the agent faces this task \(k\) times, as a deployed system serving \(k\) customers would, how likely is it to succeed every time? This is pass^\(k\) ("pass hat \(k\)"), introduced by the τ-bench paper (Yao et al., 2024)[33] for exactly that reason: \(\text{pass}^k = p^k\), which falls as \(k\) grows. A customer-service agent that resolves a request 60% of the time is not "60% good"; across eight customers with the same request, all eight are served correctly with probability \(0.6^8\approx1.7\%\).

Definition — pass@k and pass^k over a task set

Let an evaluation set have \(m\) tasks, and let \(p_j\) be the per-attempt success probability on task \(j\). Then

\[ \text{pass@}k=\frac1m\sum_{j=1}^m\Big(1-(1-p_j)^k\Big),\qquad \text{pass}^k=\frac1m\sum_{j=1}^m p_j^{\,k}. \]

Both equal the mean success rate \(\bar p=\frac1m\sum_j p_j\) at \(k=1\). They are estimated from \(n\ge k\) attempts per task, of which \(c_j\) succeed, by the unbiased estimators \(1-\binom{n-c_j}{k}\big/\binom{n}{k}\) and \(\binom{c_j}{k}\big/\binom{n}{k}\) respectively, averaged over tasks.

The averaging over tasks has a consequence that is easy to miss and important in practice: pass^\(k\) depends on how success is distributed across tasks, not just on its mean. By Jensen's inequality, since \(x\mapsto x^k\) is convex, \(\frac1m\sum_j p_j^k\ge\bar p^{\,k}\), with equality only when every task has the same difficulty. An agent whose successes are concentrated on tasks it solves reliably is far more consistent than one whose successes are spread thinly across many tasks it solves by luck, even at the same average success rate. The worked example makes this concrete.

Worked example — consistency depends on the spread of difficulty

Two support agents each have an average success rate of 60% on an evaluation set of airline requests. Agent A succeeds with probability 0.6 on every task. Agent B succeeds with probability 0.95 on half the tasks (routine changes) and 0.25 on the other half (complicated refunds): its mean is \(\tfrac12(0.95+0.25)=0.6\).

pass^8. Agent A: \(0.6^8=0.0168\). Agent B: \(\tfrac12(0.95^8+0.25^8)=\tfrac12(0.6634+0.0000153)=0.332\). Agent B is twenty times more likely to handle eight repetitions of a task correctly.

pass@8. Agent A: \(1-0.4^8=0.99934\). Agent B: \(\tfrac12\big[(1-0.05^8)+(1-0.75^8)\big]=\tfrac12(1.0000+0.8999)=0.950\). With eight tries and a perfect checker, A is better.

Interpretation. Same average, opposite rankings. Agent B is the better product: it is reliable on half of the traffic, which can be routed to it with confidence, while the other half can be escalated to a human. Agent A is never reliable on anything. When someone quotes a single success rate for an agent, ask for pass^\(k\) or for the distribution of per-task success.

Cost and time

A model that answers a question makes one call. An agent makes many, and each call reads the whole context, which grows with every step. This makes the cost of an agent episode grow faster than its length, and it is why a technique that is a minor optimisation for chat, prompt caching, is essential for agents. When consecutive calls share a long common prefix (the system prompt, the tool definitions and the history so far), a serving system can keep the internal state computed for that prefix and charge much less for re-reading it; at our reference prices, cached input costs $0.30 per million tokens against $3 for fresh input. The companion book explains the mechanism (the KV cache and prefix caching); Chapter 4 explains how to arrange a context so that caching works. Here we only compute what it is worth.

Worked example — the cost of one coding-agent episode

The coding agent runs for \(H=40\) steps. The first call's context holds 8,000 tokens (system prompt, tool definitions and the issue). Each step appends about 2,500 tokens: roughly 300 tokens of model output (reasoning and a tool call) plus 2,200 tokens of observation (file contents, test output). So the context at step \(t\) is \(n_t=8{,}000+2{,}500(t-1)\) tokens.

Input tokens. \(\sum_{t=1}^{40}n_t=40\times8{,}000+2{,}500\sum_{t=1}^{40}(t-1)=320{,}000+2{,}500\times780=2{,}270{,}000\). The agent reads 2.27 million tokens to produce \(40\times300=12{,}000\) output tokens: a ratio of almost 190 to 1.

Without caching. \(2.27\,\text{M}\times\$3/\text{M}=\$6.81\) for input plus \(0.012\,\text{M}\times\$15/\text{M}=\$0.18\) for output: $6.99 per episode.

With caching. Only the newly appended tokens are fresh: \(8{,}000+39\times2{,}500=105{,}500\) tokens at $3/M, or $0.32. The remaining \(2{,}164{,}500\) tokens are cache reads at $0.30/M, or $0.65. With output, the total is $1.15, six times cheaper. (Real providers may also charge a premium for writing to the cache; Chapter 4 includes it.)

Time. Per step, prefilling the 2,500 fresh tokens takes \(2{,}500/5{,}000=0.5\) s, decoding 300 tokens takes \(300/60=5\) s, and suppose the tool (often running tests) takes 3 s on average. That is 8.5 s per step and \(40\times8.5=340\) s, about 6 minutes per episode, of which 59% is the model writing. Decode speed, not reading, dominates the wall clock.

The example generalises into a rule worth remembering. If the context grows by \(\Delta\) tokens per step from an initial \(n_1\), the total input over \(H\) steps is \(Hn_1+\Delta H(H-1)/2\): quadratic in the horizon. Doubling the length of a task roughly quadruples its uncached input cost when the history dominates. Caching reduces the constant by an order of magnitude but not the quadratic shape, and so long-horizon agents must also stop the context from growing without bound, by summarising, discarding stale observations or delegating to sub-agents with fresh contexts. Those are the techniques of Chapter 14. The time computation teaches the complementary lesson: for latency, what matters is the number of sequential steps and the number of tokens the model writes, so the levers are fewer steps, shorter outputs and parallel tool calls (Chapter 21).

Drill 1.2 — pass@k for a coding agent

A coding agent resolves a particular issue on 30% of attempts. (a) With five independent attempts and the hidden tests as a checker, what is pass@5? (b) What is pass^5? (c) How many attempts are needed for pass@\(k\ge0.95\)?

(a) \(1-0.7^5=1-0.16807=0.832\). (b) \(0.3^5=0.00243\). (c) Solve \(0.7^k\le0.05\): \(k\ge\ln0.05/\ln0.7=2.996/0.3567=8.4\), so \(k=9\). Note the cost: nine full episodes, at the $1.15 of the worked example, is about $10 to be 95% sure of one fix, and only if a reliable checker exists. Chapter 6 develops this into the theory of best-of-\(n\) search with imperfect verifiers.

A research agent starts with a 3,000-token context and adds 6,000 tokens per step (each fetched page is long). (a) How many input tokens does a 30-step episode read? 1.11 Why now, and what remains hard

We can now answer the question this chapter began with. Agents became practical in 2023–2025 because, for the first time, all three of the historical shortages were relieved at once. The knowledge that symbolic AI could not write down, and that reinforcement learning could not gather, arrived as a prior: a pre-trained, instruction-tuned language model already knows roughly how files, browsers, airlines and programming languages work. The interface that robotics struggled with became trivial for software environments: an observation is text, an action is a structured function call, and protocols like MCP make any software reachable. And the learning that RL demanded at enormous scale became affordable in a new form: starting from the prior, reinforcement learning on verifiable tasks needs comparatively few samples to teach a model to reason longer, recover from errors and use tools well, because it is shaping an already-competent policy rather than creating one from nothing.

Reliability: per-step error compounds, and even the best agents of 2025 completed only about half of the tasks a skilled human does in two hours. And learning: we would like agents to improve from their own experience, which brings back every difficulty of reinforcement learning, now on policies with hundreds of billions of parameters.

Looking ahead

This chapter used a deliberately informal picture of an agent: a loop of observations and actions with a language model inside, and a crude reliability model in which each step independently succeeds with probability \(\rho\). Both need to be made precise before we can reason with them. What exactly is the "state" an LLM agent is in, when the environment is a code base it has only partly read? In what sense is the context a sufficient summary of the past, and when does it fail to be? What does it mean for an agent to recover from an error, and how does recovery change the \(\rho^H\) law? When is a fixed workflow better than an autonomous agent? Chapter 2 answers these questions by formalising the agent as a policy in a partially observable Markov decision process, the mathematical object that the rest of the book builds on.

Chapter summary

  • An agent is a closed loop: it observes, chooses an action with its policy, and the action changes what it observes next. The difficulty of agents is concentrated in the policy, and in the fact that errors propagate around the loop.
  • Cybernetics (1948) gave us feedback and the vocabulary of state and estimation, but needed equations for the world. Symbolic planning (GPS, STRIPS, A*) chose actions by searching a world model, but foundered on the frame problem and knowledge acquisition. Situated and BDI agents added reactivity and commitment but still relied on hand-written plans.
  • Deep reinforcement learning learned superhuman policies from reward alone, but needed millions of trials, a well-specified reward and a simulator, and started with no prior knowledge.
  • Language models supplied a broad prior over behaviour. WebGPT, SayCan, MRKL and ReAct (2021–2022) grounded them by closing the loop; ReAct's interleaving of thoughts, actions and observations is the template for modern agents.
  • Per-step errors compound: an \(H\)-step task succeeds with probability \(\rho^H\approx e^{-H(1-\rho)}\), and the half-success horizon is \(\approx0.69/(1-\rho)\). The four levers are recovery, higher \(\rho\), shorter \(H\) and verification.
  • Function calling, realistic benchmarks (SWE-bench), agent–computer interfaces, reasoning models, computer use, MCP and RL on verifiable tasks made agents useful between 2023 and 2026; METR's time horizon doubled roughly every seven months.
  • pass@\(k\) \(=1-(1-p)^k\) measures best-of-\(k\) with a checker; pass^\(k\) \(=p^k\) measures consistency. Over a task set, pass^\(k\) depends on the spread of per-task difficulty.
  • Agent input cost grows quadratically with the horizon; prompt caching reduces it several-fold, and wall-clock time is dominated by sequential steps and output tokens.

In STRIPS, applying an operator \((\mathrm{pre},\mathrm{add},\mathrm{del})\) to a state \(s\) with \(\mathrm{pre}\subseteq s\) yields:

  1. \(s\cup\mathrm{add}\cup\mathrm{del}\)
  2. \((s\setminus\mathrm{del})\cup\mathrm{add}\)
  3. \(\mathrm{add}\setminus\mathrm{del}\)
  4. \(s\cap\mathrm{add}\)
Remove the deleted facts, then add the new ones. Facts not mentioned are assumed unchanged, which is STRIPS's pragmatic answer to the frame problem.

The frame problem is the difficulty of:

  1. Rendering a robot's camera frames quickly enough
  2. Choosing the right heuristic for A*
  3. Specifying everything an action does not change, without an unmanageable number of axioms
  4. Splitting a long task into frames of fixed length
McCarthy and Hayes (1969) observed that formalising the non-effects of actions is the hard part of a logical world model. STRIPS sidesteps it with a closed-world, unchanged-unless-stated assumption.

  1. Is computed in constant time
  2. Never overestimates the true remaining cost
  3. Never underestimates the true remaining cost
  4. Is learned from data
An admissible heuristic is optimistic: \(h(s)\le h^*(s)\). With such a heuristic A* never discards a node that could lie on an optimal path.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself. Levels: Warm-up, Core, Deep-dive, Design.

Warm-up What is an AI agent? How is it different from a chatbot?

An agent is a system that repeatedly observes an environment, decides on an action and executes it, so that its actions affect what it observes next. A chatbot that answers each message in one model call is a degenerate case: its only action is a reply, and its "environment" is the user. An LLM agent uses the model as its policy inside a loop run by a harness: the model emits tool calls, the harness executes them against real systems (files, shells, APIs, browsers), the results are appended to the context, and the loop continues until a stopping condition. The practical differences follow from the loop: the agent can gather information and correct itself, but errors compound over steps, cost grows with the horizon, and actions with side effects raise safety questions a chatbot never faced. A strong answer adds that "agentic" is a spectrum, from fixed workflows where code decides the control flow to autonomous agents where the model does.

Warm-up Explain the ReAct pattern and why it works better than chain-of-thought alone or acting alone.

ReAct interleaves three kinds of text in one context: thoughts (free-form reasoning), actions (structured commands executed by the harness) and observations (the results). Chain-of-thought alone must reason from the model's parametric knowledge, so on knowledge-intensive tasks it hallucinates facts and cannot check them. Acting alone, with no reasoning, tends to issue poorly chosen actions and loses track of what it has learned. Interleaving lets reasoning choose informative actions and interpret their results, while actions ground the reasoning in real data. It also makes trajectories interpretable and debuggable, because the reasoning behind each action is visible. Modern function-calling agents are ReAct with structured tool calls and, often, hidden reasoning tokens.

Warm-up What is the difference between pass@k and pass^k? When would you report each?

pass@k is the probability that at least one of k attempts succeeds: \(1-(1-p)^k\) for a task with per-attempt success p. It is appropriate when a reliable selector exists, such as hidden tests or a human choosing among candidates, for example in offline code generation. pass^k is the probability that all k attempts succeed, \(p^k\): it measures consistency and is appropriate for deployed agents that face the same kind of task repeatedly, such as customer service, where each customer gets one attempt. pass@k increases with k and pass^k decreases. Over a task set both are averages of per-task quantities, so pass^k depends on how success is distributed across tasks: concentrated success yields higher pass^k than evenly spread success at the same mean.

Core A task takes 30 steps and your agent is 97% reliable per step. Estimate its success rate, and describe three ways to improve it.

Under independence, \(0.97^{30}=e^{30\ln0.97}=e^{-0.914}\approx0.40\). Three levers: (1) Recovery: add verification after risky steps (run tests, re-read the file after an edit, validate tool outputs) so that many errors cost a retry instead of the task; with good recovery the decay becomes far gentler than exponential. (2) Shorter horizon: better tools that do more per call (a search tool returning only relevant lines, an edit tool that applies a whole patch), or decomposing the task so that sub-tasks are verified independently. (3) Higher per-step reliability: a stronger or reasoning model for hard steps, clearer tool descriptions, better context (relevant files, examples), and constrained output formats to eliminate parsing errors. I would also measure where failures actually occur before choosing, because errors are correlated, for example a misunderstanding of the task at step one dooms the rest and is fixed by clarification, not by any per-step improvement.

Core Why did classical symbolic planning not lead to general agents, and what do LLMs change?

Planning chooses actions by searching a world model, and works superbly when the model is correct and compact. For open-ended domains the model had to be written by hand in logic, which ran into the frame problem (specifying what actions do not change), combinatorial explosion (realistic domains need hand-crafted heuristics) and above all the knowledge-acquisition bottleneck (writing and maintaining the facts and operators). LLMs supply an implicit, broad, if unreliable, world model and action prior learned from text, so the agent does not need a hand-written model to act sensibly. They do not give soundness or optimality guarantees, which is why hybrid designs (an LLM translates a problem into PDDL and a classical planner solves it, or an LLM proposes and a verifier checks) are attractive where correctness matters.

Core Deep RL produced superhuman game-playing agents. Why didn't it produce useful software agents, and why does RL work for LLM agents now?

Three obstacles: sample efficiency (DQN needed tens of millions of frames per game, OpenAI Five tens of thousands of years of play), which is affordable only in fast simulators; reward specification, since real tasks lack a score and naive rewards are hacked; and the absence of priors, since policies started from random weights and had to learn everything about each environment. With LLMs, RL starts from a policy that already reads, writes code and follows instructions, so it shapes behaviour rather than creating it and needs far fewer episodes. Verifiable rewards (unit tests, exact answers, database end-states) avoid hand-written reward functions for many tasks. Sandboxed software environments can be run in parallel at scale. Reward hacking remains a real problem: agents learn to special-case tests or claim success, so environment and reward design are still the hard part.

Core Estimate the cost of a 40-step coding-agent episode whose context starts at 8k tokens and grows by 2.5k per step, at $3/M input, $15/M output, $0.30/M cached, 300 output tokens per step.

Total input is \(\sum_t n_t = 40\cdot8000 + 2500\cdot\frac{40\cdot39}{2} = 320{,}000+1{,}950{,}000=2.27\)M tokens; output is 12k tokens. Uncached: \(2.27\times3=\$6.81\) plus \(\$0.18\) output, about $7. With caching, only the 105.5k newly appended tokens are full price ($0.32); 2.16M cached tokens cost $0.65; total about $1.15. The point to make: input dominates by two orders of magnitude, it grows quadratically with the horizon, and caching is worth 6× here. I would also note the cache must be kept warm (calls within the provider's time-to-live) and the prefix must be stable, so tool definitions and system prompt go first and nothing earlier in the context is edited.

Core What is a harness or scaffold, and why does it matter as much as the model?

The harness is the ordinary software around the model: it assembles the context for each call (system prompt, tool definitions, task, memory, history), parses and validates the model's tool calls, executes them with appropriate permissions, formats observations, enforces budgets and stopping rules, and decides when to ask a human. It matters because many agent failures are harness failures: a tool returning 10,000 lines of noise, an ambiguous tool description, a missing check after an edit, a context that drops the original goal, no limit on repeated actions. SWE-agent showed that redesigning tools alone multiplied resolution rates with the same model, and benchmark scores for the same model vary widely across scaffolds. When comparing agents, one must therefore compare model-plus-harness systems.

Core How would you interpret a chart showing an agent benchmark going from 33% to 77% in one year?

As a real trend with caveats. Check: are the numbers from the same scaffold, sampling settings and task subset (vendor-reported numbers often differ in all three)? Is it single-attempt or best-of-k? Has the benchmark been optimised against, possibly with contamination of tasks in training data? Are the remaining failures hard tasks or flawed ones? (SWE-bench Verified was created because many original tasks were under-specified.) Does the benchmark reflect my distribution of tasks? I would also ask for consistency (pass^k) and cost per resolved task, since a jump in success at ten times the cost may not be progress for a product. The underlying lesson is that benchmark gains combine model, harness and evaluation changes, and only controlled comparisons separate them.

Deep-dive The independent-steps model \(\rho^H\) is clearly wrong in detail. In what ways, and what would a better model look like?

It is wrong in at least four ways. (1) Not every error is fatal: agents recover, so failure is closer to an absorbing state reached only by unrecovered errors; with per-step error \(\epsilon\) and recovery probability \(r\), the effective fatal-error rate is about \(\epsilon(1-r)\), giving success \(\approx e^{-H\epsilon(1-r)}\) at the cost of extra steps. (2) Steps are not identically difficult: a few critical steps (locating the bug, understanding the policy) carry most of the risk. (3) Errors are correlated through the context: a misunderstanding early on raises the error rate of every later step, and long contexts degrade attention, so \(\rho\) may fall with \(t\). (4) \(H\) is random and depends on the agent's behaviour; a failing agent often takes more steps. A better model is a Markov chain on states such as on-track, off-track-but-recoverable and failed, with transition probabilities estimated from logged trajectories; Chapter 2 develops it. The \(\rho^H\) model survives as a first-order guide because it captures the exponential sensitivity to per-step error.

Deep-dive Prove that pass^k over a task set is minimised, for fixed mean success, when all tasks are equally hard. What does this imply for evaluating agents?

pass^k \(=\frac1m\sum_j p_j^k\) with \(\frac1m\sum_j p_j=\bar p\) fixed. For \(k\ge1\), \(f(x)=x^k\) is convex on \([0,1]\), so by Jensen \(\frac1m\sum f(p_j)\ge f(\bar p)=\bar p^k\), with equality iff all \(p_j\) are equal (strict convexity for \(k\ge2\)). Conversely, pass@k \(=1-\frac1m\sum(1-p_j)^k\le1-(1-\bar p)^k\), maximised when difficulties are equal. Implications: a single mean success rate does not determine consistency; to predict how a deployed agent behaves you need multiple trials per task to estimate the distribution of \(p_j\). It also suggests product strategy: identify task types with high \(p_j\) and automate them, and route low-\(p_j\) types to humans, which raises the consistency of what is automated.

Deep-dive METR reports a 50% time horizon doubling every seven months. What does that imply, and what are the main reasons to be careful with it?

Seven-month doubling is about 3.3× per year; extrapolated naively, hour-long tasks in early 2025 become day-long tasks within roughly three years. Reasons for care: the horizon is measured on a particular suite (mostly software and research tasks with automatic scoring), so it may not transfer to messier work; the 50% threshold is far from the reliability production needs, and the 80% horizon is several times shorter; human task times are themselves noisy and depend on the humans' context; the fit has wide confidence intervals; and trend extrapolation assumes the drivers (scale, RL on agentic tasks, better scaffolds) continue. Still, the regularity is useful: it gives a quantitative way to compare models on agentic capability, independent of any one benchmark's saturation.

Deep-dive Why does agent input cost grow quadratically with the number of steps, and what are the engineering responses?

Each call re-reads the full context, and the context grows roughly linearly with the step count as actions and observations are appended, so the sum over steps is quadratic: \(Hn_1+\Delta H(H-1)/2\). Responses: (1) prompt caching, which charges about a tenth for re-read prefixes and avoids recomputation, but requires an append-only, stable prefix; (2) smaller observations, by designing tools that return concise, relevant output (line ranges, summaries, filtered logs); (3) context management, by compacting old history into summaries, dropping stale tool outputs, or keeping notes in files; (4) delegation, where sub-agents with fresh contexts do bounded sub-tasks and return short results; (5) cheaper models for routine steps. The first lowers the constant; the others change the growth rate.

Design You are asked to "build an agent" to automate first-line customer support for an airline. Before writing code, what questions do you ask and what do you measure?

Scope: which request types (changes, cancellations, refunds, baggage), their volumes and what a correct resolution is for each; the written policy and how often it requires judgement; which actions have irreversible or financial effects. Tools: which systems the agent can query and modify, with what permissions and rate limits. Success criteria: per-type success measured against end-states in the booking database and policy compliance, not just customer satisfaction; consistency (pass^k on repeated simulated conversations); escalation rate and correctness of escalation; cost per conversation; latency per turn. Risk: what the agent must never do (refund outside policy, reveal another customer's data), how it handles adversarial users, and human approval for high-impact actions. I would start with the highest-volume, most verifiable request types, build a simulated-customer evaluation set from historical tickets, measure a baseline of a fixed workflow before giving the model more autonomy, and route uncertain cases to humans from day one.

Design Sketch the components of a coding agent that fixes GitHub issues, and say where you expect it to fail.

Components: a sandboxed container with the repository and its dependencies; tools for searching code, viewing files with line numbers, editing with syntax checks, and running tests or arbitrary commands with time limits; a harness that builds the context (system prompt with conventions, issue text, repository map), runs the loop, caches the prefix and compacts history when long; a stopping rule (tests pass and the model submits, or a budget is exhausted); and an output step that produces a patch and an explanation for review. Expected failures: mislocalising the bug (reading the wrong files), fixing the symptom and not the cause, breaking other tests, editing tests to pass, getting stuck in loops of the same failing command, environment set-up failures, and claiming success without running tests. Mitigations: localisation tools and a repository map; requiring a test run before submission; reproducing the bug first with a new test; loop detection; forbidding edits to test files unless asked; sampling several candidate patches and selecting by test results; and human review of the final diff.

Design When would you not build an agent, and use a fixed workflow or a single model call instead?

When the steps are known in advance (extract fields, classify, then route), a fixed workflow in code is cheaper, faster, easier to test and more reliable, because the model is only asked to do bounded sub-tasks and the control flow cannot go wrong. When one call suffices (summarise this document), a loop adds cost and failure modes without benefit. Agents are worth their cost when the number and kind of steps depend on what is discovered along the way (debugging, research, open-ended customer requests), when the environment provides feedback the model can use, and when errors can be detected and corrected. A good practice is to begin with the simplest design, measure, and add autonomy only where measurements show the fixed design failing, which is the recommendation of most practitioners who have deployed agents at scale.
