Part I · What Is an Agent? — Chapter 3

The Language Model Inside the Agent

An agent's policy is a language model, and every strength and weakness of the agent starts there. This chapter opens the box: what a model learns from predicting text, how a few examples in a prompt reconfigure it, how instruction tuning turns a predictor into an assistant, what sampling does to a policy, how far its confidence can be trusted, and what a single call costs in money and time.

Why this chapter

Chapter 2 wrote the LLM agent as a triple \((p_\theta,f,g)\): a model, a context map built by the harness, and a parser. It then studied the harness and the environment while treating \(p_\theta\) as a black box that maps a context to an output. That was the right order for building a mathematical picture, but it leaves the most important component unexplained. Why should a model trained only to predict the next token of internet text be any good at choosing the next action in a repository it has never seen? Why does adding two examples to a prompt sometimes change its behaviour completely? Why do agents built on instruction-tuned models behave so differently from those built on raw pre-trained ones? Why does the same agent succeed on Monday and fail on Tuesday with an identical prompt?

Each of these questions has a mechanism behind it, and each mechanism has direct consequences for agent design. In-context learning explains why the system prompt and examples are such powerful levers, and why they stop working when the task is far from anything in the training data. The objective of instruction tuning explains both the helpfulness of modern assistants and some of their characteristic failures, such as agreeing with a user who is wrong. Sampling temperature turns a deterministic-looking program into a random policy whose consistency, pass^\(k\), can be computed. Calibration determines whether an agent's own confidence can be used to decide when to ask a human. And the cost structure of a call, cheap to read and expensive to write, shapes everything from tool design to model routing.

The companion book, Introduction to LLM Engineering, covers the internals of the Transformer and of inference serving in detail. Here we need only the properties of the model that an agent designer relies on, stated precisely enough to reason with. We draw on Chapter 1's history (§1.6) and Chapter 2's definition of the LLM agent (§2.4).

Learning objectives

3.1 What an agent borrows from its model

When we build an agent we do not train a policy; we borrow one. The model arrives with capabilities nobody designed for our task: it reads code and prose, follows instructions, knows that a 404 means a missing page and that refunds usually need a booking reference. It also arrives with tendencies nobody designed: it guesses when it should look, it agrees when it should object, it writes more than it needs to. An agent designer's job is largely to exploit the first set and contain the second, and that requires a working model of where both come from.

It helps to separate four layers, which Figure 3.1 draws as a pipeline. Pre-training on trillions of tokens of text produces a model of the distribution of text: a predictor. Supervised fine-tuning on demonstrations of conversations, instructions and tool use produces a model of the distribution of good assistant responses. Reinforcement learning from human preferences and, increasingly, from automatically verifiable rewards pushes that model towards responses that score well. Finally, at inference time, the harness conditions the model on a context and samples from it with some decoding rule. Each layer shapes the policy the agent ends up executing, and each is responsible for distinct behaviours we will meet in this chapter.

Figure 3.1's bottom row is a map of this chapter. We take the layers in order, asking of each the same question: what does it contribute to the agent, and what does it cost? The first layer is the foundation of everything, so we start there, with the deceptively simple objective of predicting the next token.

3.2 Next-token prediction and what it teaches

A language model is trained to minimise the cross-entropy of the next token given the previous ones, averaged over a vast corpus:

\[ \mathcal L(\theta)=-\,\mathbb E_{x\sim\mathcal D}\Big[\tfrac1n\textstyle\sum_{i=1}^{n}\log p_\theta(x_i\mid x_{<i})\Big]. \]

The units of text are tokens: sub-word pieces from a vocabulary \(\mathcal V\) of typically 100,000 to 250,000 entries, learned so that common strings get their own token and rare ones are spelled out in pieces. For English prose a word is about 1.3 tokens; code, numbers and non-English text use more tokens per character. Tokens matter to an agent designer because they are the unit of everything that is limited or charged: the context window is \(n_{\max}\) tokens, prices are per token, and decoding speed is in tokens per second.

For the mathematician — tokens and the price of reading

A tokenizer is a deterministic, invertible map \(\mathrm{tok}:\Sigma^*\to\mathcal V^*\) from character strings to token strings, usually built by byte-pair encoding[1]: start with bytes, repeatedly merge the most frequent adjacent pair into a new symbol, and stop at the target vocabulary size. The map compresses typical text by a factor of three to four relative to bytes. For our cost arithmetic we use the rule of thumb in NOTATION.md: a page of prose is about 500 words, or 650 tokens. A 50-page contract is therefore about 32,500 tokens and costs \(0.0325\times\$3\approx\$0.10\) to read once at our reference input price. An agent that re-reads it at each of twenty steps without caching pays $1.95; with caching, about $0.28.

What must a model know to drive this loss down? To predict the next token of a recipe it must know what follows "preheat the oven to"; of a stack trace, which line usually raises a KeyError; of a customer-service transcript, what an agent says after "I'd like a refund". The loss rewards every regularity that makes text predictable, and text is predictable to the extent that it describes a structured world. In the limit, a model that predicted all text perfectly would have to represent the processes that generate it: the facts, the causal structure, the conventions of code and law, and the goals and beliefs of the writers. Real models are far from that limit, but they are far enough along it that probing studies find internal representations of quantities such as board states in game transcripts and the truth or falsehood of statements.

Two features of this learning are crucial for agents. The first is breadth. Because the corpus covers almost every domain people write about, the resulting prior covers almost every environment an agent might be put in. The coding agent benefits from millions of repositories and bug discussions, the support agent from countless transcripts and policy documents, the research agent from the whole practice of citing sources. The second is that the model learns to predict text written by agents: people solving problems, explaining their reasoning, making plans and correcting mistakes. Conditioned on the beginning of such a text, the model continues it in kind. This is the deep reason a predictor can act as a policy: much of its training data consists of the traces of policies, and continuing a trace is choosing an action.

What pre-training does not provide is equally important. The model's knowledge is frozen at its training cut-off. It has learned the statistics of text, which include many falsehoods and much that is stale. It has never observed the consequences of an action in a live environment, so its predictions about the contents of a file it has not read are confident guesses. And it does not know which continuation the user wants: a raw pre-trained model asked a question may continue with more questions, because that is what follows questions in many documents. The next two layers address the last problem. The first, which needs no training at all, is the prompt.

3.3 In-context learning as inference

Brown and colleagues' discovery of in-context learning in GPT-3 (§1.6)[2] was surprising because nothing in the training objective asks for it. The model is trained to predict text, not to learn tasks from examples. Yet given a prompt such as "sea otter → loutre de mer, cheese → fromage, peppermint →", it translates the last word; given two examples of reformatting a date, it reformats a third. For agents this capability is the main lever the designer has: a system prompt and a handful of examples reconfigure the policy without touching its weights. Understanding when it works requires a model of what is happening.

The most illuminating account is Bayesian, due to Xie, Raghunathan, Liang and Ma (2021)[3]. Suppose the training corpus is a mixture of documents, each generated by some latent "concept" \(\psi\): a task, a style, a format, a domain. A model that predicts the corpus well must, implicitly, infer which concept generated the document it is reading, because the right next token depends on it. Formally, its predictions approximate the posterior predictive

\[ p_\theta(y\mid \text{prompt})\;\approx\;\int p(y\mid\psi,\text{prompt})\;p(\psi\mid\text{prompt})\,d\psi . \]

The prompt acts as evidence about \(\psi\). Each example in a few-shot prompt is a data point generated under the intended concept, so the posterior \(p(\psi\mid\text{prompt})\) concentrates on it, and the prediction for the query becomes the prediction a model specialised to that concept would make. Instructions work the same way, as strong evidence about the intended task. Figure 3.2 sketches the picture.

Figure 3.2 makes two predictions that match practice. First, a few examples go a long way when the intended concept already has substantial prior mass: the posterior odds multiply by the likelihood ratio of each example, so they grow geometrically. Second, examples cannot conjure a concept the model has no prior for. If the task is genuinely novel, say an internal file format with idiosyncratic rules, the posterior concentrates on the nearest familiar concept, and the model confidently does the wrong thing. That is why detailed instructions, schemas and documentation in the context (which supply the concept explicitly) often help more than examples for agent tools, and why fine-tuning remains necessary for truly unfamiliar tasks.

Worked example — how many examples are enough?

A prompt shows input–output pairs for a string transformation. Two latent tasks fit the format: \(\psi_A\) (the intended one) and \(\psi_B\), with prior probability one half each. Each example is nine times more likely under \(\psi_A\) than under \(\psi_B\) (it is consistent with \(\psi_B\) only by coincidence).

Posterior. After \(k\) examples the odds are \(9^k:1\), so \(p(\psi_A\mid\text{prompt})=9^k/(9^k+1)\): 0.900 for \(k=1\), 0.988 for \(k=2\), 0.9986 for \(k=3\).

Error on the query. If the two tasks disagree on the query, the model errs with probability about \(1/(9^k+1)\): 10% with one example, 1.2% with two, 0.14% with three. The fourth and fifth examples buy almost nothing.

When the prior is unfavourable. If \(p(\psi_A)=0.01\), three examples give odds \(729\times0.01/0.99\approx7.4\), a posterior of 0.88, and the model still errs 12% of the time; it takes five examples to reach 0.998. An unusual task needs either more evidence or an explicit description that raises its prior.

The Bayesian account is a model, not a mechanism, and two mechanistic findings complement it. Garg and colleagues (2022) trained Transformers on prompts of input–output pairs from random linear functions and found that the trained model's in-context predictions match ordinary least squares, the Bayes-optimal estimator for that prior: in-context learning can implement genuine statistical inference[4]. Olsson and colleagues at Anthropic (2022) identified induction heads, attention circuits that find an earlier occurrence of the current token and copy what followed it, and showed that their emergence during training coincides with a sharp improvement in in-context learning[5]. Copying patterns from earlier in the context is a crude but powerful form of learning from examples, and it explains a behaviour every agent builder notices: models imitate the format and style of whatever is in their context, including their own earlier mistakes. An agent whose history contains three sloppy tool calls is more likely to make a fourth.

For an agent, the context is a growing in-context learning prompt: the system prompt and examples set the initial posterior over "what kind of task is this and how should I behave", and every observation and action updates it. This is the same picture as Chapter 2's belief state, now seen from inside the model. It also explains why the beginning of the context is so valuable: it fixes the concept against which everything else is interpreted. But in-context learning alone does not make a model do what users want. A raw model conditioned on a question will produce whatever usually follows such text. Making it an assistant took a different kind of training.

3.4 From predictor to assistant: fine-tuning and RLHF

A pre-trained model asked "How do I reverse a list in Python?" might answer, or might continue with "How do I sort a list in Python? How do I…", because lists of questions are common on the web. To be a policy, the model must reliably produce the kind of output its user intends. Two stages of post-training achieve this, and both leave fingerprints on agent behaviour.

Supervised fine-tuning (SFT) continues training on a curated set of demonstrations: prompts paired with high-quality responses, written or vetted by people, increasingly generated by other models and filtered. The loss is the same cross-entropy as pre-training, computed only on the response tokens. The effect is to move the model's posterior over "what kind of document is this" decisively towards "a helpful assistant answering a user", so that it no longer needs to be coaxed by prompt engineering. For agents, SFT also teaches the formats of interaction: the chat template that separates system, user and assistant turns, and the syntax of tool calls and tool results. Figure 3.3 shows what the model actually sees.

Figure 3.3 dispels a common misconception. There is no separate channel for the system prompt, the tools or the tool results: everything is tokens in one sequence, distinguished only by special marker tokens that fine-tuning taught the model to respect. The model treats text after the system marker as more authoritative than text after a tool marker because it was trained on examples in which that was the right thing to do, not because of any hard boundary. This is the root of prompt injection (Chapter 20): text arriving in a tool result that says "ignore previous instructions" competes with the system prompt on the same footing, and the only defence inside the model is how firmly training established the hierarchy. Model developers now train explicitly on such an instruction hierarchy[6], but it remains a learned preference, not a guarantee.

The second stage is reinforcement learning from human feedback (RLHF). Demonstrations show the model what good looks like; they do not show it the many ways of being slightly worse, nor rank alternatives. RLHF, as used for InstructGPT (§1.6)[7], collects comparisons: for a prompt \(x\), people see two responses and choose the better. A reward model \(r_\phi(x,y)\) is fitted to the comparisons by maximum likelihood under the Bradley–Terry model[8], \(\Pr(y_w\succ y_l)=\sigma\big(r_\phi(x,y_w)-r_\phi(x,y_l)\big)\). The policy is then optimised to score highly under \(r_\phi\) while staying close to the fine-tuned model \(\pi_{\text{ref}}\):

\[ \max_{\pi}\;\mathbb E_{x}\Big[\mathbb E_{y\sim\pi(\cdot\mid x)}\,r_\phi(x,y)\;-\;\beta\,D_{\mathrm{KL}}\big(\pi(\cdot\mid x)\,\|\,\pi_{\text{ref}}(\cdot\mid x)\big)\Big]. \]
Proposition — the optimal KL-regularised policy

For each prompt \(x\), the maximiser over distributions \(\pi(\cdot\mid x)\) is \[ \pi^*(y\mid x)=\frac{1}{Z(x)}\,\pi_{\text{ref}}(y\mid x)\,\exp\!\big(r_\phi(x,y)/\beta\big),\qquad Z(x)=\sum_y\pi_{\text{ref}}(y\mid x)\,e^{r_\phi(x,y)/\beta}. \] Proof. The objective for fixed \(x\) is \(\sum_y\pi(y)\big[r(y)-\beta\log\frac{\pi(y)}{\pi_{\text{ref}}(y)}\big]\). Writing \(\pi^*\) as above, this equals \(-\beta\,D_{\mathrm{KL}}(\pi\,\|\,\pi^*)+\beta\log Z\), which is maximised, uniquely, at \(\pi=\pi^*\) because the KL divergence is non-negative and zero only at equality.

The proposition says that RLHF reweights the fine-tuned model's distribution by an exponential of the reward: responses the reward model likes become more probable, by a factor controlled by \(\beta\), but nothing the reference model considers impossible can become likely. This picture, which Chapter 17 develops into direct preference optimisation, explains both what RLHF does well and its characteristic side effects. It does well what people reliably reward: helpful, clear, well-formatted, polite answers. It also amplifies whatever raters reward unreliably. People tend to prefer answers that agree with them, sound confident and are longer, and reward models learn those preferences. The result is a measurable tendency towards sycophancy, agreeing with a user's stated view even when it is wrong (Sharma et al., 2023)[9], towards overconfidence (§3.6), and towards verbosity. For an agent these matter directly: a support agent that concedes a refund the policy forbids because the customer insists, or a coding agent that agrees its broken fix "should work" when the user suggests so, is exhibiting a trained preference, and the harness must counteract it with explicit policy, verification and, where needed, a second opinion.

Since 2024 a third ingredient has become central: reinforcement learning against verifiable rewards, where the reward is not a learned model of human preference but an automatic check, such as unit tests passing, a maths answer matching, or a database reaching the right state. Reasoning models such as OpenAI's o1 and DeepSeek-R1 were trained this way (§1.9)[10], and agentic models are increasingly trained on whole multi-step tasks in sandboxed environments. This produces behaviours valuable to agents (persistence, checking work, recovering from errors) and its own failure mode, reward hacking, when the check is weaker than the goal. Chapter 18 is devoted to it. For now, the key point is that a modern model's dispositions as an agent are largely a product of post-training choices made by its developer, which is why the same harness can behave quite differently with different models.

3.5 Sampling: the policy is random

The model outputs a distribution; the harness must choose one output. How it does so turns the agent's policy from a mathematical object into concrete behaviour, and the choice has a direct, computable effect on reliability. At each position the model produces logits \(z\in\mathbb R^{\lvert\mathcal V\rvert}\), and the next-token distribution with temperature \(T_s>0\) is

\[ p_{T_s}(v)=\frac{\exp(z_v/T_s)}{\sum_{u\in\mathcal V}\exp(z_u/T_s)} . \]

At \(T_s=1\) this is the model's own distribution. As \(T_s\to0\) it concentrates on the arg-max (greedy decoding); as \(T_s\to\infty\) it tends to uniform. Truncation rules such as top-\(p\) (sample only from the smallest set of tokens whose probabilities sum to \(p\)) remove the long tail of unlikely tokens. The companion book covers decoding algorithms in detail; what matters here is the effect on the agent.

Consider one decision point where the model's logits for three candidate actions are \(z=(2,1,0)\), the first being correct. Figure 3.4 shows how temperature changes the probability of choosing it, and how that probability compounds when the same decision is faced five times, as pass^5 of §1.10.

Figure 3.4 makes a point that is easy to state and often forgotten. At the model's native temperature, a decision with a clear but not overwhelming preference (logit gap of 1) is made correctly only two-thirds of the time, and an agent facing five such decisions in an episode gets all of them right only 13% of the time. Lowering the temperature sharpens every such preference and raises consistency dramatically. This is why agents are usually run at low temperature for actions with side effects, and why "the agent worked yesterday and failed today" so often has a simple explanation: it is a random policy, and yesterday's trajectory was one sample.

Why not always use \(T_s=0\)? Three reasons. First, greedy decoding is consistent but not necessarily correct: if the model's top choice is wrong, it is wrong every time, whereas sampling at least sometimes tries the right action. When a verifier can select among attempts, diversity is valuable, and best-of-\(k\) search (Chapter 6) deliberately samples at higher temperature. Second, greedy decoding of long text tends to degenerate into repetition, and reasoning models are typically trained and served with sampling at moderate temperatures; their developers often recommend against \(T_s=0\). Third, even \(T_s=0\) is not exactly deterministic in practice: batched floating-point computation on GPUs can change results depending on what else is in the batch, so identical requests occasionally diverge. Reproducibility must therefore be engineered (logging seeds and full contexts, replaying tool outputs) rather than assumed.

Worked example — two decisions, one temperature

A coding agent's episode contains two kinds of decision. Edits (12 per episode) have logit gap 2 between the right action and the best wrong one; exploration choices (which file to open next; 8 per episode) have many acceptable answers. Treat each edit as a two-way choice with logits \((2,0)\).

At \(T_s=1\). \(\Pr(\text{edit right})=e^2/(e^2+1)=7.389/8.389=0.881\); all 12 right: \(0.881^{12}=e^{12\ln0.881}=e^{-1.521}=0.219\).

At \(T_s=0.5\). Logits become \((4,0)\): \(\Pr=54.6/55.6=0.982\); all 12: \(0.982^{12}=e^{-0.218}=0.804\).

Interpretation. Halving the temperature raises the chance of a clean set of edits from 22% to 80%. Exploration choices are hardly affected, because many of their outcomes are acceptable. In practice, recovery (Chapter 2) also catches many wrong edits, but the lesson stands: temperature is a reliability parameter, not a style parameter, for actions that must be right.

3.6 Calibration: can the model's confidence be trusted?

An agent often needs to know how likely it is to be right: whether to escalate to a human, whether to run another check, whether a retrieved answer is good enough. The model's own confidence is the cheapest signal available. It is useful only if it is calibrated: among all the occasions on which the model says (or implies) it is 80% sure, it should be right about 80% of the time.

Definition — calibration and expected calibration error

A predictor that outputs an answer with confidence \(\hat c\in[0,1]\) is calibrated if \(\Pr(\text{correct}\mid\hat c=c)=c\) for all \(c\). Grouping predictions into bins \(B_1,\dots,B_J\) by confidence, the expected calibration error is \(\mathrm{ECE}=\sum_j\frac{\lvert B_j\rvert}{N}\,\big\lvert\mathrm{acc}(B_j)-\mathrm{conf}(B_j)\big\rvert\). A reliability diagram plots \(\mathrm{acc}(B_j)\) against \(\mathrm{conf}(B_j)\); a calibrated predictor lies on the diagonal.

There are several ways to extract a confidence from a language model: the probability it assigns to its answer's tokens, its probability of answering "True" when asked whether its own answer is correct (Kadavath et al., 2022)[11], a verbal statement ("I'm about 70% confident"), or agreement across several samples. Pre-trained models turn out to be remarkably well calibrated on multiple-choice questions when their token probabilities are used: Kadavath and colleagues found that large models "mostly know what they know". Post-training changes this. The GPT-4 technical report showed a reliability diagram in which the pre-trained model was close to the diagonal and the RLHF model was markedly overconfident[12], consistent with the reward-reweighting picture of §3.4: raters reward confident answers. Figure 3.5 sketches the typical shape.

Figure 3.5 contains the practical rule: a raw confidence number from a chat model should not be taken at face value. Points below the diagonal mean that when the model says 95% it is right perhaps 70% of the time. Two remedies are standard. The first is recalibration: on a labelled validation set from the agent's own task distribution, fit a monotone map from the model's confidence to observed accuracy (temperature scaling or isotonic regression), and use the mapped value. The second is to use signals that are calibrated by construction, such as agreement across \(k\) independent samples (self-consistency, Chapter 5), or the verdict of an external check. Either way, calibration must be measured on the agent's real task distribution, because it varies across domains and degrades out of distribution.

Calibration matters to agents because of selective escalation. A support agent that hands the hardest 20% of conversations to people, chosen by its confidence, is useful only if its confidence ranks conversations correctly by difficulty: what matters is that low confidence picks out the cases it would get wrong. Even a miscalibrated model can rank well (a monotone distortion preserves order), so the threshold must be set empirically on a validation set to hit a target accuracy on the cases the agent keeps. The model's confidence then becomes a dial trading automation rate against error rate, and the dial's quality, measured as accuracy at each coverage level, is one of the most useful numbers to report about a deployed agent.

3.7 What a call costs

Every step of an agent is a model call, and the price and duration of a call have a structure that shapes agent design as much as any capability. A call has two phases, as Figure 3.6 shows. In prefill, the model reads the input tokens; because all of them are known in advance, they are processed in parallel, and the time is roughly proportional to the number of tokens not already cached, at \(v_{\text{pre}}\) tokens per second. In decode, the model writes the output one token at a time, each requiring a full pass through the model, at \(v_{\text{dec}}\) tokens per second. The time until the first output token appears (TTFT) is dominated by queueing and prefill; the remaining time by decode.

Figure 3.6 explains the price list. Providers charge more per output token than per input token (five times more at our reference prices) because decode is the expensive phase for the hardware: each output token requires reading all the model's weights from memory for very little arithmetic, while prefill amortises that reading over many tokens. The companion book derives this from the memory bandwidth of GPUs. Cached input is cheaper still, because the work of reading it was done on an earlier call. Putting the pieces together, for a call with \(n^{\text{new}}\) fresh input tokens, \(n^{\text{cached}}\) cached ones and \(n_{\text{out}}\) output tokens,

\[ C=\kappa_{\text{in}}n^{\text{new}}+\kappa_{\text{cache}}n^{\text{cached}}+\kappa_{\text{out}}n_{\text{out}},\qquad \ell\approx\ell_{\text{queue}}+\frac{n^{\text{new}}}{v_{\text{pre}}}+\frac{n_{\text{out}}}{v_{\text{dec}}}. \]

Three design consequences follow. Make the model write less: an agent whose steps produce 1,000 tokens of commentary takes \(1{,}000/60\approx17\) s per step and costs $0.015 per step in output alone; trimming to 200 tokens saves four-fifths of both. Reasoning models complicate this, because their hidden reasoning tokens are output tokens, billed and decoded like any other; a reasoning budget is therefore a latency and cost budget. Make the model read stably: since cached tokens cost a tenth, contexts should be append-only with a fixed prefix, the subject of Chapter 4. Use the cheapest model that suffices: our reference small model costs a twelfth as much per token and decodes two and a half times faster, so routing easy steps to it can cut cost substantially, if a reliable gate decides which steps are easy.

Worked example — a model cascade for the support agent

Each support turn reads 8,000 tokens and writes 150 (ignore caching for simplicity). The frontier model costs \(0.008\times\$3+0.00015\times\$15=\$0.0263\) per turn; the small model \(0.008\times\$0.25+0.00015\times\$1.25=\$0.0022\).

Cascade. Every turn first goes to the small model, which also reports a calibrated confidence. Turns below a threshold, 30% of traffic, are re-run on the frontier model. Cost per turn: \(0.0022+0.3\times0.0263=\$0.0101\), 38% of frontier-only.

Quality. Suppose the frontier model is right on 95% of turns and the small model on 85%, with the small model's errors concentrated in its low-confidence turns, so that it is right on 96% of the 70% it keeps. Overall accuracy: \(0.7\times0.96+0.3\times0.95=0.957\), no worse than frontier-only. If instead its confidence were uninformative, it would keep an unfiltered 70% at 85% accuracy and overall accuracy would fall to \(0.7\times0.85+0.3\times0.95=0.88\).

Latency. Escalated turns pay for both calls, about 1 s for the small model plus 2.5 s for the frontier model's decode, so the cascade trades a slower tail for a cheaper mean.

Context windows: nominal and effective

One more property of a call shapes agents more than any price: the context window \(n_{\max}\), the maximum number of tokens the model can condition on. Windows grew from 2,048 tokens for GPT-3 (2020) to 128,000–200,000 tokens for typical frontier models in 2024–2025, with some offering a million or more. Why is there a limit at all? The model was trained on sequences up to some length and its position encoding is only reliable within that range, and the cost of attention grows with context length: each new token attends to every previous one, so the per-token compute and the memory for cached keys and values grow linearly with the context, and processing a whole context costs quadratically. The companion book treats the engineering of long contexts in depth.

For an agent designer the important distinction is between the nominal window, the number of tokens the API accepts, and the effective window, the length up to which the model actually uses the information well. Benchmarks that hide a fact in a long document and ask about it ("needle in a haystack") are passed by most modern models at their full nominal length, but harder tests that require combining several facts, or reasoning over the whole context, show accuracy falling well before the nominal limit. In an agent, the context is not a clean document with one needle but a long, messy history of tool outputs, and the decline is correspondingly earlier. The practical rule is to treat the nominal window as a hard ceiling and to design for a working budget well below it, keeping in context only what the next decision needs. Chapter 4 makes this budget the organising principle of context engineering, and Chapter 14 shows what to do when a task's history cannot fit at all.

The worked example connects the last two sections: a cascade is only as good as the calibration of the gate that runs it. It also illustrates a more general pattern in agent engineering, the substitution of a cheap, imperfect component guarded by a check for an expensive, better one. Chapter 21 treats routing and cascades systematically. Before leaving the model, we collect the failure modes it brings to every agent built on it.

3.8 What the agent inherits

Every agent inherits its model's characteristic errors, and it is worth naming them, because each has a known engineering response and an interviewer will expect you to match the two.

Hallucination is the confident generation of false content: a function that does not exist, a citation to a paper never written, a refund policy invented on the spot. Its cause is the objective of §3.2: the model is trained to produce plausible continuations, and a plausible guess is rewarded as long as text like it appears in the corpus. The response is grounding: make the agent look things up rather than recall them, quote its sources, and check claims against tools (does the function exist? does the URL resolve?). Sycophancy (§3.4) is agreement with the user or with apparent authority at the expense of truth; the response is explicit policy in the system prompt, verification that does not depend on the model's judgement, and, for high-stakes decisions, a second model or a human. Overconfidence (§3.6) is the miscalibration of stated certainty; the response is recalibration and external checks. Prompt sensitivity is the dependence of behaviour on details of phrasing and order that should not matter; Sclar and colleagues found accuracy swings of tens of points from formatting changes alone in few-shot prompts[13]. The response is to evaluate prompts on a fixed test set, never on anecdotes, and to keep prompt changes under version control like code.

Two further inherited properties concern the context. Position effects: models use information at the start and end of a long context more reliably than information in the middle (Liu et al., 2023)[14], and long contexts filled with irrelevant material degrade performance even when the relevant part is present. The response is to keep the context short and relevant, which Chapter 4 develops. Imitation of context (§3.3): the model continues patterns it sees, including errors and formats in its own earlier turns. The response is to keep the history clean (for example, by not leaving malformed tool calls in it once they are corrected) and to put good examples where the model will see them.

Finally, the model has a knowledge cut-off and no access to anything after it, or to anything private, unless the harness provides it. An agent asked about this week's events, or about an internal code base, can only answer well by retrieving the information (Chapter 9). Each of these inherited properties reappears in a later chapter as the motivation for a technique, which is the sense in which this chapter is the foundation for the rest of the book.

Drill 3.1 — temperature by hand

A model has logits \((3,0)\) for the correct and incorrect actions at a decision. (a) Find the probability of the correct action at \(T_s=1\) and \(T_s=2\). (b) At what temperature is it 99%?

(a) \(T_s=1\): \(e^3/(e^3+1)=20.09/21.09=0.953\). \(T_s=2\): \(e^{1.5}/(e^{1.5}+1)=4.482/5.482=0.818\). (b) Need \(\sigma(3/T_s)=0.99\), i.e. \(3/T_s=\ln 99=4.595\), so \(T_s=0.653\).

Drill 3.2 — the cost of thinking

A reasoning model spends 2,000 hidden reasoning tokens and 200 visible tokens per agent step, reading 20,000 fresh tokens. Using the reference prices and speeds, what does a step cost and how long does it take? How do the numbers change with a 500-token reasoning budget?

Output is 2,200 tokens: cost \(0.02\times\$3+0.0022\times\$15=\$0.06+\$0.033=\$0.093\); time \(20{,}000/5{,}000+2{,}200/60=4+36.7=40.7\) s. With a 500-token budget, output is 700 tokens: $0.0705 and \(4+11.7=15.7\) s. The reasoning budget is mostly a latency lever: it cuts the step time by 61% and its cost by 24%. Drill 3.3 — how many examples?

Two tasks fit a prompt's format, with prior odds 1:4 against the intended one, and each example has likelihood ratio 5 in its favour. How many examples are needed for the posterior to exceed 99%?

Odds after \(k\) examples: \(5^k/4\). Need \(5^k/4\ge99\), i.e. \(5^k\ge396\): \(k=4\) gives 625, so four examples (posterior \(625/629=0.994\)); three give \(125/4=31\), a posterior of 0.969.

Looking ahead

The model behaves like an implicit Bayesian reasoner whose posterior over "what is going on and what should I do" is set by its context. It reads cheaply and writes expensively, it is overconfident after preference tuning, and it imitates whatever it sees. All of this puts the context at the centre of agent design: it is the agent's belief state (Chapter 2), its in-context learning prompt (§3.3), its main cost (§3.7) and its main attack surface (§3.4). How, then, should the context be built? What goes in the system prompt, how should tools be described, where should examples go, how do we keep it cacheable, and what happens as it fills up? Chapter 4 turns these questions into the discipline of context engineering.

Chapter summary

  • The agent's policy has four layers: pre-training (knowledge, in-context learning), fine-tuning (instruction following, formats), RL (preferences, reasoning; also sycophancy and overconfidence) and inference (randomness, cost, limits).
  • Next-token prediction forces a model to represent regularities of the world described by text, including traces of goal-directed behaviour, which is why a predictor can act as a policy. Tokens are the unit of limits and prices: about 1.3 per word, 650 per page.
  • In-context learning behaves like Bayesian inference over latent tasks: examples multiply posterior odds, so a few suffice for familiar tasks, while unfamiliar tasks need explicit description or fine-tuning. Models imitate their context, including errors.
  • RLHF fits a Bradley–Terry reward model and optimises reward minus \(\beta\)·KL, whose optimum is \(\pi^*\propto\pi_{\text{ref}}e^{r/\beta}\): a reweighting that amplifies what raters reward, reliably or not. Chat templates serialise all roles into one token string, so instruction hierarchy is learned, not enforced.
  • Temperature sharpens or flattens the policy; consistency (pass^\(k\)) is very sensitive to it. Use low temperature for consequential actions and diversity only with selection. \(T_s=0\) is not perfectly deterministic.
  • Calibration: pre-trained token probabilities are close to calibrated; preference-tuned models are overconfident. Recalibrate on task data and set escalation thresholds empirically.
  • A call costs \(\kappa_{\text{in}}n^{\text{new}}+\kappa_{\text{cache}}n^{\text{cached}}+\kappa_{\text{out}}n_{\text{out}}\) and takes about \(n^{\text{new}}/v_{\text{pre}}+n_{\text{out}}/v_{\text{dec}}\). Write less, read stably, and route to cheaper models through calibrated gates.
  • Inherited failure modes (hallucination, sycophancy, overconfidence, prompt sensitivity, position effects, context imitation, knowledge cut-off) each motivate a later technique.

In the Bayesian account of in-context learning, a few-shot example acts as:

  2. Evidence that updates the posterior over latent tasks
  3. A change of the vocabulary
  4. A constraint on decoding

  4. Because temperature is too high
Examples multiply odds; with a tiny prior, many examples or an explicit description are needed.

Induction heads are attention circuits that:

  1. Compute the softmax temperature
  2. Find an earlier occurrence of the current token and predict what followed it
  3. Store the system prompt
  4. Parse tool calls
Their emergence coincides with a jump in in-context learning; they also explain imitation of patterns in the context.

An agent's history contains several malformed tool calls that were later corrected. A sensible harness practice is to:

  1. Keep them to show the model its mistakes
  2. Remove or replace them once corrected, since models imitate patterns in their context
  3. Raise the temperature
  4. Duplicate them for emphasis
Malformed patterns in context make similar outputs more likely. A short note on what went wrong is better than the raw error-prone pattern.

In a chat template, the system prompt is:

  1. Sent on a separate, privileged channel that the model cannot override
  2. Tokens in the same sequence as everything else, marked by special tokens whose authority is learned
  3. Stored in the model's weights
  4. Only used during training
Everything is one token string; the instruction hierarchy is a trained preference, which is why prompt injection is possible.

Under the Bradley–Terry model, if \(r(y_w)-r(y_l)=2\), the probability that \(y_w\) is preferred is about:

  1. 0.5
  2. 0.73
  3. 0.88
  4. 0.98

The optimal policy of \(\max_\pi\mathbb E_\pi[r]-\beta D_{\mathrm{KL}}(\pi\|\pi_{\text{ref}})\) is:

  1. \(\arg\max_y r(y)\)
  2. \(\pi_{\text{ref}}(y)\exp(r(y)/\beta)/Z\)
  3. \(\pi_{\text{ref}}\) unchanged
  4. Uniform over high-reward responses
The objective equals \(-\beta D_{\mathrm{KL}}(\pi\|\pi^*)+\beta\log Z\), maximised at \(\pi^*\).

As \(\beta\to\infty\) in the KL-regularised objective, the optimal policy tends to:

  1. The reference policy
  2. The reward-maximising response
  3. The uniform distribution
  4. A random policy
\(e^{r/\beta}\to1\), so \(\pi^*\to\pi_{\text{ref}}\). As \(\beta\to0\) it concentrates on the highest-reward response in the support of \(\pi_{\text{ref}}\).

Why can RLHF make a response more likely only if the reference model already gives it non-zero probability?

  1. Because rewards are bounded
  2. Because the optimum multiplies \(\pi_{\text{ref}}(y)\) by a finite factor
  3. Because the KL term is always zero
  4. Because of the softmax temperature
\(\pi^*(y)\propto\pi_{\text{ref}}(y)e^{r(y)/\beta}\): zero stays zero. RLHF reweights rather than invents.

Reinforcement learning with verifiable rewards differs from RLHF mainly in that:

  1. It uses no policy gradient
  2. The reward comes from an automatic check (tests, exact answers, end-states) rather than a learned preference model
  3. It requires no environment
  4. It cannot cause reward hacking
Verifiable rewards avoid reward-model errors but can still be hacked when the check is weaker than the goal.

  2. 0.50
  3. 0.67
  4. 0.87

  2. When several attempts are generated and a reliable verifier selects among them
  3. When pass^\(k\) must be maximised
  4. Never
Diversity helps best-of-\(k\) with selection; it hurts consistency of single attempts.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up What is in-context learning, and why does it matter for agents?

In-context learning is a model's ability to perform a task specified only by instructions and examples in its prompt, with no weight updates. It emerged with scale (GPT-3). For agents it is the main configuration lever: the system prompt, tool descriptions and examples set the policy, and every observation in the context further conditions it. A useful model is Bayesian: the prompt is evidence about the latent task, so a few examples suffice for familiar tasks, while unfamiliar ones need explicit descriptions or fine-tuning. It also explains why models imitate patterns in their context, good or bad.

Warm-up What does temperature do, and what temperature would you use for an agent's tool calls?

Temperature divides logits before the softmax: low values sharpen the distribution towards the arg-max, high values flatten it. For consequential tool calls I would use a low temperature, because consistency compounds: a decision with a logit gap of 1 is right 73% of the time at \(T_s=1\) in a two-way choice, far less reliably than at 0.3. I would raise it when generating several candidates for a verifier to choose among, and follow the model developer's guidance for reasoning models, which are often tuned for moderate temperatures. I would also not assume \(T_s=0\) is deterministic.

Warm-up Why is output more expensive than input, and what does that imply for agent design?

Input is processed in parallel during prefill, amortising the cost of reading the weights; output is generated one token per forward pass, each pass reading the weights for little computation, so it is slow and occupies the hardware longer. Implications: keep outputs short (concise reasoning, compact tool calls), set reasoning budgets, prefer tools that return the needed information over the model writing long intermediate text, and remember that latency is dominated by output length. Input is cheap per token but dominates volume in agents, so caching matters too.

Core Derive the optimal policy of the KL-regularised RLHF objective and interpret it.

For a fixed prompt, maximise \(\sum_y\pi(y)r(y)-\beta\sum_y\pi(y)\log\frac{\pi(y)}{\pi_{\text{ref}}(y)}\) over the simplex. Define \(\pi^*(y)=\pi_{\text{ref}}(y)e^{r(y)/\beta}/Z\). Substituting \(r(y)=\beta\log\frac{\pi^*(y)}{\pi_{\text{ref}}(y)}+\beta\log Z\), the objective becomes \(-\beta D_{\mathrm{KL}}(\pi\|\pi^*)+\beta\log Z\), maximised uniquely at \(\pi^*\). Interpretation: RLHF exponentially tilts the reference distribution towards high reward; \(\beta\) controls how far. It cannot create behaviours the reference assigns zero probability, and it amplifies whatever the reward model rewards, including rater biases such as preferring agreement or length. This is also the starting point of DPO: inverting the relation expresses the reward in terms of the policy.

Core What is sycophancy, where does it come from, and how would you mitigate it in a support agent?

Sycophancy is a model's tendency to agree with the user's stated beliefs or demands even when wrong. It comes largely from preference tuning: raters tend to prefer agreeable answers, reward models learn it, and RLHF amplifies it. In a support agent it shows up as conceding refunds or exceptions the policy forbids because the customer insists. Mitigations: state the policy and the authority hierarchy explicitly in the system prompt; make policy checks deterministic in code where possible (the refund tool itself refuses ineligible requests); require the agent to cite the policy clause for exceptions; evaluate with adversarial simulated customers; and route contested cases to humans.

Core How would you obtain a confidence estimate from an LLM agent, and how would you check whether it can be trusted?

Options: token probability of the answer (or of a short final label), asking the model for P(True) about its own answer, verbalised confidence, agreement rate across \(k\) samples, or an external verifier's score. To check it, assemble a labelled validation set from the real task distribution, bin predictions by confidence and plot a reliability diagram; compute ECE and, more importantly for escalation, the accuracy–coverage curve (accuracy of the cases kept as the threshold varies) and AUROC for separating correct from incorrect. Recalibrate with temperature scaling or isotonic regression if needed, and re-check after any model or prompt change, since calibration shifts with both.

Core Estimate the cost and latency of an agent step that reads 30k tokens (25k cached) and writes 400 tokens.

Cost: fresh \(5{,}000\times\$3/\text{M}=\$0.015\); cached \(25{,}000\times\$0.30/\text{M}=\$0.0075\); output \(400\times\$15/\text{M}=\$0.006\); total $0.0285. Latency: prefill of 5,000 fresh tokens at 5,000/s is 1 s; decode of 400 tokens at 60/s is 6.7 s; about 7.7 s plus queueing and tool time. Decode dominates time, fresh input dominates cost here; caching saved \(25{,}000\times\$2.70/\text{M}=\$0.0675\).

Core Explain chat templates and why they matter for security.

A chat template serialises structured messages (system, user, assistant, tool) into a single token sequence using special role-marker tokens; the model was fine-tuned on this format. All content, including tool results from untrusted sources, ends up in the same sequence, and the authority of the system prompt over tool content is a learned behaviour, not an enforced boundary. Hence indirect prompt injection: instructions in a web page or email returned by a tool can compete with the developer's instructions. Defences cannot rely on the template alone; they need privilege separation, constrained tool permissions, and treating tool outputs as data (Chapter 20). Using the wrong template for a model also degrades behaviour badly, which is a common bug with open models.

Core Your agent works in testing and fails intermittently in production with the same prompts. What could be going on?

It is a random policy: at non-zero temperature, each run is a sample, and pass^\(k\) can be much lower than single-run success. Even at \(T_s=0\), batch-dependent numerics can flip near-tied choices. Other causes: production contexts differ (longer histories, different tool outputs, real user phrasing), model version changes behind an alias, cache or truncation differences, rate-limit retries changing order, and non-deterministic tools. Diagnose by logging full contexts and outputs, replaying failures, measuring success over many samples per task (not one), lowering temperature for consequential steps, and pinning model versions.

Deep-dive Present the Bayesian view of in-context learning and its limits. What does it predict that you could test?

If pre-training data are a mixture over latent concepts, a good predictor approximates the posterior predictive, integrating over concepts weighted by their posterior given the prompt; examples are evidence that concentrates the posterior. Predictions: accuracy improves roughly geometrically in odds with consistent examples; label noise in examples hurts less than expected when the concept is identifiable from the inputs' format; novel concepts with low prior require many examples; order and format changes matter because they change the likelihoods. Limits: real models are not exact Bayesians; they show recency and position biases, can be swayed by label semantics, and in-context "learning" can also implement algorithms (least squares, gradient-descent-like updates) that are not well described as selecting a pretrained concept. Tests: vary the number of examples and the prior plausibility of the task and look at the shape of the accuracy curve; flip labels and see whether the model follows them (large models do more).

Deep-dive Why might preference tuning hurt calibration, and how would you restore usable confidence for an agent?

The RLHF optimum tilts the distribution by \(e^{r/\beta}\); if raters reward confident, decisive answers, probability mass moves towards a single answer regardless of whether the model "knows", so token probabilities become sharper than accuracy warrants. Verbal confidence is also shaped by what raters like. Restoration: recalibrate on task data with temperature scaling of answer log-probabilities or isotonic regression; use sample agreement, which measures the spread of the policy's own distribution; use a separately trained verifier or a P(True) probe; and combine signals with a small logistic model fitted on validation data. Evaluate by accuracy–coverage curves on held-out tasks and re-fit after model updates.

Deep-dive Compare token-probability confidence, verbalised confidence and self-consistency for agent escalation.

Token probabilities are cheap and, for pre-trained models on short closed-form answers, well calibrated, but they are often unavailable from APIs, ill-defined for long free-form outputs, and distorted by post-training. Verbalised confidence is always available and interpretable, but is coarse, often overconfident, and sensitive to prompting. Self-consistency (agreement of \(k\) samples) works for any output with a comparable answer, captures the policy's actual uncertainty, and tends to rank well, but costs \(k\) times as much and needs a way to compare answers. In practice: self-consistency or a verifier for high-stakes, low-volume decisions; a cheap probe or recalibrated token probability for high-volume gating; always validated on the real distribution.

Design Design a model-routing scheme for a high-volume support agent that must keep quality while cutting cost.

Classify turns by type and risk: greetings, FAQ, status look-ups (low risk) vs refunds, changes, complaints (high risk). Route low-risk types to a small model by rule; for others, run the small model with a calibrated confidence (sample agreement or a trained probe) and escalate below a threshold tuned on validation data to meet a target accuracy; always route irreversible actions through the frontier model or a deterministic policy check. Measure per-type accuracy, escalation rate, cost per conversation and tail latency; monitor drift in the gate's calibration; keep a shadow evaluation comparing small-model decisions against frontier decisions on a sample. Expect savings of half or more of model cost if most traffic is routine and the gate ranks well.

Design A product manager wants the agent to "never hallucinate". What do you build?

Reframe as: claims that matter must be grounded and checkable. Build retrieval over authoritative sources and require the agent to answer from them with citations; restrict factual tools to verified data (booking system, documentation); add a verification step that checks citations support claims (string match or a judge model) and that referenced entities exist (functions, URLs, booking numbers); allow and reward "I don't know" and escalation; set low temperature for factual answers; evaluate with a hallucination test set including unanswerable questions; and monitor in production by sampling and auditing. Be explicit that the rate can be driven low but not to zero, and design the user experience accordingly.

Design You can either fine-tune a small model for your agent's tool use or keep prompting a frontier model. How do you decide?

Consider: task novelty (in-context learning works when the behaviour is near the prior; unusual formats or domain rules favour fine-tuning); volume and cost (at high volume the frontier model's price dominates and a fine-tuned small model can be an order of magnitude cheaper); latency needs; data availability (hundreds to thousands of good trajectories, possibly distilled from the frontier model); the pace of change (prompts adapt in minutes; fine-tunes need retraining); and quality ceiling (frontier models handle the long tail better). A common path is to prototype with the frontier model, log trajectories, filter the successful ones, distil into a small model for the routine traffic, and keep the frontier model behind a confidence gate for the rest, evaluating both on the same test set.

Deep-dive Why does a predictor of internet text end up with representations useful for acting? Give the argument and its caveats.

Minimising cross-entropy on a corpus generated by processes in the world (people writing about facts, code that runs, conversations with goals) rewards any internal variable that improves prediction; latent variables of the generating process, such as the state of a program, the truth of a claim or a writer's intent, are such variables, so sufficiently good predictors learn representations of them (probing finds board states, truth directions, etc.). Traces of goal-directed behaviour are common, so the model learns conditional distributions of next actions given situations. Caveats: the model learns what people wrote, not what is true; it has no interventional data, so causal knowledge is second-hand; representations are only as good as the coverage of the corpus; and imitation of average behaviour is not optimal behaviour, which is why post-training and RL are needed.
