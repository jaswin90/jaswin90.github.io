Part I · What Is an Agent? — Chapter 4

Context Engineering

The context is the only thing an agent's policy ever sees. It is the agent's belief state, its instructions, its tool manual and its memory, and every token in it is paid for at every step. Context engineering is the craft of deciding what goes in, in what order, in what form, and for how long.

Why this chapter

Chapter 2 identified the context map \(f\), which turns the agent's history into the string the model reads, as the place where an LLM agent's information is kept or lost. Chapter 3 showed that the model behaves like an implicit Bayesian reasoner whose posterior over "what is going on and how should I behave" is set by that string, that it imitates whatever it sees, uses the middle of long contexts less reliably, and reads cached tokens for a tenth of the price. Put together, these facts make the context the single most important engineering surface of an agent. Changing the model is expensive and changing the environment is often impossible, but the context is entirely under the designer's control, and it can be changed in minutes.

The term context engineering came into wide use in 2025, displacing the older "prompt engineering", and the change of name reflects a change of problem. A prompt is written once for a single call. An agent's context is assembled anew at every step, from a fixed part written by the designer (the system prompt, tool definitions and examples) and a growing part written by the episode (messages, tool calls and observations). The questions are therefore not only "how should I phrase the instructions?" but also "what should the agent keep from step 30 when it reaches step 60?" and "how do I arrange things so that the expensive prefix is cached across calls?" This chapter treats both parts, in the order an engineer meets them: the budget, the fixed part, the format of outputs, caching, and the growing part.

Learning objectives
  1. Treat the context as a budget, and allocate it across system prompt, tools, examples, task, memory and history for a given agent.
  2. Write a system prompt at the right level of specificity, and explain how its structure interacts with the model's learned instruction hierarchy.
  3. Explain why tool definitions are part of the prompt, and quantify their cost.
  4. Describe structured output and constrained decoding as masking of the next-token distribution, and its effect on reliability.
  5. Derive the economics of prompt caching, including the break-even hit rate, and lay out a context so that caching works.
  6. Explain context rot and position effects, and choose among pruning, summarising and just-in-time retrieval for a growing history.

We use the LLM agent \((p_\theta,f,g)\) of §2.4, the episode cost model of §2.8, and the properties of models in §3.3–§3.7.

4.1 The context as a budget

Every call to the model is conditioned on a single string, at most \(n_{\max}\) tokens long, and every token of it has three prices. It costs money: \(\kappa_{\text{in}}\) per call if fresh, \(\kappa_{\text{cache}}\) if cached. It costs time: fresh tokens must be prefilled. And it costs attention: a token that is irrelevant to the next decision competes with the relevant ones, and long contexts degrade the model's use of what matters (§3.8). The third price is the least visible and often the largest. A context engineer's first habit is therefore to think of the context as a budget to be allocated, not a bucket to be filled.

A typical agent context has six regions, drawn in Figure 4.1 in the order they usually appear. The system prompt states who the agent is, what it is for and the rules it must follow. The tool definitions describe each available action: its name, purpose and parameters. Examples, if any, show the desired behaviour. The task is the user's request or the issue to fix. Memory is information brought in from outside the episode: retrieved documents, notes from earlier sessions, a map of the repository. The history is the episode so far: messages, the agent's outputs and tool results. The first three are fixed by the designer and identical across steps and, often, across episodes; the last three are specific to the episode, and the history grows at every step.

Figure 4.1 already encodes the most important layout rule, which §4.5 derives: stable things first, changing things last. It also suggests the budgeting question for each region. How long must the system prompt be to specify the behaviour? How many tools does the agent really need? Do examples earn their tokens? How much memory should be retrieved? And, above all, what part of the history must survive into the next step? A useful mental model is a knapsack: each piece of information has a cost in tokens and a value in improving the next decision, and the context map should select the set with the highest value within the budget. The value of a piece of information is not additive (two copies of a file are worth no more than one), which is what makes the problem interesting, but the frame is right: something earns its place in the context only if it changes, or could change, what the agent does next.

For the mathematician — the context as an information budget

In the language of §2.4, the ideal context \(c_t\) is a sufficient statistic of the history for the next decision. With a budget \(n\) on its length, the context map solves, at least approximately, \(\max_{f:\lvert f(h)\rvert\le n}\,\mathbb E\big[V^{\pi_\theta(\cdot\mid f(h_t))}\big]\): choose the compression of the history that maximises the expected value of the policy that reads it. This is a rate–distortion problem in which the distortion is measured by decision quality rather than reconstruction error. It has no closed-form solution, but it explains the shape of good heuristics: keep what the policy's next actions depend on (the goal, the constraints, the current state of artefacts), drop what it does not (superseded file contents, verbose logs of successful commands), and summarise what it might need later.

To make the budget concrete, consider the coding agent of §1.10 at its first step: about 2,000 tokens of system prompt, 3,000 of tool definitions, 1,000 for the issue and 2,000 for a repository map, 8,000 in all. By step 40 the history has added 97,500 more. The fixed regions were carefully designed and the history was not designed at all; it is whatever the tools happened to return. This imbalance, a few thousand curated tokens and a hundred thousand accidental ones, is typical, and it is why the second half of this chapter, on managing the history, matters as much as the first. We start, however, with the region that sets the posterior for everything else.

4.2 The system prompt

The system prompt is the first thing the model reads and, by training, the most authoritative (§3.4). In the Bayesian picture of §3.3, it is the evidence that fixes the latent task: what kind of agent this is, what it is trying to achieve, and what rules constrain it. Everything later in the context is interpreted against it. A good system prompt is therefore less like a list of commands and more like the briefing one would give a capable new colleague on their first day: what the job is, why it matters, what good work looks like, what is forbidden, and what to do when unsure.

The central design decision is the level of specificity, which Anthropic's guidance calls the right altitude[1]. At one extreme, a prompt full of rigid rules ("if the customer mentions baggage, call lookup_baggage first; never use the word 'unfortunately'") tries to hard-code a workflow in natural language. It is brittle: it fails on every case the rules did not anticipate, and the rules interact in ways the author did not foresee. At the other extreme, a vague prompt ("you are a helpful airline assistant") gives the model no information about the specific policy, goals and constraints, so it falls back on its generic prior, which may be wrong for this airline. The right altitude states the goals and the reasons for the rules, gives concrete guidance where the model's prior is known to be wrong for this task, and trusts the model's judgement elsewhere. Reasons matter more than one might expect: a model told "do not issue refunds above the fare paid, because refunds are reconciled against the original payment" generalises better to unanticipated cases than one told only "do not issue large refunds".

A system prompt also has to say what happens when instructions conflict, because in an agent they constantly do. The developer's policy says refunds require a booking reference; the customer says they lost it and insists; a retrieved help-centre page, out of date, says references are optional. Models are trained to give the system prompt precedence over the user and the user over tool outputs (§3.4), but that training is a tendency, and a prompt that states the order of authority explicitly, and says what to do in a conflict (follow the policy, explain why, offer the alternative, escalate if the customer disputes it), turns a fragile tendency into an explicit rule the model has read. It also gives evaluators something to test: a conflict that the prompt resolves explicitly is a conflict on which a failure is a bug, not a matter of taste.

Structure helps the model find things. Organising the prompt into labelled sections (background, goals, policies, tool-use guidance, output format), using headings or XML-style tags, plays to the formats the model saw in training and makes it easier for both the model and the engineer to locate a rule. Rules that are critical should be stated once, clearly, near the top; repeating them in capitals throughout tends to make models over-apply them. And because the system prompt is part of the cached prefix, it must not contain anything that changes between calls: the current time, the user's name or the conversation's ID belong later in the context, a point whose cost §4.5 will compute.

Worked example — a support agent's system prompt, by section

A system prompt for the airline support agent might allocate its roughly 3,000 tokens as follows.

Role and goal (150 tokens). Who the agent serves, what a successful conversation achieves (the customer's request resolved within policy, or escalated with a summary), and the tone.

Policy (1,800 tokens). The fare rules, change and cancellation fees, refund eligibility and compensation rules, stated with their reasons, plus the order of authority: policy over customer requests.

Procedure guidance (500 tokens). Authenticate the customer before reading or changing a booking; confirm the details of any change with the customer before executing it; read back the booking after a change; never invent booking details.

Escalation (250 tokens). When to hand over to a human (threats, legal claims, requests outside policy that the customer disputes, low confidence) and what to include in the hand-over.

Format (300 tokens). Short replies, plain language, one question at a time; tool-call conventions.

Assessment. The policy dominates, as it should: it is the information the model's generic prior lacks. Procedure guidance targets known failure modes (acting before confirming, sycophantic concessions, §3.4). Nothing in it changes per customer, so all 3,000 tokens are cacheable across every conversation.

The worked example also shows what the system prompt cannot do. It can state the refund policy, but it cannot enforce it: a sycophantic model under pressure may still concede. Rules whose violation is costly should therefore be enforced in code, in the tools themselves (the refund tool rejects ineligible refunds), with the prompt explaining the rule so that the model does not waste steps attempting what will be refused. This division of labour, the prompt for judgement and the code for guarantees, recurs throughout the book. The tools are the next region of the context, and they are prompts too.

4.3 Tools are prompts

A tool is presented to the model as a name, a natural-language description and a schema for its parameters, all serialised into the context (Figure 3.3). The model decides whether and how to call it entirely from that text. A tool description is therefore not documentation for humans that the model happens to see; it is a prompt, and it deserves the same care as the system prompt. The SWE-agent results of §1.9, where redesigning the tools multiplied success with the same model, are the strongest evidence for this.

Good descriptions say what the tool does, when to use it and when not to, what each parameter means with its units and format, what the tool returns, and what errors it can produce. Consider two descriptions of the same search tool. "search(q): searches" leaves the model to guess whether q is a regular expression, whether the search covers file names or contents, and how many results come back. "search_code(pattern, path='.'): searches file contents under path for a literal string or Python regular expression; returns up to 50 matches as file:line: text; use it to find where a function is defined or used; for file names use find_files" removes each ambiguity in one sentence. Every ambiguity left in a tool description is a per-step error rate \(\epsilon\) waiting to happen.

Tool definitions also cost budget, and the cost grows with the number of tools. A typical definition with a description and a parameter schema is 150 to 400 tokens. An agent connected to many services through a protocol such as MCP (Chapter 12) can easily carry 50 or 100 tools, which is 10,000 to 40,000 tokens of definitions in every call. Figure 4.2 computes the cost of carrying tool definitions through a 40-step episode at 250 tokens per tool.

Figure 4.2 shows that, with caching, tool definitions are affordable in money even in large numbers: under 40 cents an episode for a hundred tools. The more serious costs are the other two. A hundred tools take an eighth of a 200,000-token window before the task has even been stated, and a long menu of similar tools makes selection harder: the model must discriminate between get_booking, lookup_reservation and fetch_trip, and ambiguity among near-duplicates is a reliable source of errors. Evaluations of function calling consistently find accuracy declining as the number of available functions grows. Three remedies are standard. Curate: give each agent only the tools its task needs, and merge overlapping tools. Namespace: group related tools with consistent prefixes (booking_get, booking_change) so that the menu has visible structure. Load on demand: expose a small set of tools plus a way to search for and load others when needed, keeping the definitions of rarely used tools out of the context until they are relevant. Chapter 8 returns to tool design in depth.

4.4 Examples

Examples are the most direct way to show a model what is wanted, and §3.3 explained why they work: each consistent example multiplies the posterior odds of the intended behaviour. For agents, though, examples need more care than for single-call prompts, for three reasons.

First, models imitate examples closely, often too closely. An agent shown one example trajectory in which it searches, opens a file and edits it will tend to follow that exact sequence, including on tasks where it is wrong. A set of examples should therefore be diverse, covering the range of situations the agent faces and the different correct responses, so that what is shared across them (the reasoning, the checks, the format) is what the model learns, rather than the surface sequence of any one. Second, agent examples are long: a full trajectory can be thousands of tokens, so a handful of them can dominate the budget. Short, canonical fragments that illustrate a single difficult judgement ("here is how to respond when the customer asks for a refund the policy does not allow") are usually better value than complete transcripts. Third, the best examples are often already in the context: the agent's own earlier successful steps. A clean history of well-formed tool calls is an implicit few-shot prompt for the next one, and a messy one is an implicit prompt for more mess.

When the window is large, many examples can help. Agarwal and colleagues (2024) studied many-shot in-context learning with hundreds or thousands of examples and found continued gains on many tasks, sometimes approaching fine-tuning, along with the ability to override some pre-training biases that few-shot prompts could not[2]. For a high-volume agent with a stable task, a cached prefix of many examples can therefore be a cheap alternative to fine-tuning. But each example also lengthens the context through which the model must find the relevant information in every call, and the gains must be measured rather than assumed. As with every region of the context, an example earns its tokens only if an evaluation shows it changes behaviour for the better.

Choosing examples per task

A fixed set of examples must serve every task the agent sees, which forces a compromise between coverage and length. An alternative is to retrieve examples: keep a library of annotated examples (successful past trajectories, curated edge cases) indexed by a description of the situation, and insert the few most similar to the current task into the context. This is the in-context analogue of nearest-neighbour methods, and in the Bayesian picture it is choosing the evidence most informative about the latent task at hand. It often beats a larger fixed set at a fraction of the tokens. It has two costs. Retrieved examples differ from task to task, so they cannot sit in the cross-episode cached prefix; they must go after it, where they are cached only within the episode. And the library itself becomes an asset that must be curated, versioned and evaluated, since a bad example retrieved for exactly the situations it misdescribes does more harm than no example at all. Chapter 13 returns to example libraries as a form of procedural memory, and Chapter 9 supplies the retrieval machinery.

4.5 Structured output

The parser \(g\) of §2.4 turns the model's output into an action, and when it fails the step fails. Early agents asked for actions in free-form text and parsed them with regular expressions, and a missing bracket or an extra sentence was enough to break a step. The fix, which became standard in 2023–2024, is to have the model emit actions in a machine-readable format, usually JSON conforming to a declared schema, and, increasingly, to guarantee conformance by constraining decoding.

For the mathematician — schemas and constrained decoding

A JSON Schema is a specification of a set of acceptable documents: an object with these fields, of these types, some required, some drawn from an enumerated list. The set of token strings that serialise a valid document is (for most schemas used in practice) a regular language, or close to one, and so is recognised by a finite automaton. Constrained decoding runs the automaton alongside generation: at each position, the tokens that would lead the automaton into a dead state are masked, by setting their logits to \(-\infty\), and the model samples from the renormalised distribution over the rest. Formally, if \(A_i\subseteq\mathcal V\) is the set of allowed tokens at position \(i\), the constrained distribution is \(p(v\mid x_{<i})\mathbf 1[v\in A_i]/\sum_{u\in A_i}p(u\mid x_{<i})\). Every completed output is valid by construction. Libraries such as Outlines precompile the automaton into a token-level index so that the mask costs almost nothing per step[3].

Figure 4.3 shows both the power and the limit of the technique. Malformed actions disappear, which removes a whole class of per-step errors; providers now offer schema-constrained "structured outputs" and strict tool calling for this reason. But the mask guarantees syntax, not semantics: it ensures that amount is a number, not that it is the right number. Worse, when the model's preferred continuation is masked, the renormalised distribution may concentrate on tokens the model considered unlikely, producing outputs that are valid and wrong. If the model wanted to write "about 120" because it was unsure, the mask forces a confident-looking number. Constrained decoding should therefore be paired with schemas that leave room for uncertainty where it is legitimate (an optional notes field, an explicit "unknown" value) and with semantic checks in the tool itself.

A second subtlety concerns reasoning. A model that must answer in a strict format immediately has no room to think first, and some studies have reported accuracy losses on reasoning tasks under tight format constraints (Tam et al., 2024)[4]; others attribute the losses to poorly designed prompts. The robust practice is to let the model reason before it commits to the structured part: either in free text before the tool call, which function-calling models do naturally, or through a reasoning field placed before the answer fields in the schema, since the model generates fields in order. A schema whose first field is the answer and whose last is "reasoning" asks for a justification after the fact, which is worth much less.

Designing the output, not only the input

Context engineering is usually discussed as the design of what the model reads, but what it writes is part of the next step's context and the main driver of latency (§3.7). Every token the agent writes at step \(t\) is read again at every later step, so verbose reasoning, restated plans and long apologies are paid for many times over. Three practices keep outputs lean. The first is to say what is wanted: "explain your reasoning in at most three sentences before each tool call" or "reply to the customer in under 80 words" is followed well by modern models and can cut output length several-fold. The second is to move bulk out of the model's output and into tools: an edit tool that takes a short patch is better than asking the model to rewrite a whole file, both because the output is shorter and because a shorter output has fewer places to go wrong. The third, for reasoning models, is to set the reasoning budget deliberately, since hidden reasoning tokens are output tokens with output prices and output speeds; whether a smaller budget hurts must be measured on the task, but for routine steps it often does not. A useful habit is to log output tokens per step alongside input tokens: in many agents the cheapest large improvement in latency is found there.

4.6 Prompt caching

We have used prompt caching since Chapter 1 as a tenfold discount on re-read tokens. It is time to see how it works and what it requires, because a context laid out without regard to caching can cost several times what it should. When a model processes a prompt, it computes for every token internal vectors (the keys and values of attention, the KV cache described in the companion book) that later tokens attend to. These depend only on the token and everything before it. If a later request begins with exactly the same tokens, the provider can reuse the stored vectors instead of recomputing them, skipping that part of prefill. Providers expose this as prompt caching: cached prefixes are charged at a fraction of the input price and contribute almost nothing to time-to-first-token.

Three properties of the mechanism dictate how contexts must be laid out. Caching is by exact prefix: the reuse extends only up to the first token that differs from a cached request, so a change at position 100 invalidates everything after it, even if the remaining 50,000 tokens are identical. Caches have a time to live: entries are evicted after minutes of disuse (some providers offer longer lifetimes at a higher price), so a cache is valuable only if requests sharing a prefix arrive close together. And writing to the cache may cost a premium: some providers charge more than the normal input price for tokens written to the cache (for example 1.25 times), recovered only if the prefix is read again.

The premium makes caching a bet, and we can compute when it pays. Let a prefix of \(P\) tokens be sent on many calls, let \(h\) be the fraction of calls on which it is found in the cache (the hit rate), let a write cost \(w\,\kappa_{\text{in}}\) per token and a read \(\kappa_{\text{cache}}=\eta\,\kappa_{\text{in}}\) per token. With caching enabled, a hit costs \(\eta\kappa_{\text{in}}P\) and a miss \(w\kappa_{\text{in}}P\) (the prefix is processed and written); without caching every call costs \(\kappa_{\text{in}}P\). The expected prefix cost relative to no caching is

\[ \frac{\mathbb E[C_{\text{prefix}}]}{\kappa_{\text{in}}P}=h\,\eta+(1-h)\,w,\qquad \text{caching pays iff } h>\frac{w-1}{w-\eta}. \]

With our reference \(\eta=0.1\) and a write premium \(w=1.25\), the break-even hit rate is \(0.25/1.15\approx0.22\): caching pays as soon as more than about one call in five finds its prefix. Figure 4.4 plots the relative cost against the hit rate. Within an agent episode, where consecutive calls share almost their entire context and arrive seconds apart, hit rates above 90% are normal, and the prefix costs a sixth or less of its uncached price.

Figure 4.4 turns into layout rules directly. Put the stable regions first and in a fixed order: system prompt, then tool definitions, then examples, so that they form a prefix shared across every call and every episode. Never put anything that varies per call (the current time, a request ID, a randomly ordered list) before them, because it caps the cacheable prefix at the position of the first difference. Keep the history append-only: editing or deleting earlier history, however sensible for the budget, invalidates the cache from the point of the edit. Keep the tool set stable within an episode: adding or removing a tool rewrites the tool region and everything after it. And keep calls flowing: an agent that pauses for long tool runs may find its cache evicted when it returns.

Worked example — the timestamp that cost four times as much

The support agent of §2.8 has a 6,000-token fixed prefix and 12 turns per conversation, appending 400 tokens per turn. With caching working, a conversation costs about $0.085 (§2.8). A developer adds "Current time: 14:03:27" to the first line of the system prompt so that the agent knows the time.

Effect. The time changes on every call, so the first differing token is near position 10 and nothing after it is ever reused. Every call becomes a miss, and with a write premium every call pays \(1.25\kappa_{\text{in}}\) for its whole context.

Cost. Input tokens per conversation: 98,400 (§2.8). At \(1.25\times\$3\) per million: $0.369, plus $0.027 of output: $0.40, nearly five times the cached cost and more than the $0.32 of not caching at all.

Fix. Put the time, to the minute, in the latest user turn, or provide it through a tool. The prefix is restored and the cost returns to about $0.085.

Figure 4.5 shows the worked example as a picture, and the picture is worth remembering because it applies to every per-call value, not only the time: a user's name, a request ID, a randomly ordered list of tools or retrieved documents, a "turn number" counter. Each belongs as late in the context as its role allows, and anything that must appear early must be stable for the lifetime of the cache.

The worked example is a real and common failure, and it illustrates why caching must be monitored rather than assumed: providers report the number of cached tokens in each response, and a sudden fall in that number is often the first symptom of a context change that broke the prefix. Caching also creates a tension with the history management of §4.8, where we will want to edit old history to keep the context small. Before that, we look at why a small context is worth wanting even when tokens are cheap.

4.7 Context rot

If cached tokens cost a tenth and the window holds 200,000 of them, why not simply keep everything? The answer is that a model's use of its context degrades as the context grows, a phenomenon practitioners have come to call context rot. Three effects contribute, and each has been measured.

The first is position. Liu and colleagues placed the document containing the answer to a question at different positions among twenty retrieved documents and found a U-shaped curve: accuracy was highest when the relevant document was first or last and lowest when it was in the middle, in some cases falling below the accuracy of answering with no documents at all[5]. The second is distraction. Shi and colleagues showed that adding irrelevant sentences to arithmetic word problems substantially reduced accuracy, even though the needed information was unchanged[6]: a model does not simply ignore what does not matter. The third is length itself. Benchmarks that go beyond finding a single fact, such as RULER, which requires tracking several facts or aggregating across a long input, show accuracy falling well before the nominal window for most models[7], and studies of many models on simple tasks at increasing lengths have found consistent degradation as input grows, even when the task does not get harder[8].

For an agent, all three effects are amplified. The history is not a curated set of documents but a heap of tool outputs, most of them irrelevant by the time they are old: a directory listing from step 3, a test log from step 12 that has since been fixed, the contents of a file that turned out to be unrelated. The goal and constraints, stated once at the start, drift towards the middle of the context as the history grows behind them. And the agent's own earlier reasoning, including abandoned hypotheses, sits in the context as a standing invitation to re-adopt them (§3.3). Long-running agents that degrade after dozens of steps (repeating actions, forgetting constraints, losing the thread of the task) are usually suffering from context rot, not from a lack of model capability. The remedy is to manage the history actively, which is the subject of the next section.

4.8 Managing the growing history

The history is the part of the context nobody designed, and in long episodes it is almost all of it. Managing it means choosing, at each step, a context map \(f\) that keeps what matters within a budget. Figure 4.6 shows the four basic operations, which real systems combine.

Figure 4.6 orders the operations by how much they change. Pruning keeps the agent's own outputs (its reasoning and actions) but replaces old observations, which are usually the bulk, with stubs such as "[output of pytest at step 12: 3 failures, since fixed]". It is cheap and safe because the decisions remain visible and the raw data can be re-fetched by running the tool again. Summarising, often called compaction, asks a model to rewrite a span of history as a concise note of what was learned and what remains to be done, and replaces the span with it; it bounds the context but is lossy, and its classic failure is a summary that omits the goal or a constraint (§2.4). Offloading keeps information outside the context, in files or a memory store, with only a pointer or a short note inside; the agent re-reads what it needs, when it needs it. This just-in-time style, in which the context holds lightweight references (file paths, queries, IDs) rather than the data itself, is how capable coding agents navigate large repositories: they do not load the code base, they search it[1]. Chapters 13 and 14 develop offloading into memory architectures and long-horizon techniques.

There is a trap in combining these operations with caching. Pruning and summarising edit earlier history, and §4.6 showed that any edit invalidates the cache from that point. Doing them at every step can cost more than it saves.

Worked example — pruning versus caching

The coding agent's context starts at 8,000 tokens and grows by 2,500 per step (300 of output and 2,200 of observation) over 40 steps. Policy P: at every step, replace observations older than five steps with 200-token stubs, so that old steps cost 500 tokens.

Input tokens under P. For \(t\le6\), \(n_t=8{,}000+2{,}500(t-1)\), summing to 85,500. For \(t\ge7\), \(n_t=8{,}000+5\times2{,}500+500(t-6)\), and \(\sum_{t=7}^{40}n_t=34\times20{,}500+500\times\frac{34\times35}{2}=697{,}000+297{,}500=994{,}500\). Total: 1.08 million, against 2.27 million unpruned.

But the cache. Each step's pruning rewrites the observation that has just turned six steps old, about 13,000 tokens from the end (the new stub plus the five most recent steps), so each call can reuse only the part before the edit. About 13,000 tokens per call are fresh instead of 2,500: roughly 460,000 fresh tokens in all, with the remaining 620,000 cached. Cost: \(0.46\times\$3+0.62\times\$0.30+\$0.18\approx\$1.75\).

Comparison. Unpruned with caching: $1.15 (§1.10). Pruning at every step raised the cost by half while halving the tokens. Batch instead: prune once every ten steps, so that the cache is broken four times rather than 34. The context stays near the pruned size, most calls hit the cache, and the cost falls below $1.15, with the quality benefit of a shorter context.

The example generalises to a design rule: edit history rarely and in large batches, at natural boundaries such as the completion of a sub-task, rather than continuously. This is how compaction is usually implemented in practice: when the context passes a threshold (say 70% of the window or a fixed token budget), a single summarisation replaces most of the history, the cache is rebuilt once, and the episode continues from a much smaller context. The threshold itself is a parameter to tune: too low and the agent loses information it needed, too high and it suffers context rot before the compaction comes.

Keeping the goal in view

One simple technique addresses context rot from the other side. Instead of only removing material from the history, the agent periodically adds a short restatement of what matters at the end of the context, where models attend most reliably: the goal, the plan, what is done and what remains. Coding agents often do this by maintaining a to-do list or plan file and rewriting it after each milestone, so that the latest version is always near the end of the context; practitioners building long-running agents have reported that this kind of recitation noticeably reduces drift and forgotten sub-goals[9]. In the terms of §2.4 the agent is writing its own belief summary into the context, a learned approximation to the sufficient statistic that the harness could not compute. The cost is a few hundred tokens per update, appended rather than edited, so it is compatible with caching. It is not a substitute for compaction, because the old history is still there, but it moves the most decision-relevant information to the most reliable position.

Drill 4.1 — break-even hit rate

A provider charges cache writes at 2× the input price and cache reads at 0.1×. (a) What hit rate is needed for caching to pay? (b) A prefix is shared by bursts of requests: within each burst of \(m\) requests arriving within the cache lifetime, the first misses and the rest hit. For what \(m\) does caching pay?

(a) \(h>(w-1)/(w-\eta)=1/1.9\approx0.53\). (b) \(h=(m-1)/m>0.53\) requires \(m>2.1\), so bursts of three or more. With \(w=1.25\), any burst of two or more pays, since \(h=0.5>0.22\).

Drill 4.2 — how much of the window is left?

A research agent has a 4,000-token system prompt, 40 tools at 300 tokens each, 3 examples of 1,500 tokens, and adds 6,000 tokens per step. The team wants to compact when the context reaches 60% of a 200,000-token window. At which step does compaction trigger, and how much of the budget is the fixed prefix?

Fixed prefix: \(4{,}000+12{,}000+4{,}500=20{,}500\) tokens, 10% of the window. Threshold: 120,000. Need \(20{,}500+6{,}000t\ge120{,}000\), so \(t\ge16.6\): compaction at step 17. Cutting to the 15 tools actually used saves 7,500 tokens and delays compaction by about one step; the bigger lever is the 6,000 tokens per step, which retrieval of relevant passages (Chapter 9) could cut several-fold.

Drill 4.3 — where did the tokens go?

A coding agent's logs show that at step 30 its 85,000-token context contains: 8,000 fixed, 9,000 of its own outputs, 41,000 of file views (of which 30,000 are files it never edited), 22,000 of test logs (all but the latest 3,000 superseded) and 5,000 of search results. Looking ahead

Part I is complete. We have a formal model of an agent (Chapter 2), an understanding of the model at its heart (Chapter 3), and the craft of building the context that model reads (this chapter). With these, an agent can be given the right information and asked for an action in a reliable format. But the action may still be wrong, because the model chose it in a single forward pass of reasoning, as it were, without thinking it through. The most important discovery about language models since in-context learning is that letting them generate reasoning before answering makes them markedly more accurate, and that this accuracy can be bought with more computation at inference time. Why does writing out a chain of thought help, how much does it help, how should several reasoning attempts be combined, and what did reasoning models change? Chapter 5 begins Part II, on reasoning and planning.

Chapter summary

  • The context is a budget with three prices per token: money, time and attention. Its regions are system prompt, tools, examples, task, memory and history; the first three are stable and designer-written, the last three episode-specific, and the history usually dominates.
  • The system prompt fixes the latent task. Write it at the right altitude: goals and reasons, concrete guidance where the prior is wrong, judgement elsewhere. Enforce costly rules in code, not prose.
  • Tools are prompts: unambiguous descriptions lower per-step error. Many tools cost budget and selection accuracy; curate, namespace and load on demand.
  • Examples work but are imitated closely: prefer diverse, short, canonical fragments; many-shot prefixes can substitute for fine-tuning when cached and measured.
  • Constrained decoding masks tokens to guarantee schema-valid output; it fixes syntax, not semantics, and should leave room for uncertainty and reasoning before the answer.
  • Prompt caching reuses exact prefixes. Relative prefix cost is \(h\eta+(1-h)w\); break-even \(h>(w-1)/(w-\eta)\approx22\%\) at reference prices. Stable regions first, nothing varying before them, append-only history, stable tool sets.
  • Context rot: position effects, distraction and length degrade use of the context; long agent histories amplify them.
  • Managing history: prune observations, summarise (compact), offload and retrieve just in time. Edit rarely and in batches to preserve caching.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up What is context engineering and how is it different from prompt engineering?

Prompt engineering is writing the instructions for a single call. Context engineering is designing the whole string an agent's model reads at every step: the fixed regions (system prompt, tool definitions, examples) and the dynamic ones (task, retrieved memory, and the growing history of actions and observations), with attention to token budget, ordering for prompt caching, and what to keep, prune, summarise or offload as the episode grows. It treats the context as the agent's belief state and working memory, which must stay sufficient for the next decision while staying small enough to be cheap and to avoid context rot.

Warm-up How does prompt caching work and how should you lay out a context to benefit from it?

The provider stores the attention key/value states computed for a prompt prefix; a later request that begins with exactly the same tokens reuses them, so those tokens cost a fraction of the input price and little prefill time. Reuse stops at the first differing token, entries expire after minutes of disuse, and writes may cost a premium. Layout: stable regions first in a fixed order (system prompt, tools, examples), nothing per-call (timestamps, IDs) before them, append-only history, stable tool sets within an episode, and calls close enough in time to keep the cache warm. Monitor cached-token counts.

Warm-up What makes a good tool description?

It states what the tool does, when to use it and when to use something else, each parameter's meaning, type, units and format with an example, what it returns and in what format, its limits (pagination, maximum results), and its error behaviour. Names should be distinct and namespaced. Every ambiguity becomes a source of per-step errors, so descriptions should be tested: give the model tasks and check that it picks the right tool with the right arguments.

Core Derive the break-even cache hit rate given write premium \(w\) and read discount \(\eta\).

Per call, with caching, the prefix costs \(\eta\kappa P\) on a hit and \(w\kappa P\) on a miss; without caching, \(\kappa P\). Expected relative cost with hit rate \(h\) is \(h\eta+(1-h)w\). Setting it below 1 gives \(w-h(w-\eta)<1\iff h>(w-1)/(w-\eta)\). For \(w=1.25,\eta=0.1\), \(h>0.217\); for \(w=2\), \(h>0.53\). Within agent episodes hit rates exceed 90%, so caching is a large win; for sporadic traffic with long prefixes and short cache lifetimes it can lose.

Core An agent's cost per episode quadrupled after a deploy, with no change in behaviour. What do you check?

Cache hit rate first: look at cached-token counts per call before and after. Likely causes: something per-call inserted early in the context (timestamp, request ID, user name in the system prompt), non-deterministic ordering (tools or examples serialised from an unordered set), a tool list that now changes between calls, edits to earlier history (a new pruning policy), a model or endpoint change with a different cache, or longer gaps between calls causing eviction. Also check token counts per region for growth (a tool now returning verbose output) and output lengths (a prompt change making the model verbose).

Core What is constrained decoding and what are its limits?

It compiles a schema or grammar into an automaton and, at each generation step, masks tokens that would make the output invalid, renormalising the model's distribution over the allowed ones. It guarantees parseable, schema-valid outputs, removing a class of per-step failures. Limits: it guarantees syntax, not correctness; masking can force confident-looking values when the model was uncertain; tight formats with no room to reason can reduce accuracy, so reasoning should precede answer fields or happen in free text before the call; very complex grammars can be costly; and it can interact badly with the model's tokenisation if the implementation is naive.

Core Explain context rot and what you would do about it in a long-running coding agent.

Context rot is the degradation of a model's use of its context as the context grows: position effects (middle content used less), distraction by irrelevant material, and general length effects on multi-fact reasoning. In a coding agent it shows as repeated actions, forgotten constraints and stale beliefs about file contents. Remedies: concise tool outputs (paged views, filtered logs); pruning old observations to stubs; batch compaction at thresholds that preserves the goal, constraints, current plan and state of edited files; offloading notes and plans to files the agent re-reads; just-in-time loading via search; sub-agents for exploratory sub-tasks; and restating the goal near the end of the context after compaction.

Core How would you decide whether few-shot examples are worth their tokens?

Measure: run the agent on a fixed evaluation set with and without the examples (and with alternative sets), comparing success, pass^k, cost and the specific failure modes the examples target. Prefer short fragments targeting hard judgements (refusals, escalations, edge cases) over full trajectories, and make them diverse so the model does not copy one surface sequence. Check for over-imitation (agent copying the example's tool sequence on unrelated tasks). With caching, cost is small, so the decision is mainly about behaviour and context-length effects.

Core How should an agent's system prompt handle rules that must never be broken?

State them clearly once, with the reason, near the top; but do not rely on the prompt to enforce them. Enforce in code: tools validate their inputs against the policy and refuse violations with an informative error; permissions restrict what the agent can call; high-impact actions require confirmation or human approval. The prompt then explains the rule so the agent plans accordingly and the code guarantees it. Test with adversarial cases, since sycophancy and prompt injection target exactly these rules.

Deep-dive Formalise context selection as an optimisation problem. Why is it hard, and what heuristics follow?

Choose \(f\) with \(\lvert f(h)\rvert\le n\) to maximise \(\mathbb E[V^{\pi_\theta(\cdot\mid f(h_t))}]\): a rate–distortion problem with decision-quality distortion. It is hard because value is non-additive (redundancy, interactions), depends on future decisions not yet known, and the model's use of context is position-dependent and nonlinear; the space of compressions is combinatorial. Heuristics: always keep the goal, constraints and current artefact state; keep the agent's own decisions, drop or stub bulky observations; deduplicate (keep only the latest version of a file); summarise spans whose details are unlikely to matter; offload with pointers when future need is uncertain; place critical information at the start and end. Evaluation by ablation on trajectories (replay a step with a pruned context and check whether the action changes) estimates the value of a region empirically.

Deep-dive Analyse the interaction between history pruning and prompt caching, and design a policy that gets the benefits of both.

Pruning reduces tokens and context rot, but editing position \(j\) invalidates cached states after \(j\), so continuous pruning near the end turns most of each call into fresh tokens. With per-step pruning in the worked example, fresh tokens rose from about 2,500 to 13,000 per call and cost rose from $1.15 to $1.75 despite halving total tokens. Better: batch pruning or compaction at thresholds (e.g. every 10 steps or at 50% of a budget), so the cache is rebuilt a few times per episode; prune far-back regions (whose invalidation costs only the tail anyway) together; keep a stable region immediately after the fixed prefix for compacted summaries so subsequent appends cache. Cost model: each rebuild costs roughly the context size at fresh (or write) price; choose the interval minimising rebuild cost plus cached-read cost plus a penalty for context length.

Deep-dive When can many-shot prompting replace fine-tuning, and what are the trade-offs?

When the task is stable, examples are available, volume is high enough that a cached prefix is reused many times, and the needed behaviour is within reach of in-context learning (many-shot can override some priors few-shot cannot). Advantages: no training pipeline, instant updates, works with closed models. Costs: every call carries the examples (cheap when cached, but still prefill on misses and window space), longer contexts can degrade other parts of the task, latency on cache misses, and performance may plateau below fine-tuning. Fine-tuning wins for very high volume on small models, for novel formats, and when the context window is needed for other content. Decide by measuring both on the same evaluation set and computing cost per successful task.

Design Design the context for a research agent that reads 50 web pages per task.

Fixed prefix: system prompt with goals, citation rules and source-quality guidance; a small tool set (search, fetch, extract, note, write); one short example of a well-cited paragraph. Pages never enter the main context raw: a fetch tool returns the page to a cheap extraction step (small model or the same model in a sub-call) that returns the passages relevant to the current sub-question, with URL and quotes, typically a few hundred tokens. Running notes (claims, evidence, open questions) live in a notes file the agent updates and re-reads; the context keeps the question, the plan, the notes summary and recent actions. Sub-questions can go to sub-agents with fresh contexts, returning summaries. Compact at a threshold, preserving the plan and the evidence table. Cache the prefix; keep the history append-only between compactions. Evaluate on citation accuracy and coverage.

Design An agent platform exposes 300 tools through connectors. How do you keep tool selection accurate?

Do not put 300 definitions in every context. Expose a small core set plus a tool-search tool that returns relevant tool definitions by description (embedding or keyword search); load selected definitions into the context for the rest of the episode (append, to preserve caching). Organise tools by namespace, deduplicate overlapping ones, and enforce description quality (purpose, when to use, parameter formats). Route by task type to curated subsets where possible. Measure selection accuracy on a tool-use test set as the catalogue grows, and track the token cost of definitions per call.

Design Write the outline of a compaction prompt for a coding agent and say how you would test it.

The compaction call receives the history and must output: the original task verbatim; constraints and user preferences; the current plan and what remains; files modified with a summary of each change (and that their current contents can be re-read); key findings (root cause hypotheses confirmed or ruled out, with evidence); the latest test status; open questions and pitfalls already encountered; and next step. It must not invent progress. Test by replay: take logged trajectories, compact at step k, continue the agent from the compacted context, and compare success and step count with continuing from the full context; also check with a judge that each summary contains the task and constraints. Track failures where agents redo work or violate earlier constraints after compaction.

Core Why place reasoning before the answer in structured outputs?

Generation is left-to-right, so the tokens of the answer can only depend on what precedes them. Reasoning fields placed first let the model compute before committing; placed last, they are a post-hoc rationalisation that cannot improve the answer. With function-calling models, free-text reasoning before the call serves the same purpose. With reasoning models, hidden reasoning precedes the output anyway, so schemas can be tight without this cost.
