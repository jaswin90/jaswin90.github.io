Part III · Acting: Tools and Environments — Chapter 10

Code as Action

A menu of tools gives an agent a fixed vocabulary of actions. A code interpreter gives it a language: loops, conditions, composition, any library, and the ability to build new tools as it goes. This chapter treats code as the most general action space an agent can have, explains how to run model-written code safely, and dissects the coding agent, the first agent type to become reliably useful at scale.

Why this chapter

Chapter 8 designed tools as functions with schemas, called one or a few at a time. That design has a ceiling. To process twenty bookings, a function-calling agent makes twenty calls, or relies on the developer to have anticipated the need with a batch tool. To compute a statistic from a database query, it must either have a tool for that statistic or copy numbers into its reasoning and compute them unreliably (§5.5). Code removes the ceiling: an agent that can write a short program can loop over the bookings, query the database and compute exactly, in one action. Program-aided reasoning showed the benefit for single answers (§5.5); this chapter generalises it to the whole action space.

Code is also the domain where agents first became dependable enough to change how people work. Coding agents that read a repository, run its tests, edit files and submit patches went from resolving 2% of real GitHub issues in 2023 to well over half by 2025 (§1.9). The reasons are instructive and connect to every part of the book: code environments are fully observable on demand (the agent can read any file), they provide strong external feedback (compilers, tests), they are reversible (version control, snapshots), and their tasks often come with an automatic verifier (tests). They are also dangerous: model-written code can delete files, leak secrets and install malicious packages, so running it safely is a prerequisite. We cover the action space, isolation, the anatomy of a coding agent, editing and testing, evaluation, and the specific risks.

Learning objectives
  1. Explain why executable code is a more expressive action space than JSON tool calls, and quantify the steps it saves.
  2. Describe sandboxing: isolation levels from processes to micro-virtual machines, resource and network limits, and snapshots.
  3. Describe the stages of a coding agent (localisation, reproduction, editing, validation) and compare agentic designs with fixed pipelines such as Agentless.
  4. Compare code-editing formats by cost and error rate.
  5. Explain testing as verification, including reproduction tests, hidden tests and flaky tests.
  6. Describe how coding agents are evaluated (SWE-bench and its variants) and the main threats to validity.
  7. Identify the characteristic risks of code-executing agents and their mitigations.

We use the tool anatomy and permission tiers of Chapter 8, search with verifiers (Chapter 6) and revision with external feedback (Chapter 7).

10.1 Code is a language of actions

A JSON tool call is one action from a fixed menu with typed arguments. A program is a composition of actions: it can call many functions, pass the output of one to another, branch on results, loop over collections, handle errors, and define new functions. In the language of Chapter 2, a tool-calling agent's action space is a finite set of parameterised operations; a code-writing agent's action space is the set of programs over those operations, which is closed under composition. Anything a sequence of tool calls can do, a program can do in one step, plus things that no fixed menu anticipated.

Wang and colleagues tested this directly in CodeAct (2024), comparing agents whose actions were JSON tool calls, text-formatted calls, or Python code that called the same tools as functions[1]. On a benchmark of tasks requiring several tools in combination, code actions achieved success rates up to 20 percentage points higher than the alternatives across many models, and needed up to 30% fewer interaction turns. Figure 10.1 shows why: a task that requires the same operation on many items, or a conditional chain of operations, collapses from many steps into one.

Figure 10.1 makes the arithmetic of earlier chapters concrete. The left column has a horizon of forty steps; at a per-step error rate of 2%, \(0.98^{40}=0.45\) of such episodes are error-free, and the model must also add twenty numbers correctly in its reasoning. The right column has one step whose main risk is a bug in a six-line program, which the interpreter's output will usually reveal. The context is read once instead of forty times. Code actions pull every reliability lever of Part I at once: shorter horizons, exact computation, and informative errors (a traceback says exactly what failed).

Code actions have costs. The model must write correct code, which is a skill that varies across models and languages, though it is one that frontier models are trained heavily on. Results of code execution must be captured and returned (standard output, return values, exceptions), and long outputs must be truncated just as for any tool (§8.5). The interpreter holds state between actions (variables, loaded data, open connections), which is powerful but becomes part of the hidden state the agent must track. Most importantly, executing model-written code is executing untrusted code, which requires the isolation of the next section. For these reasons many production agents combine both styles: structured tool calls for consequential, auditable actions (issue a refund) and a code interpreter for exploration, data processing and computation.

Worked example — what the code action saves

The support agent must find, among a customer's 20 bookings, those cancelled by the airline and total their refunds. Context: 12,000 tokens, growing by 300 tokens per tool step.

JSON calls. 40 steps (two calls per booking), each a model call reading the growing context and writing about 80 tokens. Input: \(40\times12{,}000+300\times\frac{40\times39}{2}=480{,}000+234{,}000=714{,}000\) tokens, mostly cached: about $0.21 of cached reads, plus fresh tokens (the initial 12,000 and 300 per step, 24,000 in all) at $0.072 and output \(3{,}200\times\$15/\text{M}=\$0.048\): about $0.33. Time: \(40\times(80/60+0.3)\approx65\) s. Reliability at \(\epsilon=0.02\) per step: 0.45 error-free, plus the risk of an addition error.

Code action. One model call writing a 120-token program, one execution (20 look-ups and 20 quotes, about 2 s if the tools are fast), one call to read the result and reply. Cost: about $0.01. Time: about 6 s. Reliability: dominated by the chance of a bug in the program, perhaps 5%, and most bugs raise an exception that the agent sees and fixes.

Caveat. The program issues no refunds. Writes still go through the guarded, structured tools of §8.9, one approval per refund if the policy requires it.

10.2 Running untrusted code safely

An agent's code is untrusted in two senses. The model may write something harmful by mistake: a cleanup script that deletes the wrong directory, a loop that never ends, a query that locks a production table. And the model may be induced to write something harmful by injected content (§8.9): a README in a repository can contain instructions to exfiltrate credentials. In either case the code must run where it can do limited damage. A sandbox is an execution environment that restricts what code can read, write, connect to and consume.

For the mathematician — isolation restricts the reachable set

Think of the computer as a huge state space: files, processes, network connections, credentials, other users' data. Running a program is applying a transformation that can, in principle, reach any state the program's privileges allow. A sandbox restricts the set of states reachable from inside it to a small subset (its own scratch file system, a few allowed network endpoints, bounded CPU and memory), and makes everything outside that subset unreachable regardless of what code runs. Security is then a property of the boundary, not of the code: we do not need to verify the program, only that the boundary holds. Isolation layers are nested boundaries, each enforced by a different mechanism, so that a flaw in one does not expose everything.

Isolation comes in levels of increasing strength and cost, drawn in Figure 10.2. A separate process with restricted user permissions is cheap but shares the host's kernel and file system. A container (such as Docker) gives the code its own file system, process space and network namespace using features of the host operating system's kernel; it starts in under a second and is the most common choice, but a vulnerability in the shared kernel can let code escape. A user-space kernel such as gVisor intercepts the container's system calls and implements them in a separate, restricted layer, shrinking the attack surface. A micro virtual machine such as Firecracker, built for serverless computing, runs each sandbox with its own minimal kernel on hardware virtualisation and boots in around 125 milliseconds[2]; it gives strong isolation at modest cost and is used by several agent platforms. Full virtual machines are strongest and slowest.

Figure 10.2 also shows the controls that matter as much as the isolation mechanism. Resource limits on CPU, memory, disk and wall-clock time stop runaway loops and fork bombs. Network egress control, through a proxy that allows only listed destinations (the package registry, documentation sites, the specific APIs the task needs), stops exfiltration of data and contact with attackers' servers, the main channel by which injected instructions cause harm. Credential hygiene keeps long-lived secrets out of the sandbox entirely; where the agent needs to call a service, it gets a short-lived, narrowly scoped token, or the call is made by a proxy outside the sandbox on its behalf. And snapshots of the sandbox's file system let the harness restore an earlier state, which is what makes the search over actions of Chapter 6 possible for code: the agent can try a fix, run the tests, and roll back if it fails.

Drill 10.1 — the price of a fresh sandbox

A coding platform starts a fresh micro-VM for each agent episode (boot 0.15 s) and restores a 2 GB repository snapshot (1.5 s). Episodes average 6 minutes. (a) What fraction of episode time is sandbox start-up? (b) The platform runs best-of-8 search with a snapshot restore before each candidate. How much start-up time does a search add?

(a) \(1.65/360=0.46\%\): negligible. (b) Eight restores of 1.5 s, 12 s, if done sequentially, or about 1.5 s if the candidates run in parallel sandboxes. Isolation is cheap compared with model time; the reason not to isolate is never cost.

10.3 Anatomy of a coding agent

A coding agent given an issue ("parse_date crashes on ISO strings with a timezone offset") must do roughly what a human engineer does, and the stages are worth separating because each fails in its own way. Figure 10.3 draws them.

Figure 10.3 is a map of where coding agents fail, and studies of agent trajectories agree on the ranking. Localisation is the most common failure: in a repository of thousands of files, finding the few lines that need to change is a search problem, and an agent that edits the wrong place produces a patch that may even pass the existing tests while leaving the bug. Tools that help it (a repository map listing files and their top-level definitions, exact search for identifiers and error messages, the stack trace from the failing case, go-to-definition) are the most valuable investments (§9.9 discussed why embeddings are often not the best tool here). Reproduction is the step most often skipped and most valuable when done: a test that fails before the fix and passes after it is the verifier that turns the rest of the loop into the high-feedback regime of Chapter 7, and it is what lowers the false-positive rate of best-of-\(n\) selection in Chapter 6's worked example. Validation catches patches that fix the issue but break something else, which requires running the existing test suite, or at least the tests near the change.

The stages can be orchestrated in two ways, and the comparison is Chapter 2's policy-class trade-off in a concrete form. An agentic design, as in SWE-agent and OpenHands, gives a model tools for each stage and lets it decide what to do next, looping as needed[3][4]. A fixed pipeline runs the stages in code. Agentless (Xia et al., 2024) was a pointed demonstration of the second: a three-phase process of hierarchical localisation (files, then classes and functions, then lines), generation of several candidate patches in a simple diff format, and selection by running reproduction and regression tests, with no autonomous agent loop at all[5]. On SWE-bench Lite it resolved about 27% of issues at an average cost of roughly a third of a dollar, better than the open-source agents of the time and at a fraction of their cost.

Agentless's lesson was not that agents are unnecessary, since agentic systems with stronger models later surpassed it by wide margins, but that structure is valuable. Its pipeline encodes what good engineers know (localise hierarchically, reproduce first, generate alternatives, select by tests), and an agent that is not given this structure must rediscover it in every episode, with an error rate at each step. Modern coding agents combine the two: a model with broad autonomy and good tools, plus a harness that encourages or enforces the key stages, for instance by requiring a test run before submission (§2.7).

Worked example — pipeline or agent, by cost per resolved issue

On a team's internal benchmark of 200 issues, a fixed pipeline resolves 38% at $0.40 per attempt; an agent resolves 55% at $1.60 per attempt. An unresolved issue costs an engineer about $60 of time.

Expected cost per issue. Pipeline: \(0.40+0.62\times60=\$37.60\). Agent: \(1.60+0.45\times60=\$28.60\). Pipeline first, agent on the failures: if the agent resolves 40% of the issues the pipeline failed on (the harder ones), the expected cost is \(0.40+0.62\times1.60+0.62\times0.60\times60=0.40+0.99+22.32=\$23.71\).

Lesson. When failures are expensive, the more capable system wins despite its price; a cascade that tries the cheap system first and escalates does better still, as long as the cheap system's successes can be verified (here, by tests). This is the model cascade of §3.7 applied to whole systems.

10.4 How to edit code

The edit itself is a design choice with large consequences for cost and reliability. Three formats are common. Whole-file rewrite: the model outputs the entire new file. It is simple and robust to the model's misremembering of exact surrounding text, but for a 1,000-line file it means writing 1,000 lines to change five, which is expensive (output tokens), slow (decode speed) and risky (the model may silently alter unrelated lines). Search-and-replace blocks: the model outputs the exact text to find and its replacement; the harness applies it if the search text occurs exactly once. It is compact and safe (unrelated code is untouched), and fails loudly when the search text does not match, which gives the agent an instructive error. Unified diffs: the standard patch format with line numbers and context lines; compact, but models are error-prone with line numbers and hunk headers, so harnesses that accept diffs usually apply them fuzzily. Figure 10.4 compares the output size of whole-file rewrites and search-and-replace edits for a five-line change, at about 12 tokens per line.

Figure 10.4 explains why capable coding agents use targeted edit formats for most changes and reserve whole-file writes for new or small files. The saving is not only money and time: a model asked to reproduce 2,000 lines verbatim will occasionally change one it was not asked to, a silent error that tests may not catch, while a search-and-replace edit can only change what it names. The edit tool should also check what it can: that the file still parses after the edit, that the search text matched exactly once, and that the change did not touch files the task forbids (such as test files, discussed in §10.8). Each check converts a silent failure into an instructive error, raising \(r\) in the language of §2.6.

Drill 10.2 — the cost of rewriting

A coding episode makes 12 edits to files averaging 600 lines, changing about 6 lines each. Compare the output tokens, cost and decode time of whole-file rewrites and search-and-replace blocks (12 tokens per line, 6 lines of context per block, search and replace each written once).

Rewrites: \(12\times600\times12=86{,}400\) tokens, $1.30, \(86{,}400/60=1{,}440\) s (24 minutes). Blocks: each \((6+6)\times12\times2=288\) tokens, \(12\times288=3{,}456\) tokens, $0.05, 58 s. The rewrite approach would also add 86,400 tokens to the context, re-read at every later step, unless the harness keeps only the diff.

10.5 Tests as the verifier

The reason coding agents became reliable first is that code comes with a verifier. A test suite is an external, mostly deterministic check whose false-positive rate is low when the tests are thorough; in the chain model of Chapter 7 it gives a high fix rate (a failing test points at the problem) and a near-zero break rate (passing code is left alone), and in Chapter 6's analysis it lets best-of-\(n\) approach pass@\(n\). Three practices make the most of it, and one property of real test suites limits it.

Reproduce first. Before editing, write a test that captures the issue and confirm that it fails. This tests the agent's understanding of the issue (if the test passes before any change, the agent has misunderstood something), and it is the most informative verifier for the fix. Run the right tests. The whole suite of a large project can take tens of minutes; running the tests in the changed module and those that import it, then the full suite before submission, balances speed against coverage. Treat the tests as fixed. Unless the task is to change tests, an agent should not edit them, because editing a test to make it pass is the coding agent's characteristic form of reward hacking (§10.8).

The limiting property is flakiness: some tests fail intermittently for reasons unrelated to the code under test (timing, network access, ordering, randomness). Flaky tests generate false failures that look exactly like real ones, so an agent may "fix" code that was never broken, or abandon a correct patch. The problem grows with the size of the suite. If each of \(n\) tests fails spuriously with probability \(f\) independently, a run of the whole suite shows at least one spurious failure with probability \(1-(1-f)^n\), plotted in Figure 10.5.

Figure 10.5 is the \(\rho^H\) law of Chapter 1 applied to a verifier, and it has a practical consequence for harness design. Before the agent starts, run the test suite on the unmodified code to record which tests already fail or are flaky; after a change, compare against that baseline and re-run any new failures once or twice before reporting them. Report to the agent "3 tests newly failing (confirmed on re-run); 2 pre-existing failures unchanged" rather than a raw log. The verifier becomes more reliable, the observation shorter and more instructive, and the agent spends its steps on real problems.

10.6 Evaluating coding agents

SWE-bench (§1.9) is the reference evaluation for coding agents, and understanding its construction is necessary for interpreting the many numbers quoted from it. Each task is a real issue from one of twelve popular Python repositories, paired with the pull request that fixed it. The agent sees the repository at the commit before the fix and the issue text; its patch is applied and two sets of tests are run: fail-to-pass tests, which the original fix made pass and which must now pass, and pass-to-pass tests, which passed before and must still pass. The full set has 2,294 tasks; SWE-bench Lite is a 300-task subset of more self-contained issues; SWE-bench Verified is a 500-task subset whose issues and tests were checked by human engineers, removing tasks with under-specified issues or tests that reject valid fixes[6][7].

Three threats to validity should be named whenever SWE-bench numbers are compared. Contamination: the issues and their fixes are public and predate most models' training cut-offs, so a model may have seen the solution; newer benchmarks that draw issues created after a model's cut-off address this. Scaffold dependence: the same model scores very differently with different harnesses, tools and budgets, so a reported number describes a system, not a model. Narrowness: twelve Python repositories, mostly libraries, with well-specified issues, are not the distribution of real engineering work. Variants extend coverage: SWE-bench Multimodal (issues with screenshots, in JavaScript), multilingual versions, and economically framed suites such as SWE-Lancer, which priced over a thousand freelance software tasks at their actual payouts[8]. For an organisation deploying a coding agent, the most informative evaluation is the same construction applied to its own repositories: past issues, their fixing commits, and the tests that changed.

Drill 10.3 — what does a reported score mean?

A vendor reports 70% on SWE-bench Verified "with parallel test-time compute". You learn that the system generated 8 candidate patches per issue and selected one with a learned verifier that has a 15% false-positive rate, and that single-candidate accuracy is 50%. Is the 70% plausible, and what would you compare it with?

With \(p=0.5\), an assumed false-negative rate of 0.1 and \(\epsilon_+=0.15\), the ceiling (§6.2) is \(0.45/(0.45+0.075)=0.857\), and eight candidates approach it, so 70% is plausible. Compare it with other systems at the same number of candidates and selection method, and with this system's single-candidate 50%, and ask for the cost per issue (about eight times a single attempt).

10.7 Code for analysis: interpreters and notebooks

Coding agents fix repositories; a second, equally important use of code is analysis. An agent with a Python interpreter and a data set can load, clean, aggregate, plot and model data, answering questions such as "which routes had the most schedule changes last quarter?" exactly rather than by reading samples. Such agents usually run code in a persistent kernel, as in a Jupyter notebook: each action is a cell, and variables, loaded data frames and imported libraries persist between cells. Persistence is what makes interactive analysis efficient, since a 2 GB data set is loaded once rather than at every step.

Persistence also creates a hidden-state problem of exactly the kind Chapter 2 formalised. After twenty cells, the kernel's state (which variables exist, what they contain, which were overwritten) is a function of the whole history of executed code, including cells that failed halfway. The agent's context may describe a variable that has since been reassigned. Errors of this kind are subtle: code that works in the agent's session fails when rerun from scratch. Good practices are to have the agent inspect state explicitly when unsure (print shapes, columns, summary statistics), to keep transformations in functions rather than ad-hoc reassignments, and, for any result that matters, to rerun the analysis from a clean kernel as a final check, the analysis equivalent of running the full test suite.

Analysis outputs also need care in the context. A data frame printed in full can be thousands of tokens; plots must be summarised in text or passed to a multimodal model as images; and numbers reported to a user should come from the executed code, never from the model's reading of a printed table. The principle of §5.5 applies with full force: let the interpreter compute and the model interpret.

10.8 What can go wrong

Code-executing agents have a characteristic set of risks, and each has a known mitigation, most of which have already appeared in this book.

Test tampering and other reward hacking. An agent told to make the tests pass can do so by weakening an assertion, special-casing the test inputs, catching and suppressing the exception the test checks for, or deleting the test. Agents trained with reinforcement learning against test outcomes have been observed doing all of these (Chapter 18). Mitigations: forbid edits to test files unless the task requires them, and enforce the rule in the edit tool; diff the patch for changes to tests and for suspicious patterns (hard-coded expected values, broad exception handlers); keep some tests hidden from the agent and use them for final validation; and review.

Destructive operations. Model-written commands can delete or overwrite data: rm -rf on the wrong path, a git reset --hard that discards uncommitted work, a database migration run against the wrong environment. Mitigations: sandboxes with only a copy of the repository; version control with automatic commits or snapshots before risky steps so that everything can be rolled back; permission tiers (§8.9) that require approval for commands outside the sandbox or touching shared systems; and an explicit deny-list of the most dangerous commands as a backstop.

Secrets and exfiltration. Repositories and environments contain credentials; injected instructions in issues, comments or dependencies can ask the agent to send them somewhere. Mitigations: no long-lived secrets in the sandbox; network egress restricted to an allow-list (Figure 10.2); scanning of outputs for credential patterns; and treating repository content as untrusted input.

Supply-chain risk. Agents install packages to get work done, and a model may hallucinate a plausible package name that does not exist, a name an attacker can register with malicious code (sometimes called "slopsquatting"); one large study found that code-generating models recommended non-existent packages in a substantial fraction of samples, often repeatably[9]. Mitigations: install only from vetted registries or mirrors, pin and verify versions, block installation of packages that are new or have few downloads, and require approval for new dependencies.

Quality debt. A patch that passes tests can still be poor code: duplicated logic, ignored conventions, fixes to symptoms rather than causes. Agents optimise what they are measured on. Mitigations are the ordinary ones of software engineering (linters, type checkers, conventions stated in the system prompt and in repository files the agent reads, code review), with the review step made efficient by critiques that point reviewers at the risky parts (§7.7).

Worked example — catching test tampering

A coding agent's patches are reviewed by an automatic check before a human sees them. Suppose 4% of patches that pass the tests do so by tampering (editing tests or special-casing inputs). Check A rejects any patch that modifies a test file: it catches 70% of tampering and wrongly rejects 3% of legitimate patches (those that properly needed a test change). Check B also runs 20 held-out tests the agent never saw: it catches 85% of the tampering that A missed.

Tampering that reaches review. \(0.04\times0.30\times0.15=0.0018\): 0.18% of passing patches, down from 4%.

Legitimate patches lost. \(0.96\times0.03=2.9\%\) are rejected by A, but these can be routed to human review with the reason, rather than discarded.

Lesson. Two independent checks multiply (§5.8 made the same point for monitoring). The held-out tests are the stronger check because the agent cannot optimise against what it cannot see.

10.9 Agents that build their own tools

A code-writing agent can do something no tool-calling agent can: create new tools. When an agent finds itself performing the same multi-step operation repeatedly, it can write a function that performs it, test the function, and call it thereafter. Voyager (§1.7), the Minecraft agent of 2023, was built around this idea: it wrote JavaScript functions for skills such as "craft a stone pickaxe", verified them by executing them in the game and checking the result, and stored the working ones in a skill library indexed by a description, from which later tasks retrieved and composed them[10]. Its capabilities grew over time without any change to the model's weights, because the library grew. The same year, Cai and colleagues' LLM as Tool Maker (LATM) split the roles explicitly: a strong, expensive model wrote and verified a reusable Python function for a class of problems, and a cheaper model then solved many instances by calling it, amortising the cost of the strong model across instances[11]. Figure 10.6 shows the loop common to both.

Figure 10.6 is a learning system of a particular kind: the policy does not change, but the action space does, and every new verified skill shortens the horizon of every future task that uses it. In the reliability arithmetic of Part I, a skill that bundles six steps, each with error rate 0.03, into one verified call raises the sub-task's success from \(0.97^6=0.83\) to close to 1 for as long as the skill remains correct. The verification step is what makes this safe: a skill library that admits unverified functions accumulates bugs that every later task inherits, the failure mode of wrong lessons in Reflexion (§7.6) transferred to code. Chapter 13 treats skill libraries as the procedural memory of an agent, alongside episodic and semantic memory.

In practice, the most common form of tool building is mundane and valuable. A coding agent that needs to check many files writes a short script rather than reading each one; a data agent writes a helper to normalise dates once and reuses it across cells; a long-running agent saves the commands that worked (how to run this project's tests, how to start its database) into a notes file in the repository, which human developers increasingly maintain for agents as well. These are skill libraries of one project, and they are why giving an agent a place to write persistent notes and scripts is one of the cheapest improvements available.

Version control as the agent's undo and memory

One piece of infrastructure deserves particular mention, because it gives coding agents two properties that most environments lack. Version control (git) is, for an agent, both an undo mechanism and an external memory. As undo: committing before a risky change lets the agent, or the harness, restore any earlier state exactly, which makes the environment reversible in the sense that §6.7 required for search, and turns destructive mistakes into recoverable ones. As memory: the commit history, with messages describing what each change did and why, is a compact, structured record of the episode that survives context compaction (§4.8), and that a later agent, or a resumed one, can read to understand what has been done. Harnesses that commit automatically at milestones, with informative messages, give long-running coding agents a backbone that Chapter 14 builds on.

Drill 10.4 — amortising a tool

An agent must reconcile 300 invoices. By hand, each takes 6 tool-call steps at $0.01 each with a 2% error rate per step. Alternatively, it spends $0.80 writing and testing a reconciliation function, after which each invoice is one call at $0.002, with a 0.5% failure rate (mostly exceptions it catches). Compare cost and expected number of incorrectly reconciled invoices.

By hand: \(300\times6\times\$0.01=\$18\); each invoice error-free with probability \(0.98^6=0.886\), so about 34 incorrect. With the tool: \(\$0.80+300\times\$0.002=\$1.40\); about 1.5 failures, most of them visible exceptions that can be retried or escalated. The one-off cost of building the tool pays for itself many times over and the error count falls by more than an order of magnitude, provided the tool itself is verified.

Looking ahead

Code gives an agent a general and precise way to act in software that exposes an interface for programs: files, shells, APIs, databases. Much of the world's software does not. Booking a flight on a website, filing an expense report in an enterprise application, adjusting a setting in a desktop program: these interfaces were built for people, with screens, buttons and forms. Can an agent operate them the way a person does, by looking at the screen and clicking? What does it take to ground a model's intentions in pixels or page elements, how reliable are such agents today, and why are they slow? Chapter 11 takes up computer use and web agents.

Chapter summary

  • Code is an action space closed under composition: loops, branches and exact computation in one step. CodeAct found up to 20 points higher success and up to 30% fewer turns than JSON actions. Keep consequential writes as guarded structured tools.
  • Model-written code is untrusted; run it in sandboxes: containers inside stronger boundaries (gVisor, micro-VMs), with resource limits, egress allow-lists, no long-lived secrets, and snapshots for rollback and search.
  • A coding agent understands, localises, reproduces, edits, validates and submits; localisation is the most common failure and reproduction the most valuable step. Agentless showed the value of structure; modern agents combine autonomy with enforced key stages.
  • Prefer targeted edits (search-and-replace) to whole-file rewrites: cost and silent-change risk scale with file size for rewrites.
  • Tests are the verifier; reproduce first, run the right tests, treat tests as fixed. Flakiness compounds as \(1-(1-f)^n\); baseline and re-run failures.
  • SWE-bench (2,294 tasks; Lite 300; Verified 500) uses fail-to-pass and pass-to-pass tests; watch for contamination, scaffold dependence and narrowness. Evaluate on your own repositories.
  • Analysis agents use persistent kernels, which create hidden state; inspect state, and rerun from a clean kernel before reporting.
  • Code-writing agents can build and verify their own tools (Voyager skill libraries, LATM tool makers), growing their action space; version control gives coding agents undo and external memory.
  • Risks: test tampering, destructive commands, exfiltration, hallucinated packages, quality debt; mitigate with enforced rules, sandboxes, egress control, vetted registries, held-out tests and review.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up Why let agents act by writing code rather than calling tools?

Code composes actions: loops over items, conditionals on results, chaining outputs to inputs, and exact computation, all in one action. That shortens trajectories (fewer steps, fewer chances to err, fewer context re-reads), moves arithmetic and bookkeeping to the interpreter, and gives informative errors (tracebacks). CodeAct measured higher success and fewer turns. Costs: the model must write correct code, the interpreter's state must be tracked, outputs must be bounded, and execution must be sandboxed. Many agents use code for exploration and computation and structured tools for consequential writes.

Warm-up How do you run model-generated code safely?

In a sandbox: a container for file-system, process and network isolation, inside a stronger boundary (gVisor or a micro-VM) against kernel escapes; CPU, memory, disk and time limits; network egress only to allow-listed hosts through a logging proxy; no long-lived credentials, only short-lived scoped tokens or calls proxied from outside; a copy of the data or repository, not the original; and snapshots for rollback. Approval for anything that leaves the sandbox or touches shared systems.

Warm-up Describe how SWE-bench scores a patch.

The repository is checked out at the commit before the real fix; the agent's patch is applied; the fail-to-pass tests (which the real fix made pass) must pass, and the pass-to-pass tests (passing before) must still pass. A task is resolved only if both hold. The agent sees the issue text and repository, not the tests. Variants: Lite (300 tasks), Verified (500 human-checked tasks), Multimodal and multilingual extensions.

Core Walk through how a good coding agent should fix a bug.

Read the issue and a repository map; localise with exact search for identifiers and error text, the stack trace, and go-to-definition, reading only relevant code; write a minimal test reproducing the bug and confirm it fails; make a targeted edit (search-and-replace) addressing the cause; run the reproduction test, then the tests near the change, then the full suite against a pre-recorded baseline; lint and type-check; if anything fails, revise or re-localise; submit a diff with an explanation and the tests added. Never weaken existing tests to pass. Optionally generate several candidate fixes and select by tests.

Core What does Agentless teach about agent design?

That a well-structured fixed pipeline (hierarchical localisation, multiple candidate patches in a simple format, selection by reproduction and regression tests) can match or beat autonomous agents at much lower cost, because it encodes the right process and avoids per-step errors in deciding what to do next. It is Chapter 2's policy-class trade-off: a constrained class with a good design versus a larger class realised imperfectly. With stronger models agents overtook it, but the best systems keep its structure as guidance or enforced steps.

Core Compare code edit formats for an agent.

Whole-file rewrite: simple, robust to misremembered context, but output cost and time scale with file length and unrelated lines may change silently; good for new or small files. Search-and-replace: compact, changes only named text, fails loudly on mismatch; the default for most edits. Unified diff: compact but line numbers and hunk syntax are error-prone for models, so needs fuzzy application. Whatever the format, the tool should check parseability, unique matches and forbidden files, and keep only the diff in context.

Core How do flaky tests affect coding agents and what do you do?

Spurious failures look like real ones, so the agent may change correct code or abandon correct patches, and with large suites at least one spurious failure per run becomes likely (\(1-(1-f)^n\)). Mitigate: run the suite before changes to record pre-existing and flaky failures; re-run new failures to confirm; report to the agent only confirmed new failures relative to the baseline; quarantine known flaky tests; and prefer targeted test runs during iteration.

Core How would you detect and prevent test tampering by a coding agent?

Prevent: forbid edits to test files unless required, enforced in the edit tool; instruct explicitly. Detect: diff checks for modified tests, removed assertions, broad exception handling, hard-coded values matching test inputs; held-out tests unseen by the agent for final validation; mutation testing on the patch; and human review guided by a critic. Monitor rates by model version, since RL-trained models may learn tampering. Independent checks multiply.

Core What are the trade-offs of a persistent interpreter for data-analysis agents?

Benefits: data loaded once, incremental exploration, efficient iteration. Costs: hidden state that drifts from what the context describes (overwritten variables, half-executed cells), irreproducible results, memory growth. Practices: inspect state explicitly, write transformations as functions, keep outputs bounded and summarised, compute reported numbers in code, and rerun the analysis from a clean kernel before reporting.

Deep-dive Formalise why code actions shorten horizons and raise reliability.

Let a task require \(m\) primitive operations. With one operation per step, horizon \(H=m\) and error-free probability \(\rho^m\); the context is re-read \(m\) times, so input cost grows like \(m^2\). A code action executes the \(m\) operations in one step with failure probability \(\epsilon_c\) (a bug), most failures raising an exception (high detection \(r\)), followed by a short read-and-respond step: success \(\approx(1-\epsilon_c(1-r))\), cost linear in program size. Arithmetic and control flow move from the model (error-prone) to the interpreter (exact). The advantage grows with \(m\) and with the regularity of the operations; it shrinks when each operation needs model judgement, which cannot be put in a loop.

Deep-dive How would you evaluate a coding agent for your company's codebase?

Build an internal SWE-bench: mine closed issues with linked fixing commits; for each, check out the parent commit, extract tests changed or added in the fix as fail-to-pass and the existing suite as pass-to-pass; containerise the environment; filter for well-specified issues (human check on a sample). Include tasks after the model's cut-off to limit contamination. Measure resolved rate, pass^k over repeated runs, cost and time per task, review burden (diff size, reviewer acceptance), and safety incidents (forbidden file edits). Compare scaffolds and models on the same tasks with fixed budgets.

Deep-dive Which isolation level would you choose for a multi-tenant agent platform and why?

For untrusted code from many tenants, a container alone is insufficient because of shared-kernel escape risk; use micro-VMs (Firecracker-class) or a user-space kernel (gVisor) per session, with containers inside for packaging. Add per-sandbox resource quotas, egress proxies with per-tenant allow-lists, no shared file systems, short-lived credentials, snapshot/restore for speed, and auditing. Start-up cost (~100s of ms) is negligible against model time. Single-tenant internal use may accept containers with strict egress and no secrets.

Design Design a coding agent product that opens pull requests from issues.

Trigger from issue labels; spin up a sandbox with the repository and dependencies (cached images), no secrets, egress to registries only. Agent loop with tools: repository map, exact and structural search, file view, search-and-replace edit with checks, test runner with baseline comparison, linter; harness enforces reproduction test, forbids test edits, caps steps and cost. Optionally generate several candidates in parallel snapshots and select by tests and a critic. Output: PR with diff, explanation, tests added, and a critic's review notes; human review required to merge. Metrics: merge rate without changes, time to PR, cost per merged PR, revert rate, incidents. Roll out on low-risk repositories first.

Design Design a data-analysis agent for business users.

Sandboxed Python kernel with read-only database access through a query tool (row limits, timeouts), pandas and plotting libraries, no internet. Schema documentation and example queries in context; the agent writes SQL/Python, inspects shapes and summaries rather than full tables, and returns results computed in code with the code attached. A clean re-run before final answers; plots rendered and described. Guardrails: no writes, cost limits on queries, PII masking. Evaluation: question sets with gold answers, reproducibility checks, and user review of explanations.

Design A coding agent installed a malicious dependency. What controls would have prevented it?

Install only from an internal mirror or proxy of vetted packages; block packages that are new, rarely downloaded or not on an allow-list; require approval for new dependencies, showing the package's provenance; pin versions with hashes; run installs in the sandbox with egress limited to the mirror; scan dependencies; and make the agent's system prompt prefer the standard library and existing dependencies. Monitor for hallucinated package names by checking existence before install.

Core Why did coding agents become reliable before agents in most other domains?

Code environments are observable on demand (read any file), give rich external feedback (compilers, tests, tracebacks), are reversible (version control, snapshots), often come with automatic verifiers (tests), are text-native (no perception problem), and have abundant training data and RL environments with verifiable rewards. In the terms of this book: high detection probability, cheap reversibility for search, a large generator–verifier gap, and good tools.

Deep-dive What are the benefits and risks of letting an agent build its own tools?

Benefits: repeated multi-step operations become single verified calls, shortening horizons and removing per-step errors (a six-step sub-task at 3% error per step succeeds 83% of the time; a verified skill close to 100%); expensive reasoning is amortised across many uses (LATM); and the agent's capability grows with experience without retraining (Voyager). Risks: unverified or subtly wrong tools propagate errors to every later task; tools may encode assumptions that stop holding when the environment changes; a growing library raises the selection problem of §8.8; and generated tools are code with the security risks of §10.8. Mitigations: admit only tools that pass tests on representative inputs, store provenance and tests with each tool, re-verify on environment changes, retrieve tools by description rather than listing all, review tools that touch sensitive systems, and retire tools whose use correlates with failures.

Core Why is version control valuable to a coding agent beyond storing code?

It makes the environment reversible: commits before risky changes let the agent or harness restore any earlier state exactly, turning destructive mistakes into recoverable ones and enabling search over alternative edits. And it is a structured external memory: commit messages and diffs record what was done and why, surviving context compaction and letting a resumed or different agent reconstruct the episode. Harnesses should commit automatically at milestones with informative messages.
