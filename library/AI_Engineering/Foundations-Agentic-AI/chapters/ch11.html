Part III · Acting: Tools and Environments — Chapter 11

Computer Use and Web Agents

Most of the world's software was built for people, not programs: it has screens, buttons, menus and forms, and no API. An agent that can see a screen and operate a mouse and keyboard can, in principle, use all of it. This chapter explains how such agents perceive interfaces, how they turn intentions into clicks, why they are slow and still unreliable, and how to deploy them safely.

Why this chapter

Chapters 8 to 10 gave agents tools, retrieval and code, all of which assume that the systems the agent acts on expose interfaces designed for programs: functions with schemas, searchable indexes, shells and APIs. A great deal of useful work happens in software that offers no such interface: an airline's internal booking terminal from the 1990s, a government website, an enterprise application with a web front end and no public API, a desktop spreadsheet. People operate these through graphical user interfaces (GUIs). An agent that can do the same becomes, in principle, universal: anything a person can do at a computer, it can attempt.

The price of universality is that every problem the earlier chapters solved by design comes back. The observation is no longer a concise tool result but a screen of pixels or a page of markup; the action is no longer a typed function call but a click at a coordinate; the environment changes asynchronously (pages load, pop-ups appear); and nothing is designed to be read by a model. This chapter follows the history from toy benchmarks to agents that operate real desktops, then examines each part of the loop: how the screen is represented, how actions are grounded in it, what limits speed and reliability, and how to keep an agent that can click anything from clicking the wrong thing. It ends with the pragmatic rule of thumb: use APIs where they exist, and GUIs where they do not.

Learning objectives
  1. Trace computer-use agents from MiniWoB and WebShop through Mind2Web, WebArena and OSWorld to commercial computer-use models, with the capability gap they measured.
  2. Compare observation representations (HTML, accessibility trees, screenshots, set-of-marks) by information, token cost and robustness.
  3. Explain the grounding problem and how models predict where to act.
  4. Estimate the latency and token cost of a GUI episode, and the effect of keeping or dropping old observations.
  5. Analyse the reliability of long GUI tasks and the role of verification by screenshot.
  6. Identify the specific safety risks of computer use (injection through web content, irreversible actions, credentials) and their mitigations, and decide between GUI and API access.

We use the POMDP view (Chapter 2), context budgets (Chapter 4), tool design and permissions (Chapter 8) and sandboxing (Chapter 10).

11.1 Why operate interfaces built for people?

Consider the support agent of the running examples. Its tools in Chapter 8 assumed the airline has clean APIs for bookings, fares and refunds. Many do not. Behind a modern web page may sit a mainframe reservation system reachable only through a terminal emulator, a partner's website for hotel bookings, and an internal tool for compensation claims that exists only as a web form. Building an API for each is expensive and slow; the people who do this work today simply use the interfaces. An agent that can do the same can automate the long tail of tasks for which nobody will ever build an API.

The same argument holds far beyond airlines, and it explains why computer use became a major research and product direction in 2024–2025. The economic value of software work done through GUIs is enormous, the interfaces are already built, and a model that understands screens has a single, general skill that transfers across applications. The difficulty is equally clear. In the POMDP language of Chapter 2, a GUI environment has a large, partially observed state (the application's internal data, other windows, scrolled-off content), observations that are high-dimensional and noisy (screenshots), actions that are low-level (move the pointer, click, type a character), and transitions that are slow and sometimes non-deterministic (network latency, animations, pop-ups). Every one of these makes per-step errors more likely and steps more numerous, the two factors that §1.8 showed compound.

Figure 11.1 draws the loop that every computer-use agent runs. The harness captures the screen (or the page's structure), sends it to the model with the task and history, receives an action such as "click at (412, 305)" or "type 'Friday' into the date field", executes it with a virtual mouse and keyboard or a browser-automation library, waits for the interface to settle, and captures the screen again.

Figure 11.1 differs from the tool-calling loop of Figure 8.2 in two places, and they are where computer use is hard. The observation stage must turn a visual interface into something the model can read, which §11.3 examines. The model's output must specify not only what to do but where, in screen coordinates or by reference to an element, which is the grounding problem of §11.4. Before those, it helps to see how capability developed and how far it still has to go.

11.2 From toy pages to real desktops

Research on agents that operate web interfaces predates language models. World of Bits and its benchmark MiniWoB (Shi et al., 2017) offered about a hundred tiny web tasks, such as clicking a named button, entering a date or choosing from a menu, on small synthetic pages, solved by reinforcement learning from pixels and the page structure[1]. The tasks were small enough for RL to learn, but the agents did not transfer to real websites. Language models changed the starting point. WebShop (Yao et al., 2022) built a simulated shopping site with over a million real products and asked agents to find and buy items matching instructions such as "a pair of waterproof hiking boots under $100 in size 10"[2]. Mind2Web (Deng et al., 2023) collected over 2,000 tasks on 137 real websites with human demonstrations, testing whether agents generalise to unseen sites[3].

Industry had its own answer to GUI automation long before language models: robotic process automation (RPA). From the 2000s, RPA tools recorded or scripted sequences of clicks and keystrokes ("open this window, click the field at this position, paste the value from that spreadsheet") and replayed them, automating repetitive back-office work in banks, insurers and airlines at large scale. RPA scripts are fast and cheap to run, but they are brittle in exactly the way the hand-written policies of §1.3 were: they encode one path through one version of an interface, and they break when a button moves, a field is renamed, a pop-up appears or the data takes an unanticipated form. Maintaining them became a substantial cost. A language-model agent is, in this light, an RPA system whose script is replaced by a policy that reads the screen and decides afresh at every step: slower and costlier per run, but robust to the changes that break scripts. The two are converging, with agents used to handle the exceptions that scripts cannot and, increasingly, to write and repair the scripts themselves.

The benchmarks that defined the current era added realism and execution-based evaluation. WebArena (Zhou et al., 2023) hosted functional copies of real web applications (an online store, a forum, a code-hosting site, a content-management system, a map) and judged tasks by checking the resulting state; the best GPT-4 agent succeeded on about 14% of tasks, against 78% for humans[4]. OSWorld (Xie et al., 2024) went further, giving agents a full desktop operating system in a virtual machine and 369 tasks spanning office applications, browsers, file management and multi-application workflows; the best agents at publication succeeded on about 12% of tasks, against 72% for humans[5]. Figure 11.2 shows how quickly that gap narrowed once frontier models were trained for computer use.

Figure 11.2 records the arrival of models trained specifically for computer use. In October 2024 Anthropic released computer use for Claude 3.5 Sonnet, a model trained to read screenshots and emit mouse and keyboard actions, reporting 14.9% on OSWorld with screenshots only. In January 2025 OpenAI released its Computer-Using Agent, behind the Operator product, reporting 38.1% on OSWorld and 58.1% on WebArena. By late 2025 the best reported OSWorld results exceeded 60%. The same cautions apply as to Figure 1.4: these are vendor numbers with different budgets and harnesses. But the trend is unmistakable, and it was driven by the same recipe as coding agents: models trained, with reinforcement learning, on large numbers of tasks in environments where success can be checked. The remaining gap to humans is concentrated in long, multi-application tasks and in fine visual grounding, which the next two sections explain.

11.3 What the agent sees

A GUI must be turned into tokens before a model can reason about it, and there are three main representations, each with a different balance of information, cost and robustness. Figure 11.3 shows them for the same booking page.

Figure 11.3 lays out the trade-offs. Raw HTML (or the browser's document object model) contains every element and attribute, but modern pages run to tens or hundreds of thousands of tokens, most of it styling, scripts and nesting with no bearing on the task, and it says little about what is actually visible. Accessibility trees, the structured descriptions that browsers and operating systems expose for screen readers, list the interactive elements with their roles ("button", "textbox"), labels and states, often in a few thousand tokens, and give each element an identifier the agent can act on ("click [4]"). They are the most efficient representation when the application provides a good one, but many do not: custom-drawn controls, canvas-based applications and poorly built sites have missing or misleading labels. Screenshots work for any application, show layout and visual cues (a greyed-out button, a red error message, an image), and cost a fixed, modest number of tokens (a 1,280 × 800 image is roughly 1,400 tokens under a common pricing rule of about one token per 750 pixels), but they require the model to understand the image and to locate where to act.

Practical agents combine them. Browser agents often send the accessibility tree plus a screenshot; desktop agents trained for computer use work mainly from screenshots, which generalise across every application, sometimes with the accessibility tree as a hint. The choice has a large effect on cost over an episode, because observations accumulate in the context (§4.1). Figure 11.4 computes the total input tokens of an episode with a 3,000-token base context and 150 output tokens per step, under four policies for keeping observations.

Figure 11.4 shows that the most important decision is not which representation to use but how much history to keep. GUI observations are bulky and mostly stale within a step or two, since the current screen supersedes the previous one. Keeping only the latest observation (or the last few screenshots, which help the model notice what changed), together with the full text of the agent's own actions and reasoning, is the GUI version of the observation pruning of §4.8. It bounds the context's growth, cuts cost several-fold, and reduces the distraction of out-of-date screens, at the price that the agent must record anything it needs from an earlier screen (a confirmation number, a price) in its own notes.

11.4 Grounding: where to click

Deciding what to do ("open the date picker") is reasoning; deciding where to do it ("click at (612, 238)") is grounding, and it is a distinct skill with its own failure modes. With an accessibility tree, grounding is selecting an element identifier, which models do well when labels are good. With screenshots, the model must output coordinates, and early multimodal models were poor at this: they could describe a screen accurately and still click thirty pixels off the target. Benchmarks such as ScreenSpot isolate the skill by asking models to locate a described element in screenshots of mobile, desktop and web interfaces[6], and general-purpose models scored poorly on it until they were trained on large sets of screenshots annotated with element locations.

Two approaches made grounding workable. The first is set-of-marks prompting (Yang et al., 2023): before sending the screenshot, the harness detects interactive elements (from the accessibility tree or with a detector) and draws a numbered box on each, so that the model need only say "click 7"[7]. Figure 11.5 shows the idea; it converts coordinate prediction into a choice among labelled options, which models handle much better. The second is training for coordinates: models fine-tuned on millions of (screenshot, instruction, location) examples learn to output precise positions directly, as in SeeClick and later dedicated grounding models, and the computer-use models of 2024–2025 were trained this way. Direct coordinate output generalises to interfaces with no accessibility information, which set-of-marks cannot handle.

Figure 11.5 makes clear that grounding errors and reasoning errors are different, which matters for debugging: an agent that clicked the wrong button may have decided correctly and grounded badly, or the reverse. Logging the model's stated intention ("I will click the Search button") alongside the executed action separates the two. Grounding also interacts with screen resolution. Models see images resized to a fixed maximum, so on a large, high-resolution screen small controls shrink to a few pixels; harnesses typically scale the screenshot to the resolution the model was trained on and scale coordinates back, and zooming into a region before a precise click is a common technique. Small, dense, low-contrast interfaces remain the hardest case for visual grounding.

How computer-use models are trained

The jump in Figure 11.2 came from training, and it is worth understanding what the training consists of, because it explains both the strengths and the blind spots of these models. Three kinds of data are combined. Grounding data: very large collections of screenshots paired with descriptions of elements and their locations, harvested from web pages (whose markup gives the location of every element for free), from mobile and desktop applications rendered in emulators, and from synthetic interfaces. This teaches the "where" of §11.4. Demonstrations: recordings of people, or of scripted programs, performing tasks, as sequences of screenshots and actions; these teach the "how" of common workflows, such as how date pickers, file dialogs and checkout flows behave. Interactive reinforcement learning: the model attempts tasks in virtual machines or browsers whose final state can be checked automatically (the file was saved with the right name, the form was submitted with the right values), and is rewarded for success. As for reasoning models (§5.6) and coding agents (Chapter 10), RL teaches behaviours that demonstrations rarely show: checking whether an action worked, closing an unexpected dialog, scrolling to find an element that is not visible, trying another route when one fails.

The consequence for an agent designer is that a computer-use model is strongest on interfaces resembling those it was trained on (common web patterns, popular office and operating-system applications) and weakest on unusual ones: bespoke enterprise software, old terminal-style interfaces, dense dashboards, non-English interfaces with little training coverage. A short evaluation on the actual target applications (§11.6's verification habits help a great deal there) is always worth more than a benchmark number. It also explains why the environments used to train and evaluate these agents, virtual desktops with checkable tasks, have become valuable infrastructure in their own right, a theme Chapter 18 develops for agent training in general.

11.5 Why computer use is slow

A person filling in a web form makes an action every second or two. Computer-use agents of 2025 typically take several seconds or more per action, and a task that takes a person three minutes can take an agent ten. The reason is structural, and the arithmetic of §3.7 lays it out. Each step involves capturing the screen (fast), sending an image and context to the model (prefill of the new image, a second or less), the model reasoning and emitting an action (decode; often hundreds of tokens of reasoning at tens of tokens per second), executing the action (fast), and waiting for the interface to settle (page loads, animations; often one to three seconds). The model's decode time dominates, and it is paid on every step, including trivial ones such as "scroll down".

GUI tasks also have many steps, because GUI actions are low-level. Changing a flight through a web interface might mean: click "Manage booking", type the reference, type the surname, click "Find", click "Change flight", open the date picker, click Friday, click "Search", scroll, click a flight, click "Continue", check the fare difference, click "Confirm". Thirteen actions for what one API call (§8.6) does. Since each action is a step with its own error probability, the length of GUI trajectories is the main reason their reliability lags (§11.6).

Worked example — time and cost of a GUI task

The support agent changes a flight through the airline's web interface in 25 steps. Per step: 0.3 s prefill (image plus new text, with the rest cached), 180 output tokens of reasoning and action at 60 tokens/s (3 s), 0.2 s execution and 1.5 s waiting for the page: about 5 s. The context starts at 6,000 tokens, keeps the last three screenshots (1,400 tokens each) and grows by 180 tokens of output per step.

Time. \(25\times5=125\) s, about two minutes, against about 6 s for the equivalent API calls.

Input tokens. \(\sum_{t=1}^{25}\big(6{,}000+1{,}400\min(t,3)+180t\big)=150{,}000+1{,}400\times72+180\times325=150{,}000+100{,}800+58{,}500=309{,}300\). Mostly cached except each new screenshot: fresh about \(25\times1{,}600=40{,}000\) tokens ($0.12), cached about 269,000 ($0.08); output \(25\times180=4{,}500\) tokens ($0.07). Total about $0.27.

Comparison. The API route costs about two cents and takes seconds. Computer use is a fallback for when no API exists, not a substitute for one.

Three techniques reduce the time. Fewer, bigger actions: typing a whole field value as one action rather than character by character, using keyboard shortcuts, navigating directly to a URL instead of clicking through menus. Less reasoning on routine steps: the reasoning-budget argument of §5.9 applies with force, since most GUI steps (scroll, click the obvious button) need little thought. Smarter waiting: waiting for a specific element to appear rather than a fixed delay, which browser-automation libraries support. Even so, GUI agents are an order of magnitude slower than API agents, which shapes how they are deployed: in the background, on tasks where a few minutes are acceptable.

11.6 Reliability on long GUI tasks

GUI environments generate errors that API environments do not. A click lands on the wrong element; a page has not finished loading when the agent acts; a cookie banner or a chat pop-up covers the button; a date picker behaves differently from the one the model expects; an element is below the fold and must be scrolled to; a session times out. Each is a per-step error \(\epsilon\) in the sense of Chapter 2, and with trajectories of dozens of steps they compound as \(\rho^H\). The remedy is the one that works everywhere in this book: make errors visible and recover from them.

In GUIs, visibility comes from verification by observation: after each consequential action, check the new screen for the expected change (the date field now says Friday; the confirmation page shows the new flight) before proceeding. Agents trained for computer use learn to do this, and harnesses can enforce it for key steps. A related technique is to prefer actions whose effects are easy to verify, such as typing into a field and reading the field back, over actions whose effects are invisible until much later. When an unexpected screen appears, the agent should recognise it as such (an error page, a pop-up, a login prompt) and handle it explicitly, rather than proceed as if the expected screen had appeared.

Worked example — the value of checking the screen

A 25-step GUI task has a per-step error rate of 4%: wrong clicks, unhandled pop-ups, acting before the page loads. Without verification, the agent notices perhaps 30% of its errors.

Without verification. Fatal rate \(0.04\times0.7=0.028\); success \(0.972^{25}=e^{25\ln0.972}=e^{-0.710}=0.49\).

With verification after every step. Checking the screen raises detection to 85%: fatal rate \(0.04\times0.15=0.006\); success \(0.994^{25}=0.86\). Each detected error costs about two extra steps, so the expected length rises from 25 to \(25(1+0.04\times0.85\times2)=26.7\) steps, about 9 s more.

Lesson. On long GUI tasks, the habit of confirming each action's effect is worth more than any improvement in click accuracy that is plausibly available.

Timing deserves a separate word, because it is the class of GUI error least like anything in API-based agents. A web page is a program that keeps running after it is displayed: content loads in pieces, buttons become clickable only after scripts finish, lists re-order as results arrive, and animations move elements while the agent is deciding where to click. An agent that captures the screen, spends four seconds deciding, and clicks where a button was may hit whatever has moved there since. The environment is non-stationary on the time scale of a single step, a violation of the assumption, implicit in Chapter 2's POMDP, that the state does not change between observation and action. Harness-level remedies are simple and effective: wait for the page to be idle (no pending network requests, no running animations) before capturing; re-capture immediately before executing a click and abort if the target has moved; and prefer element-based actions (click the element with this identifier) over coordinate-based ones wherever the platform allows, since an element reference survives a layout shift and a coordinate does not.

Drill 11.1 — grounding versus reasoning errors

An agent's logs show that on 1,000 steps it stated the right intention 970 times and, of those, executed the intended action 950 times; on the 30 wrong intentions it executed what it intended. (a) What are the reasoning and grounding error rates? (b) Which should the team work on, if a better grounding model would halve grounding errors and a reasoning model would halve reasoning errors at triple the cost?

(a) Reasoning errors: 30/1,000 = 3%. Grounding errors among right intentions: 20/970 ≈ 2.1%. Total per-step error ≈ 5%. (b) Halving grounding errors gives about 4%; halving reasoning errors gives about 3.5%. Reasoning is slightly better per point but at triple the cost; combining a better grounding model (cheap) with verification by screenshot (§11.6) may give more than either. The logs make the choice possible only because intention and action were recorded separately.

Phones, desktops and browsers

Computer use spans three platforms with different properties. Browsers are the most tractable: pages expose a document structure and an accessibility tree, browser-automation libraries can wait for elements and read their contents exactly, and a fresh browser profile is easy to sandbox. Desktops are the most general: any application, but accessibility information varies widely, actions include drag-and-drop and keyboard combinations, and several windows interact. Mobile applications add touch gestures (swipe, long press), small screens with dense layouts, and frequent system interruptions (permission dialogs, notifications); research agents for phones, evaluated in emulated Android environments such as AndroidWorld, operate through the same screenshot-and-action loop with platform-specific action sets[8]. For a given task, the platform choice is often available: many services have both a website and an app, and the website is usually the easier target for an agent.

Worked example — parallel browsing for the research agent

The research agent must collect the change-fee policies of eight airlines from their websites, none of which offers an API. Each site takes a computer-use sub-agent about 12 steps at 5 s per step, so a minute per site, and about $0.12 in tokens.

Sequentially. Eight minutes and about $1.00, with the main agent's context receiving eight short summaries.

In parallel. Eight sandboxed browsers run at once (§8.6): about a minute of wall-clock time for the same cost, limited by how many browsers the platform allows per user and by the sites' tolerance of automated access.

Reliability. If each sub-agent succeeds with probability 0.85 and failures are reported (not silent), the expected number of sites needing a retry or a human is \(8\times0.15=1.2\). The main agent should present what it found and say which sites failed, rather than filling the gaps from memory.

Courtesy and terms. Many sites restrict automated access in their terms of service; a production agent must respect them, which may mean preferring official data feeds or asking the user to visit certain sites themselves.

11.7 Safety for agents that can click anything

An agent operating a real browser or desktop has, in principle, every capability the logged-in user has: it can buy things, send messages, change settings, delete files and accept terms of service. The permission tiers of §8.9 are harder to apply, because a GUI does not label its buttons with their risk; "Confirm" may mean confirming a search or confirming a $2,000 purchase. And the agent reads content written by third parties on every page it visits, which makes indirect prompt injection (§8.9) its central security problem: a web page, an email or a document can contain text, visible or hidden, instructing the agent to do something else. Evaluations built specifically to test this, placing injected instructions in realistic web environments, have found that computer-use agents often begin to follow injected instructions, even when they do not complete the attacker's goal[9].

The mitigations combine the isolation of Chapter 10 with human oversight. Run the agent in a dedicated, sandboxed environment: a virtual machine or container with its own browser, not the user's everyday browser with all their sessions, and with network access limited to the sites the task needs. Give it minimal credentials: log in only to the accounts the task requires, and keep payment methods and password managers out of reach. Require confirmation before consequential actions: purchases, messages, submissions, deletions, and anything that accepts legal terms; deployed computer-use products pause and ask the user at such points, and hand control to the user for logins and CAPTCHAs. Monitor for signs of injection: actions unrelated to the task, navigation to unexpected sites, attempts to access credentials. And prefer read-only work where possible: gathering information through a GUI is much less risky than changing things through one.

Handing control back to people

Some steps should not be automated at all, and a well-designed computer-use agent knows how to stop and hand the screen to a person. Logins with multi-factor authentication, CAPTCHAs (whose purpose is precisely to exclude automated agents), payments, and decisions the user has not delegated are the common cases. The pattern is a takeover: the agent pauses, explains what it needs ("please sign in to your account; I will continue once you are on the bookings page"), the user acts in the same browser, and control returns to the agent, which re-observes the screen before continuing. Takeover turns a hard failure (the agent cannot pass a login) into a short human step, and it keeps sensitive actions, such as entering a password, out of the agent's hands entirely. It also changes how such agents should be evaluated: the relevant measure is not only autonomous success but success per minute of human attention, since an agent that needs one 20-second takeover to finish a ten-minute task is far more useful than one that fails without asking.

11.8 APIs where possible, GUIs where necessary

The arithmetic of this chapter leads to a simple architectural rule. A GUI action is slower, costlier and less reliable than an API call that does the same thing, by an order of magnitude in each, and it is harder to secure. So an agent should use structured tools wherever they exist and fall back to computer use only for the gaps. Figure 11.6 shows the resulting hybrid architecture.

Figure 11.6 also shows a structural choice worth copying: the GUI work is done by a sub-agent with its own context and environment, which returns a short textual result ("hotel night cancelled; confirmation H-48213") to the main agent. The main agent's context is not filled with screenshots, the risky browsing happens in an isolated environment, and the sub-agent can be given exactly the credentials its narrow job needs. Chapter 15 generalises this pattern of delegation. Over time, as more systems expose programmatic interfaces, often through the protocols of the next chapter, the GUI fallback shrinks; but the long tail of software built only for people will keep computer use valuable for years.

Drill 11.2 — API or GUI?

A team can spend two engineer-weeks ($15,000) building an API integration for a partner system, or use a computer-use agent at $0.30 per task, 2 minutes per task and 85% reliability (failures go to a person at $8 each). An API-based agent would cost $0.03 per task with 99% reliability. Above what monthly volume does the integration pay for itself within a year?

Per-task cost difference: GUI \(0.30+0.15\times8=\$1.50\); API \(0.03+0.01\times8=\$0.11\); saving $1.39 per task. Break-even: \(15{,}000/1.39\approx10{,}800\) tasks in a year, about 900 a month. Below that, computer use is the cheaper route, before counting the value of the faster turnaround.

Drill 11.3 — choosing an observation policy

A browser agent runs 20-step tasks. Option A sends the accessibility tree (6,000 tokens) and keeps only the latest; option B sends a screenshot (1,400 tokens) and keeps the last three; option C sends both, keeping the latest tree and the last screenshot. With a 3,000-token base and 150 output tokens per step, which reads the fewest input tokens? (Use \(\sum_{t=1}^{20}t=210\) and \(\sum_{t=1}^{20}\min(t,3)=57\).)

A: \(20\times3{,}000+20\times6{,}000+150\times210=60{,}000+120{,}000+31{,}500=211{,}500\). B: \(60{,}000+1{,}400\times57+31{,}500=171{,}300\). C: \(60{,}000+20\times7{,}400+31{,}500=239{,}500\). B is cheapest; C costs about 40% more than B but gives both semantic handles and visual context, which often pays for itself in fewer errors. Measure success, not only tokens.

11.9 Training models to use computers

General-purpose models were not trained to operate interfaces, and in 2023 their weakest skill was grounding: given a screenshot and an instruction, they could describe what to do but not where to click (§11.4). Progress since has come mostly from training data designed for the problem, in three layers.

Grounding data pairs screenshots with referring expressions and coordinates: "the Save button" with its bounding box. It can be harvested at scale from rendered web pages, where the HTML gives every element's text and position for free, and from mobile and desktop accessibility trees. SeeClick (Cheng and colleagues, 2024) pre-trained a vision-language model on such data and introduced ScreenSpot, a benchmark of grounding across web, desktop and mobile, showing that better grounding translated directly into better agent success[6]. Trajectory data records sequences of observations and actions that complete tasks, from people (expensive, slow, but natural) or from models exploring environments and keeping the trajectories a checker accepts, the rejection sampling of §17.3. Reflection and recovery data teaches what to do after a mistake: trajectories in which an error is made and then noticed and corrected, which plain demonstrations rarely contain and which, as §17.2 showed, matter most for long horizons.

UI-TARS (Qin and colleagues at ByteDance, 2025) combined all three in a native GUI agent model, trained end to end on large-scale screenshot data for perception and grounding, on action traces in a unified action space across platforms, and on reflective traces including corrections, and then improved with iterative training on trajectories collected in many virtual machines[10]. The same period saw frontier models from several developers add computer use as a trained capability. The general lesson repeats Part VI: once a capability has a verifiable environment (a virtual machine with a checker), it can be trained with the policy's own experience, and progress follows the availability of environments and checks.

Two cautions apply to training data for interfaces. Interfaces change, so models trained on last year's layouts can mis-ground on this year's, and evaluation should include recently changed applications. And trajectories collected on real accounts carry personal data and can include injected content from the pages visited, so data pipelines need the same redaction and filtering as production traces (§21.5, §20.2).

Looking ahead

The chapter's last section argued that the best interface for an agent is a programmatic one. But each tool in Chapter 8 was integrated by hand: someone wrote its schema, its description and the code that calls it, for one agent framework. As agents multiply and the systems they must reach number in the thousands, integrating every tool with every agent separately becomes the bottleneck. Is there a standard way for any agent to discover and use any tool, data source or other agent? How are such connections authorised, so that an agent acts with the user's permissions and no more? Chapter 12 examines the protocols that emerged in 2024–2025 to answer these questions.

Chapter summary

  • Computer use lets agents operate software built for people, covering the long tail with no API, at the cost of high-dimensional observations, low-level actions and slow, noisy transitions.
  • History: MiniWoB (2017), WebShop (2022), Mind2Web (2023), WebArena (GPT-4 ≈14% vs human 78%), OSWorld (≈12% vs 72%); trained computer-use models from Oct 2024 raised OSWorld to over 60% by late 2025.
  • Observations: HTML (complete, huge), accessibility trees (compact, actionable, sometimes missing), screenshots (universal, ≈1.4k tokens, need visual grounding). Keep only recent observations; history policy dominates cost.
  • Grounding (where to act) is distinct from reasoning (what to do); set-of-marks turns coordinates into choices, coordinate-trained models generalise; log intention and action separately.
  • GUI steps take seconds and tasks need many low-level steps: an order of magnitude slower and costlier than API calls.
  • Verify each consequential action's effect on screen; recovery turns 49% success into 86% in the worked example.
  • Safety: dedicated sandboxed environments, minimal credentials, confirmation before consequential actions, monitoring for injection, read-only where possible.
  • Use APIs by default and a sandboxed computer-use sub-agent as a fallback.
  • Computer-use skill comes from training data: grounding pairs harvested from rendered pages, trajectories filtered by checkers, and reflection data showing recovery (SeeClick, UI-TARS).

Warm-up How does a computer-use agent work?

A harness captures the screen (screenshot, often with an accessibility tree), sends it with the task and history to a multimodal model trained for computer use, receives a low-level action (click at coordinates or on an element, type text, scroll, press keys), executes it with a virtual mouse and keyboard or browser automation, waits for the interface to update, and repeats until done. Key problems: representing the screen compactly, grounding actions precisely, the many slow steps, reliability over long tasks, and safety when acting with a user's access.

Warm-up Compare screenshots and accessibility trees as observations.

Accessibility trees: compact, semantic (roles, labels, states), with element handles that make actions easy to ground; but often missing or wrong for custom or canvas-based interfaces, and they omit visual cues. Screenshots: universal across applications, show layout and visual state, fixed modest token cost (~1.4k for 1280×800); but require visual understanding and precise grounding. Combining both is common; desktop agents rely mainly on screenshots.

Warm-up Why are computer-use agents slow?

Each step costs a model call with several seconds of decoding plus waiting for the interface to settle, and GUI tasks need many low-level steps (a dozen clicks and typings for what one API call does). The model's decode time is paid even on trivial steps. Mitigations: bigger actions (type whole values, shortcuts, direct URLs), low reasoning effort on routine steps, waiting for specific elements, and using APIs where they exist.

Core What is grounding and how have systems improved it?

Grounding maps an intended action to a precise screen location or element. Early multimodal models described screens well but clicked inaccurately. Improvements: set-of-marks (label interactive elements so the model chooses a number), using accessibility-tree identifiers when available, training models on large datasets of screenshots with element locations so they output coordinates directly, scaling screenshots to the training resolution, and zooming for small targets. Separately logging intention and action shows whether failures come from reasoning or grounding.

Core How would you make a computer-use agent reliable on 30-step tasks?

Raise detection: verify the effect of each consequential action on the next screen, recognise unexpected screens (pop-ups, errors, logins) explicitly, and read back values after typing. Shorten the horizon: bigger actions, direct navigation, and APIs for any part of the task that has one. Improve per-step accuracy: good observations (tree plus screenshot), set-of-marks or a grounding model, scaled resolution. Keep the context focused (latest screenshots only, notes for key facts). With 4% per-step error, raising detection from 30% to 85% moves 25-step success from about 49% to 86%.

Core Estimate the cost of a 25-step browser task.

With a 6k-token base, the last three screenshots (1.4k each) kept and 180 output tokens per step: total input ≈ Σ(6000 + 1400·min(t,3) + 180t) ≈ 309k tokens, of which ~40k fresh (new screenshots and outputs) at $3/M ≈ $0.12 and ~269k cached at $0.30/M ≈ $0.08; output 4.5k tokens ≈ $0.07; total ≈ $0.27. Time ≈ 25 × 5 s ≈ 2 minutes. An API route would be cents and seconds.

Core What are the main safety risks of a browsing agent and how do you mitigate them?

Indirect prompt injection from page content; unintended consequential actions (purchases, messages, deletions, accepting terms); credential exposure; data exfiltration. Mitigations: a dedicated sandboxed VM/browser with only the needed logins; egress limited to task-relevant sites; no payment methods or password managers; confirmation before consequential actions and user takeover for logins/CAPTCHAs; monitoring for off-task actions; read-only operation where possible; treating all page content as untrusted data.

Core When would you choose computer use over building an API integration?

When no API exists or building one is expensive relative to volume; when the target system changes rarely; when tasks are low-risk or can be confirmed by a person; and when a few minutes of latency are acceptable. Compute break-even: integration cost divided by the per-task saving (including failure handling). At low volume or for one-off tasks, computer use wins; at high volume, invest in APIs. Often, use APIs for the core and computer use for the long tail.

Deep-dive Model the token cost of observation-history policies for a GUI agent.

With base context \(n_0\), observations of \(o\) tokens, outputs of \(u\) tokens per step, and keeping the last \(w\) observations, step \(t\) reads \(n_0+o\min(t,w)+ut\); total over \(H\) steps is \(Hn_0+o\sum\min(t,w)+uH(H+1)/2\). Keeping all observations (\(w=\infty\)) makes the middle term \(oH(H+1)/2\), quadratic in \(H\) with a large coefficient; a fixed window makes it linear (\(\approx owH\)). For \(o=8{,}000\), \(H=30\), keeping all costs ~3.9M tokens vs ~0.4M keeping one. The remaining quadratic term comes from the agent's own outputs, which are small. Trade-off: shorter windows lose information about earlier screens, which the agent must note explicitly.

Deep-dive Why did computer-use performance improve so fast in 2024–2025, and what remains hard?

Models were trained specifically for the task: large datasets of screenshots with element locations for grounding, demonstrations of GUI workflows, and reinforcement learning in virtual desktops and browsers with checkable outcomes, which teaches verification and recovery behaviours. Harnesses improved (better observation pipelines, history pruning). What remains hard: long multi-application workflows (compounding error), precise grounding on dense or unusual interfaces, dynamic pages and timing, speed, and robustness to adversarial content. Benchmarks also lag real-world variety.

Deep-dive How would you evaluate a computer-use agent before deployment?

Build execution-based tasks in replicas of the target applications (sandboxed VMs, staging sites) with automatic state checks, covering the real workflows and their variations (pop-ups, errors, slow loads, layout changes). Measure success, pass^k over repeated runs, steps, time, cost, and per-step error types (reasoning vs grounding). Run adversarial tests with injected instructions in page content and count how often the agent deviates. Test consequential-action confirmations. Re-evaluate after application UI changes, which can silently break agents.

Design Design a computer-use component for the airline support agent that handles hotel cancellations on partner websites.

Main support agent decides a hotel cancellation is needed and calls a cancel_partner_hotel tool with the booking details. The tool launches a computer-use sub-agent in a fresh sandboxed VM with a browser, egress limited to the partner's domain, and a scoped service-account login (no customer credentials). The sub-agent navigates, verifies each step on screen, and stops before the final "Cancel booking" click to return a summary for confirmation (or proceeds if policy allows), then captures the confirmation number. It returns only a short structured result to the main agent; screenshots are logged for audit. Failures escalate to a human queue with the trace. Evaluate on a staging copy and monitor for UI changes.

Design A user wants a personal agent that books travel on any website. What do you build and what do you refuse to automate?

A browser agent in a dedicated cloud browser with the user's travel-site logins only (no email or banking sessions), preferring APIs and structured search where available. It researches options with read-only browsing, presents choices, and pauses for explicit confirmation before any purchase, with the final payment step completed by the user or with a virtual card limited to the confirmed amount. It treats site content as untrusted, flags anything unusual, and logs actions. Refuse fully autonomous purchases without confirmation, handling of the user's primary passwords, solving CAPTCHAs on the user's behalf in violation of site terms, and actions on sites outside the task.

Design How would you reduce the latency of a browser agent by half?

Profile time per step: decode, prefill, action, waiting. Cut decode with minimal reasoning on routine steps (or a smaller model for them and a larger one for decisions), shorter action formats, and bigger actions (fill forms in one action, keyboard shortcuts, direct URLs). Cut waiting with element-based waits. Cut steps by replacing sub-flows with APIs or scripted macros the agent can invoke. Keep context small (latest observation only) to reduce prefill. Run independent browsing sub-tasks in parallel browsers.

Core Why is a GUI "Confirm" button a problem for permission policies?

Permission tiers rely on knowing an action's risk; API tools declare it in their name and schema, but GUI controls do not: "Confirm" could finalise a search or a purchase. The agent or harness must infer risk from context (page content, URL, amounts shown), so policies are applied as rules such as "pause before any action on a checkout or payment page", "pause before submitting forms with amounts", combined with domain allow-lists and user confirmation.

Core What is set-of-marks prompting?

Before sending a screenshot to the model, the harness detects interactive elements (from the accessibility tree or a detector) and overlays numbered boxes on them; the model then specifies actions by number ("click 7"), and the harness maps the number to coordinates. It turns hard coordinate regression into an easier selection problem, improving grounding for general multimodal models, at the cost of depending on element detection.

Deep-dive What training data and environments produce a good computer-use model, and what does that imply for deployment?

Grounding data (screenshots with element descriptions and locations, cheaply harvested from web markup and emulated apps), demonstrations of workflows (human or scripted screenshot–action sequences), and reinforcement learning in virtual machines and browsers with automatically checkable end states, which teaches verification, recovery and exploration. Implications: performance is best on interfaces like the training distribution (common web patterns, popular applications) and weaker on bespoke enterprise software, legacy terminals, dense dashboards and under-represented languages; evaluate on the actual target applications; and investing in sandboxed replicas of target systems pays off both for evaluation and, if training is possible, for fine-tuning.

Core How do computer-use agents relate to robotic process automation (RPA)?

RPA replays scripted sequences of GUI actions: fast and cheap per run, but brittle, since scripts encode one path through one version of an interface and break on layout changes, pop-ups or unexpected data, making maintenance costly. A language-model agent replaces the script with a policy that reads the screen each step: slower and costlier per run, but robust to change and able to handle exceptions. In practice they combine: scripts for high-volume stable flows, agents for exceptions and for writing or repairing scripts, and APIs wherever possible.
