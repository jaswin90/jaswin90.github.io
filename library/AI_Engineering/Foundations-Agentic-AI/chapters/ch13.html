Part IV · Memory and State — Chapter 13

Memory Architectures

An agent's context is its working memory: everything it currently knows, held in a finite, expensive buffer that is erased when the episode ends. Useful agents need more: to remember a customer's preferences next month, to recall how a repository's tests are run, to learn from last week's mistakes. This chapter builds the memory systems that give agents a past, drawing on the psychology of human memory for its vocabulary and on the rest of this book for its engineering.

Why this chapter

Part III ended with an agent that can act through tools, retrieval, code, interfaces and protocols, and every one of those capabilities fills the same finite buffer. Chapter 4 showed how to manage that buffer within an episode: budget it, cache it, prune and compact it. But the deeper limitation is temporal. When an episode ends, the context is discarded. The support agent that learned in the morning that a customer always wants aisle seats and is travelling with a service dog starts the afternoon's conversation knowing nothing. The coding agent that spent twenty minutes discovering that a project's tests need a particular environment variable rediscovers it the next day. The research agent that found three excellent sources on a topic finds them again from scratch.

Memory is what turns a sequence of independent episodes into an agent that accumulates knowledge and competence. It is also where some of the subtlest failures live: memories that were true and became stale, memories that were never true, memories planted by an attacker, memories of one user leaking to another. This chapter starts from a taxonomy borrowed from cognitive science, examines each kind of memory with its canonical system (MemGPT for working memory, Generative Agents for episodic memory, fact stores for semantic memory, skill libraries for procedural memory), then turns to the policies that decide what to write, what to retrieve and what to forget, the risks, and how memory is evaluated.

Learning objectives
  1. Distinguish working, episodic, semantic and procedural memory, and map each to an agent mechanism using the CoALA framework.
  2. Explain MemGPT's treatment of the context as a cache over an external memory hierarchy, with the model managing its own paging.
  3. Compute the Generative Agents retrieval score (recency, importance, relevance) and explain reflection as memory consolidation.
  4. Design semantic memory with extraction, update and conflict resolution, and procedural memory with verified skills and lessons.
  5. Specify write, retrieval and forgetting policies, and reason about their effect on cost and on performance over many sessions.
  6. Identify memory failure modes (staleness, false memories, poisoning, cross-user leakage) and their mitigations, and describe how memory is evaluated.

We use the POMDP and sufficient-statistic view of Chapter 2, in-context learning (§3.3), context management (§4.8), retrieval (Chapter 9), Reflexion (§7.6) and skill libraries (§10.9).

13.1 What memory is for

In the formal picture of Chapter 2, an agent's policy acts on a context \(c_t=f(h_t)\) built from the history. An ideal agent would condition on its entire history, across all episodes, since anything it has ever observed might bear on the current decision. Memory is the machinery that approximates this: it stores information from the past outside the context and brings the relevant parts back when they are needed, so that the context can stay small while the agent behaves as if it remembered everything that matters. In Chapter 2's language, memory extends the context map \(f\) across episodes, and its design is the same problem of keeping a sufficient statistic within a budget, now with a much longer history.

Memory serves three purposes, and they correspond to the three running examples. Continuity: the support agent should remember the customer's situation across conversations, so that the customer need not repeat it. Personalisation: it should remember preferences (aisle seats, a loyalty number, a preferred language) and apply them without being asked. Learning: the coding agent should get better at working in a repository over time, remembering how things are done there and what went wrong before, and the research agent should build up knowledge of a field across questions. The first two are about facts concerning the world and the user; the third is about competence. Different kinds of memory serve each, as psychologists noticed long before agents existed.

13.2 A taxonomy from cognitive science

Psychology distinguishes several memory systems, and the distinctions, though developed for human minds, map remarkably well onto agent design. Atkinson and Shiffrin's 1968 model separated a short-term store of limited capacity from a long-term store of effectively unlimited capacity, with rehearsal moving information between them; Baddeley later refined the short-term store into working memory, the active workspace for the task at hand[1]. Within long-term memory, Tulving distinguished episodic memory, the record of specific experiences ("the conversation on Tuesday in which the customer complained about the seat"), from semantic memory, general knowledge abstracted from experience ("this customer prefers aisle seats")[2]. A further distinction separates these declarative memories, which can be stated, from procedural memory, knowledge of how to do things, expressed in skilled performance rather than recall.

Sumers, Yao, Narasimhan and Griffiths used this taxonomy to organise language agents in their framework CoALA (Cognitive Architectures for Language Agents, 2023)[3]. In CoALA, an agent has a working memory (the variables and context of the current decision cycle) and long-term episodic, semantic and procedural memories; its actions include not only external actions on the environment but internal ones: retrieving from long-term memory, reasoning over working memory, and learning by writing to long-term memory. Figure 13.1 shows the mapping we will use throughout the chapter.

Figure 13.1 also shows the flows that make the taxonomy useful. Experience enters as episodes. Some of it is consolidated into semantic facts (repeated observations that a customer chooses aisle seats become the fact "prefers aisle") and into procedural knowledge (a failed and then corrected approach becomes the lesson "run the migrations before the tests"). Retrieval brings the relevant parts of all three back into working memory for the current decision. Each kind of memory has a different structure, a different write policy and a different failure mode, which is why lumping them into one undifferentiated "memory" (a vector store of everything) tends to work badly. We take them in turn, starting with the one every agent already has.

13.3 Working memory and the context as a cache

Working memory is the context, and Chapter 4 treated its management within an episode. One system made the connection to long-term memory explicit and gave the agent itself control over it. MemGPT (Packer et al., 2023) took its inspiration from operating systems, which give programs the illusion of a large memory by keeping the active part in fast, small main memory and paging the rest to slow, large disk[4]. MemGPT divided the context into a fixed system section, a working context of key facts that the agent edits, and a queue of recent messages, and kept everything else in external storage: a recall store of the full conversation history and an archival store of arbitrary documents and notes. The agent was given functions to page information in and out: search the recall store, search and insert into the archival store, edit the working context. When the context approached its limit, the system warned the agent ("memory pressure"), which then saved what mattered to archival storage and let older messages be evicted, summarised into the queue. Figure 13.2 shows the hierarchy.

For the mathematician — caches and the cost of a miss

A cache is a small, fast store holding a subset of a large, slow one, chosen so that most accesses hit the small store. If a fraction \(h\) of accesses hit and a hit costs \(c_{\text{hit}}\) while a miss costs \(c_{\text{miss}}\), the expected cost per access is \(hc_{\text{hit}}+(1-h)c_{\text{miss}}\), so a cache is valuable when accesses are concentrated (high \(h\)) and misses are much costlier than hits. For agent memory, a "hit" is information already in the context when needed, and a "miss" is information that must be fetched (a retrieval call, a few seconds and some tokens) or, worse, information that is never fetched because the agent does not know it exists, whose cost is a wrong decision. That last case has no counterpart in hardware caches, and it is the central difficulty: the agent must decide to look before it knows what it would find.

MemGPT's lasting contribution is the idea, now standard, that the agent manages its own memory through tools, deciding what to save and when to search, rather than having a fixed pipeline decide for it. Its limitation is the one the bridge box names. Paging works when the agent knows what it needs; it fails when the relevant memory is not suggested by anything in the current context. A support agent that has forgotten the service dog will not search for "service dog". This is why practical systems combine agent-directed retrieval with automatic retrieval: the harness, before each conversation or step, retrieves memories likely to be relevant (the customer's profile, recent interactions) and places them in the context without being asked, and the agent can search for more. The question then becomes which memories to bring in automatically, and that requires a way to score them.

13.4 Episodic memory: what happened

Episodic memory records experiences: each conversation, each task attempt, each notable observation, with a time stamp. The storage is easy; the hard part is retrieval, because an agent that has lived through thousands of episodes must bring back the few that bear on the present. Park and colleagues confronted this in Generative Agents (2023), the simulated village of 25 language agents mentioned in §1.7, each of which lived through simulated days, observed its neighbours, held conversations and planned its time[5]. Every observation went into a memory stream, a list of natural-language records with creation and last-access times. To decide what to place in the context, each memory \(d\) was scored against the current situation by a weighted sum of three components:

\[ \operatorname{score}(d)=\alpha_{\text{rec}}\cdot\operatorname{recency}(d)+\alpha_{\text{imp}}\cdot\operatorname{importance}(d)+\alpha_{\text{rel}}\cdot\operatorname{relevance}(d,q), \]

where recency decays exponentially with the time since the memory was last accessed (a factor of 0.995 per simulated hour), importance is a score from 1 to 10 that a model assigned when the memory was written ("brushing teeth" low, "a break-up" high), and relevance is the cosine similarity between the memory's embedding and the current query (Chapter 9). Each component was normalised to \([0,1]\) over the candidate memories, the weights were set to one, and the top-scoring memories that fitted the context budget were retrieved. Figure 13.3 shows how the recency component discounts the past for three decay rates.

Figure 13.3 shows why recency alone is a poor retrieval rule for agents whose users return at irregular intervals: a customer who calls once a month would find every memory of them nearly forgotten. The three-part score handles this by letting relevance and importance override recency. A month-old memory that a customer's dog is a registered service animal scores low on recency but high on importance and, when the customer mentions travelling with the dog, high on relevance. The decay rate should match the half-life of the information: a coding agent's memory of yesterday's failing test should fade within days, while a customer's dietary requirement should hardly fade at all, which suggests different rates for different types of memory rather than one global constant.

Worked example — scoring three memories

A customer calls to book a flight for herself and her dog. Three candidate memories, with raw component values:

(A) "Asked for aisle seat on last booking" — 400 hours ago, importance 4, relevance 0.62.
(B) "Travels with a registered service dog; needs bulkhead seat" — 1,500 hours ago, importance 9, relevance 0.81.
(C) "Complained about a delayed refund" — 48 hours ago, importance 6, relevance 0.30.

Raw recency at 0.995 per hour: A \(0.995^{400}=0.135\); B \(0.995^{1500}=0.0005\); C \(0.995^{48}=0.786\).

Normalise each component to \([0,1]\) over the three (min–max). Recency: A \((0.135-0.0005)/(0.786-0.0005)=0.171\), B 0, C 1. Importance (4, 9, 6): A 0, B 1, C 0.4. Relevance (0.62, 0.81, 0.30): A 0.627, B 1, C 0.

Scores (weights 1): A \(0.171+0+0.627=0.80\); B \(0+1+1=2.00\); C \(1+0.4+0=1.40\). With room for two memories, B and C are retrieved. The service-dog fact, the one that matters, wins despite being two months old. The complaint, recent but irrelevant to the booking, takes the second slot; the aisle preference is left out, which a semantic profile (§13.5) would fix.

Generative Agents added a second mechanism that turned out to be as important as retrieval: reflection. Periodically (when the summed importance of recent memories passed a threshold), an agent was prompted to ask itself what high-level questions its recent memories raised, retrieve memories relevant to those questions, and write insights ("Klaus is dedicated to his research on gentrification") back into the memory stream as new memories, with pointers to the memories that supported them. Reflections could themselves be reflected on, forming a hierarchy from raw observations to abstractions. In ablations, removing reflection, planning or observation memory each degraded the believability of the agents' behaviour as judged by human raters. Figure 13.4 shows the structure.

Figure 13.4 is consolidation in the psychologist's sense: turning episodes into general knowledge. For agents it has two practical benefits. It compresses memory, since one insight replaces many episodes in the context. And it makes memory useful at the right level of abstraction: the agent planning a booking needs "prefers bulkhead aisle seats", not three separate anecdotes about seats. It also has a cost and a risk: reflections are model-generated generalisations, and a generalisation from too little evidence is a false memory with a citation. Linking every insight to its evidence, as Generative Agents did, lets the agent (or a person) check it, and lets the system revise it when contrary evidence arrives. Consolidated facts of this kind are the subject of the next section.

13.5 Semantic memory: what is true

Semantic memory holds facts: about the user (name, preferences, constraints), about the world as the agent has learned it (this API requires authentication; this supplier ships only on weekdays), and about the organisation (who approves exceptions). Unlike episodes, facts are meant to be current: the useful memory is not every address the customer has ever had but the one that is true now. This makes semantic memory a database problem as much as a retrieval problem, with operations for creating, updating and deleting facts, and it is where most production "memory" features for assistants live.

A typical pipeline has three stages. Extraction: after (or during) an interaction, a model reads the conversation and proposes candidate facts ("user's preferred seat: aisle"; "user is vegetarian"; "project uses Python 3.12"), each with a type, a value, a source and a confidence. Reconciliation: each candidate is compared with existing facts of the same type; it may be new (add it), a duplicate (reinforce it), a refinement (merge it) or a contradiction (decide which is current, usually the more recent explicit statement, and keep the old one in history rather than delete it). Retrieval: at the start of each interaction, the relevant facts (often the whole profile, if small) are placed in the context, typically near the system prompt so that they are cached and read early. Systems built this way, such as Mem0, reported large reductions in tokens and latency relative to keeping full conversation histories, with comparable or better accuracy on long-conversation benchmarks[6].

Worked example — a contradiction in the profile

The support agent's profile for a customer says seat_preference: aisle (source: three bookings, last March). Today the customer says, "Put me by the window this time, I want to sleep."

Naive append. The store now holds "prefers aisle" and "prefers window". Next month the agent retrieves both and must guess, or picks whichever appears last in its context.

Naive overwrite. The profile says "prefers window". Next month, on a short daytime flight, the agent books a window seat the customer did not want; the request was for this trip.

Reconciliation. The extractor classifies the statement as a trip-specific request, not a change of standing preference, because of "this time". The profile keeps seat_preference: aisle and the booking records the exception. Had the customer said "I've switched to window seats", the preference would be updated with the old value moved to history and a timestamp, so that the change is explainable.

Lesson. Facts need scope (standing or one-off), provenance and time. A memory store that only appends or only overwrites will be wrong in predictable ways.

Two further design choices matter. Representation: facts can be stored as free-text sentences retrieved by embedding, as typed key–value records, or as a knowledge graph of entities and relations (the customer, her dog, her usual routes), which makes multi-hop questions ("which of my frequent flyers travel with animals?") answerable. Typed records are the most reliable for facts that drive actions; free text is the most flexible. Visibility: users should be able to see what an agent remembers about them and correct or delete it. Beyond being good practice and, in many jurisdictions, a legal requirement for personal data, it is the most effective error-correction mechanism available, since the user is the authority on their own preferences.

13.6 Procedural memory: how to act

Procedural memory holds the agent's know-how: how to do things well in its environment. We have met several forms already, and it helps to see them as one kind of memory. Lessons from experience, such as Reflexion's verbal reflections (§7.6), are procedural memories in the form of advice: "in this repository, run the database migrations before the tests". Skills, such as Voyager's verified functions (§10.9), are procedural memories in executable form. Instruction files written by people for agents (§12.7) are procedural memories supplied from outside. And the model's weights are procedural memory in the deepest sense: fine-tuning on an agent's successful trajectories, the subject of Chapter 17, writes experience into the policy itself rather than into its context.

The forms differ in how they are retrieved and how much they cost. Lessons and instructions are text that must be placed in the context, so they compete for budget and, if numerous, must be retrieved by relevance; they are easy to write, read and correct. Skills extend the action space and need only a short description in the context until used. Weights cost nothing at inference time but are expensive and slow to update, hard to inspect and impossible to edit precisely. A sensible progression is from the cheap and inspectable to the expensive and opaque: capture a lesson as text first; if it is applied often and reliably, turn it into a skill or an instruction; if a large body of such knowledge accumulates and the volume justifies it, distil it into the weights.

Procedural memories need validation more than any other kind, because they change behaviour on every future task they touch. A wrong lesson ("tests in this repository are flaky, ignore failures") can do more damage than a wrong fact, since it is applied with confidence in situations where it does not hold. Practical safeguards are those of §7.6 and §10.9: write lessons only from verified outcomes, scope them (this repository, this tool, this customer type), record their evidence, and retire lessons whose use correlates with failure.

13.7 Policies: what to write, what to retrieve, what to forget

A memory system is defined less by its storage than by its policies. Three decisions recur, and each has a characteristic failure on either side.

Write policy. Writing everything (every message, every observation) makes storage cheap and retrieval hard: the relevant memory is buried among trivia, and the score of §13.4 must work harder to find it. Writing too little loses information that turns out to matter. Good write policies are selective and typed: store episodes in full in a cheap log (for audit and later re-extraction), but write to the retrievable stores only what passes a salience test, such as an importance score, an explicit user statement ("remember that…"), a verified outcome (a lesson from a fixed failure), or a fact that changes the profile. The agent itself can decide, MemGPT-style, by calling a memory-writing tool; or a background process can extract after each interaction, which keeps the agent's own steps focused on the task.

Retrieval policy. How many memories, of which kinds, enter the context, and when? Automatic retrieval at the start of an interaction (the profile, the last few interactions) handles the cases the agent would not think to search for (§13.3); agent-directed search handles the rest. The budget principle of Chapter 4 applies: memories compete with everything else for tokens and attention, and a context crowded with marginal memories suffers the same rot as one crowded with stale tool outputs. Retrieved memories should be marked as such, with dates and provenance, so that the model can weigh an eighteen-month-old preference differently from yesterday's explicit request.

Forgetting policy. Memories should not all live forever. Some become false (an address changes), some become irrelevant (a resolved complaint), some must be deleted on request or by regulation (personal data), and an ever-growing store degrades retrieval precision, as the distractor arithmetic of §9.5 predicts. Mechanisms include decay in retrieval scores (Figure 13.3), explicit expiry for time-bound facts, consolidation that replaces many episodes with one insight, and deletion on contradiction or request. Forgetting is also the main defence against the slow accumulation of errors. Figure 13.5 makes this concrete with a simple model of an agent that learns lessons across sessions.

Figure 13.5 is a model, with illustrative parameters, but its shape is the important lesson. The benefit of memory saturates (there is only so much to learn about one environment), while the harm of uncorrected errors accumulates linearly, so an agent that only ever adds to its memory eventually gets worse. The two remedies are validation at write time (only store lessons backed by verified outcomes) and correction over time (forget or revise memories whose use correlates with failure). The same arithmetic applies to semantic facts: a store with a small rate of wrong extractions, never corrected, becomes less reliable the longer the agent runs.

Worked example — memory versus full history for a returning customer

A customer has had 30 previous conversations with the support agent, averaging 4,000 tokens each. The agent could (a) include the full history in context, (b) retrieve the 5 most relevant past exchanges (500 tokens each) plus a 600-token profile, or (c) use only the profile.

Tokens per call. (a) 120,000 tokens, most of a 200,000 window. (b) 3,100 tokens. (c) 600 tokens.

Cost per 12-turn conversation (memory block cached after the first call). (a) First call \(0.12\times\$3=\$0.36\), then \(11\times0.12\times\$0.30=\$0.40\): about $0.76 for memory alone. (b) \(0.0031\times\$3+11\times0.0031\times\$0.30\approx\$0.02\). (c) under a cent.

Quality. (a) contains everything but buries it (§4.7); (b) contains what is relevant if retrieval works; (c) contains only consolidated facts. A well-built system uses (c) always and (b) on demand, which covers nearly all needs at about a fortieth of the cost of (a).

Putting the pieces together

The previous sections described each memory type separately; a working system combines them into two paths, drawn in Figure 13.6. The write path runs mostly after each interaction, off the critical path of the user's conversation: the full transcript goes to an episodic log; an extractor proposes facts and lessons; a reconciler merges them into the semantic profile and the procedural store, applying the scope, provenance and validation rules of §13.5–§13.6; and periodically a consolidation job reflects over recent episodes, writes insights and expires what should be forgotten. The read path runs at the start of each interaction and during it: the harness loads the profile and the most relevant lessons automatically, places them in a marked block after the system prompt, and the agent can search episodic memory and the archival store through tools when it needs more. Keeping writes off the critical path matters for latency, since extraction and reconciliation take model calls, and keeping reads small matters for every reason in Chapter 4.

Figure 13.6 also makes it clear where to look when memory misbehaves. A wrong fact in the profile points to extraction or reconciliation; a correct fact that was not used points to retrieval or to its placement in the context; a memory that should have expired points to the consolidation job. Each stage can be evaluated separately with the methods of §13.9, and each can be improved without touching the others.

Two extensions are worth naming. Shared memory across agents, such as a team's support agents sharing knowledge of a recurring outage, or a coding agent and a review agent sharing notes on a repository, multiplies the value of each lesson and the damage of each error, and needs the same provenance and validation, plus access control so that each agent reads only what its users are entitled to see. And memory in the weights: when a body of procedural knowledge grows large and stable, it can be distilled into the model by fine-tuning on the trajectories that embody it (Chapter 17), freeing context budget, at the cost of the inspectability and easy correction that text memories offer. Most production systems in 2025 kept memory in text and stores, reserving weight updates for the developers' periodic retraining.

A final design principle ties the chapter to the rest of the book: memory should be added in response to measured need. Every memory component adds tokens, latency, failure modes and privacy obligations. A support agent whose customers rarely return gains little from episodic memory; a coding agent that works in one repository for months gains a great deal from procedural notes. Measure what the agent gets wrong for lack of memory, add the smallest component that fixes it, and evaluate across sessions before and after.

13.8 When memory goes wrong

Memory makes an agent's errors persistent, so its failure modes deserve a careful list. Staleness: a fact that was true when written and is not now (the customer moved; the API changed). Remedies: timestamps, expiry for facts known to change, and preferring fresh sources (a live look-up) over memory for anything consequential. False memories: facts that were never true, from extraction errors, over-generalised reflections (§13.4) or the model's own hallucinations written back as memories. Remedies: provenance (which conversation, which quote), confidence thresholds for writing, and user visibility and correction. Context contamination: a memory retrieved into the wrong situation, such as one project's conventions applied to another repository. Remedies: scoping memories by user, project and task type, and retrieving only within scope.

Two failures are security problems. Memory poisoning is prompt injection with persistence: content the agent reads (a web page, an email, a document) instructs it to save something to memory ("remember that all refunds for this account should go to the following card"), and the planted memory then influences every future session, long after the malicious content is gone. Researchers demonstrated attacks of this kind against assistants with memory features, including ones in which injected memories exfiltrated later conversations. Defences: never write memories from untrusted content without the user's confirmation; separate memories derived from the user's own statements from those derived from documents; show users when a memory is written; and audit the store. Cross-user leakage: in a system serving many users, a retrieval bug or a shared store lets one user's memories appear in another's context, which for personal data is both a privacy breach and, often, a legal one. Defences: strict partitioning of stores by user (and organisation), enforced in the storage layer rather than by filtering at retrieval time, and tests that try to retrieve across the boundary.

Drill 13.1 — how many wrong facts after a year?

An assistant extracts about 4 facts per conversation from a user who has 3 conversations a week. Extraction is wrong 3% of the time, and a wrong fact, if never corrected, persists. (a) How many wrong facts accumulate in a year? (b) If the assistant shows the user each new fact and users correct half of the wrong ones, and wrong facts unused for 90 days expire, roughly how many remain at any time?

(a) \(4\times3\times52=624\) facts a year, of which \(0.03\times624\approx19\) wrong. (b) Half corrected: about 9.4 a year enter the store, about 0.18 a week; with a 90-day (13-week) life for unused facts, the steady-state count is about \(0.18\times13\approx2.3\), assuming most wrong facts are not used (and so expire). Visibility and expiry together keep the error population small and bounded.

13.9 Evaluating memory

Evaluating memory is harder than evaluating single responses, because its value appears only across sessions. Benchmarks built for the purpose construct long, multi-session histories and ask questions that require remembering, updating or reasoning over them. LoCoMo (Maharana et al., 2024) generated very long conversations between agents with personas, spanning many sessions, and tested single-hop and multi-hop recall, temporal reasoning ("what did she say she would do after the trip?") and adversarial questions about things never said[7]. LongMemEval (Wu et al., 2024) tested five abilities: information extraction, multi-session reasoning, temporal reasoning, knowledge updates (using the latest value when facts change) and abstention (declining to answer when the information was never given), and found that commercial assistants and long-context models lost substantial accuracy as histories grew[8].

For a deployed agent, the useful evaluation follows the same structure on the agent's own domain: replay or simulate multi-session histories, then measure whether the agent uses what it should (a preference stated three sessions ago), updates what it should (a changed address), forgets what it should (a one-off request), and declines to invent what it was never told. Two operational metrics complement these: the precision of written memories (what fraction of stored facts are correct, from audits) and the cost and latency of memory per interaction. Above all, memory should be evaluated with ablations: the same agent with and without each memory component, on the same multi-session tasks, since memory that adds tokens and risk without improving outcomes should be removed.

Drill 13.2 — the right decay rate

A coding agent stores observations about a repository ("test X is flaky"; "module Y is being refactored"). Such observations remain true for about two weeks on average. What hourly decay factor gives a recency weight of one half after two weeks (336 hours)? What would it be for customer preferences that last about two years?

Solve \(r^{336}=0.5\): \(r=0.5^{1/336}=e^{-0.693/336}=e^{-0.00206}\approx0.99794\). For two years (about 17,500 hours): \(r=e^{-0.693/17{,}500}\approx0.99996\). One decay rate cannot serve both; use rates per memory type.

Drill 13.3 — budget for memories

A research agent has a 200,000-token window and wants to keep memory under 5% of it. Its profile of the user's interests is 800 tokens, and past findings are stored as 300-token notes. How many notes can it retrieve per call? If retrieval precision is 0.6 (the fraction of retrieved notes that are relevant), how many relevant notes does that give, and how many tokens are spent on irrelevant ones?

Budget 10,000 tokens; minus 800 for the profile leaves 9,200, or 30 notes. Relevant: \(0.6\times30=18\); irrelevant: 12 notes, 3,600 tokens per call. A reranker that raised precision to 0.85 for the same 18 relevant notes would need only 21 notes, saving about 2,700 tokens per call and reducing distraction.

13.10 Privacy and user control

An agent that remembers is an agent that holds personal data, and memory changes the privacy properties of a system in ways a stateless assistant never had to consider. A user who tells a stateless chatbot about a medical condition has disclosed it for one conversation; a user who tells an agent with memory has, unless the design prevents it, disclosed it to every future conversation, to any sub-agent that reads the memory store, and possibly to anyone who can influence what the agent retrieves. The engineering of memory therefore includes four controls that are as much a part of the design as the retrieval policy.

Visibility and editing. Users should be able to see what the agent has stored about them, in plain language, and correct or delete it. This is both a legal requirement in many jurisdictions and a correctness mechanism: users are the best detectors of wrong memories (§13.8). Consent and scope. Some information should never be written without asking (health, finances, other people's details), and memories should be scoped: a fact learned in a work context should not surface in a personal one. Isolation. Memories must be partitioned by user and tenant at the storage layer, with access enforced by the retrieval service, not by the prompt; a retrieval bug that returns another user's memory is a data breach, whatever the model then does with it. Retention and deletion. Memories should expire unless they remain useful, and deletion must propagate.

Deletion is harder than it looks, because memory systems derive new records from old ones: summaries of episodes, consolidated facts, reflections (§13.4–§13.5). If a user deletes a fact, every derived record that contains it must be found and rewritten or removed. The clean way to guarantee this is lineage: each derived memory records the identifiers of the records it was derived from, so the set of records affected by a deletion is the descendants of the deleted node in a directed acyclic graph, computable by a graph traversal. Without lineage, deletion is best effort, and a consolidated profile may keep repeating a fact the user asked to forget. Embeddings deserve the same treatment: an embedding of a deleted text must be deleted with it, since embeddings can leak information about their source.

These controls cost little if designed in and a great deal if retrofitted. They also shape what memory is worth building: a feature that stores sensitive facts must earn the privacy obligations it creates, which is one more reason, alongside cost and error, to add memory only where it is measured to help.

Looking ahead

Memory lets an agent carry knowledge across episodes. A different problem arises within a single episode that is simply too long: a coding task that takes four hours and hundreds of steps, a research project spanning days, a migration of a large code base. Such tasks overflow any context, accumulate errors (§1.8) over hundreds of steps, and outlast the processes, sessions and even machines they run on. How do agents work for hours without losing the thread: how do they compact their context, keep notes, delegate sub-tasks to fresh agents, checkpoint their progress and resume after interruption? And what does the evidence say about how long agents can now work? Chapter 14 takes up long-horizon agents.

Chapter summary

  • Memory extends the context map across episodes, giving continuity, personalisation and learning. Use psychology's taxonomy: working (the context), episodic (what happened), semantic (what is true), procedural (how to act); CoALA maps it onto agents.
  • MemGPT treats the context as a cache over recall and archival stores, with the agent paging via memory tools; combine with automatic retrieval, since agents cannot search for what they do not know exists.
  • Generative Agents retrieve by recency (decay 0.995/hour) + importance + relevance, normalised; reflection consolidates episodes into linked insights.
  • Semantic memory needs extraction, reconciliation (add, reinforce, merge, supersede with history), scope (standing vs one-off), provenance and user visibility.
  • Procedural memory spans lessons, skills, instruction files and weights, from cheap and inspectable to expensive and opaque; validate before writing.
  • Policies: selective, typed writes; automatic plus agent-directed retrieval within a budget; forgetting by decay, expiry, consolidation and deletion. Unvalidated memory eventually makes an agent worse.
  • Failures: staleness, false memories, contamination across scopes, memory poisoning (persistent injection) and cross-user leakage; defences include provenance, confirmation for writes from untrusted content, and storage-level partitioning.
  • Evaluate across sessions (LoCoMo, LongMemEval; extraction, multi-session reasoning, temporal reasoning, updates, abstention) and by ablation.
  • Memory brings privacy obligations: user visibility and editing, consent and scope, storage-level isolation, retention, and deletion that propagates through derived records via lineage.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up What kinds of memory does an agent need?

Working memory (the context for the current step), and long-term memory of three kinds: episodic (records of past interactions and trajectories, timestamped), semantic (current facts about the user, world and organisation, often a profile or fact store) and procedural (how to act: lessons, skills, instruction files, and ultimately the weights). Each has a different structure, write policy and failure mode; a single undifferentiated vector store of everything tends to retrieve poorly and accumulate errors.

Warm-up Explain MemGPT.

MemGPT treats the context window like main memory in an operating system and external storage like disk. The context holds fixed instructions, an agent-editable working context of key facts and a queue of recent messages; older messages are evicted (with summaries) under memory pressure into a searchable recall store, and the agent can insert into and search an archival store. The agent manages its own memory through function calls. Its key idea, agent-directed memory via tools, is widely used; its limitation is that agents do not search for memories they do not know exist, so automatic retrieval is also needed.

Warm-up How do Generative Agents decide which memories to retrieve?

Each memory gets a score: recency (exponential decay, 0.995 per hour since last access), importance (1–10, assigned by a model when written) and relevance (cosine similarity to the current query), each min–max normalised over candidates and summed with weights. The top memories that fit the budget enter the context. Periodically, reflection synthesises higher-level insights from recent memories and stores them, linked to their evidence.

Core How would you handle contradictory facts in an agent's user profile?

Store facts as typed records with scope (standing vs one-off), provenance (source conversation, quote) and timestamps. On a new statement, classify it: duplicate (reinforce), refinement (merge), trip-specific exception (record against the task, keep the standing fact), or genuine change (supersede, moving the old value to history). Prefer explicit recent statements over inferred ones. Show changes to the user, allow correction, and for consequential facts confirm before acting.

Core Design write, retrieval and forgetting policies for a support agent's memory.

Write: log full conversations to an audit store; extract typed facts (preferences, constraints, open issues) after each conversation with confidence thresholds; write only user-stated or verified facts to the profile; record open issues with expiry. Retrieve: automatically load the profile and recent open issues at conversation start (cached near the system prompt); let the agent search past conversations on demand; cap memory at a token budget. Forget: expire resolved issues and time-bound facts; decay retrieval of episodic memories; delete on user request; supersede contradicted facts with history. Partition stores per customer in the storage layer.

Core What is memory poisoning and how do you defend against it?

Injected content (a web page, email or document) instructs the agent to save a malicious memory, e.g. a payment detail or an instruction to forward data, which then persists and influences future sessions. Defences: do not write memories from untrusted content without user confirmation; tag memories by source (user-stated vs document-derived) and weight or restrict the latter; never let memories expand permissions; show users new memories; audit and allow deletion; and monitor for memories containing instructions rather than facts.

Core When should an agent use memory versus a fresh look-up?

Use memory for context, preferences and know-how that the authoritative systems do not hold or that would be expensive to re-derive. Use a fresh look-up for facts that drive consequential actions and can change (booking status, balances, current prices, code contents), since memories can be stale. A common pattern: memory supplies the hint ("customer had a pending refund"), and a look-up confirms the current state before acting.

Core How would you evaluate an agent's memory?

Construct or replay multi-session histories in the target domain and test extraction (does it remember stated facts?), multi-session reasoning, temporal reasoning, knowledge updates (latest value wins), scope (one-off requests not generalised), and abstention (no invented memories). Measure precision of written memories by audit, retrieval precision and recall, tokens and latency per interaction, and end-task success. Run ablations with and without each memory component. Public benchmarks such as LoCoMo and LongMemEval cover the general abilities.

Deep-dive Model the long-run effect of an agent that learns lessons across sessions, including wrong ones.

Let success at session \(k\) be \(s_k=s_\infty-(s_\infty-s_0)(1-\alpha)^k-\delta\,w\,k\), where correct lessons close a fraction \(\alpha\) of the gap each session and wrong lessons arrive at rate \(w\) per session, each costing \(\delta\) and never removed. The first term saturates; the last grows linearly, so \(s_k\) peaks at finite \(k\) and eventually falls below \(s_0\). With \(s_0=0.6,s_\infty=0.85,\alpha=0.3,w=0.3,\delta=0.03\), the peak is around session 6. Remedies change the parameters: validation at write lowers \(w\); retirement of lessons correlated with failure makes the wrong-lesson population bounded rather than growing (a birth–death process with a stationary size), restoring monotone improvement.

Deep-dive Compare free text, typed records and knowledge graphs for semantic memory.

Free text: flexible, easy to extract, retrieved by embeddings; but hard to update precisely, prone to duplicates and contradictions, weak for exact facts. Typed records: precise, updatable, auditable, ideal for facts that drive actions; but require a schema and miss unanticipated information. Knowledge graphs: entities and relations support multi-hop and aggregate queries and consolidation; but extraction is error-prone and maintenance is costly. Practical systems combine: typed profile for core facts, free-text notes for the rest, graph structure where relations matter (organisations, networks of entities).

Deep-dive Why can memory make an agent worse, and what does that imply for deployment?

Memory adds tokens (distraction, cost), retrieves stale or irrelevant items, persists errors (false facts, wrong lessons, poisoned instructions), and can leak across scopes. Unlike a stateless agent, a memoryful one's failures are correlated across sessions and can grow over time. Implications: validate writes, scope and partition, decay and expire, give users visibility, monitor memory quality metrics over time, and evaluate with long multi-session tests and ablations before enabling memory broadly; consider memory off by default for high-risk tasks.

Design Design memory for a coding agent that works in the same repositories over months.

Procedural: a repository notes file (or instruction file) of verified conventions and commands (how to run tests, environment variables, code style), written only when a command or convention is confirmed by success, reviewed by humans, versioned in the repository. Episodic: logs of past tasks with outcomes, searchable by file and error message, decayed over weeks. Semantic: facts about the code base (owners, modules under refactor, flaky tests) with expiry. Retrieval: load the notes file and repository map at task start; search past tasks when touching the same files or seeing the same error. Guard against stale knowledge by re-verifying commands that fail, and partition by repository.

Design A personal assistant remembers things about users across chats. What privacy and safety controls do you build?

Per-user (and per-organisation) storage partitions enforced in the database; encryption; user-visible memory list with edit and delete; notification when a memory is written; no memories written from untrusted documents or web content without confirmation; sensitive categories (health, finances, others' personal data) excluded or confirmed; retention limits and deletion on account closure; memories never used to expand tool permissions; audit logs; and evaluation for leakage across users. Provide a memory-off mode.

Design How would you choose decay rates and budgets for memory retrieval?

Estimate each memory type's useful lifetime from data (how long facts stay true, how long episodes stay relevant) and set per-type decay so the recency weight halves at that lifetime (\(r=0.5^{1/T_{1/2}}\)). Set a total memory token budget (e.g. a few per cent of the window) and allocate it by type (profile always, recent episodes, retrieved notes). Tune the score weights and budget on multi-session evaluation tasks, measuring end-task success and token cost; add a reranker if retrieval precision is low.

Core What is reflection in agent memory and what are its risks?

Periodic synthesis of higher-level insights from accumulated episodes ("prefers aisle seats", "Klaus researches gentrification"), stored as new memories linked to their evidence. It compresses memory and makes it useful at the right abstraction. Risks: over-generalisation from little evidence (false memories that look supported), drift through reflections on reflections, and cost. Mitigate with evidence thresholds, links to sources, revision on contrary evidence, and user visibility for personal insights.

Core Why combine agent-directed and automatic memory retrieval?

Agent-directed retrieval (memory as a tool) lets the agent fetch what it knows it needs, flexibly. But an agent cannot search for a memory whose existence nothing in the current context suggests, such as a forgotten constraint. Automatic retrieval (loading the profile and likely-relevant recent memories before the interaction) covers those cases. Together they approximate a sufficient context without loading everything.

Core Why should memory writes happen off the critical path of an interaction?

Extraction, reconciliation and consolidation each require model calls and storage operations that add seconds of latency; doing them during the conversation slows every turn for a benefit realised only in future sessions. Running them after the interaction (or asynchronously in the background) keeps the user-facing path fast and lets the write pipeline use more careful (and expensive) validation. The exception is memory the agent needs within the same episode, which it can keep in its working context or a scratchpad until the episode ends.

Deep-dive When should procedural knowledge move from text memory into the model's weights?

When it is large (consuming significant context budget if kept as text), stable (unlikely to change soon), validated (consistently associated with success), and applies to high-volume traffic, so that fine-tuning on trajectories embodying it pays back through lower per-call tokens and better reliability. Costs: training effort, slower updates, loss of inspectability and precise editing, and risk of entangling it with other behaviours. Keep fast-changing, user-specific or safety-relevant knowledge in text, where it can be read, audited and corrected; distil only the stable core, and keep the text version as documentation and for evaluation.
