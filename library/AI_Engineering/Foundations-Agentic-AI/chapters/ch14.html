Part IV · Memory and State — Chapter 14

Long-Horizon Agents

Some tasks take an agent minutes; the ones that matter most often take hours: migrating a code base, building a feature end to end, researching a question thoroughly. Over hundreds of steps, contexts overflow, errors accumulate, plans go stale and processes crash. This chapter assembles the techniques that let agents work for hours without losing the thread: compaction, notes, delegation, verified milestones and checkpoints, and the arithmetic that says how much each is worth.

Why this chapter

Chapter 1 introduced the \(\rho^H\) law and METR's measurements of the length of task agents can complete (Figure 1.5), which doubled roughly every seven months from 2019 to 2025. Chapter 2 refined the law with error detection and recovery, and showed that cost grows quadratically with the horizon. Chapter 4 managed the context within an episode, and Chapter 13 gave the agent memory across episodes. This chapter brings these threads together for the case that stresses all of them at once: a single task so long that no context can hold its history, no per-step error rate is low enough to survive it unaided, and no process can be assumed to run uninterrupted from start to finish.

The organising idea is that a long task should not be executed as one long trajectory. It should be decomposed into pieces that each fit within a context, each end in a state that can be verified, and each leave behind a record from which the next piece can start, so that the agent's progress accumulates in the environment and in its notes rather than only in a fragile, growing context. Every technique in this chapter is a way of doing that: compaction trims the trajectory, notes and version control externalise its state, sub-agents give pieces their own contexts, milestones make progress verifiable, and checkpoints make it durable. We quantify each with the models of earlier chapters and one new one, from the theory of fault tolerance.

Learning objectives
  1. Characterise long-horizon tasks and interpret time-horizon measurements at 50% and 80% reliability.
  2. Design compaction: what to preserve, when to trigger it, and how to test it.
  3. Use external state (plans, progress notes, version control) as the agent's durable working memory.
  4. Use sub-agents to isolate context, and compute what delegation saves.
  5. Model verified milestones with retries and show how they change success on long tasks.
  6. Derive the optimal checkpoint interval (Young's formula) and apply it to agent runs.
  7. Decide how and when humans should supervise long-running agents.

We use Chapters 1 and 2 (reliability, cost), Chapter 4 (context management), Chapter 10 (version control as memory) and Chapter 13 (memory).

14.1 What makes a task long

A task is long-horizon, in the sense that matters for agents, when it has three properties together. It needs many dependent steps, hundreds rather than dozens, so that per-step errors compound. It produces more history than fits in a context, so that the agent cannot simply keep everything it has seen. And it takes longer than the infrastructure can be assumed stable: hours of wall-clock time over which model calls fail, sandboxes are recycled, rate limits bite and, for the longest tasks, humans need to see progress and steer. Migrating a hundred-thousand-line code base from one framework to another has all three. So does producing a thorough literature review, or building and testing a new service.

The evidence on how long agents can work comes mainly from METR's time-horizon measurements (§1.9). Two features of those measurements matter here. First, the time horizon is defined by human task length, so a task a skilled person does in two hours may take an agent more or less time, and many more or fewer steps. Second, METR reported both a 50% and an 80% horizon, and the 80% horizon was several times shorter: a model that completed two-hour tasks half the time completed only tasks of a few tens of minutes four times in five[1]. The gap between "sometimes" and "reliably" is the gap between the curves of Figure 1.3, and closing it, rather than extending the 50% horizon, is the main concern of anyone who wants to deploy long-running agents. By late 2025, developers of frontier models reported agents working autonomously for many hours on single software tasks, and coding agents that run for an afternoon had become ordinary tools, but always within harnesses built from the techniques of this chapter.

Figure 14.1 shows the shape of such a harness. The agent's context holds only what the current piece of work needs. Its durable state lives outside: a plan with milestones, progress notes, the version-control history of the work itself, and a store of findings. Sub-agents with fresh contexts handle self-contained pieces and return summaries. Checkpoints after each verified milestone let the run resume after any interruption, and a human can inspect the plan and progress at any time.

Figure 14.1's central claim, that the context is disposable, is the inversion this chapter argues for. In a short task the context is the agent's state; in a long one, the context should be a view onto state kept elsewhere, cheap to rebuild at any point. If the context were wiped at any moment, a well-designed long-horizon agent should be able to read its plan, notes and recent commits and continue, losing only the work since the last checkpoint. The rest of the chapter takes the components in turn.

14.2 Errors at length

Before the techniques, the problem in numbers. Suppose that after the agent's own detection and recovery (§2.6) a fraction \(\epsilon_f\) of steps still introduce an error that goes unnoticed and dooms the task. Then a task of \(H\) steps succeeds with probability \((1-\epsilon_f)^H\). At \(\epsilon_f=0.01\), a level that would be excellent for many agents, a 200-step task succeeds 13% of the time and a 400-step task 2%. No plausible improvement in per-step reliability rescues tasks of thousands of steps by itself. What changes the picture is structure: making errors detectable not only step by step but at milestones, where the state of the work can be checked against the goal, and making it possible to go back to the last good milestone and try again.

Long tasks also suffer errors that short ones rarely do. Drift: over many compactions and sub-tasks, the agent's working understanding of the goal shifts, so that late work solves a slightly different problem from the one posed. Inconsistency: decisions made early (a naming scheme, an interface) are forgotten and contradicted later. Premature completion: after hours of work, the agent declares the task done with parts unfinished, a long-horizon version of the false success claims of §2.7. And budget exhaustion: the run stops when its money or time runs out, wherever it happens to be. Each has a structural remedy: drift is countered by keeping the original goal verbatim in every context (§4.8), inconsistency by recording decisions in notes, premature completion by checking every milestone against an explicit list, and budget exhaustion by planning milestones so that every completed one leaves the work in a usable state.

14.3 Compaction

Compaction, introduced in §4.8, replaces a long span of history with a summary when the context approaches its budget. For short tasks it is an occasional convenience; for long ones it happens many times per run, and its quality determines whether the agent keeps the thread. Figure 14.2 shows the life of a context over a long run with compaction.

Figure 14.2 shows two design parameters and one hazard. The threshold sets how full the context gets before compaction: too high and the agent suffers context rot (§4.7) before each compaction; too low and it compacts so often that it loses detail it still needed and pays to rebuild its cache (§4.6) each time. The summary size sets the floor after compaction. The hazard is the creeping floor: if each compaction keeps the previous summary and adds a new one, summaries accumulate until the post-compaction context is itself near the threshold. Long-running harnesses avoid this by keeping only a bounded summary in the context (rewritten, not appended, at each compaction) and moving the durable content (decisions, findings, completed milestones) into notes outside the context, where it can be read on demand.

What should a compaction summary contain? The answer is the sufficient-statistic principle of Chapter 2, made concrete: everything the next decisions depend on and nothing else. In practice that means the original task verbatim (never paraphrased, which is how drift starts); constraints and preferences stated by the user; the current plan, which milestones are done and which remain; the current state of the artefacts (which files changed and how, or which sections of a report are drafted); decisions taken and their reasons; approaches tried and abandoned, with why, so that they are not retried; open questions; and the immediate next step. It should not contain raw tool outputs, which can be fetched again, or the reasoning that led to decisions, beyond a sentence of justification.

Worked example — how often to compact

A migration agent's context has a 12,000-token fixed prefix, grows by 3,000 tokens per step, and is compacted to a 6,000-token summary (on top of the prefix) whenever it reaches a threshold \(n_c\). Each compaction is a model call that reads the whole context and writes the summary, and invalidates the cache, so the next call pays for the context fresh.

Threshold 150,000. Each cycle grows from 18,000 to 150,000 tokens: 44 steps. Average context about 84,000 tokens. Compaction cost per cycle: reading 150,000 tokens ($0.045 cached) and writing 6,000 ($0.09), plus one fresh rebuild of 18,000 ($0.054): about $0.19 per 44 steps.

Threshold 60,000. Cycles of 14 steps, average context about 39,000 tokens. Compaction cost per cycle: \(0.018+0.09+0.054=\$0.16\) per 14 steps, about three times as often per step.

Reads. Cached reads per step: about $0.025 at the high threshold, $0.012 at the low one. Over 440 steps: high threshold \(440\times0.025+10\times0.19=\$12.90\); low threshold \(440\times0.012+31\times0.16=\$10.24\).

Verdict. The lower threshold is somewhat cheaper and keeps the agent out of the regime where long contexts degrade its decisions, at the price of three times as many summaries, each a chance to lose something. The right setting is found by measuring task success, not by arithmetic alone; the arithmetic shows that cost does not forbid compacting often.

Compaction must be tested like any other component (Chapter 7's advice to measure \(\mu\) and \(\nu\) applies). The most direct test is replay: take logged long runs, compact at a step, continue from the compacted context and from the full one, and compare what the agent does next. A good compaction makes the continuation indistinguishable; a bad one shows the characteristic symptoms of redone work, contradicted decisions and forgotten constraints. A cheaper test is a checklist judged by a model or a person: does the summary contain the task verbatim, the constraints, the plan with its status, the changed artefacts and the next step?

14.4 External state: plans, notes and commits

The most effective single technique for long tasks is also the simplest: have the agent keep its working state in files. A plan file lists the milestones with their status, rewritten as work proceeds. A progress notes file records findings, decisions with reasons, and pitfalls ("the legacy module imports itself through a shim; edit the shim, not the module"). Version control (§10.9) records the work itself, with a commit at each milestone whose message says what was done. These files persist across compactions, crashes and even changes of agent; they are human-readable, so a person can see progress and correct course; and they keep the context small, since the agent reads them when it needs them rather than carrying their contents.

In the vocabulary of Chapter 13, this is procedural and semantic memory scoped to one task, kept in the environment. In the vocabulary of Chapter 2, the agent is maintaining its own belief summary explicitly, outside the context, where it can be inspected and where it survives. Anthropic's guidance for long-running agents describes exactly this pattern, including an initial session that sets up the plan and environment and later sessions that each read the progress files, make incremental progress on one item, test it and commit[2]. The habit of reading the notes at the start of every session and updating them at the end of every milestone is what lets a run be resumed by a fresh context with no loss beyond the current milestone.

Structure helps. A plan kept as a checklist with explicit acceptance criteria per item ("all modules under billing/ import the new client; their tests pass") is something both the agent and a verifier can check. Progress notes with fixed sections (decisions, findings, pitfalls, open questions) are easier to search and harder to let rot than free prose. Some harnesses keep the plan as structured data that the harness itself reads, so that it, rather than the model, decides which milestone comes next and when the task is complete, the workflow-versus-agent trade-off of §2.5 applied to the outer loop.

One pattern for structuring these files has proved particularly effective for coding agents working across many sessions. A first, initialising session does no feature work at all: it reads the task, sets up the environment (scripts to install dependencies and run the tests), writes the plan as a list of small, independently testable items with explicit criteria, and commits everything. Every later session follows a fixed routine: read the plan, the notes and the recent commit log; confirm that the environment works and the existing tests pass; pick one unfinished item; implement it; test it against its criteria; commit with a descriptive message; update the plan and notes; stop. Working on one item at a time keeps each session's context small and its work verifiable, and the routine at the start of each session catches problems (a broken build left by the previous session) before new work piles on top of them. It is a direct application of the milestone structure of §14.6 to the scale of sessions, and the reason it works is that each session begins from durable, checked state rather than from a fading memory of the previous one.

14.5 Sub-agents and context isolation

Some parts of a long task are self-contained: search the code base for every use of a deprecated function, read twenty papers on a sub-topic and extract their results, try three approaches to a tricky sub-problem. Doing them in the main agent's context fills it with search results, file contents and failed attempts that are irrelevant once the part is done. Delegating them to a sub-agent, a fresh agent with its own context, instructions and perhaps a narrower tool set, keeps the main context clean: the sub-agent does the messy work and returns only a short result. Figure 14.3 shows the pattern.

Figure 14.3's arithmetic is simple and favourable. Without delegation the main context would absorb about 190,000 tokens of detail; with it, about 4,500 tokens of summaries. Because the sub-agents' contexts are discarded after use, the quadratic growth of §1.10 applies only within each sub-task, not across the whole run. Independent sub-agents can also run in parallel, shortening wall-clock time. The costs are real too. Each sub-agent pays its own fixed prefix and its own ramp-up (it must read enough to understand its piece), so total tokens across all agents often rise even as the main context shrinks. And the handover is lossy in both directions: the sub-agent knows only what its instructions tell it about the wider task, and the main agent knows only what the summary says about what was found.

Worked example — is delegation worth it?

A main agent must locate every use of a deprecated API across a repository before planning a migration. Done inline, the search takes 25 steps, each adding 2,400 tokens of results to a context that already holds 40,000 tokens and will be carried for the remaining 150 steps of the run.

Inline. The 60,000 tokens of search results stay in the context (until the next compaction, say 50 steps later): \(60{,}000\times50=3{,}000{,}000\) extra cached token-reads, $0.90, plus the cost of the 25 steps themselves on a growing context, about \(25\times(40{,}000+30{,}000)=1.75\) million cached tokens, $0.53.

Delegated. A sub-agent starts with a 6,000-token context (prefix and task), runs the same 25 steps on its own context (\(25\times(6{,}000+30{,}000)=0.9\) million tokens, $0.27), and returns a 1,500-token list of files and call sites. The main context carries 1,500 tokens for 50 steps (75,000 token-reads, $0.02).

Verdict. About $0.29 against $1.43, and a cleaner main context. The saving comes from not carrying detail that the main agent no longer needs; it is largest for sub-tasks with bulky intermediate results and small final answers.

When should a long-horizon agent delegate? The worked example points to the criterion: when a sub-task's intermediate results are large and its final result is small, and the sub-task can be specified clearly in a few sentences with explicit criteria for done. Searches, surveys, explorations and attempts at isolated sub-problems fit; tightly coupled work, where each step depends on subtle details of the main state, does not, because the handover would lose exactly those details. Chapter 15 studies delegation in its general form, systems of many agents.

14.6 Verified milestones

The reliability problem of §14.2 is that errors accumulate over a long trajectory and are discovered, if at all, only at the end. The remedy is to divide the task into milestones, each ending in a state that can be checked against an explicit criterion, and to keep a checkpoint at each one so that a failed milestone can be retried from the last good state rather than from the beginning. Figure 14.4 shows the structure.

Figure 14.4 can be analysed with the tools of Chapter 2. Let a task of \(H\) steps be split into milestones of \(\Lambda\) steps each (\(H/\Lambda\) milestones), with fatal error rate \(\epsilon_f\) per step, so that a milestone is completed correctly with probability \(p_m=(1-\epsilon_f)^{\Lambda}\). The milestone's check detects a failed milestone with probability \(r_m\), after which it is retried from the checkpoint, up to \(n_r\) times in all. An undetected failure dooms the task. A milestone then succeeds with probability \(\sum_{i=0}^{n_r-1}p_m\big((1-p_m)r_m\big)^i\), and the task with that probability raised to the power \(H/\Lambda\). Figure 14.5 plots the result for \(\epsilon_f=0.01\), \(\Lambda=20\) and \(r_m=0.9\).

Figure 14.5 is the quantitative case for the structure of Figure 14.4. Retries from checkpoints convert most failures into extra work, and the curve's remaining decline comes almost entirely from the 10% of failed milestones that pass their checks undetected, which is why the quality of each milestone's check matters as much as the existence of milestones. It also tells us how to choose milestone size: smaller milestones fail less often and are cheaper to retry, but each needs a meaningful check, and checks have costs (running a test suite, a review by a critic) and need natural boundaries in the work. The practical rule is to place a milestone wherever the work reaches a state that can be checked cheaply against the goal, aiming for a few tens of steps between them.

Drill 14.1 — the value of a better check

In the setting of Figure 14.5 (200 steps, 20-step milestones, \(\epsilon_f=0.01\), one retry), what is the success probability if the milestone check catches 99% of failures instead of 90%? If it catches only 50%?

\(p_m=0.99^{20}=0.818\). With \(r_m=0.99\): milestone success \(0.818+0.182\times0.99\times0.818=0.818+0.147=0.965\); task \(0.965^{10}=0.70\). With \(r_m=0.5\): \(0.818+0.182\times0.5\times0.818=0.892\); task \(0.892^{10}=0.32\). The check's detection rate moves task success from 32% to 70%; investing in milestone checks (tests that exercise the milestone's acceptance criteria) is among the best uses of effort.

14.7 Checkpoints and resumption

Long runs are interrupted. Model APIs return errors and rate limits; sandboxes are recycled after a maximum lifetime; the harness process is redeployed; a budget cap pauses the run; a human asks it to stop. An agent that must start over after every interruption cannot complete a task longer than the typical time between interruptions. Checkpointing saves enough state to resume: the plan and notes, the version-controlled work, the agent's compacted context, and the harness's own bookkeeping (which step, which milestone, which tool calls are in flight). Durable execution frameworks, borrowed from workflow engines used for long-running business processes, make this systematic by persisting each step's inputs and outputs so that a crashed run can be replayed to the point of failure without re-executing completed steps, which requires that steps with side effects be idempotent or recorded (§8.7).

How often should a long run checkpoint? Checkpoints cost time (writing notes, committing, persisting state), and too few of them lose work at each interruption. This is a classical problem in fault-tolerant computing, and its standard answer is Young's formula of 1974[3].

Derivation — the optimal checkpoint interval

Let a checkpoint cost \(C_{\text{ck}}\) seconds, let interruptions arrive as a Poisson process with mean time between them \(M_{\text{int}}\), and let the agent checkpoint every \(\tau_c\) seconds of work. Per interval, the overhead is \(C_{\text{ck}}\); an interruption, which occurs in an interval with probability about \(\tau_c/M_{\text{int}}\) when \(\tau_c\ll M_{\text{int}}\), loses on average half an interval of work. The expected overhead as a fraction of useful time is therefore \[ \Omega(\tau_c)\approx\frac{C_{\text{ck}}}{\tau_c}+\frac{\tau_c}{2M_{\text{int}}}. \] Setting \(\Omega'(\tau_c)=-C_{\text{ck}}/\tau_c^2+1/(2M_{\text{int}})=0\) gives \(\tau_c^*=\sqrt{2C_{\text{ck}}M_{\text{int}}}\), at which both terms are equal and \(\Omega(\tau_c^*)=\sqrt{2C_{\text{ck}}/M_{\text{int}}}\).

Figure 14.6 shows the characteristic flat-bottomed curve: the optimum is broad, so a checkpoint interval within a factor of two of \(\tau_c^*\) costs little extra, and the formula's main use is to rule out bad choices (checkpointing every minute, or once an hour on unreliable infrastructure). For agents the formula has a convenient corollary. Milestones (§14.6) are natural checkpoints, since the work is in a verified state there and the notes and commit are being written anyway, so the checkpoint cost is small. Choosing milestone sizes so that they take roughly \(\tau_c^*\) of wall-clock time aligns the reliability argument and the fault-tolerance argument, and gives a harness one rule instead of two.

Drill 14.2 — checkpoints for an overnight run

An overnight migration runs for 8 hours on infrastructure that interrupts it on average every 90 minutes. Writing notes, committing and persisting the harness state takes 45 seconds. What checkpoint interval minimises overhead, and how much of the night is lost to checkpoints and interruptions?

\(\tau_c^*=\sqrt{2\times45\times5{,}400}=\sqrt{486{,}000}\approx697\) s, about 12 minutes. Overhead \(\sqrt{2\times45/5{,}400}=\sqrt{0.0167}\approx0.129\): about 13%, roughly an hour of the eight. Making interruptions rarer (longer sandbox lifetimes, retries for transient API errors) is the bigger lever: at one interruption every 6 hours the overhead falls to about 6.5%.

Budgeting a long run

A long run should have a budget in money and time, set before it starts, and the budget should be spent with the same discipline as any other resource. The arithmetic of earlier chapters gives its components. Each milestone costs its steps (input dominated by cached reads of the context, output by reasoning and edits, §3.7), its checks (test runs, critic calls) and its expected retries (\((1-p_m)r_m\) extra attempts per milestone, from §14.6). Compaction adds a periodic cost (§14.3), sub-agents their own prefixes (§14.5), and checkpointing its overhead (§14.7). A per-milestone budget, with the run's total as their sum plus a reserve, lets the harness detect a run that is overspending early and decide whether to continue, to escalate, or to stop with the completed milestones intact. Because the milestones were chosen so that each leaves the work in a usable state, stopping early is a partial success rather than a total loss: a migration that completes seven of ten modules overnight has done seven modules' worth of work.

Drill 14.3 — the budget for an overnight run

A run has 12 milestones. Each takes about 25 steps, each step reading an average of 60,000 cached tokens and 3,000 fresh tokens and writing 400 output tokens; each milestone's check costs $0.20; milestones fail detectably 20% of the time and are retried once. Compaction and checkpoints add 10%. Estimate the budget.

Per step: \(0.06\times\$0.30+0.003\times\$3+0.0004\times\$15=\$0.018+\$0.009+\$0.006=\$0.033\). Per milestone attempt: \(25\times0.033+0.20=\$1.03\). Expected attempts per milestone \(1+0.2=1.2\): $1.23. Twelve milestones: $14.8; plus 10%: about $16. A budget of $25 leaves a reserve for unexpected retries; a run that has spent $12 by milestone 4 is running at three times plan and should alert someone.

Testing that resumption works

Resumability is a property that is easy to claim and rarely tested until it is needed. The discipline that distributed-systems engineers call fault injection applies directly: deliberately interrupt runs at random points (kill the harness process, recycle the sandbox, make a model call fail, make a tool time out) and measure whether the run resumes correctly, how much work it loses, and whether any side effect is duplicated. A harness that has never been killed in testing will lose work, or worse, repeat a write, the first time it is killed in production. Three measurements summarise the result: the resumption success rate (the fraction of interrupted runs that complete correctly after restart), the work lost per interruption (which should be about half a checkpoint interval, as Young's model assumes, and is much more if the checkpoint state is incomplete) and the duplicate side-effect rate (which should be zero, by the idempotency rules of §8.7). The same tests catch a subtler failure: a run that resumes, but from a context rebuilt from notes that omit something important, so that it repeats or contradicts earlier work. Comparing resumed runs with uninterrupted ones on the same tasks measures the quality of the notes as a carrier of state, the external-state analogue of the compaction replay test of §14.3.

14.8 Supervising agents that run for hours

A long-running agent changes the relationship with the person who launched it. In a short task, the person watches and intervenes; over hours, they cannot and should not, but they still need to know what is happening, to catch a run that has gone wrong before it wastes the night, and to make the decisions that are theirs to make. Three practices make supervision efficient. Legible state: the plan and progress notes of §14.4 double as a status report, readable in a minute, so a person can check progress at any time without reading a transcript. Scheduled check-ins at decisions: the agent pauses for a human at the few points where its choice is consequential or ambiguous (an architectural decision, a destructive migration step, a change of plan) rather than at fixed intervals or every few steps, which is consent fatigue (§12.4) in another form. Early-warning signals: the harness watches for the signatures of a run going wrong, such as the same milestone failing repeatedly, the context compacting far more often than expected, cost per milestone rising, or the agent editing files outside the plan's scope, and alerts a person or stops the run.

The cost of supervision is attention, and its value can be estimated like that of an approval (§8.9). A run that would waste a night of compute and produce an unusable result if it went wrong early justifies a brief human look at its plan before it starts and at its first milestone, which catch the most expensive failures (a misunderstood task, a flawed approach) at the cheapest moment. Most of the value of supervising long runs comes from these early looks.

Worked example — where a human's five minutes are best spent

An overnight run costs $40 of compute and, if successful, saves two days of an engineer's work. Suppose 20% of runs fail because the task was misunderstood or the plan was wrong from the start, and 15% fail for other reasons later. A five-minute human review of the plan before the run catches 70% of the first kind; a five-minute review at 2 a.m. would catch some later failures but nobody is awake.

Without review. Success 65%; failed runs waste $40 and a day of calendar time.

With the plan review. Of the 20% of runs with a bad start, 70% (14% of all runs) are corrected before they begin, so 94% of runs reach the later stage, where, as before, \(65/80=81\%\) of them succeed. Success rises to \(0.94\times0.8125\approx76\%\). Expected wasted compute falls from \(0.35\times\$40=\$14\) to \(0.24\times\$40=\$9.60\), and the two-day saving is realised 11 percentage points more often, for five minutes of attention at the moment it is most valuable.

14.9 What limits the horizon today

It is worth asking, at the end of this chapter, what actually limits how long agents can work, because the answer shows where progress is coming from. Four limits interact. The first is the fatal error rate \(\epsilon_f\): how often a step goes wrong in a way nothing catches. Models trained with reinforcement learning on long, verifiable tasks (§5.6, Chapter 18) have reduced it steadily, both by erring less and by checking their own work more, and this is the main driver of the METR trend of Figure 1.5. The second is verifiability: Figure 14.5 showed that milestone checks are what make long tasks feasible, so tasks whose intermediate states can be checked automatically (code with tests, data pipelines with validations) reach much longer horizons than tasks whose quality is judged only at the end (a strategy document, a design). The third is state management: an agent that loses the thread after a few compactions is limited by its harness, not its model, and the techniques of §14.3–§14.5 move this limit outward. The fourth is cost and time: even with caching, long runs cost dollars to tens of dollars and take hours, so the economic value of the task must justify them, and failures late in a run are expensive.

The practical consequence for a designer is a ranking of investments. For a task class that should run for hours, first make progress checkable at milestones, since this moves the success curve more than anything else; then externalise state so that runs survive compaction and interruption; then choose the model, preferring one trained for long agentic work; and finally tune costs. The reverse order, starting with the most capable model and hoping it will manage a long unstructured run, is the most common way long-running agents disappoint.

14.10 Hierarchical decomposition

The techniques of this chapter share an underlying structure: they break a long task into pieces whose errors can be contained. Hierarchical decomposition makes the structure explicit. A goal is split into sub-goals, each of which is either executed directly or split again, until the leaves are tasks short enough to be done reliably. The idea is old in AI (hierarchical task networks in classical planning, options in reinforcement learning), and for language agents it is the natural shape of an orchestrator's plan (§15.4) and of the milestone structure of §14.6.

The arithmetic shows why it helps and what it requires. A task of \(H\) steps at per-step reliability \(\rho\) succeeds with \(\rho^H\). Split it into \(M\) sub-goals of \(H/M\) steps, each with a check of completion that detects failure, and allow up to \(n_r\) attempts per sub-goal. A sub-goal then succeeds with \(1-(1-\rho^{H/M})^{n_r}\), and the task with that quantity raised to the power \(M\). The expected number of attempts per sub-goal is \(\sum_{j=0}^{n_r-1}(1-\rho^{H/M})^j\), which bounds the extra cost.

Worked example — decomposing a 60-step migration

A 60-step task at \(\rho=0.98\) succeeds with \(0.98^{60}=29.8\%\) undecomposed.

Six sub-goals of ten steps, each with a reliable completion check and up to three attempts: a sub-goal succeeds first time with \(0.98^{10}=0.817\), within three attempts with \(1-0.183^3=0.994\), and the task with \(0.994^6=96.4\%\).

Cost. Expected attempts per sub-goal \(1+0.183+0.033=1.22\): about 22% more steps buys a jump from 30% to 96%.

The catch. The gain rests on the checks. If a check misses 20% of failed sub-goals, those failures propagate, and the task's success falls back towards the undecomposed value; the decomposition is only as good as its verification at the boundaries.

Decomposition introduces two new failure modes. A bad decomposition, with sub-goals that overlap, leave gaps or depend on each other in ways the plan does not record, produces sub-goals that each succeed while the whole fails; reviewing the plan (by a person or a separate model call) before execution is cheap insurance. And re-planning is needed when a sub-goal turns out to be impossible as specified: the parent must be able to revise the plan rather than retry a doomed sub-goal, which means the hierarchy needs feedback upwards as well as instructions downwards. With both handled, decomposition is the most general tool for turning the \(\rho^H\) law from a ceiling into a design parameter.

Looking ahead

Part IV gave agents a past (memory) and the stamina for long tasks (compaction, notes, milestones, checkpoints). One technique from this chapter, delegation to sub-agents with their own contexts, points beyond the single agent. If one agent can hand a self-contained piece of work to another, why not build systems of many agents: specialists with different tools, critics that check each other, planners and workers, agents that debate? When do many agents genuinely beat one, what do they cost, how do they communicate and coordinate, and how do their errors compound? Part V begins with multi-agent systems in Chapter 15.

Chapter summary

  • Long-horizon tasks have many dependent steps, more history than fits in context, and durations over which infrastructure and plans are unstable. METR's 80% horizons are several times shorter than its 50% horizons; reliability, not reach, is the challenge.
  • Make the context disposable: progress should live in the environment, notes and version control, so any context can be rebuilt.
  • Compaction: preserve the task verbatim, constraints, plan status, artefact state, decisions, abandoned approaches and next step; rewrite rather than append summaries; tune the threshold; test by replay.
  • External state: plan files with acceptance criteria, structured progress notes and commits per milestone make runs resumable and legible.
  • Sub-agents isolate bulky intermediate work, returning short results; delegate when intermediate results are large, final results small and the task is clearly specifiable.
  • Verified milestones with retries from checkpoints turn a 13% chance on 200 steps into 61–77% (at \(\epsilon_f=0.01\)); the checks' detection rate dominates the residual loss.
  • Checkpoint every \(\tau_c^*=\sqrt{2C_{\text{ck}}M_{\text{int}}}\) (Young), with overhead \(\sqrt{2C_{\text{ck}}/M_{\text{int}}}\); align milestones with checkpoints. Durable execution replays without re-executing completed side effects.
  • Budget runs per milestone with a reserve; stopping early should leave completed milestones usable. The horizon is limited by fatal error rate, verifiability, state management and cost, in roughly that order of leverage.
  • Supervise through legible state, check-ins at consequential decisions and automatic early-warning signals; the earliest human looks are worth most.
  • Hierarchical decomposition into verified sub-goals with retries turns \(\rho^H\) into \((1-(1-\rho^{H/M})^{n_r})^M\); it is only as good as the completion checks and needs re-planning.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up How do you make an agent work reliably on a task that takes several hours?

Decompose it into verified milestones with checkpoints; keep durable state outside the context (a plan with acceptance criteria, progress notes, version-control commits per milestone); compact the context with summaries that preserve the task verbatim, constraints, plan status and decisions; delegate self-contained bulky sub-tasks to sub-agents with fresh contexts; make the run resumable after interruption (checkpoint at milestones, idempotent side effects); and supervise through legible progress, check-ins at consequential decisions and early-warning signals.

Warm-up What is context compaction and what can go wrong?

Replacing a long span of history with a model-written summary when the context nears a threshold, so the agent can continue within its window. Failure modes: losing or paraphrasing the goal (drift), dropping constraints or decisions (contradictions, redone work), forgetting abandoned approaches (retrying them), accumulating summaries (creeping floor), and compacting too rarely (context rot) or too often (lost detail, cache rebuilds). Test by replaying from compacted versus full contexts.

Warm-up When should an agent use a sub-agent?

When a sub-task is self-contained, clearly specifiable with done criteria, produces bulky intermediate material (search results, file contents, failed attempts) and a small final result, and can be done without subtle details of the main state. Examples: codebase-wide searches, literature surveys, isolated experiments. Avoid for tightly coupled work, where the handover would lose essential details.

Core Model the effect of verified milestones with retries on long-task success.

Split \(H\) steps into milestones of \(\Lambda\) steps; per-step fatal error \(\epsilon_f\) gives milestone success \(p_m=(1-\epsilon_f)^\Lambda\). A check detects failure with probability \(r_m\), allowing a retry from the checkpoint, up to \(n_r\) attempts: milestone success \(\sum_{i=0}^{n_r-1}p_m((1-p_m)r_m)^i\); task success is that to the power \(H/\Lambda\). At \(\epsilon_f=0.01\), \(\Lambda=20\), \(r_m=0.9\), \(H=200\): 13% without milestones, 61% with one retry, 77% with two. Residual loss is from undetected milestone failures, so check quality is critical.

Core Derive the optimal checkpoint interval for a long agent run.

With checkpoint cost \(C\), Poisson interruptions with mean interval \(M\), and checkpoint interval \(\tau\ll M\): overhead per unit time \(\approx C/\tau+\tau/(2M)\) (checkpoint time plus, per interruption, half an interval of lost work at rate \(1/M\)). Minimising gives \(\tau^*=\sqrt{2CM}\) and overhead \(\sqrt{2C/M}\) (Young, 1974). With \(C=30\) s and \(M=2\) h: about 11 minutes and 9% overhead. The optimum is flat; align it with milestone boundaries, and reduce \(M\)'s complement (interruptions) where possible.

Core What should go in an agent's progress notes for a long task?

The goal verbatim; the plan with milestones and status; decisions taken with brief reasons; findings (facts learned about the codebase or domain); pitfalls and abandoned approaches with why; open questions; and the next step. Keep it structured (fixed sections), concise, updated at each milestone, and readable by a human. Pair it with version-control commits whose messages describe each milestone.

Core How do you make a long run resumable after a crash?

Persist at checkpoints: the plan and notes, committed work, the compacted context, and harness bookkeeping (current milestone, in-flight tool calls). Make side-effecting steps idempotent (keys) or record their completion so replay does not repeat them (durable execution). On restart, rebuild the context from the plan, notes and recent commits, verify the state of the last milestone, and continue. Test resumption deliberately by killing runs.

Core Why can per-step reliability improvements alone not make thousand-step tasks feasible?

Success decays as \((1-\epsilon_f)^H\); for \(H=1{,}000\) even \(\epsilon_f=0.001\) gives only 37%, and per-step rates that low are hard to reach. What changes the scaling is structure: detecting failures at milestones and retrying from checkpoints converts most failures into extra work, so success depends on undetected-failure rates per milestone rather than on raw per-step error over the whole task.

Deep-dive Analyse the cost trade-off of compaction frequency.

Context grows by \(\Delta\) per step from floor \(n_f\) to threshold \(n_c\), giving cycles of \((n_c-n_f)/\Delta\) steps with average context \((n_c+n_f)/2\). Per-step read cost is proportional to the average; per-cycle compaction cost is reading \(n_c\), writing the summary and rebuilding \(n_f\) fresh (cache invalidation). Lower thresholds reduce average context (cheaper reads, less rot) but increase compaction frequency (more summary writes, more fresh rebuilds, more lossy summaries). Total cost per step ≈ \(\kappa_{\text{cache}}(n_c+n_f)/2+\text{(compaction cost)}\Delta/(n_c-n_f)\), minimised at an interior threshold; quality effects (rot vs loss) usually dominate and must be measured.

Deep-dive What failure modes are specific to very long agent runs, and how do you detect them automatically?

Drift (late work solving a different problem), inconsistency (contradicting earlier decisions), loops at milestone level (repeated failures), premature completion, scope creep (editing beyond the plan), budget exhaustion mid-milestone, and degradation after many compactions. Automatic signals: milestone failure counts, compaction frequency, cost per milestone, diff scope versus plan, test pass trends, checks that the goal string in the context matches the original, and periodic judge reviews comparing recent work with the plan. Alert or pause when thresholds are crossed.

Deep-dive Compare continuing in one long context with restarting fresh contexts from notes at each milestone.

One long context (with compaction) keeps implicit details the notes may omit and benefits from caching, but accumulates rot, drift and creeping summaries. Fresh contexts per milestone (rebuilt from plan, notes and commits) bound context size and rot, make each milestone's work reproducible and resumable, and force state to be externalised, but pay ramp-up each time and depend entirely on notes' quality. Long runs increasingly favour the fresh-start pattern for robustness, with good notes and repository state as the carrier, keeping one context within a milestone.

Design Design a harness for an agent that migrates a large codebase overnight.

Before: the agent drafts a plan of milestones (modules or layers) with acceptance criteria (tests, type checks, no old-API imports), which a human approves. Environment: a sandboxed clone with snapshots, CI-equivalent test commands, branch per run. Per milestone: fresh or compacted context rebuilt from PLAN.md, NOTES.md and the last commits; sub-agents for codebase-wide searches; edits; run the milestone's checks; commit on pass with a descriptive message and update notes; on fail, restore and retry up to two times, then mark blocked and continue with independent milestones. Checkpoint at milestones (aligned with Young's interval for the infrastructure). Monitoring: cost, failures, scope, with alerts. Morning: a summary report, the branch with commits per milestone, and a list of blocked items for human attention.

Design How would you design a research agent that works on one question for a day?

Plan sub-questions and a report outline with evidence criteria; maintain a findings store (claim, evidence, source, confidence) and a running notes file; delegate each sub-question to sub-agents that search, read and extract in their own contexts and return structured findings; the main agent integrates, identifies gaps and contradictions, and assigns further sub-tasks; checkpoint after each integration round; compact the main context to the outline, findings summary and open questions; a verification phase checks citations and seeks second sources for key claims; a human reviews the outline at the start and the draft before finalisation.

Design How should a team supervise many long-running agents at once?

A dashboard of runs showing plan progress, milestone pass/fail, cost, elapsed time and alerts; plans approved before starting for high-impact runs; agents pause only at defined decision points, queuing requests for humans; automatic stop rules for runaway cost or repeated failures; summaries and diffs per milestone for asynchronous review; sampling of completed runs for deeper audit; and post-mortems on failed runs feeding improvements to plans, checks and prompts.

Core Why does delegation to sub-agents reduce cost even though it adds tokens?

The main agent's context is carried for many subsequent steps, so every token it holds is paid repeatedly; bulky intermediate results kept there cost (size × remaining steps). A sub-agent's context is discarded after its task, so its bulk is paid only during the sub-task, and the main context carries only the short result. When intermediate material is large and long-lived in the main context, this saving exceeds the sub-agent's own prefix and ramp-up cost.

Core What makes a good milestone check?

It tests the milestone's acceptance criteria against the goal rather than the agent's beliefs (tests that exercise the new behaviour, type checks, absence of old patterns, a critic comparing work with the plan), it is cheap enough to run at every milestone, its false-negative rate on failures is low (detection drives the residual loss), and it produces informative output for the retry. Hidden or independent checks resist the agent optimising against them.

Deep-dive What limits how long agents can work today, and where would you invest to extend it for a given task class?

The fatal (undetected) error rate per step, the verifiability of intermediate states, the harness's management of state across compactions and interruptions, and cost and time. Investment order for a task class: make milestones checkable automatically (biggest effect on success, per the milestone model); externalise state (plans, notes, commits) and make runs resumable; select a model trained for long agentic work, which lowers the error rate and improves self-checking; then optimise cost (caching, delegation, compaction thresholds). Tasks without checkable intermediate states will remain shorter-horizon regardless of model, so for them invest in human review at milestones.

Core How would you test that a long-running agent harness survives interruptions?

Fault injection: kill the harness, recycle sandboxes, fail model calls and time out tools at random points in test runs; then measure resumption success rate, work lost per interruption (compare with half the checkpoint interval), duplicated side effects (must be zero, via idempotency keys or recorded completions), and behavioural divergence of resumed runs from uninterrupted ones (repeated or contradicted work signals incomplete notes). Run these tests continuously, since harness changes easily break resumption.
