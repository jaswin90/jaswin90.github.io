Part V · Many Agents — Chapter 16

Agent Architectures and Frameworks

Every agent system in this book, from a single tool-calling loop to a multi-agent research system, is assembled from a handful of building blocks: chains, routers, parallel branches, loops with evaluators, orchestrators and autonomous agents. This chapter names the blocks, shows how to choose the right amount of autonomy for each part of a system, explains how agent systems are built as explicit graphs with durable state, and assesses what the popular frameworks provide and what they cost.

Why this chapter

Chapter 2 framed workflows and agents as nested policy classes: a fixed sequence of steps, a router that chooses among sequences, and an agent that chooses every step (§2.5). Later chapters added more structure: plan-and-execute (§6.5), evaluator–optimizer loops (§7.8), sub-agents and milestones (Chapter 14), orchestrators with workers (§15.4). A practitioner designing a real system faces these choices not once but at every point in the system: should the support agent's eligibility check be a deterministic workflow or a model's judgement? Should requests be routed to specialised flows or handled by one general agent? Should the research system's sub-questions be fixed by a template or chosen by the lead?

This chapter provides the vocabulary and the engineering for those decisions. We begin with the catalogue of building blocks that practitioners converged on by 2024, then give a method for assigning autonomy component by component, with the arithmetic of routing and chaining. We then show how a system built from these blocks is best represented as an explicit graph of states and transitions, which makes properties such as "no refund without a policy check" checkable, and how such graphs are executed durably, with checkpoints, human interruptions and replay. Finally we survey agent frameworks: what problems they solve, what they hide, and when to use one.

Learning objectives
  1. Name and describe the canonical building blocks: augmented model, prompt chain, router, parallelisation (sectioning and voting), orchestrator–workers, evaluator–optimizer, autonomous agent.
  2. Assign autonomy to each component of a system using variability, feedback and cost of error, and compute the reliability of chains with and without gates.
  3. Analyse routing: overall accuracy as a function of router accuracy, and when specialised flows beat a general agent.
  4. Represent an agent system as a graph with typed state, and use the graph to guarantee safety properties.
  5. Explain durable execution: checkpointed state, human-in-the-loop interrupts and replay.
  6. Evaluate agent frameworks by what they abstract, and decide between a framework and direct implementation.
  7. Test an agent architecture at the levels of nodes, tools, trajectories and properties.

We use the policy classes of §2.5, the evaluator–optimizer of §7.8, tool design (Chapter 8), long-horizon structure (Chapter 14) and multi-agent patterns (Chapter 15).

16.1 A vocabulary of building blocks

In December 2024 Anthropic published a short guide, Building Effective Agents, distilled from work with many teams deploying agent systems[1]. Its most influential contribution was a vocabulary: a small set of composable patterns, ordered by increasing autonomy, from which most successful systems were built. Figure 16.1 draws them, and we use the guide's names throughout.

Figure 16.1 orders the blocks by how much of the control flow the model decides. The foundation of all of them is the augmented model, a language model with retrieval, tools and memory (Chapters 8–13), able to decide within a single call which tools to use. Prompt chaining decomposes a task into a fixed sequence of calls, each consuming the previous one's output, with programmatic gates between them (a schema check, a length check, a policy check): a support reply might be drafted, checked against the policy, then translated. Routing classifies an input and sends it to a specialised flow: refunds to one prompt and tool set, baggage questions to another, unusual requests to a general agent. Parallelisation runs calls simultaneously, either sectioning a task into independent parts or voting over several attempts (§5.4, §15.3). Orchestrator–workers lets a model decide the sub-tasks at run time (§15.4). Evaluator–optimizer loops a generator against an evaluator until the output passes (§7.8). And the autonomous agent lets the model choose every action in a loop with the environment (§1.1).

The guide's central advice, which has held up well, was to use the simplest block that works and add autonomy only when measurement shows a simpler design failing: "the most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns." This is the policy-class argument of §2.5 turned into practice. Every step up the ladder buys flexibility at the price of predictability, cost and testability, and the price is worth paying only where the task's variability demands it.

16.2 Choosing autonomy component by component

A real system is not one block but a composition, and the autonomy decision should be made separately for each component. Chapter 2 identified three properties that favour more autonomy: variability (the right sequence of steps differs between inputs), feedback (the environment reports the consequences of actions, so errors can be caught) and a low cost of error (mistakes are cheap or reversible). Applying them component by component gives architectures in which most steps are fixed and a few are autonomous, which is how successful agent products usually look.

Consider the support agent as a system. Authentication of the customer varies little and errors are costly: a fixed workflow. Classifying the request type varies and is cheap to get wrong if misroutes can be detected: a model-based router. Answering a common question (baggage allowance) is low-variability: a chain with retrieval. Changing a booking varies moderately, has feedback (the booking system validates changes) and is consequential: a constrained agent with read tools, a deterministic quote tool and a guarded write (§8.9). Handling an unusual complaint is high-variability and needs judgement: an autonomous agent with escalation to a human. The policy check before any refund is not a model decision at all: deterministic code. The resulting system is a graph in which the model's autonomy is concentrated where it pays.

Chaining has its own arithmetic. If each of \(k\) stages succeeds with probability \(\rho_s\), a chain succeeds with \(\rho_s^k\), the \(\rho^H\) law of Chapter 1 at the level of stages. Gates between stages change this exactly as detection did in §2.6: a gate that catches a fraction \(r_g\) of stage failures and triggers one retry raises a stage's effective success to \(\rho_s+(1-\rho_s)r_g\rho_s\). Figure 16.2 shows the effect for \(\rho_s=0.95\) and \(r_g=0.8\).

Figure 16.2 is why chains with gates are so effective in practice and why their design deserves care. A gate can be deterministic (does the output parse, does the amount lie within policy, does every cited quote appear in its source?) or a model check (does the draft answer the question?); deterministic gates are cheaper and have known error rates, so they should be used wherever a property can be checked by code. The same arithmetic warns against long ungated chains, which are as fragile as long ungated agent trajectories, and it suggests where to put gates: after the stages with the lowest success rates and before any stage whose errors are expensive to propagate.

Worked example — router plus specialised flows, or one general agent?

A support system receives three request types. Specialised flows (each a chain with gates and the right tools) resolve their type correctly 97% of the time, but a misrouted request (sent to the wrong flow) is resolved only 60% of the time, usually after the flow notices and escalates. A single general agent resolves 88% of all requests.

Overall accuracy with a router of accuracy \(r\). \(0.97r+0.60(1-r)\). At \(r=0.95\): \(0.9215+0.03=0.9515\). At \(r=0.80\): 0.896. At \(r=0.75\): 0.8775, just below the general agent.

Break-even. \(0.97r+0.6(1-r)=0.88\Rightarrow r=0.28/0.37=0.757\). Routing pays if the router is right more than about 76% of the time, which a classifier on clearly distinct request types easily achieves.

Cost. Specialised flows can use a cheaper model and shorter prompts, so the router architecture is usually also cheaper, as long as misroutes are detected rather than silently mishandled.

Figure 16.3 generalises: specialisation pays when the specialised components are much better than the general one on their own inputs and the router is reliable, and it fails when misroutes are frequent or silent. Two design habits make routing robust. Give every specialised flow a way to say "this is not mine" and hand back to the router or a general agent, which turns silent misroutes into detected ones and raises the misrouted resolution rate. And keep a general agent as the destination for anything the router is unsure about, using the router's confidence (§3.6) as the threshold.

16.3 Agents as graphs

As systems grow from one loop into compositions of chains, routers, agents and checks, the question "what can this system do next?" becomes hard to answer by reading prompts. The architectural answer, adopted by frameworks such as LangGraph in 2024, is to make the control flow an explicit graph: nodes are steps (a model call, a tool call, a deterministic function, a sub-agent, a human approval), edges say which step may follow which, some edges are conditional on the state (a model's routing decision, a check's result), and a typed state object carries the data that nodes read and write[2]. An autonomous agent is then a graph with a loop (model node to tool node and back) and a conditional exit; a workflow is a graph without model-chosen edges; and everything in between is expressible.

Figure 16.4 shows the principal benefit of the explicit graph: properties of the system become properties of the graph that can be checked without running it. The safety requirement "no write without a passing policy check" holds if and only if every path from the start node to the write node passes through the policy-check node with policy_ok set, which is a reachability question on a small directed graph. In a single autonomous agent with all tools available, the same requirement depends on the model choosing to call the check, and can only be tested statistically. Making safety-critical sequencing a structural property of the graph, and leaving the model free inside the nodes where its judgement is needed, combines the predictability of workflows with the flexibility of agents.

For the mathematician — an agent graph is a controlled transition system

Let the system's configurations be pairs \((v,\sigma)\) of a node \(v\) in a finite directed graph \(G\) and a state \(\sigma\) of a typed record. Each node is a map \(\sigma\mapsto\sigma'\), deterministic for code nodes and stochastic for model nodes (it samples from \(\pi_\theta\)); each edge \((v,w)\) carries a guard, a predicate on \(\sigma\), and the next node is chosen among out-edges whose guards hold, by code or by a model. Safety properties of the form "every execution reaching \(w\) has previously visited \(u\) with predicate \(\phi\) true" are temporal-logic properties of this transition system. If every model node can only change the fields its type allows, and the guards on edges into \(w\) are deterministic, such properties can be verified on the graph alone, independent of what the models do, because no model output can create an edge that does not exist.

Worked example — a structural guarantee versus a prompted one

In design A, one autonomous agent has the tools check_policy and issue_refund, and its system prompt says to always check the policy before refunding. In design B, the graph of Figure 16.4 makes issue_refund reachable only from the policy-check node.

Design A. Testing on 2,000 conversations finds the agent skips the check in 0.4% of refunds (usually under customer pressure). At 300 refunds a day, about 1.2 unchecked refunds a day, of which perhaps a third are ineligible: about 150 improper refunds a year.

Design B. The check cannot be skipped: the only edge to the write node starts at the check node, and the write node's guard requires policy_ok. Improper refunds now come only from errors in the policy code itself, which can be tested exhaustively against the policy's rules.

Cost. Design B constrains the agent only where the rule applies; everywhere else (understanding the request, choosing alternatives, explaining) the model is as free as in A.

16.4 State, durability and human interruptions

A graph with typed state also solves the durability problems of Chapter 14 at the architectural level. Because all the information that flows between nodes lives in the state object, the runtime can checkpoint the state after every node, keyed by a thread or run identifier. A crashed or paused run resumes by loading the last checkpoint and continuing from the next node, without re-running completed nodes, as in durable execution (§14.7), provided that nodes with side effects record their completion or are idempotent (§8.7). The same mechanism gives three capabilities that are otherwise hard to build. Human-in-the-loop interrupts: a node can pause the run and wait, for minutes or days, for a person to approve, edit the state or provide input, after which execution resumes from the checkpoint; the approval node of Figure 16.4 is implemented this way. Replay and time travel: a developer can load the checkpoint before a bad decision, change the prompt or the state, and re-run from there, which is the most efficient way to debug a long trajectory. And streaming and observability: each node's inputs and outputs are natural units for logs and traces (§15.7). Figure 16.5 shows the life of a run with an interrupt.

Figure 16.5 also shows why state design matters. The state object is the system's sufficient statistic (Chapter 2) in explicit form: whatever is not in it is lost at a checkpoint boundary, and whatever is in it is carried, logged and visible to every later node. A good state schema separates what the model needs to see (messages, findings) from control data (flags such as verified and policy_ok, which only code should set), keeps large artefacts as references rather than inline (a file path, not the file), and is versioned, since a change to the schema must be compatible with runs paused under the old one.

Drill 16.1 — what replay saves

A 60-node research run fails at node 52 because of a bad prompt in the synthesis node. Each node costs on average $0.04 and 9 seconds. How much does fixing the prompt and re-running cost with and without checkpoint replay?

Without replay: the whole run again, \(60\times\$0.04=\$2.40\) and 9 minutes, and different searches may yield a different, non-comparable result. With replay from the checkpoint before node 52: 9 nodes, $0.36 and 81 seconds, on exactly the same inputs, so the effect of the prompt change is isolated. For debugging, the comparability matters more than the saving.

16.5 Frameworks: what they give and what they cost

An ecosystem of agent frameworks grew up between 2023 and 2025, and an engineer will meet several. Early general-purpose libraries, LangChain (from late 2022) and LlamaIndex, offered abstractions for prompts, model providers, retrieval pipelines, tools and memory, and became the default starting point for many applications. Graph and state-machine runtimes, notably LangGraph, provided the explicit graphs, checkpointing and interrupts of §16.3–§16.4. Multi-agent frameworks, AutoGen and CrewAI among them, provided abstractions for agents with roles and conversations among them (Chapter 15). In 2025 the model providers released their own toolkits, OpenAI's Agents SDK and Anthropic's Claude Agent SDK, built on the harnesses behind their own agent products, and Google released its Agent Development Kit; lighter libraries such as Hugging Face's smolagents emphasised minimalism and code actions (Chapter 10).

What frameworks provide is real: integrations with many model providers, tools, vector stores and protocols (MCP, Chapter 12); implementations of the patterns of Figure 16.1; state management, checkpointing and human interrupts; tracing and evaluation hooks; and, in the providers' SDKs, harness features tuned for their models (context compaction, tool-use conventions, sub-agents). For a team without existing infrastructure, these can save weeks.

What frameworks cost is equally real, and the costs fall exactly where this book has argued that quality is decided. Hidden prompts and context: abstractions that assemble prompts, format tool results and manage memory make it hard to see, and therefore to engineer, the context the model actually receives (Chapter 4). Leaky abstractions: when an agent misbehaves, debugging requires understanding the framework's internals as well as the model's behaviour. Lag and churn: model capabilities and provider APIs changed rapidly in 2023–2025, and frameworks sometimes lagged them or changed their own interfaces frequently. Lock-in: state formats and abstractions make it costly to move. Anthropic's guide recommended starting with direct calls to model APIs, many patterns needing only a few lines of code, and using a framework only with an understanding of the code underneath; experienced teams frequently build thin internal harnesses for exactly the reasons above.

A practical decision rule follows. Use direct API calls and a thin harness when the system is a single agent loop or a small composition, when the context must be tightly controlled, or when the team is still discovering what the system should do. Use a graph runtime when the system has many components, long-running or paused runs, human approvals and safety properties that should be structural. Use a provider's agent SDK when building an agent of the kind the provider's own products are (a coding agent, a research agent) and the harness features match. In every case, keep the prompts, tool definitions and state schema in the team's own code, under version control and evaluation, so that the framework is an execution engine rather than the place where the system's behaviour is defined.

16.6 Testing an architecture

A composed system can be tested at four levels, from the cheapest and most precise to the most realistic, and a mature agent project uses all four. Node tests treat each component as a function: given this state, does the router choose the right flow, does the chain produce a valid draft, does the policy node accept and reject the right cases? Code nodes get ordinary unit tests; model nodes get small labelled datasets, run on every change to their prompt or model, since a prompt is code (§3.8). Contract tests check the interfaces between components and with external systems: does each tool accept the arguments its schema declares and return what its description promises, and does each node write only the state fields it is allowed to? Trajectory tests run the whole system on recorded or simulated tasks and check outcomes (the database end state, the final answer) and, where it matters, the path ("the policy node ran before the write"). Golden trajectories, replays of real past interactions with their correct outcomes, catch regressions when anything changes. Property tests check invariants over many generated inputs: no path reaches a write without a check; no output contains another customer's data; the system terminates within the step budget. For graphs, some properties can be checked statically, as §16.3 showed; the rest are checked by running many randomised episodes, including adversarial ones (injection attempts, abusive users, malformed tool outputs).

Two practices make this sustainable. Make model nodes replaceable by recorded outputs, so that trajectory tests of the surrounding logic are deterministic and cheap, and run the expensive end-to-end tests with live models on a schedule rather than on every commit. And track each node's measured quality over time (router accuracy, chain pass rates, gate catch rates), since the reliability arithmetic of §16.2 lets a change in one node's quality be translated into its effect on the whole system before deployment. Chapter 19 develops the statistics of agent evaluation that these tests rely on.

Drill 16.2 — where to put the gate

A five-stage chain has stage success rates 0.99, 0.90, 0.98, 0.95, 0.99. You can afford one gate (catching 80% of its stage's failures and retrying once). Which stage should it follow, and what is the chain's success before and after?

Before: \(0.99\times0.90\times0.98\times0.95\times0.99=0.821\). A gate on stage \(s\) raises its success to \(\rho_s+0.8(1-\rho_s)\rho_s\): stage 2 becomes \(0.90+0.8\times0.1\times0.9=0.972\), multiplying the chain by \(0.972/0.90=1.08\), to 0.887; stage 4 would become \(0.95+0.8\times0.05\times0.95=0.988\), a factor 1.04, to 0.854. Put the gate after the weakest stage: stage 2.

16.7 Event-driven and background agents

The architectures so far began with a person typing a request. A growing share of agent work is triggered instead by events: a new issue is filed and a coding agent proposes a fix; an email arrives and an assistant triages it; a monitoring alert fires and an agent gathers diagnostics; a nightly schedule starts a report. Such agents run in the background, without a person waiting, and they turn the agent graph into one stage of a larger asynchronous pipeline, drawn in Figure 16.6. Event-driven operation introduces three engineering concerns that interactive agents can ignore.

Figure 16.6's first concern is capacity: how many agent runs must be in flight at once, and therefore how many sandboxes, model-rate-limit headroom and budget the system needs. The answer comes from a result of queueing theory that holds under very general conditions[3].

For the mathematician — Little's law

For any stable system in which items arrive, spend some time and leave, the long-run average number of items in the system \(\bar n\) equals the arrival rate \(\lambda\) times the average time each spends in it \(W\): \(\bar n=\lambda W\). The law needs no assumptions about the distributions of arrivals or durations, only stationarity, which is why it is the first tool for sizing any service. For agents: if issues arrive at \(\lambda\) per hour and each agent run takes \(W\) hours, \(\lambda W\) runs are in progress on average; peaks are higher, so capacity is set with headroom above the mean.

Applied to the running examples, Little's law gives quick, useful numbers. A repository that receives 120 issues a day, each handled by a six-minute coding-agent run, has on average \(120/1{,}440\times6=0.5\) runs in flight: a single worker suffices. An airline whose support agent handles 50 new conversations a minute, each lasting four minutes, has \(50\times4=200\) concurrent conversations, each holding a context and possibly a sandbox, and the model provider's rate limits must accommodate the corresponding tokens per minute. A research service that receives 30 requests an hour, each taking 20 minutes, needs 10 concurrent runs, and if each run spawns 8 workers (Chapter 15), 80 concurrent agent contexts.

The second concern is delivery semantics. Event systems usually guarantee that each event is delivered at least once, because guaranteeing exactly once is expensive; a webhook may be retried if the receiver was slow to acknowledge it. An agent triggered twice by the same issue would open two pull requests. The remedies are those of §8.7 applied to whole runs: deduplicate events by their identifier at the queue, make each run's outputs idempotent (look for an existing pull request for this issue before opening one), and record run completion durably. The third concern is backpressure and cost control. A burst of events (a monitoring storm, a spam wave) can launch hundreds of runs and a matching bill; queues should rate-limit, prioritise and drop or merge redundant events (one diagnosis run per incident, not per alert), and budgets should be enforced per source as well as per run.

Worked example — sizing a triage pipeline

An email-triage agent receives on average 600 emails an hour, with peaks of three times the mean. Each triage run takes 20 seconds (a classification, a summary, a draft reply for some) and uses about 6,000 input and 400 output tokens.

Concurrency. Mean: \(600/3{,}600\times20=3.3\) runs in flight; peak about 10. Provision 12 workers.

Throughput of tokens. At peak, 1,800 emails an hour, 30 a minute: \(30\times6{,}400=192{,}000\) tokens a minute, which must fit within the provider's rate limits with headroom.

Cost. Per email \(0.006\times\$3+0.0004\times\$15=\$0.024\) on the frontier model; on the small model, \(0.006\times\$0.25+0.0004\times\$1.25=\$0.002\). At 600 an hour around the clock: about $346 a day on the frontier model, $29 on the small one, which motivates the per-node model choice of §16.8.

16.8 Choosing a model for each node

Once a system is a graph, the model becomes a per-node decision rather than a global one, and this is one of the largest cost levers available. Nodes differ in difficulty and in the cost of their errors. A router classifying requests into clear categories, an extractor pulling fields from a document, a summariser condensing a tool output: these are routine and a small model handles them well. A planner decomposing an open research question, an agent diagnosing an unfamiliar bug, a judge deciding a disputed refund: these benefit from the strongest model and, often, from reasoning (Chapter 5). Assigning models by node concentrates expensive capability where it changes outcomes.

The decision for each node follows the cascade logic of §3.7. Measure each candidate model's accuracy on the node's own labelled data; estimate the cost of the node's errors (including their propagation, which the chain arithmetic of §16.2 quantifies); and choose the cheapest model whose accuracy is within a tolerance of the best, or use a cascade (small model first, escalating on low confidence) where the small model's confidence is informative. In practice, systems that start with one frontier model everywhere and then move routine nodes to smaller models commonly cut model costs by large factors with little loss of quality, because most tokens flow through routine nodes. The reverse adjustment matters too: a node where errors are costly and rare (the eligibility decision in the support graph) may deserve a stronger model, a reasoning budget, or a vote of several models (§15.3), even if the rest of the system runs on small ones.

Drill 16.4 — per-node models in the support graph

Per conversation, the support graph spends tokens as follows: router 3,000 in / 20 out; FAQ or change flow 40,000 in / 1,500 out; policy-explanation node 8,000 in / 300 out. Compute the model cost per conversation with the frontier model everywhere, and with the small model for the router and the flow but the frontier model for the policy node.

Frontier everywhere: inputs 51,000 tokens ($0.153), outputs 1,820 ($0.0273): about $0.18. Mixed: router and flow on the small model, \(43{,}000\times\$0.25/\text{M}+1{,}520\times\$1.25/\text{M}=\$0.0108+\$0.0019=\$0.0127\); policy node on the frontier model, \(8{,}000\times\$3/\text{M}+300\times\$15/\text{M}=\$0.024+\$0.0045=\$0.0285\); total about $0.041, a quarter of the original, provided the small model's accuracy on the router and the flow has been verified.

Drill 16.3 — the value of a "not mine" exit

In the routing worked example, misrouted requests are resolved 60% of the time. Suppose each specialised flow is given a way to detect that a request is not its type (catching 70% of misroutes) and hand it to the general agent (88%). What is the new resolution rate of misrouted requests, and the overall accuracy at router accuracy 0.85?

Misrouted: \(0.7\times0.88+0.3\times0.60=0.616+0.18=0.796\). Overall at \(r=0.85\): \(0.85\times0.97+0.15\times0.796=0.8245+0.1194=0.944\), against 0.9145 without the exit. Turning silent misroutes into detected ones is worth three points here, and lowers the router accuracy at which routing pays from 0.76 to about 0.48.

Architectural anti-patterns

Experience with deployed systems has produced a short list of designs that repeatedly disappoint, each the violation of a principle from this chapter. The everything agent: one autonomous loop with dozens of tools and a long system prompt for every case, which dilutes tool selection (§8.8), makes safety depend on prompting (§16.3) and resists testing. The ungated chain: a long pipeline of model calls with no checks between them, whose reliability decays as \(\rho_s^k\) (Figure 16.2). The silent router: specialised flows with no way to hand back a misrouted request, so that routing errors become wrong answers instead of detours. Persona theatre: many role-playing agents chatting where one agent following a procedure would do (§15.5). State in the prompt: control decisions (has the customer been verified? has the policy passed?) recorded only as text in the conversation, where a model can misread or be persuaded about them, rather than as typed flags that only code sets. And framework first: adopting a large framework before knowing what the system must do, then fighting its abstractions to see and shape the context. Each has a direct remedy in the preceding sections, and checking a design against the list is a useful review step before building.

16.10 From prototype to production

Most agent systems begin as a prototype: a notebook or a script, one model, a long prompt, a few tools, and a demonstration that works on the examples its author tried. The distance from there to a dependable system is large, and teams that try to cross it in one step usually rebuild. An incremental path, in which each stage adds the structure the next one needs, is cheaper, and it maps onto the chapters of this book.

Stage 1: a measured prototype. Before improving anything, collect fifty to a hundred real tasks with a definition of success and run the prototype on them (Chapter 19). The number will be lower than the demonstration suggested, and the error analysis of §19.8 will say why. Stage 2: the right skeleton. Using the failure taxonomy, decide which parts should be fixed workflow, which routed, which autonomous (§16.2), and move policy rules from the prompt into code. Stage 3: tools and context. Reshape the tools and their outputs (§8.5, §8.10), make the context cache-friendly (§4.6), and add retrieval or memory only where failures show missing knowledge. Stage 4: instrumentation and gates. Add tracing, a regression suite with a release gate, guardrails and budgets (Chapter 21), so that every later change is measured. Stage 5: scale and optimise. Only now add routing, cascades, distillation or training (Chapters 17–18, §21.3), where traces show the cost and the evaluation can confirm quality.

The anti-patterns are the stages taken out of order. Framework first: adopting an elaborate framework before the problem's shape is known locks in abstractions that may not fit (§16.5). Prompt sprawl: fixing each observed failure with another paragraph of instructions, until the prompt is long, contradictory and impossible to test; failures that recur should become code, tools or examples. Agents everywhere: giving the model autonomy over steps that never vary, paying in cost and reliability for flexibility no one uses. Optimising unmeasured: adding multi-agent structure, reflection or fine-tuning before an evaluation exists, so that no one can tell whether it helped. And invisible state: keeping essential state only in the model's context, where it cannot be inspected, checkpointed or recovered (§16.4). Each is a shortcut that saves a day and costs a month, and each is avoided by the order above: measure, structure, then optimise.

The stages also give a vocabulary for reviewing a system someone else built. Ask which stage it is in: is there an evaluation set, and what does it say; which policies live in code and which in prompts; what do the traces show about cost and failures; what gate does a change pass before it ships. A system with impressive components and no answer to these questions is a prototype, whatever its size, and the next step for it is stage 1, not another component.

Looking ahead

Parts I to V built agents by composing a fixed model with context, tools, memory, structure and other agents. Everything the agent knows how to do came either from the model's training or from what we put in its context. That leaves the most powerful lever unused: changing the model itself so that it becomes a better agent. Can an agent learn from demonstrations of good behaviour, from people's preferences between its attempts, and from the outcomes of its own trajectories? How do supervised fine-tuning on trajectories, reinforcement learning from human feedback and direct preference optimisation work, and when is training worth its cost compared with better prompting? Part VI begins with learning from demonstrations and preferences in Chapter 17.

Chapter summary

  • Building blocks, by increasing autonomy: augmented model, prompt chaining with gates, routing, parallelisation (sectioning, voting), orchestrator–workers, evaluator–optimizer, autonomous agent. Use the simplest that works; compose them.
  • Assign autonomy per component by variability, feedback and cost of error: deterministic code for rules and writes, chains for routine flows, agents where steps vary and feedback exists.
  • Chains succeed as \(\rho_s^k\); gates catching \(r_g\) of failures with a retry raise stages to \(\rho_s+(1-\rho_s)r_g\rho_s\); put gates after the weakest stages.
  • Routing to specialised flows beats a general agent when the router is accurate enough (\(0.97r+0.6(1-r)>0.88\Rightarrow r>0.76\) in the example); "not mine" exits make misroutes detectable.
  • Explicit graphs with typed state make control flow inspectable and safety properties structural (every write path passes the policy check), verifiable without running the models.
  • Durable execution checkpoints state per node, enabling resumption, human-in-the-loop interrupts, replay and observability; design the state schema as the system's explicit sufficient statistic.
  • Frameworks provide integrations, patterns, state and tracing, at the cost of hidden context, leaky abstractions, churn and lock-in. Keep prompts, tools and state schemas in your own code; start simple.
  • Event-driven agents need capacity sized by Little\'s law \(\bar n=\lambda W\), deduplication and idempotent runs for at-least-once delivery, and backpressure and per-source budgets.
  • Choose the model per node: small models for routine nodes, strong models or votes where errors are costly; most tokens flow through routine nodes.
  • Test at four levels: nodes, contracts, trajectories (golden replays), properties (static and randomised).
  • Move from prototype to production in order: measure on real tasks, fix the skeleton and move policy into code, shape tools and context, instrument and gate, and only then optimise; avoid framework-first, prompt sprawl, agents everywhere, unmeasured optimisation and invisible state.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up Name the common building blocks of agent systems.

The augmented model (LLM with retrieval, tools and memory); prompt chaining (fixed steps with gates); routing (classify and dispatch to specialised flows); parallelisation (sectioning and voting); orchestrator–workers (model-chosen sub-tasks); evaluator–optimizer (generate, evaluate, revise loop); and autonomous agents (model chooses every step). Real systems compose them, using the least autonomy that works at each point.

Warm-up When would you use a fixed workflow instead of an agent?

When the steps are predictable, errors are costly or irreversible, rules are known, and testability, latency and cost matter: e.g. authentication, policy checks, data extraction pipelines. Use agents where the right steps vary by input and the environment gives feedback. Most systems mix: workflows for the skeleton, agents in the nodes that need judgement.

Warm-up Should you use an agent framework?

It depends on the system. Frameworks give integrations, patterns, state, checkpointing and tracing, but can hide the context the model sees, leak abstractions when debugging, change quickly and lock you in. Start with direct API calls and a thin harness for small systems; adopt a graph runtime for complex, long-running systems with approvals and structural safety needs; consider a provider SDK for agents like the provider's products. Keep prompts, tools and state schemas in your own code.

Core Compute the reliability of a prompt chain and show how gates help.

A chain of \(k\) stages with success \(\rho_s\) succeeds with \(\rho_s^k\): ten 95% stages give 60%. A gate catching a fraction \(r_g\) of a stage's failures with one retry raises that stage to \(\rho_s+(1-\rho_s)r_g\rho_s\): 0.988 for \(\rho_s=0.95,r_g=0.8\), so ten gated stages give 89%. Place gates after the weakest or most consequential stages; prefer deterministic gates (schema, policy, citation checks) for known error rates.

Core When does routing to specialised flows beat a single general agent?

When \(r\,a_{\text{spec}}+(1-r)a_{\text{mis}}>a_{\text{gen}}\), where \(r\) is router accuracy, \(a_{\text{spec}}\) the specialised flows' accuracy on their own inputs, \(a_{\text{mis}}\) the resolution rate of misrouted requests and \(a_{\text{gen}}\) the general agent's. With 97%, 60% and 88%, routing pays above \(r\approx0.76\). Adding "not mine" exits to the general agent raises \(a_{\text{mis}}\) and lowers the threshold; routing uncertain cases (low router confidence) to the general agent helps too. Specialised flows are often also cheaper.

Core Why represent an agent system as an explicit graph?

It makes control flow inspectable and safety properties structural: if every edge into a write node comes from a policy-check node guarded by a code-set flag, no model output can bypass it, which can be verified by reachability on the graph rather than tested statistically. Graphs also give a natural unit for checkpointing, interrupts, tracing and testing, and they let model autonomy be concentrated inside specific nodes.

Core Explain durable execution for agent graphs.

The runtime persists the typed state after each node, keyed by run. On crash or pause it resumes from the last checkpoint without re-running completed nodes (side-effecting nodes must be idempotent or recorded). Interrupts let nodes wait for human approval or input for long periods without holding resources. Checkpoints enable replay from any point for debugging and provide a per-node trace. State schema design matters: separate model-visible data from control flags, store references for large artefacts, version the schema.

Core How do you test an agent system?

Node tests (unit tests for code nodes; labelled datasets for model nodes, re-run on prompt or model changes), contract tests (tool schemas and behaviours, allowed state writes), trajectory tests (golden replays of real interactions, simulated users and environments, outcome and path checks), and property tests (invariants over randomised and adversarial episodes, or static graph checks). Replace model nodes with recorded outputs for deterministic logic tests; run live end-to-end evaluations on a schedule; track per-node quality metrics over time.

Deep-dive Formalise when a safety property of an agent system can be verified without reasoning about the model.

Model the system as a transition system over (node, state) with guarded edges; model nodes are stochastic maps restricted to writing certain state fields; guards are predicates. A property "every path to node \(w\) passes node \(u\) with \(\phi\) true" can be verified on the graph if (a) all edges into \(w\) are guarded by predicates implying \(\phi\) was established at \(u\), (b) the fields \(\phi\) depends on are writable only by code nodes (notably \(u\)), and (c) no model node can create edges or invoke tools outside its node's allowed set. Then for any model behaviour the property holds. Where model nodes have tools that act directly, the property depends on the model and needs statistical testing.

Deep-dive How do you decide the granularity of nodes in an agent graph?

A node should be a unit of work with a clear input and output in the state, a natural checkpoint, a meaningful test, and a single responsibility (one model decision, one tool action, one check). Too coarse (one giant agent node) loses structural guarantees and observability; too fine (a node per token-level decision) adds overhead and makes the graph rigid. Place node boundaries where you want a gate, an approval, a checkpoint or a change of model or permissions, and keep free-form agent loops inside nodes where variability is high.

Deep-dive What are the risks of hidden context in frameworks, and how do you mitigate them?

Frameworks may inject their own system prompts, format tool results verbosely, append memory automatically, reorder messages or change templates across versions, so the model sees a context the team did not design and cannot easily inspect; caching may break, costs rise, and behaviour shifts with framework upgrades. Mitigations: log the exact request sent to the model for every call; pin framework versions; override or own prompt templates; test with golden trajectories on upgrades; and prefer frameworks that expose the raw context.

Design Architect the airline support system end to end.

Graph: start → authentication (code) → router (small model, confidence threshold) → FAQ chain (retrieval + citation gate) / change agent (read tools, deterministic quote tool) / refund flow / general agent with escalation; every write path → policy check (code) → approval above threshold (human interrupt) → idempotent write → read-back → reply. Typed state with code-only control flags; checkpoints per node; per-node tracing. Specialised flows have "not mine" exits. Tests: node datasets, tool contracts, golden conversations, adversarial property tests (injection, pressure for exceptions). Metrics: resolution rate per type, router accuracy, gate catch rates, escalations, cost and latency per conversation.

Design A team built everything as one autonomous agent with 40 tools. Performance is erratic. How would you re-architect?

Mine logs for task types and their tool sequences. Extract deterministic parts (validation, policy, computations) into code nodes. Add a router for clearly distinct task types with specialised flows using small tool sets (raising selection accuracy, §8.8). Keep a general agent for the long tail. Make safety-critical sequencing structural in a graph. Add gates after weak steps. Introduce typed state and checkpoints. Measure each component and the whole on a fixed evaluation set before and after, aiming for higher reliability and lower cost without loss of coverage.

Design How would you design the state schema for a durable research-agent graph?

Fields: question (verbatim), plan (sub-questions with status and assigned worker), findings (references to stored claim–evidence records with source URLs and confidence), open questions, budget counters (tokens, time, rounds), control flags (plan_approved, citations_verified) writable only by code or humans, draft report reference, and message history for the lead (bounded). Large artefacts (pages, drafts) stored externally by reference. Versioned schema with migrations for paused runs. This makes the run resumable, inspectable and testable.

Core What is the evaluator–optimizer pattern and when does it fit?

A generator produces an output and an evaluator gives feedback in a loop until the output passes or a round limit is reached. It fits when evaluation criteria are clear and checking is easier than generating (code with tests, translations with explicit requirements, citations against sources), and iterative refinement measurably helps. Its value depends on the evaluator's reliability (Chapter 7); bound rounds and revise only on specific flags.

Core Where should gates go in an agent architecture?

After stages with the lowest success rates, before stages whose errors are expensive to propagate or irreversible (writes, external messages), and at boundaries between components (handovers). Prefer deterministic gates where properties can be checked by code; use model or human checks where they cannot. Each gate should produce an actionable error for retry.

Core How would you size the infrastructure for an event-triggered agent?

Use Little's law: average runs in flight \(=\) arrival rate \(\times\) average run duration, then add headroom for peaks (e.g. three times the mean). From concurrency derive sandboxes, workers and the tokens per minute the model provider must allow. Add deduplication by event ID (at-least-once delivery), idempotent outputs (check for an existing PR before opening one), rate limiting and prioritisation in the queue, merging of redundant events, and per-source and per-run budgets.

Core How do you choose which model to use at each node of an agent system?

Measure candidate models on each node's labelled data; estimate the cost of the node's errors including propagation; pick the cheapest model within tolerance of the best, or a cascade where the small model's confidence is informative. Routine nodes (routing, extraction, summarisation) usually go to small models, which carry most tokens; consequential, rare decisions get the strongest model, a reasoning budget or a diverse vote. Re-measure when models change.
