Part VII · Reliability, Safety and Production — Chapter 21

Agents in Production

A working agent is not yet a product. Production adds a budget, a latency target, thousands of concurrent users, a need to see what each run did, and the obligation to keep working as models, tools and traffic change. This chapter gives the quantitative models of production operation: the cost and latency of an agent task, routing and cascades between models, caching, observability and tracing, guardrails, the economics of human review, and safe change over time.

Why this chapter

The previous chapters built an agent that works, measured how well (Chapter 19) and made it hard to subvert (Chapter 20). Each of them used cost and latency as constraints, from the price of a call (§3.7) and the economics of caching (§4.6) to the break-even of distillation (§17.8). This chapter makes them the subject. A product manager deciding whether an agent can replace a workflow asks quantitative questions: what does a resolved task cost, including the failures and the people who handle them? How long does a user wait? What happens to cost when the agent takes twice as many steps? Which requests can go to a cheaper model? And when something goes wrong for one user among thousands, how do we find out what happened?

The answers come from a handful of models that the reader can build in a spreadsheet. The cost of a task grows quadratically with its length unless the context is cached, and caching makes it nearly linear. Latency is dominated by decoding and by tools, not by prefill. A cascade from a small model to a large one is worth it when the small model knows when it does not know. Human review has an optimal level, set by the cost of an error, the cost of a review and how well the agent ranks its own uncertainty. And every one of these numbers drifts, so production is a loop of measurement and adjustment rather than a configuration.

Learning objectives
  1. Compute the cost of a multi-turn agent task with and without prompt caching, and the cost per successful task including failures and escalations.
  2. Decompose agent latency into prefill, decode and tool time, and reduce it with streaming, parallelism and model choice.
  3. Design routing and cascades between models, and compute when a cascade pays.
  4. Use caching at several levels (prompt, tool result, semantic) and reason about their risks.
  5. Instrument an agent with traces and spans, and use traces for debugging, cost attribution and online evaluation.
  6. Place guardrails and human review, and find the automation level that minimises total cost.
  7. Roll out changes to models, prompts and tools safely, with shadow traffic, canaries and regression gates.

We use the reference prices and speeds (Chapter 1), the cost of a call (§3.7), prompt caching (§4.6), the episode cost model (§2.8), permissions and approvals (§8.9), Little's law (§16.7), evaluation (Chapter 19) and guardrails as security layers (§20.5).

21.1 The economics of an agent task

A single model call is priced by its tokens: input at \(\kappa_{\text{in}}\), output at \(\kappa_{\text{out}}\), cached input at \(\kappa_{\text{cache}}\) (§3.7). An agent task is a sequence of calls in which the context grows: each turn appends the model's output and the tool's observation, and the next call re-reads everything. Let the fixed prefix (system prompt and tool definitions) be \(n_0\) tokens, let each turn add \(\Delta n\) tokens (output plus observation), and let the model write \(n_{\text{out}}\) tokens per turn. The call at turn \(t\) reads about \(n_0+t\,\Delta n\) input tokens, so an episode of \(H\) turns reads

\[ N_{\text{in}}(H)=\sum_{t=1}^{H}\big(n_0+t\,\Delta n\big)=Hn_0+\Delta n\,\frac{H(H+1)}{2}\ \text{input tokens}, \]

which is quadratic in \(H\): doubling the length of a task roughly quadruples its input cost. Prompt caching changes the picture. With a cached prefix, each call pays the full input price only for the tokens that are new since the previous call, about \(\Delta n\), and the cached price for the rest. The uncached input over the episode is then about \(n_0+H\Delta n\), linear in \(H\), and the quadratic term is paid at \(\kappa_{\text{cache}}\), a tenth of the input price in the reference setting. Figure 21.1 shows the two cost curves for the support agent.

Figure 21.1 has two lessons beyond "cache everything". First, the slope: even with caching, cost grows faster than linearly at long horizons, because the cached quadratic term eventually dominates; at 80 turns the cached reads are over half the bill. Long tasks therefore need context management (compaction, sub-agents, external state, Chapter 14) for cost reasons as well as quality ones. Second, the order of magnitude: a 20-turn task on a frontier model costs tens of cents, which is cheap compared with a person's time and expensive compared with a web request. Whether an agent is economical depends less on the per-task cost than on what a task's outcome is worth.

The cost that matters is therefore the cost per successful outcome, with failures priced in. If a task costs \(C\) in model and tool calls, succeeds with probability \(p\), and a failure costs \(F\) to handle (a person resolves the conversation, an engineer redoes the fix, a customer churns), then the expected cost per task is \(C+(1-p)F\), and the expected cost per successful agent outcome is \(C/p\) if failures are simply retried by the agent. The value of an outcome \(U\) (Chapter 2's value of success) sets the ceiling: the agent is worth deploying where \(pU-C-(1-p)F\) exceeds the same quantity for the alternative, which is usually a person or a simpler system.

Worked example — what a resolved support conversation costs

A support conversation averages 20 turns with the parameters of Figure 21.1; on the frontier model with caching it costs $0.31 in tokens, plus $0.02 in tool and infrastructure costs. The agent resolves 70% of conversations; the rest escalate to a person at $4 each. A fully human service costs $5 per conversation.

Expected cost per conversation. \(0.33+0.30\times4=\$1.53\), against $5 for the human service: a saving of $3.47 per conversation.

Without caching. \(1.335+0.02+1.20=\$2.56\): still a saving, but $1.03 of it was lost to not caching.

Sensitivity to resolution. Each point of resolution is worth \(0.01\times\$4=\$0.04\) per conversation, an eighth of the token cost. A change that raises resolution from 70% to 75% at the cost of doubling the tokens (\(0.33\to0.66\)) changes the total to \(0.66+0.25\times4=\$1.66\): slightly worse. A change that raises it to 80% at the same doubling gives \(0.66+0.8=\$1.46\): slightly better. The escalation cost, not the token cost, dominates the economics, which is why the quality of the agent usually matters more than its price.

Where the money goes within a task is the other half of the economics, and it is rarely where teams expect. A trace of the support agent (§21.5) might show 45% of token cost in cached reads of the growing history, 30% in output tokens (of which a third is reasoning the user never sees), 15% in uncached new input (mostly tool outputs, some of them long JSON payloads), and 10% in the initial prefix. Each points to a different lever: compaction for the history, a reasoning budget or a smaller model for the output (§5.7), trimming tool outputs to what the model needs (§8.5), and a shorter system prompt. Cost attribution of this kind requires the per-call token accounting that tracing provides, and it is the first thing to build after the agent itself.

21.2 Latency

Users wait for agents, and how long they wait shapes what the agent can be used for: a support agent that takes two minutes per reply is not a chat agent, and a coding agent that takes forty minutes per task is a background worker, not a pair programmer. The latency of one turn has three parts: prefill, the time to process the new input tokens (cached tokens are nearly free); decode, the time to generate the output; and tool time, the time the tool takes to respond. With prefill speed \(v_{\text{pre}}\), decode speed \(v_{\text{dec}}\) and tool latency \(\ell_{\text{tool}}\), a turn takes about

\[ \ell_{\text{turn}}\approx\frac{\Delta n}{v_{\text{pre}}}+\frac{n_{\text{out}}}{v_{\text{dec}}}+\ell_{\text{tool}}, \]

and an episode about \(H\ell_{\text{turn}}\) plus queueing. In the reference setting (\(v_{\text{pre}}=5{,}000\), \(v_{\text{dec}}=60\) tokens per second), a turn with 1,500 new input tokens, 300 output tokens and a one-second tool call takes \(0.3+5+1=6.3\) seconds, and decode is 80% of it. This is the general pattern: for agents with cached contexts, decode dominates, so the levers are fewer output tokens (concise reasoning, compact tool-call formats), faster decoding (smaller models, which decode two to three times faster in the reference setting), and parallel tool calls (§8.6), which overlap tool time.

Perceived latency differs from total latency, and most of the user-facing work is on the former. Streaming shows tokens as they are generated, so the user sees progress after the time to first token rather than after the whole turn. Progress reporting for multi-step tasks ("searching the booking system", "running the tests") makes waiting tolerable, and a short acknowledgement before a long tool call does the same. Asynchrony changes the contract: a coding agent that opens a pull request and notifies the user when it is done is judged on the quality of the result, not the minutes it took. Choosing the contract (interactive, streaming, or asynchronous with notification) is a product decision that the latency model informs.

Tail latency matters more for agents than for single calls, because an episode is a sum of many turns and a single slow tool call or a long reasoning burst sets the user's experience. If turn latencies are independent with mean \(\mu\) and standard deviation \(\sigma\), an episode of \(H\) turns has mean \(H\mu\) and standard deviation \(\sqrt H\sigma\), so relative variability falls with length; but real tails are heavier than this, driven by occasional slow tools, retries (§8.7) and rate-limit back-offs, and the 95th-percentile episode is often two or three times the median. Timeouts on tools, bounded retries and a hard limit on turns cap the tail, at the cost of turning some slow successes into failures.

Drill 21.1 — making the support agent feel fast

A support turn has 1,500 new input tokens, 300 output tokens (of which 200 are reasoning), and a one-second tool call. Compute the turn latency on the frontier model, then with (a) reasoning cut to 50 tokens, (b) the small model (\(v_{\text{dec}}=150\)) with the original output, (c) both.

Frontier: \(0.3+300/60+1=6.3\) s. (a) 150 output tokens: \(0.3+2.5+1=3.8\) s. (b) \(0.3+300/150+1=3.3\) s (small-model prefill is at least as fast). (c) \(0.3+1+1=2.3\) s. Streaming the visible 100 tokens of the reply makes the perceived wait shorter still, since the user starts reading after the reasoning and the tool call: about 1.3 s plus the time to first token in case (c). Whether (b) and (c) are acceptable depends on the small model's resolution rate, which brings in the economics of §21.1 and the routing of §21.3.

21.3 Routing and cascades

Requests differ in difficulty, and models differ in price by an order of magnitude: in the reference setting the small model costs a twelfth of the frontier model per token. Sending every request to the frontier model overpays for the easy ones; sending every request to the small model underserves the hard ones. Two architectures, shown in Figure 21.2, exploit the difference. A router classifies each request up front and sends it to one model. A cascade sends every request to the cheap model first and escalates to the expensive one only when the cheap model's answer fails a check: low confidence, a failed verifier, a refusal, a malformed output.

The arithmetic of a cascade is simple. If the small model costs \(c_s\) per request, the large model \(c_l\), and the check accepts a fraction \(a\) of the small model's outputs, the expected cost is \(c_s+(1-a)c_l\). It is below the cost of always using the large model when \(a>c_s/c_l\), which for a twelve-fold price ratio means accepting more than 8% of requests: almost always satisfied. Quality is the binding constraint. The cascade's quality is the small model's quality on accepted requests plus the large model's on escalated ones, so it matches the large model only if the check accepts mostly requests the small model got right. The cascade is exactly as good as its check, and a confidence signal that does not separate right from wrong answers (§3.6 on calibration) makes the cascade a cheaper, worse system.

The idea was developed for single calls before agents. FrugalGPT (Chen, Zaharia and Zou, 2023) learned cascades over several commercial models with a scorer deciding when to stop, and reported matching the best model's accuracy on several tasks at a fraction of its cost[1]. RouteLLM (Ong and colleagues, 2024) trained routers on human preference data to decide between a strong and a weak model, and reported large cost reductions at most of the strong model's quality[2]. For agents, routing can happen at three levels: per task (the whole conversation goes to one model, decided from the first message), per node of the architecture (§16.8: routine steps such as extraction and summarisation always go to the small model), and per turn (escalate a turn when the small model's tool call fails validation). Per-node routing is the most common in practice because it is the easiest to measure and the least likely to surprise.

Worked example — a cascade for the support agent

On the support agent, the small model costs about $0.026 per conversation (a twelfth of $0.31) and the frontier $0.31; escalation to a person costs $4. After the first turn, the small model's confidence check accepts 65% of conversations. On those, the small model resolves 85% (the frontier would resolve 88%). The frontier resolves 70% overall, so on the other 35% it resolves \((0.70-0.65\times0.88)/0.35=36.6\%\).

Resolution. Cascade: \(0.65\times0.85+0.35\times0.366=68.0\%\), against 70% for the frontier alone.

Token cost. \(0.65\times0.026+0.35\times(0.005+0.31)=\$0.127\) per conversation (the $0.005 is the small model's first turn on escalated conversations), against $0.31.

Total. Cascade: \(0.127+0.02+0.320\times4=\$1.42\). Frontier: \(0.31+0.02+0.30\times4=\$1.53\). The cascade saves $0.18 in tokens and loses $0.08 in extra escalations: a net $0.10 per conversation, 7%.

What decides it. If the check were worse, so that the small model resolved only 78% of the conversations it accepted, the cascade's resolution would fall to 63.5% and its total to $1.61, worse than the frontier alone. Measure the check's precision on held-out conversations before routing traffic through it.

Routing has costs that the example omits. Two models mean two sets of prompts to maintain, two behaviours to evaluate and two failure profiles to monitor, and the small model's errors may be different in kind (more policy violations, say) rather than just more frequent, which a resolution rate does not show. Routers drift as traffic changes. And a cascade's escalated requests are the slowest, since they pay for the small model's attempt before the large model starts, which matters for latency targets on hard requests. The general advice of §16.8 applies: start with one strong model, measure, and introduce routing where traces show a large, stable class of easy requests.

21.4 Caching

Caching is the oldest performance technique in computing, and an agent offers several places to apply it, each with a different risk.

Prompt-prefix caching (§4.6) is the one every agent should use, and it has no correctness risk, because the provider caches the computation of an identical prefix and the output is unaffected. Its effectiveness depends on discipline in how contexts are built: put stable content (system prompt, tool definitions, long documents) first and volatile content last; append to the history rather than editing it; serialise tool definitions and structured data deterministically (sorted keys, fixed formatting), since a single changed byte early in the prompt invalidates everything after it; and keep timestamps and per-request identifiers out of the prefix. A trace-level metric, the fraction of input tokens served from cache, should be monitored, because a small change to a prompt template can silently drop it from 90% to zero and multiply costs by five.

Tool-result caching stores the outputs of tool calls keyed by their arguments, so that repeated calls, common when an agent re-reads a file or re-runs a search, cost nothing. It is safe for pure, read-only tools within a short time-to-live, and unsafe for anything with side effects or rapidly changing data: a cached flight availability that is ten minutes old can be wrong. The rule from §8.7 applies: cache reads, never writes, and make the staleness bound explicit per tool.

Semantic caching stores whole responses keyed by an embedding of the request, and serves a cached response when a new request is similar enough (the similarity of dense retrieval, §9.3, with a threshold). It can remove the model call entirely for frequently asked questions. It is also the most dangerous cache, because "similar" is not "same": "can I change my flight to Tuesday?" and "can I change my flight to Thursday?" are close in embedding space and need different answers, and personalised or stateful requests should never be answered from a shared cache. Semantic caching is appropriate for stateless informational answers (baggage policy, opening hours), behind a threshold tuned on labelled pairs to keep false hits rare.

Plan and trajectory reuse is the agent-specific form: if the agent has solved a task of this type before, reuse the successful plan or tool sequence as a starting point. It is a form of procedural memory (§13.6), and it saves both tokens and turns, at the risk of applying a stale procedure to a changed environment, so reused plans should be validated as they run.

Drill 21.2 — is a semantic cache worth it?

A semantic cache could answer 30% of the support agent's first messages (informational questions) without running the agent, saving $0.31 each. On a labelled sample, 2% of cache hits are false (the cached answer is wrong for the new question), and a wrong answer costs $4 in a follow-up escalation. Per conversation, what is the expected net saving, and at what false-hit rate does it vanish?

Saving \(0.3\times0.31=\$0.093\); cost of false hits \(0.3\times0.02\times4=\$0.024\); net $0.069 per conversation. Break-even when \(0.31=f\times4\), \(f=7.75\%\). The cache pays comfortably at 2%, but the false-hit rate must be measured on real traffic and monitored, since it grows when policies change and the cache does not.

21.5 Observability: traces, spans and what to log

When a conventional web service misbehaves, its logs usually say why: a stack trace, an error code, a slow database query. When an agent misbehaves, the cause is typically a decision: the model read a tool output, misinterpreted it, and chose a wrong action five turns before anything visibly failed. Finding it requires seeing what the model saw at each step, what it did, and what came back. Observability for agents is therefore built on traces: complete, structured records of each run, in which every model call, tool call and sub-agent is a span with its inputs, outputs, timings, token counts and cost.

The vocabulary comes from distributed tracing of microservices, and the agent ecosystem adopted it: the OpenTelemetry project published semantic conventions for generative-AI spans in 2024, specifying attribute names for the model, token usage, tool calls and so on, so that traces from different frameworks can be read by the same tools[3]. Figure 21.3 shows a trace of one support conversation turn as a waterfall: each span is a bar on a time axis, nested under its parent, so that the structure of the run and the source of its latency are visible at once.

For the mathematician — a trace is a weighted tree, and latency is a longest path

A trace is a rooted tree whose nodes are spans, each with an interval \([s_v,e_v]\) on the time axis, contained in its parent's interval. Sequential children of a node occupy disjoint intervals in order; parallel children overlap. The duration of a node is determined by a max-plus recursion: for sequential children the durations add, for parallel ones the maximum is taken. The critical path is the root-to-leaf chain realising this value, the longest path through the dependency graph of the spans, and only spans on it affect end-to-end latency: shortening an off-path span changes nothing. Cost, by contrast, is additive over all nodes, so the spans that dominate cost and the spans that dominate latency are generally different sets, and optimising one does not optimise the other.

What to record in each span follows from what debugging and evaluation need. For model calls: the full input (or a reference to it, since contexts are large), the output including tool calls and, where available, reasoning, the model and its version, the sampling parameters, token counts split into cached, uncached and output, cost and timings. For tool calls: the arguments, the result (truncated if very large), status, duration and retries. For the run as a whole: the user or tenant (pseudonymised), the agent version (prompt, tools, model, policies), the outcome and any feedback. Storing full contexts is expensive (a 20-turn conversation re-reads hundreds of thousands of tokens), so systems store each new message once and reconstruct contexts by reference. Privacy rules apply to traces as to any user data: retention limits, access control, redaction of personal and secret data before storage.

Traces serve four purposes in production, and each needs different tooling. Debugging: given a reported failure, open its trace and read it, ideally with the ability to replay from any span with a changed prompt (the time travel of §16.4). Cost and latency attribution: aggregate spans by type, tool, model and node to find where money and time go (§21.1, §21.2). Online evaluation: run graders (Chapter 19) on a sample of live traces, automatic checks on all, a calibrated judge on some, people on a few, to measure quality on real traffic. And monitoring and alerting: watch rates over time (resolution, escalation, tool errors, guardrail blocks, cache hit rate, cost per task, latency percentiles) and alert on shifts. A change in any of these is usually the first sign that something upstream (a model update, a changed API, a new kind of user request) has moved.

Worked example — finding a cost regression in traces

The support agent's cost per conversation rises overnight from $0.33 to $0.71, with no change to resolution. Aggregating spans by type shows model-call input cost up five-fold; output and tool costs unchanged.

Cache hit rate. The fraction of input tokens served from cache has fallen from 91% to 55%. With \(N_{\text{in}}\approx415{,}000\) tokens per conversation, 36 points of hit rate is about 150,000 tokens moved from $0.30 to $3 per million: \(150{,}000\times2.70/10^6\approx\$0.40\) more per conversation, matching the observed rise.

Cause. Diffing the prefix of two consecutive calls in one trace shows that a deploy inserted the current time, to the minute, into the system prompt after the tool definitions, so whenever consecutive calls fall in different minutes the cached prefix ends there and the history behind it is re-read at full price.

Fix and guard. Move the timestamp to the end of the context and add an alert on cache hit rate below 80%. Without per-span token accounting, the regression would have appeared only in the monthly bill.

21.6 Guardrails

A guardrail is a check, outside the model, that inspects an input, an output or a proposed action and can block, modify or escalate it. Chapter 20 treated guardrails as security layers; in production they also enforce quality and policy: output schemas, business rules, tone and content policies, privacy rules (no card numbers in replies), and domain constraints (no medical dosing advice). Figure 21.4 shows where they sit. Input guardrails screen user messages and retrieved content before the model sees them (abuse, injection, out-of-scope requests). Action guardrails check each proposed tool call against policy before it executes (the deterministic refund check of §20.5). Output guardrails check the reply before the user sees it (schema validity, policy compliance, leaked personal data, unsupported claims).

Guardrails have costs that must be weighed like any other component. Latency: a model-based guardrail adds a model call per check; a deterministic one adds milliseconds; output guardrails on streamed replies either delay the stream or must run on chunks and retract text, which users notice. False positives: a guardrail that blocks 3% of legitimate replies degrades the product for 3% of users, and its block rate, like a judge's error rates (§19.6), must be measured on labelled traffic. False negatives: a guardrail is a verifier with a miss rate, and §20.5 showed why model-based guardrails should be counted as correlated with the agent itself. The design principles are the same as for tools (§8.5): deterministic checks wherever a rule can be written in code; model checks only for what code cannot express; and every block accompanied by a reason the agent can act on, so that a blocked refund becomes "the fare is non-refundable; offer a voucher" rather than a dead end.

21.7 Humans in the loop

People appear in production agent systems in three roles: as approvers of consequential actions (§8.9), as handlers of escalated tasks, and as reviewers of samples for quality measurement (§19.7). Each is a cost, and each can be sized. The most consequential design decision is how much the agent handles on its own, and it has a clean formulation as selective automation. Rank tasks by the agent's confidence; let the agent handle the most confident fraction \(c\) (the coverage) and route the rest to people. The error rate among handled tasks, \(e(c)\), rises with coverage, because each increase admits less confident tasks. With an agent cost \(C\) per task, a cost \(C_{\text{err}}\) per error that reaches a customer, and a human cost \(C_h\) per routed task, the expected cost per task is

\[ \text{cost}(c)=c\,\big(C+e(c)\,C_{\text{err}}\big)+(1-c)\,C_h, \]

minimised where the marginal task's expected cost equals the human cost: \(\frac{d}{dc}\big[c\,e(c)\big]C_{\text{err}}+C=C_h\). Figure 21.5 plots an example with \(C=\$0.33\), \(C_h=\$4\), \(C_{\text{err}}=\$20\) and an error curve \(e(c)=0.02+0.10c^2\) (2% error on the easiest tasks, rising to 12% at full coverage).

Figure 21.5's curve is flat near its minimum, which is good news for operators: coverage between 65% and 85% costs within a few cents of the optimum, so the threshold need not be tuned precisely. The position of the optimum, however, moves with each input, and its sensitivity is instructive. A more expensive error (a wrong refund rather than a mildly unhelpful answer) moves the optimum left; a better confidence ranking (a flatter \(e(c)\)) moves it right and lowers the whole curve; a cheaper human channel moves it left. Improving the agent's ranking of its own uncertainty is often worth more than improving its average accuracy, because it is what lets the system automate the right tasks.

Worked example — staffing the human queue

The support agent handles 50,000 conversations a month, about 1,670 a day, at 74% coverage, so 26% (about 430 a day) go to people. A person needs 8 minutes per routed conversation, and approvals of large refunds add 60 a day at 2 minutes each.

Work. \(430\times8+60\times2=3{,}560\) minutes, about 59 hours a day.

Staff. At 6 productive hours per person per day and a target utilisation of 80% (so that queues stay short), about \(59/(6\times0.8)\approx12.4\) people, spread across the hours when conversations arrive.

Waiting. By Little's law (§16.7), if arrivals peak at 60 routed conversations an hour and each waits on average 10 minutes before a person picks it up, about 10 conversations are waiting at any moment at the peak, the number the queue's design and the customer's patience must accommodate.

Sensitivity. Raising coverage to 80% removes about 100 routed conversations a day, 13 hours of work, nearly three people, while the expected error cost rises slightly: the trade of Figure 21.5 in staffing terms.

Two failure modes of human-in-the-loop design recur. Rubber-stamping: approvers who see hundreds of requests a day, almost all fine, stop reading them, so the probability of catching a bad action (\(p_{\text{catch}}\) of §8.9) falls towards zero exactly as volume rises. Remedies include showing approvers only what needs judgement, with the relevant facts highlighted, inserting known-bad test cases to measure attention, and keeping approval rates per person visible. Deskilling: when the agent handles all routine tasks, the people who handle escalations see only hard cases, without the routine experience that built their judgement, and they lose context about what normal looks like. Rotating staff through review of routine agent output, and treating escalations as training data for both the agent and the people, keeps the human channel competent.

21.8 Changing a running system

An agent in production changes constantly: model providers release new versions and deprecate old ones, prompts are edited, tools are added, policies change, and the traffic itself drifts. Each change can improve the system on average and break it for a class of tasks, and the evaluation of Chapter 19 only partly predicts which. Production practice therefore treats every change as a release, moved through stages that each limit the damage of a bad one. Figure 21.6 shows the ladder.

Each rung of Figure 21.6 answers a question the previous one could not. The offline suite checks known behaviours and blocks regressions on critical criteria. Shadow runs the new version on copies of real inputs with its actions disabled or simulated, which exposes it to the real distribution without risk, and allows paired comparison of its decisions with the current version's. A canary lets it act for a small fraction of users, so effects that only appear with real consequences (user satisfaction, downstream errors) can be measured, with the statistics of §19.4 deciding when the sample is large enough. Staged rollout widens exposure while monitoring continues. Throughout, the previous version stays deployable, so rollback is a configuration change rather than an emergency.

Three practices make the ladder work for agents in particular. Pin versions: call models by dated version identifiers rather than aliases that a provider may repoint, so that a model change is a deliberate release rather than a surprise; when a provider deprecates a version, the migration goes through the ladder like any other change. Version everything together: an agent's behaviour depends on the model, the prompts, the tool definitions, the policies and the guardrails, so a release identifier should name all of them, and traces should record it. Watch for drift: even with nothing changed on the agent's side, the world changes, as new products, new policies and new kinds of request appear, so the online metrics of §21.5 are compared against baselines continuously, and a drop in resolution on one class of requests triggers the error analysis of §19.8 before it becomes a trend.

Drill 21.3 — how long should the canary run?

The support agent's escalation rate is 30%. A new version is canaried on 5% of 1,670 daily conversations. How many days of canary are needed to detect an increase in escalation to 33% with an unpaired comparison at 80% power and the 5% level, and what does this imply?

Per arm, the standard error of the difference must be at most \(0.03/2.8=0.0107\). With the control arm large, the canary arm dominates: \(\sqrt{0.3\times0.7/n}\le0.0107\Rightarrow n\ge1{,}830\) canary conversations. At \(0.05\times1{,}670\approx84\) a day, that is about 22 days, too slow for most release schedules. Options: a larger canary share (25% gives about 4.4 days), a sharper metric (the paired shadow comparison of decisions on the same conversations), or accepting that only larger regressions will be caught at the canary stage and relying on the offline suite for small ones.

21.9 Capacity, rate limits and budgets

A production agent shares finite resources: the model provider's rate limits (requests and tokens per minute), sandboxes and browsers, tool back-ends with their own quotas, and the organisation's budget. Each must be sized for peak, not average, load, and each needs a behaviour for when it runs out. Sizing uses the tools already developed. Little's law (§16.7) gives the number of tasks in flight, arrival rate times duration; the token model of §21.1 converts tasks into tokens per minute; and the peak-to-mean ratio of the traffic, measured from logs, sets the headroom. Rate limits from model providers are usually expressed in input and output tokens per minute, and whether cached tokens count towards them varies by provider, which can change the answer by an order of magnitude.

Worked example — sizing the support agent for its peak hour

The support agent's 50,000 monthly conversations peak at 200 new conversations an hour on Monday mornings. A conversation lasts about 10 minutes of wall-clock time, including the customer's typing, and uses 415,000 input tokens (about 91% cached) and 6,000 output tokens over its 20 turns.

Concurrency. By Little's law, \(200/60\times10\approx33\) conversations in flight at the peak.

Token rate. Input \(200\times415{,}000/60\approx1.4\) million tokens per minute, of which about 125,000 are uncached; output \(200\times6{,}000/60=20{,}000\) tokens per minute. If the provider counts cached tokens towards the limit, the agent needs a 1.4-million-token-per-minute quota; if not, about 125,000.

Headroom. Retries and longer-than-average conversations add load: planning for 1.5 times the computed rate is common. Tool back-ends need the same sizing: at roughly one booking lookup per conversation per two turns, about 33 lookups a minute at peak.

When a limit is hit, the agent should degrade rather than fail. Back-off and queue: retry rate-limited calls with exponential back-off and jitter (§8.7), and queue new tasks rather than rejecting them when waiting is acceptable. Fall back: route routine nodes to a second provider or a smaller model when the primary is saturated, which requires having evaluated the fallback beforehand. Prioritise: interactive conversations before background tasks, paying customers before free ones. And shed load visibly: tell users that responses are slower rather than letting them time out.

Budgets are the financial form of the same control. A per-task budget, in tokens, turns or dollars, set at a few times the median from traces, stops runaway tasks (an agent caught in a loop of failing tool calls can otherwise spend dollars on one task) and converts them into failures that are counted and examined. Per-user and per-tenant budgets bound abuse and the damage of a compromised account. And a global budget with alerts at fractions of the month's allowance prevents the surprise bill. Like rate limits, budgets need a defined behaviour on exhaustion (stop and summarise progress, hand off to a person, or ask the user), since an agent that silently stops is worse than one that explains why.

Summary

  • Input tokens over an \(H\)-turn task grow as \(Hn_0+\Delta n\,H(H+1)/2\); prefix caching makes the uncached part linear and prices the quadratic part at \(\kappa_{\text{cache}}\). A 20-turn support task costs $1.34 uncached and $0.31 cached in the reference setting.
  • The relevant cost is per outcome: \(C+(1-p)F\) with failure costs included. Escalation costs usually dominate token costs, so quality matters more than price.
  • Turn latency \(\approx\Delta n/v_{\text{pre}}+n_{\text{out}}/v_{\text{dec}}+\ell_{\text{tool}}\) is dominated by decoding when contexts are cached; levers are shorter outputs, faster models, parallel tools, streaming and asynchronous contracts. Tails are set by slow tools and retries.
  • Cascades cost \(c_s+(1-a)c_l\) and pay on cost whenever \(a>c_s/c_l\), but are only as good as their acceptance check; routers decide up front. Route per node first.
  • Prefix caching is safe and needs disciplined prompt construction; tool-result caching is safe for reads with explicit staleness; semantic caching needs a measured false-hit rate; plan reuse needs validation.
  • Traces of spans (OpenTelemetry GenAI conventions) support debugging, cost and latency attribution, online evaluation and alerting. Latency follows the critical path; cost sums over all spans.
  • Guardrails sit at input, action and output; prefer deterministic checks, measure false-positive rates, and return actionable reasons.
  • Selective automation has an optimal coverage where the marginal task's expected cost equals a person's; better uncertainty ranking moves it up. Size human queues with workload and Little's law; guard against rubber-stamping and deskilling.
  • Size capacity for the peak with Little's law and the token model; check whether cached tokens count towards rate limits; degrade by back-off, fallback, prioritisation and visible load shedding; set per-task, per-tenant and global budgets with a defined behaviour when they run out.
  • Release changes through offline gates, shadow traffic, canaries and staged rollout with rollback; pin model versions, version all components together, and watch for drift.

Interview questions

Answer out loud first, then reveal the model answer and rate yourself.

Warm-up How do you estimate the cost of an agent task?

Tokens per turn: input \(n_0+t\Delta n\), output \(n_{\text{out}}\); sum over \(H\) turns; price uncached new input at \(\kappa_{\text{in}}\), cached re-reads at \(\kappa_{\text{cache}}\), output at \(\kappa_{\text{out}}\); add tools and infrastructure. Then cost per outcome: \(C+(1-p)F\). Measure the inputs from traces rather than guessing.

Warm-up Why does caching matter so much for agents?

Each turn re-reads the growing context, so input tokens grow quadratically with turns. Caching prices re-read tokens at about a tenth, making uncached input linear: a 20-turn task drops from $1.34 to $0.31 in the reference setting, and the gap grows with length. It also cuts prefill latency on cached tokens.

Warm-up What would you put in a trace span for a model call?

Input (or reference), output including tool calls and reasoning where available, model and version, sampling parameters, token counts (cached, uncached, output), cost, start and end times, time to first token, parent span, agent release identifier, and any errors or retries. Redact personal data and secrets.

Core Where does an agent's latency go, and how do you cut it?

Per turn: \(\Delta n/v_{\text{pre}}+n_{\text{out}}/v_{\text{dec}}+\ell_{\text{tool}}\); with caching, decode dominates. Cut output tokens (concise reasoning, compact formats), use faster models for routine nodes, parallelise independent tool calls, reduce turns (better tools, plans), cap tails with timeouts and turn limits, and improve perceived latency with streaming, progress messages or asynchronous delivery. Use the trace critical path to find what matters.

Core When does a model cascade pay?

Cost \(c_s+(1-a)c_l\) beats \(c_l\) when \(a>c_s/c_l\), almost always true for large price ratios. Quality is the constraint: the acceptance check must accept mostly correct small-model outputs. Compute total cost including failure costs: in the support example the cascade saved $0.18 in tokens and lost $0.08 to extra escalations. A worse check made it a net loss. Measure check precision on held-out data.

Core Compare the kinds of caching available to an agent.

Prefix caching: no correctness risk, needs stable prefixes and deterministic serialisation; monitor hit rate. Tool-result caching: safe for pure reads with explicit TTL, never for writes. Semantic caching: serves whole answers to similar requests; only for stateless informational queries, with a tuned threshold and measured false-hit rate. Plan reuse: saves turns, needs validation against environment changes.

Core How do you find the right level of human review?

Selective automation: rank tasks by agent confidence, automate the top fraction \(c\); cost \(c(C+e(c)C_{\text{err}})+(1-c)C_h\); optimum where the marginal task's expected cost equals a person's. Estimate \(e(c)\) from labelled data (risk–coverage curve). Errors that cost more push coverage down; better ranking pushes it up. The curve is flat near the optimum; revisit as models and costs change.

Core Where do guardrails go and how do you evaluate them?

Input (abuse, scope, injection), action (policy on each tool call, deterministic where possible), output (schema, PII, unsupported claims, policy). Evaluate like verifiers: false-positive rate on legitimate traffic, false-negative rate on known-bad cases, added latency; count model-based guardrails as correlated with the agent. Blocks return actionable reasons.

Core How do you roll out a new model version for a production agent?

Pin current version. Run the offline suite with paired comparison and regression gates on critical criteria (violations, resolution, cost, latency). Shadow on real traffic and compare decisions. Canary a small share with metrics and statistical stopping rules; staged rollout; keep the old version warm for rollback; update prompts if needed and version all components together; monitor for drift after rollout.

Core How would you detect and diagnose a cost regression?

Alert on cost per task and cache hit rate. Aggregate spans by type, model, tool and node to locate the change (input vs output vs tools). For input: check cache hit rate and prefix diffs between consecutive calls (timestamps, reordered tool definitions, non-deterministic serialisation). For output: reasoning length, verbosity changes after a model update. For turns: changes in tool behaviour causing loops. Fix and add a guard alert.

Deep Why do cost and latency optimisation target different spans?

A trace is a tree; latency is the max-plus value along the critical path, while cost is additive over all spans. Parallel tool calls off the critical path cost money but not time; a cheap but sequential slow tool costs time but little money. Optimise latency on the critical path (often model decode), cost on the largest summed spans (often cached history re-reads or long outputs).

Deep How long should a canary run, and how can you shorten it?

Long enough for the canary arm to detect the smallest regression you care about: \(n\ge p(1-p)z^2/\delta^2\) roughly; for 30%→33% escalations, ~1,830 conversations, ~22 days at 84/day. Shorten with a larger canary share, sharper metrics (paired shadow comparison of decisions on identical inputs, which removes between-task variance), sequential tests, or by accepting that small regressions are caught offline and the canary catches large ones.

Deep What goes wrong with human-in-the-loop systems over time?

Rubber-stamping (attention falls as volume rises, \(p_{\text{catch}}\to0\)); deskilling (humans see only hard cases and lose context); queue growth when coverage or traffic shifts; feedback loops where human decisions are not captured as data. Remedies: show only decisions needing judgement with key facts, seed known-bad cases to measure attention, rotate staff through routine review, size queues with Little's law, and log human decisions for evaluation and training.

Design Design the production stack for the airline support agent.

Entry: input guardrails and identity verification workflow. Agent: frontier model on hard nodes, small model for extraction and classification, cascade on simple intents; cached stable prefix. Tools: read tools with short-TTL result cache; write tools behind deterministic policy guardrails and caps; approvals above caps. Selective automation with confidence threshold near the cost optimum; human queue sized by workload and Little's law. Observability: OpenTelemetry traces, cost and cache dashboards, online graders on samples, alerts. Releases: pinned versions, shadow and canary. Targets: cost per resolved conversation, resolution, violations, p95 latency.

Design A coding agent's monthly bill tripled. Walk through your investigation.

Split by volume vs cost per task. If per task: traces aggregated by span type; check cache hit rate and prefix stability; check turns per task (loops after a tool change?), output tokens (reasoning budget, model change), tool output sizes (a test runner now printing full logs). If volume: new triggers or duplicated events (idempotency, §16.7). Fix root cause, add alerts on hit rate, turns per task and tokens per span, and budget limits per task.

Design How would you decide between a frontier model with escalation and a cheaper model with more human review?

Compute total cost per task for each: tokens + (1−resolution)×escalation cost + review costs, using measured resolution and error rates on your own traffic with intervals. Include error costs that reach customers, latency differences and staffing implications. Consider a cascade combining both. Choose on the Pareto frontier of cost, quality and risk; re-evaluate when prices or models change.

Core What metrics would you put on an agent's production dashboard?

Outcome: resolution/success rate, escalation rate, user feedback, policy violations. Reliability: tool error rates, retries, loops, timeouts. Cost: per task (distribution), tokens by type, cache hit rate. Latency: time to first token, p50/p95 per turn and per episode. Safety: guardrail block rates, injection detections, approval rates. Human channel: queue length, wait time, coverage. All by agent release and traffic segment, with alerts on shifts.
