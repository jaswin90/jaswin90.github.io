Part I · Foundations — Chapter 3

Running the Model: Prefill, Decode and the KV Cache

Generating text calls the model once per token. This chapter works out what must be remembered between calls, where the time goes, and how to predict the latency and cost of a real request from first principles.

Why this chapter

Chapter 2 gave us an exact inventory of a Transformer. Llama 3 8B has 8.03 billion parameters, occupies 16 GB in BF16, and costs about 15 GFLOPs per token plus an attention term that grows with context. An H100 performs 989 TFLOP/s. Divide one by the other and you might conclude that it should generate about 65,000 tokens per second. In reality, a single user sees something like 150. Where do the missing two and a half orders of magnitude go?

The answer is the subject of this chapter, and it is the conceptual core of the whole book. First, generation is a loop, and a naive loop wastes almost all its work recomputing things it already knew. Removing that waste requires a cache, the KV cache, whose size we can calculate exactly and which becomes the dominant consumer of GPU memory. Second, once the waste is removed, each step of the loop is limited not by arithmetic but by how fast data can be read from memory. To make that precise we introduce the most useful tool in performance engineering, arithmetic intensity and the roofline. With these we can predict, to within a factor that real systems spend the rest of this book closing, the time to first token, the time per output token, the throughput and the cost of serving a request.

  6. Predict TTFT, TPOT, throughput and cost per million tokens for a given model, GPU and workload.

3.1 Generation is a loop

A language model computes \(p(x_{t+1}\mid x_{\le t})\). To generate text from a prompt \(x_{1:n_{\text{in}}}\), we evaluate the model, sample a token from its output distribution, append the token to the sequence and repeat until an end-of-sequence token appears or a length limit is reached. Written as code, the most direct implementation is:

def generate_naive(model, tokens, n_out):
    for _ in range(n_out):
        logits = model(tokens)              # full forward pass over ALL tokens so far
        tokens.append(sample(logits[-1]))   # only the last position's logits are used
    return tokens

This works, and it is exactly how the earliest Transformer demos generated text, but look at what each iteration does. At step \(t\) it runs the whole network on all \(t\) tokens, at a cost of roughly \(2N t\) FLOPs from Chapter 2, and then throws away everything except the last position's logits. Generating \(T\) tokens costs \(\sum_{t=1}^{T}2Nt\approx NT^2\) FLOPs, quadratic in the length, when the useful output is only \(T\) tokens. For a 1,000-token answer that is about 500 times more work than necessary.

The waste is obvious once stated. At step \(t\) we recompute the hidden states of positions \(1,\dots,t-1\), which we already computed at step \(t-1\). Can we keep them instead? Not all of them are needed, and keeping them all would cost a great deal of memory. The question is which intermediate results the next step actually needs, and whether reusing them gives exactly the same answer.

Figure 3.1 contrasts the two strategies. On the left, the naive loop's work at step \(t\) is a row of \(t\) blocks, all but the last of them recomputation (grey), so the total work forms a triangle of area about \(T^2/2\). On the right, each step computes only one new block (orange), but it must read a growing row of stored results (dashed). The arithmetic becomes linear in \(T\). The price is memory to hold the stored results and bandwidth to read them, the two costs that occupy the rest of this chapter.

3.2 The KV cache

Look at one layer from the point of view of the newest position \(t\). Everything a Transformer block does is position-wise (the norms, the projections, the FFN) except for attention, where position \(t\)'s query is compared with the keys of positions \(1,\dots,t\) and averages their values. So the only information about earlier positions that the new position needs, in each layer, is their keys and values. If we store, for every layer, the keys and values of all previous positions, then processing a new token requires running the network on that token alone, plus reading the stored keys and values. That store is the KV cache.

Is it exact? Could the keys of earlier positions change when a new token arrives? For a causal model they cannot, and the proof is a short induction.

Proposition — KV caching is exact

Let \(h^{(\ell)}_j\) be the residual-stream vector of position \(j\) after layer \(\ell\). Claim: \(h^{(\ell)}_j\) depends only on the tokens \(x_{1:j}\). Proof by induction on \(\ell\). For \(\ell=0\), \(h^{(0)}_j = (W_E)_{x_j}\), the embedding of token \(x_j\). Suppose the claim holds for \(\ell-1\). In layer \(\ell\), the norms, projections and FFN act on each position separately. Attention at position \(j\) combines its query with keys and values of positions \(i\le j\) only, because of the causal mask. Each of these is a function of \(h^{(\ell-1)}_i\), which by hypothesis depends only on \(x_{1:i}\subseteq x_{1:j}\). Hence \(h^{(\ell)}_j\) depends only on \(x_{1:j}\). ∎

Consequently the keys and values of positions \(1,\dots,t\) are identical whether they are computed in one pass over \(x_{1:t}\) or incrementally, and appending tokens never changes them. Caching them is pure memoisation. (In floating point, results can differ in the last bits, because the two computations add numbers in different orders. Chapter 4 returns to this.)

For the mathematician — what a cache is

In computing, a cache stores the results of a computation so they can be reused instead of recomputed. Mathematically it is memoisation: if \(f\) will be evaluated again at the same arguments, store \(f\)'s values. The KV cache memoises the maps \(j\mapsto (k^{(\ell)}_j, v^{(\ell)}_j)\) for all layers \(\ell\). It is valid because, as the proposition shows, these values never depend on arguments that change later.

Prefill and decode, precisely

With a cache, generation splits into two phases that behave very differently. Chapter 1 introduced them informally; now we can define them.

Prefill processes the prompt. All \(n_{\text{in}}\) prompt tokens are known, so the model runs on all of them in a single forward pass, exactly like a training forward pass without the backward pass. Every weight matrix multiplies a matrix with \(B\cdot n_{\text{in}}\) rows. The pass writes the keys and values of every prompt token, in every layer, into the cache, and produces the logits of the last position, from which the first output token is sampled. Prefill therefore determines the time to first token (TTFT), apart from queueing.

Decode produces the rest of the output, one token per step. Each step feeds only the newest token of each sequence through the network. Every weight matrix multiplies a matrix with just \(B\) rows, one per sequence in the batch. Each layer computes the new token's query, key and value, appends the key and value to the cache, and attends over the whole cache. Each step yields one token per sequence, so decode determines the time per output token (TPOT).

Figure 3.2 contrasts the two phases. On the left, prefill is one large computation over all prompt tokens, and its matrix products have \(B\cdot n_{\text{in}}\) rows, often thousands. On the right, decode is a long sequence of small computations whose matrix products have only \(B\) rows. Beneath them the cache grows by one entry per step, and every step reads it in full. Sections 3.4–3.6 explain why "large matrix products" means limited by arithmetic and "small matrix products plus a full cache read" means limited by memory bandwidth. First we measure the cache.

3.3 How big is the KV cache?

For each token, each layer stores one key vector and one value vector for each of its \(n_{kv}\) key/value heads, each of dimension \(d_h\). At \(b_{kv}\) bytes per element:

\[ s_{kv} = 2\cdot L\cdot n_{kv}\cdot d_h\cdot b_{kv} \ \ \text{bytes per token},\qquad \text{KV}_{\text{total}} = s_{kv}\cdot\sum_{\text{sequences}} t_{\text{seq}} , \]

where \(t_{\text{seq}}\) is the current length (prompt plus generated tokens) of each live sequence.

A single 32k-token conversation with Llama 2 7B needs 16 GiB of cache, as much as the model's own weights. The 405B model, despite being 50 times larger than Llama 3 8B, needs only four times its cache per token, because it shares each KV head among 16 query heads. DeepSeek-V3, a 671-billion-parameter model, needs about half of Llama 3 8B's cache per token, because MLA caches a single compressed 512-dimensional latent plus a 64-dimensional rotated key per layer, rather than per-head keys and values (Chapter 8 derives this). The evolution of attention variants, MHA → GQA → MLA, is above all a story of shrinking \(s_{kv}\).

Figure 3.3 plots cache size against context length for one sequence. Every line is straight, since the cache is linear in tokens, and the slopes are the \(s_{kv}\) values of the table. Compare them with the dashed line at Llama 3 8B's weight size: a single 128k-token conversation with that model needs as much memory for its cache as for the entire model. Concurrency multiplies this. A server with 64 users at 8k tokens each holds 512k tokens of cache, 64 GiB for Llama 3 8B. That is why, in practice, KV-cache capacity, not compute, usually decides how many requests a GPU can serve at once.

Drill 3.1 — How many users fit?

Serve Llama 3 8B in BF16 on one 80 GB H100. Reserve 4 GB for activations and workspace. Users have 6,144-token contexts on average. How many can be served concurrently?

Solution. Weights take 16.1 GB, so about \(80-16.1-4\approx 59.9\) GB is left for the cache. Each user needs \(6144\times131{,}072\) B ≈ 0.805 GB, so about 74 users fit. With an FP8 cache (\(b_{kv}=1\)) about 148 fit. With Llama 2 7B's multi-head attention, only about 18 would fit.

The cache solves the recomputation problem of §3.1, but it creates a new one: every decode step must read it. Before quantifying that cost, we need a way to reason about where time goes on a GPU.

3.4 Where does the time go?

When an operation runs on a GPU, its time is spent in one of three ways. This decomposition, popularised by Horace He[1], is the first question to ask about any slow computation.

  • Compute. Time spent doing arithmetic on the compute units. For a computation of \(F\) FLOPs on a GPU with peak \(\pi\), this is at least \(F/\pi\).
  • Memory. Time spent moving data between the GPU's main memory (HBM) and its compute units. For \(Q\) bytes moved at bandwidth \(\beta\), this is at least \(Q/\beta\).
  • Overhead. Everything else: the Python interpreter deciding what to run next, the CPU telling the GPU to start each kernel (a function that runs on the GPU), scheduling, sampling logic, network I/O. Overhead does not grow with the size of the tensors, so it dominates when the work is small.

Modern GPUs can overlap computation with data movement, so to first order an operation takes the larger of its compute time and its memory time, plus whatever overhead is not hidden:

\[ t \;\approx\; \max\Big(\frac{F}{\pi},\ \frac{Q}{\beta}\Big) + t_{\text{overhead}} . \]

Figure 3.4 applies the decomposition to three situations, all with Llama 3 8B on an H100. A 2,048-token prefill performs about \(3.2\times10^{13}\) FLOPs (from §2.10), which takes 32 ms at peak. It also reads the 16 GB of weights once (4.8 ms), but that happens in parallel with the arithmetic, so prefill is compute-bound. A decode step at batch 1 must read the same 16 GB but performs only \(1.5\times10^{10}\) FLOPs, 0.016 ms of arithmetic, so it is memory-bound by a factor of 300. The third bar shows something easy to forget. A decode step on a small model launches hundreds of kernels, one or more per operation per layer, and each launch costs a few microseconds of CPU time. Without countermeasures, the overhead can rival the memory time. Production engines remove most of it by recording the whole step as a single "CUDA graph" that the GPU replays with one launch (Chapter 7). For the rest of this chapter we assume overhead has been dealt with, and focus on the competition between compute and memory.

3.5 Arithmetic intensity and the roofline

Whether an operation is compute-bound or memory-bound depends on a single number: how much arithmetic it does per byte it moves.

Definition — arithmetic intensity, roofline, ridge point

The arithmetic intensity of an operation is \(I = F/Q\), its FLOPs divided by the bytes it moves to or from main memory. Since \(t\approx\max(F/\pi, Q/\beta)\), its achieved throughput \(F/t\) obeys the roofline bound of Williams, Waterman and Patterson[2]: \[ \text{attainable FLOP/s} = \min(\pi,\ I\cdot\beta). \] The two terms are equal at the ridge point \(I^{*} = \pi/\beta\). Operations with \(I<I^{*}\) are memory-bound, and those with \(I>I^{*}\) are compute-bound. For an H100 in dense BF16, \(I^{*}\approx 989\times10^{12}/3.35\times10^{12}\approx 295\) FLOPs per byte.

The ridge point is the "295 operations per byte" of the factory-and-warehouse picture in Chapter 1 (§1.9), now given a name. The roofline converts the question "how fast will this run?" into "what is its intensity?", which is a property of the algorithm alone and can be computed with pen and paper. We now compute it for the two kinds of operation that make up an LLM.

Linear layers: intensity equals tokens per weight read

A weight matrix \(W\in\mathbb{R}^{k\times n}\) applied to \(m\) token vectors performs \(2mkn\) FLOPs. It moves \(b(kn + mk + mn)\) bytes: the weights, the input activations and the outputs. Hence

\[ I_{\text{linear}} = \frac{2mkn}{b(kn+mk+mn)} \;\xrightarrow{\;m\ll k,n\;}\; \frac{2m}{b}\qquad(=m\ \text{FLOPs per byte in BF16}). \]

The interpretation is simple and important. In BF16, every token that shares a weight read contributes about one FLOP per byte. In decode, \(m=B\), the number of sequences in the batch: at \(B=1\) the intensity is 1, and at \(B=64\) it is about 64, still well below the ridge. In prefill, \(m=B\cdot n_{\text{in}}\), typically thousands, so the intensity is far above the ridge and prefill is compute-bound. (When \(m\) becomes comparable to \(k\) and \(n\), the activation terms cap the intensity, but at hundreds or thousands of FLOPs per byte, which is still above the ridge.) For weight-dominated decode, the batch size at which the GPU becomes compute-bound is roughly the ridge point itself: \(B^{*}\approx I^{*}b/2\), about 295 on an H100 in BF16 and about 150 on an A100. This is why serving systems try to run hundreds of sequences concurrently.

Decode attention: an intensity that batching cannot raise

Attention in decode is different, because its "weights" are the KV cache, and every sequence has its own. For one sequence at context length \(t\), one layer reads its cached keys and values, \(2\,t\,n_{kv}d_h\,b_{kv}\) bytes, and performs \(4\,t\,n_hd_h\) FLOPs (scores and weighted sum over \(n_h\) query heads, §2.10). Therefore

\[ I_{\text{attn, decode}} = \frac{4\,t\,n_hd_h}{2\,t\,n_{kv}d_h\,b_{kv}} = \frac{2}{b_{kv}}\cdot\frac{n_h}{n_{kv}} = \frac{2g}{b_{kv}} . \]

In BF16, multi-head attention has intensity 1 and GQA with group size \(g\) has intensity \(g\) (4 for Llama 3 8B, 8 for Llama 3 70B). This number has two remarkable properties. It does not depend on the context length, because both FLOPs and bytes grow linearly in \(t\). And it does not depend on the batch size. A batch of \(B\) sequences reads \(B\) separate caches and does \(B\) times the arithmetic, so the ratio is unchanged. Batching amortises the weights but cannot amortise the cache. As contexts grow, the cache read grows to dominate each step, and no amount of batching helps. Only reducing \(s_{kv}\) does: more query heads per KV head (GQA, MQA), compression (MLA), fewer bytes per element (FP8 cache), or reading fewer entries (sparse attention). That list is essentially the table of contents of Chapter 8.

Figure 3.5 draws the roofline on log–log axes. To the left of the H100's ridge at 295, attainable throughput rises along a line of slope one, the bandwidth \(\beta\). To the right it is flat at \(\pi\). The A100's roofline (dashed) is lower on both counts. Its ridge is further left, at about 153, because it has relatively more bandwidth per FLOP. The green points are our operations. Decode at batch 1 and MHA decode attention sit at intensity 1, achieving at most 3.35 TFLOP/s, a third of one percent of peak. GQA-8 decode attention sits at 8. A decode linear layer at batch 64 reaches about 214 TFLOP/s. Prefill of a 2,048-token prompt sits on the flat part. Every optimisation in this book can be read as moving a point to the right (raising intensity) or raising one of the roofs (better hardware).

3.6 A latency model for decode

We can now write down the time of one decode step for a batch of \(B\) sequences whose average context is \(\bar t\). The bytes moved are the weights, once, plus every sequence's cache. The FLOPs are the weight FLOPs for \(B\) tokens plus the attention FLOPs:

\[ t_{\text{step}}(B) \approx \max\Bigg(\underbrace{\frac{N b_w + B\,\bar t\, s_{kv}}{\beta}}_{\text{memory time}},\ \underbrace{\frac{2N_{\text{mm}}B + 4Ld\bar tB}{\pi}}_{\text{compute time}}\Bigg) + t_{\text{overhead}} . \]

Per-user speed is \(1/t_{\text{step}}\) tokens per second, and total throughput is \(B/t_{\text{step}}\).

Before evaluating the formula, look at the numerator of its memory term, drawn in Figure 3.6. At batch 1 the step reads the 16 GB of weights and a negligible 0.3 GB of cache. At batch 64 it reads the same weights, which are shared, plus 17 GB of caches, which are not. At batch 224 the caches are almost four times the weights. Batching helps exactly as long as the shared part dominates.

Figure 3.7 evaluates the model for Llama 3 8B on an H100 with 2,048-token contexts. The memory line starts at 4.9 ms, the time to read the weights, and rises by 0.27 GB of cache, about 0.08 ms, per additional sequence. The compute line starts near zero and rises too, but stays far below the memory line. Two conclusions follow. First, the step is memory-bound at every batch size that fits. Second, by \(B\approx64\) the cache traffic (17 GB) already exceeds the weight traffic (16 GB). Memory capacity runs out at about 238 sequences of 2,048 tokens, before the compute line becomes relevant. For this model at these context lengths, throughput is bounded by the size and bandwidth of HBM, not by FLOPs.

Worked example — Llama 3 70B on one 8×H100 server

Setup. Llama 3 70B in BF16, its 141 GB of weights split evenly across eight H100s by tensor parallelism (Chapter 14), so that the server behaves like one device with \(8\times3.35=26.8\) TB/s of bandwidth and \(8\times989\) TFLOP/s of compute. The cache costs \(s_{kv}=2\times80\times8\times128\times2\) B = 320 KiB per token. We run 64 sequences at an average context of 4,096 tokens, with 80% of peak bandwidth, and ignore the cost of communication between the GPUs, which Chapter 17 shows adds 13–30% to a decode step unless it is overlapped with computation.

Bytes per step. The cache holds \(64\times4096\times320\) KiB = 80 GiB ≈ 86 GB. Weights plus cache are 227 GB, read (ignoring communication) in \(227/(0.8\times26.8)\approx10.6\) ms. The compute for the same step is \(64\times141\) GFLOP ≈ 9.0 TFLOP, 1.1 ms at full peak, so decode is memory-bound by a factor of ten, just as it was for the 8B model.

Throughput and cost. \(64/0.0106\approx6{,}000\) output tokens per second. Eight GPUs at $2.50 per hour cost $20 per hour, so a million output tokens cost \(20/(6000\times3600)\times10^6\approx\$0.92\), about 6.6 times the 8B figure for 8.8 times the parameters. The gap is smaller than the parameter ratio because the 70B model\'s cache per token is only 2.5 times larger: GQA with eight KV heads keeps the cache from growing in step with the weights.

Capacity. If about 90% of the 640 GB is usable, \(576-141=435\) GB remain for cache, enough for \(435/1.34\approx320\) sequences at 4k context. Running more sequences per step amortises the weights further, and §3.8 and Chapter 11 show how far that can be pushed before latency suffers.

3.7 A latency model for prefill

Prefill is compute-bound, so its time is FLOPs divided by achieved FLOP/s. From §2.10 a prompt of \(n_{\text{in}}\) tokens costs about \(2N_{\text{mm}}n_{\text{in}} + 2Ld\,n_{\text{in}}^2\) FLOPs. Real kernels do not reach the datasheet peak \(\pi\). The fraction achieved is called model FLOPs utilisation (MFU), typically 40–70% for large prefills. Hence

\[ \text{TTFT} \approx t_{\text{queue}} + \frac{2N_{\text{mm}}n_{\text{in}} + 2Ld\,n_{\text{in}}^2}{\text{MFU}\cdot\pi} . \]

Figure 3.8 plots this model for Llama 3 8B on one H100 at 50% MFU. On log–log axes the weight term (dashed) is a line of slope one. The full cost bends upward as the quadratic attention term takes over beyond about 28k tokens, the crossover found in §2.10. A 4k-token prompt prefills in about 130 ms, comfortably within an interactive budget. A 32k-token document takes about 1.5 s, and a 128k-token one about 13 s. Long prompts therefore create two problems. The user waits a long time for the first token, and while the GPU is busy with one long prefill, every other user's decode stalls. The second problem motivates chunked prefill, which splits long prompts into pieces interleaved with decode steps (Chapter 11), and disaggregation, which runs prefills on separate GPUs (Chapter 13). Prefix caching (Chapter 10) attacks the first: if the same document was read recently, its cache can be reused and the prefill skipped.

3.8 The life of a request, fully costed

We now have every piece needed to cost a real workload end to end. Here is a complete worked example of the kind interviewers love, using only quantities derived in this book.

Worked example — a chat service on one H100

Setup. Llama 3 8B in BF16 on one H100. Requests have \(n_{\text{in}}=2{,}000\) prompt tokens and \(n_{\text{out}}=500\) output tokens. We aim to run about 64 sequences concurrently in decode, and assume realistic efficiencies: 50% MFU in prefill and 80% of peak bandwidth in decode.

TTFT. Prefill FLOPs: \(2\times7.5\times10^9\times2000 + 2\times32\times4096\times2000^2 \approx 3.0\times10^{13}+1.0\times10^{12}=3.1\times10^{13}\). At \(0.5\times989\) TFLOP/s this takes about 63 ms, plus any queueing.

TPOT. With 64 sequences averaging about 2,250 tokens of context (prompt plus half the output), a step reads 16.06 GB of weights plus \(64\times2250\times131{,}072\) B ≈ 18.9 GB of cache: 35 GB. At \(0.8\times3.35\) TB/s that is 13 ms. Each user therefore sees about 77 tokens per second, comfortably faster than reading speed.

End-to-end latency. \(0.063 + 499\times0.013\approx 6.6\) s per request.

Throughput and load. \(64/0.013\approx 4{,}900\) output tokens per second. By Little's law (§1.13), sustaining 64 concurrent requests that each last 6.6 s requires an arrival rate of \(\lambda=\bar n/W=64/6.6\approx 9.7\) requests per second. (Prefills for those arrivals consume about \(9.7\times0.063\approx 0.6\) s of GPU time per second. Interleaving them with decode will lengthen TPOT noticeably, which is exactly the interference that Chapters 11 and 13 address.)

Cost. At $2.50 per GPU-hour, \(\frac{2.50}{4900\times3600}\times10^6\approx\$0.14\) per million output tokens, before accounting for prefill time.

This calculation is deliberately simple, and it is off from reality in ways the rest of the book addresses. Prefill and decode interfere. Requests do not all have the same lengths. The cache must be allocated without fragmentation. The sampling and scheduling overheads are not zero. But the structure is right, and the numbers are within a small factor of what well-tuned engines achieve. An engineer who can produce this calculation in five minutes, and explain which term each optimisation attacks, has the core skill this book is built around.

Drill 3.2 — Same service, Llama 3 70B on 4×H100

Split Llama 3 70B over four H100s with tensor parallelism (each GPU holds a quarter of every weight matrix and a quarter of the KV heads; Chapter 18). Same workload, 64 concurrent sequences. Estimate TPOT, ignoring communication.

Solution. Per GPU per step: weights \(141/4\approx35.3\) GB; cache \(64\times2250\times320\) KiB \(/4\approx 11.8\) GB. Total 47.1 GB at \(0.8\times3.35\) TB/s ≈ 17.6 ms, so about 57 tokens per second per user, before the 160 all-reduces per step that tensor parallelism adds (two per layer). Throughput is about \(64/0.0176\approx3{,}600\) tokens per second on four GPUs, roughly a fifth of what the same four GPUs give with 8B replicas. A bigger model is a direct and large cost multiplier.

3.9 Code: a KV-cached decoder you can read

The following is a complete, runnable Llama-style model with RMSNorm, RoPE, grouped-query attention, SwiGLU and a pre-allocated KV cache. It has been stripped of everything except the inference path, and it uses random weights; loading real ones only requires mapping parameter names from a checkpoint. Read it with Figure 2.1 open. Every line corresponds to a box in that figure or to an equation in this chapter. The generate function at the bottom shows the two phases explicitly: one call that processes the whole prompt (prefill), then a loop that feeds one token at a time (decode).

import torch, torch.nn as nn, torch.nn.functional as F

class Cfg:                                   # tiny Llama-style hyper-parameters
    d, L, n_h, n_kv, d_ff, V, max_T, rope_base = 512, 8, 8, 2, 1408, 32000, 2048, 10000.0

def rope_tables(c, device):
    d_h = c.d // c.n_h
    inv = c.rope_base ** (-torch.arange(0, d_h, 2, device=device) / d_h)   # θ_i, shape (d_h/2,)
    ang = torch.outer(torch.arange(c.max_T, device=device), inv)           # m·θ_i, shape (max_T, d_h/2)
    return ang.cos(), ang.sin()

def apply_rope(x, cos, sin):                  # x: (B, heads, T, d_h); cos/sin: (T, d_h/2)
    x1, x2 = x[..., 0::2], x[..., 1::2]          # coordinate pairs (2i, 2i+1)
    rot = torch.stack((x1 * cos - x2 * sin, x1 * sin + x2 * cos), dim=-1)
    return rot.flatten(-2)                      # re-interleave → (B, heads, T, d_h)

class RMSNorm(nn.Module):
    def __init__(self, d, eps=1e-6):
        super().__init__(); self.w = nn.Parameter(torch.ones(d)); self.eps = eps
    def forward(self, x):
        return self.w * x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)

class Block(nn.Module):
    def __init__(self, c):
        super().__init__(); self.c = c; d_h = c.d // c.n_h
        self.wq = nn.Linear(c.d, c.n_h * d_h, bias=False)
        self.wk = nn.Linear(c.d, c.n_kv * d_h, bias=False)
        self.wv = nn.Linear(c.d, c.n_kv * d_h, bias=False)
        self.wo = nn.Linear(c.n_h * d_h, c.d, bias=False)
        self.w1 = nn.Linear(c.d, c.d_ff, bias=False)    # gate
        self.w3 = nn.Linear(c.d, c.d_ff, bias=False)    # up
        self.w2 = nn.Linear(c.d_ff, c.d, bias=False)    # down
        self.n1, self.n2 = RMSNorm(c.d), RMSNorm(c.d)

    def forward(self, x, cache, pos, cos, sin):    # x: (B, T, d); new tokens occupy positions pos..pos+T-1
        B, T, _ = x.shape; c = self.c; d_h = c.d // c.n_h
        h = self.n1(x)
        q = self.wq(h).view(B, T, c.n_h,  d_h).transpose(1, 2)    # (B, n_h,  T, d_h)
        k = self.wk(h).view(B, T, c.n_kv, d_h).transpose(1, 2)    # (B, n_kv, T, d_h)
        v = self.wv(h).view(B, T, c.n_kv, d_h).transpose(1, 2)
        cs, sn = cos[pos:pos + T], sin[pos:pos + T]
        q, k = apply_rope(q, cs, sn), apply_rope(k, cs, sn)        # cache stores ROTATED keys
        K, Vc = cache                                              # pre-allocated (B, n_kv, max_T, d_h)
        K[:, :, pos:pos + T] = k                                   # append: the only write to the cache
        Vc[:, :, pos:pos + T] = v
        g = c.n_h // c.n_kv                                        # GQA group size
        k_all = K[:, :, :pos + T].repeat_interleave(g, dim=1)      # (B, n_h, pos+T, d_h) — real kernels avoid this copy
        v_all = Vc[:, :, :pos + T].repeat_interleave(g, dim=1)
        # query i (absolute position pos+i) may see keys j ≤ pos+i
        mask = torch.ones(T, pos + T, dtype=torch.bool, device=x.device).tril(diagonal=pos)
        o = F.scaled_dot_product_attention(q, k_all, v_all, attn_mask=mask)   # (B, n_h, T, d_h)
        x = x + self.wo(o.transpose(1, 2).reshape(B, T, c.n_h * d_h))
        h = self.n2(x)
        return x + self.w2(F.silu(self.w1(h)) * self.w3(h))     # SwiGLU FFN

class TinyLlama(nn.Module):
    def __init__(self, c):
        super().__init__(); self.c = c
        self.emb = nn.Embedding(c.V, c.d)
        self.blocks = nn.ModuleList(Block(c) for _ in range(c.L))
        self.norm = RMSNorm(c.d)
        self.head = nn.Linear(c.d, c.V, bias=False)

    def new_cache(self, B, device, dtype):
        shape = (B, self.c.n_kv, self.c.max_T, self.c.d // self.c.n_h)
        return [(torch.zeros(shape, device=device, dtype=dtype),
                 torch.zeros(shape, device=device, dtype=dtype)) for _ in range(self.c.L)]

    def forward(self, ids, cache, pos, cos, sin):
        x = self.emb(ids)                                          # gather, not a matmul
        for blk, layer_cache in zip(self.blocks, cache):
            x = blk(x, layer_cache, pos, cos, sin)
        return self.head(self.norm(x[:, -1:]))                    # logits for the LAST position only

@torch.no_grad()
def generate(model, prompt_ids, n_new, temperature=0.8):
    B, T0 = prompt_ids.shape; dev = prompt_ids.device
    cos, sin = rope_tables(model.c, dev)
    cache = model.new_cache(B, dev, next(model.parameters()).dtype)
    logits = model(prompt_ids, cache, 0, cos, sin)                 # PREFILL: all T0 tokens in one pass
    out, pos = [], T0
    for _ in range(n_new):                                        # DECODE: one token per step
        probs = torch.softmax(logits[:, -1] / temperature, dim=-1)
        nxt = torch.multinomial(probs, 1)                          # (B, 1)
        out.append(nxt)
        logits = model(nxt, cache, pos, cos, sin); pos += 1
    return torch.cat(out, dim=1)

model = TinyLlama(Cfg()).eval()
print(generate(model, torch.randint(0, Cfg.V, (2, 16)), n_new=8))   # two sequences, 16-token prompts

A torch.Tensor is an \(n\)-dimensional array that lives on a device (CPU or GPU). nn.Linear(k, n) stores a \(k\times n\) weight and computes \(xW\) on the last dimension. view and transpose reinterpret shapes without copying data, which is how heads become a batch dimension. F.scaled_dot_product_attention computes \(\operatorname{softmax}(QK^\top/\sqrt{d_h}+M)V\), dispatching to a fused kernel such as FlashAttention when it can. @torch.no_grad() disables gradient tracking, which saves memory at inference.

3.10 What production engines do differently

The code above is correct, and its cost structure is exactly what we analysed. But a production inference engine such as vLLM, SGLang or TensorRT-LLM differs from it in ways that each correspond to a later chapter, and it is worth previewing them as a road map.

First, the code allocates a contiguous cache of max_T positions for every sequence, which wastes memory on sequences that end early and caps every sequence at the same length. Engines instead allocate the cache in small fixed-size blocks on demand, with a table mapping each sequence's logical positions to physical blocks: PagedAttention, Chapter 10. Second, the code repeats each KV head \(g\) times with repeat_interleave before attending. That materialises a copy and throws away the intensity gain of GQA computed in §3.5. Real attention kernels load each KV head once into on-chip memory and apply it to all \(g\) queries there (Chapter 9). Third, the code processes a fixed batch in lockstep. Engines pack prefill tokens of new requests and decode tokens of running requests into one ragged batch at every step, admitting and retiring requests continuously (Chapter 11). Fourth, each line of Python launches separate GPU kernels. Engines fuse operations (Chapter 7) and capture whole decode steps as CUDA graphs to remove the overhead of §3.4. Finally, a model too large for one GPU is split across several with tensor or pipeline parallelism (Chapter 18).

A small but instructive detail: this code pairs RoPE coordinates as \((2r, 2r+1)\), while Hugging Face's Llama implementation pairs \((r, r+d_h/2)\) ("rotate-half"). Both are valid rotary embeddings, but weights trained with one convention give wrong results under the other unless the columns of \(W_Q\) and \(W_K\) are permuted. This is a classic bug when porting checkpoints between frameworks.

Looking ahead

We now understand generation as a cost: a compute-bound prefill that sets TTFT, followed by a memory-bound decode loop whose step time is the bytes of weights and cache divided by bandwidth. One piece of the loop has been treated as a black box: sample(logits). Turning a distribution over 128,256 tokens into one token is a modelling decision (greedy, temperature, top-p?), an engineering problem (doing it for hundreds of sequences per step on a GPU), and a correctness problem (JSON output that must parse, results that should be reproducible). Chapter 4 completes Part I by opening that box. Part II then opens the other black box of this chapter, the GPU itself, to explain where \(\pi\), \(\beta\) and the overheads come from and how kernels approach them.

Chapter summary

  • Naive generation recomputes the prefix at every step and costs \(\approx NT^2\). Caching each layer's keys and values is exact for causal models (proof by induction) and reduces the cost to \(\approx 2N\) per token plus attention.
  • Prefill processes all prompt tokens in one pass and is compute-bound; it sets TTFT. Decode processes one token per sequence per step and is memory-bound; it sets TPOT.
  • \(s_{kv}=2Ln_{kv}d_hb_{kv}\): 512 KiB per token for Llama 2 7B (MHA), 128 KiB for Llama 3 8B (GQA), ≈ 69 KiB for DeepSeek-V3 (MLA). Cache capacity usually limits concurrency.
  • Time ≈ max(FLOPs/\(\pi\), bytes/\(\beta\)) + overhead. Arithmetic intensity \(I\) = FLOPs/byte. The roofline is \(\min(\pi, I\beta)\), with ridge \(I^{*}=\pi/\beta\approx295\) on H100.
  • Linear layers have \(I\approx m\) (tokens per weight read) in BF16; decode attention has \(I=2g/b_{kv}\), independent of batch size, so batching cannot fix it.
  • Decode step ≈ \((Nb_w + B\bar ts_{kv})/\beta\); TTFT ≈ \((2N_{\text{mm}}n_{\text{in}}+2Ldn_{\text{in}}^2)/(\text{MFU}\cdot\pi)\). Together with Little's law these predict throughput, latency and cost.

Core Why is decode memory-bound but prefill compute-bound? Use arithmetic intensity.

A linear layer with weights \(k\times n\) applied to \(M\) tokens does \(2Mkn\) FLOPs and reads \(\approx bkn\) weight bytes; intensity ≈ \(2M/b\) (= \(M\) in BF16). Prefill has \(M=B\cdot n_{\text{in}}\) (thousands) → intensity far above the ridge (≈295 on H100) → compute-bound. Decode has \(M=B\) (1 to a few hundred) → below the ridge → bandwidth-bound. Decode attention is worse: intensity \(2g/b\) (1 for MHA, 8 for GQA-8) regardless of batch, because each sequence's KV cache is private. Hence prefill time ∝ FLOPs/peak and decode time ∝ bytes/bandwidth.

Deep-dive Show that attention FLOPs equal weight FLOPs at \(t\approx6d\). What changes for GQA and for long-context serving?

Per token at context \(t\): attention scores + weighted sum = \(4Ln_hd_ht=4Ldt\) FLOPs. Weight FLOPs = \(2N\approx24Ld^2\) for an MHA model with a 4d FFN. Equal when \(t=6d\). For GQA, weight FLOPs fall a bit (smaller \(W_K,W_V\)) but attention FLOPs are unchanged, so the crossover moves slightly earlier (for Llama 3 8B's actual parameter count, \(2\times7.5\text{B}/(4\times32\times4096)\approx 28.6\)k tokens because of its wide FFN). For long-context prefill, total attention FLOPs grow as \(\approx2Ldt^2\) and dominate at 128k (hence FlashAttention, context parallelism, sparse attention). For decode, attention's bytes matter far earlier than its FLOPs: KV bytes per step equal weight bytes when \(t\cdot s_{kv}=Nb\), e.g. Llama 3 8B: \(16\text{ GB}/128\text{ KiB}\approx122\)k tokens for one sequence—but with batch 64 the crossover is at under 2k tokens each.

Deep-dive Prove that KV caching is exact. Where can numerical results nevertheless differ?

Induction on layers: hidden state \(h^{(\ell)}_j\) depends only on \(x_{1:j}\). Base: embedding of \(x_j\). Step: position-wise operations preserve the property; causal attention at \(j\) uses \(k_i,v_i\) for \(i\le j\), functions of \(h^{(\ell-1)}_i\), which by hypothesis depend only on \(x_{1:i}\). So appending tokens never changes earlier K/V; caching is memoisation. Numerical differences: floating-point addition is not associative, and the kernels used for prefill (big GEMMs, tiled attention over many queries) and for decode (GEMV, split-K attention) reduce in different orders and tile sizes; batch composition can change kernel choice. Results agree to within rounding but not bit-for-bit, which matters for "temperature 0" reproducibility and for comparing speculative-decoding outputs. Truly batch-invariant kernels fix this at some speed cost (Chapter 3).

Deep-dive Derive the decode-attention arithmetic intensity, and explain why batching does not help it but GQA and MLA do.

One sequence, one layer, context \(t\): read \(K,V\): \(2tn_{kv}d_hb\) bytes. FLOPs: for each of \(n_h\) query heads, \(2td_h\) (scores) + \(2td_h\) (weighted sum) → \(4tn_hd_h\). Intensity \(=2n_h/(n_{kv}b)=2g/b\). A batch of \(B\) sequences reads \(B\) separate caches and does \(B\) times the FLOPs: the ratio is unchanged, unlike weights, which are shared. GQA raises it to \(g\) (BF16) by reusing each loaded KV head for \(g\) query heads in on-chip memory. MLA (with weight absorption) makes all \(n_h=128\) heads attend over the same 576-dim latent, so per byte of cache read it performs \(\sim 2n_h\cdot\frac{(512+64)+512}{576\cdot b}\) FLOPs—hundreds of FLOPs/byte, close to compute-bound on H100, which is why DeepSeek wrote dedicated kernels (FlashMLA). Prefix sharing (many sequences attending to the same cached prefix, e.g. a shared system prompt or parallel sampling) also raises it, enabling "cascade"/shared-prefix attention kernels.

Core Why must engines compute only last-position logits in prefill, and how does that interact with returning prompt log-probs?

Logits are \(T\times|V|\): for a 32k-token prompt and 128k vocabulary that is 4.2B elements (8.4 GB in BF16) and \(2d|V|T\) FLOPs (~34 TFLOPs for Llama 3 8B)—wasted unless needed. Engines gather the hidden state of each sequence's last token before the LM head. If the API requests prompt log-probs (common in evaluation), the engine must compute logits for all prompt positions, usually in chunks to bound memory, and may bypass optimisations such as prefix caching (vLLM documents that requests with prompt logprobs recompute the full prefill).

Core Implement single-step decode attention for one head, given cached K and V. What is its complexity? 
def decode_attn(q, K, V):            # q: (d_h,), K, V: (t, d_h)
    s = K @ q / math.sqrt(q.shape[0]) # (t,)  scores; no mask needed: all t are in the past
    s = s - s.max()                   # numerical stability
    p = torch.exp(s); p = p / p.sum() # softmax
    return p @ V                      # (d_h,)

Time \(O(td_h)\) FLOPs (\(4td_h\)), memory traffic \(O(td_h)\) bytes; it is bandwidth-bound. Follow-ups: batch over heads/sequences; GQA (one K/V for \(g\) queries); for long \(t\), split the sequence into chunks processed by different thread blocks and combine partial softmaxes with the log-sum-exp trick (FlashDecoding, Chapter 8); paged K/V via a block table (Chapter 9).

Design You must serve a 7B-class model with 32k contexts to as many concurrent users as possible on one 80 GB GPU. Which architectural and serving choices matter most?

Start from memory: weights ~14–16 GB (BF16). KV per user at 32k: MHA 7B = 16 GiB (only ~4 users!), GQA-8 (Llama 3 8B-like) = 4 GiB (~15 users). Levers, in order: (1) choose a model with GQA/MLA or sliding-window layers (e.g. interleaved local/global attention cuts most layers' cache to the window); (2) FP8 KV cache (2×) or INT4 KV with careful calibration; (3) FP8/INT4 weights to free ~8–12 GB; (4) PagedAttention to avoid reserving 32k per user when most use far less (Little's law on actual lengths); (5) prefix caching if users share system prompts/documents; (6) KV offload to CPU memory for idle conversations; (7) admission control/preemption policy. Then check bandwidth: at 32k, KV reads per step dominate; expect TPOT to grow with total live tokens, so set an SLO-aware cap on concurrent live tokens rather than users.

Design An interviewer gives you a new model config and an accelerator spec sheet. Outline, step by step, how you'd predict TTFT and TPOT.
  1. From the config: compute \(N\) (and active \(N\) for MoE), weight bytes at the serving precision, KV bytes per token \(2Ln_{kv}d_hb\) (or the MLA/sliding-window variant).
  2. From the spec sheet: dense peak FLOP/s at the precision used (not the sparse number), HBM bandwidth, capacity; interconnect if multi-GPU. Ridge point \(P/\beta\).
  3. Fit: weights + KV(batch × context) + workspace ≤ capacity → decide TP degree / max batch.
  4. TTFT ≈ queueing + prefill FLOPs \((2N_{\text{mm}}n_{\text{in}}+2Ldn_{\text{in}}^2)\) / (P × MFU≈0.4–0.6) (+ TP communication).
  5. TPOT ≈ max((weight bytes/TP + per-GPU KV bytes)/(β × MBU≈0.7–0.85), compute time) + per-step overhead (~0.5–2 ms without CUDA graphs) + TP all-reduce latency × 2L.
  6. Sanity-check against known benchmarks; state assumptions; discuss which lever (quantisation, speculative decoding, batching, disaggregation) moves which term.
Warm-up What are prefill and decode, and why do they behave so differently on a GPU?

Prefill runs the model once over all prompt tokens. Every weight matrix multiplies a matrix with \(B\cdot n_{\text{in}}\) rows (thousands), so each weight byte fetched is used for thousands of FLOPs. That is far above the H100's ridge of ≈ 295 FLOPs/byte, so prefill is compute-bound, and it writes the KV cache for the whole prompt and produces the first token (setting TTFT). Decode runs once per output token. Each weight matrix multiplies only \(B\) rows, about \(B\) FLOPs per byte, and every step also reads each sequence's whole KV cache at an intensity of \(2g/b_{kv}\). Decode is therefore memory-bandwidth-bound, and its step time sets TPOT. Consequences: prefill benefits from more FLOP/s and is hurt by long prompts (quadratic attention); decode benefits from more bandwidth, fewer bytes (quantisation, GQA/MLA) and larger batches.

Core Explain the compute / memory / overhead decomposition and give an example of each regime in LLM serving.

Time ≈ max(FLOPs/π, bytes/β) + overhead. Compute-bound: long-prompt prefill (Llama 3 8B, 2k tokens: ≈ 32 ms of arithmetic versus ≈ 5 ms of weight reads); remedies are lower precision (FP8 tensor cores), better kernels and more GPUs. Memory-bound: decode at practical batch sizes, and decode attention always; remedies are quantisation of weights and cache, GQA/MLA, batching (for weights only), and speculative decoding. Overhead-bound: decode of small models or small batches where hundreds of short kernels each cost microseconds to launch, plus Python scheduling and sampling; remedies are CUDA graphs, kernel fusion, and overlapping CPU scheduling with GPU execution (vLLM V1, SGLang). Diagnose with a profiler: if GPU kernels are idle between launches, you are overhead-bound.

Core Users complain that TTFT is several seconds for long documents. Diagnose and propose fixes.

Prefill time is ≈ \((2N_{\text{mm}}n_{\text{in}}+2Ldn_{\text{in}}^2)/(\text{MFU}\cdot\pi)\); for Llama 3 8B a 32k-token document takes ≈ 1.5 s at 50% MFU, and queueing behind other prefills adds more. Check traces to split TTFT into queueing and prefill. Fixes: (1) prefix caching: if the same document or system prompt recurs, reuse its KV cache and skip prefill (Chapter 10); (2) chunked prefill / priority scheduling so long prefills do not block everyone (Chapter 11); (3) disaggregated or dedicated prefill capacity (Chapter 13); (4) more FLOP/s: FP8 prefill, tensor or context parallelism across GPUs (Chapters 14, 18); (5) efficient attention kernels for long sequences (Chapter 9); (6) product changes: retrieval instead of stuffing whole documents, streaming a status message.

Deep-dive Cost a chat service end to end: Llama 3 8B on one H100, 2,000-token prompts, 500-token answers, ~64 concurrent decodes. Give TTFT, TPOT, throughput, request rate and cost per million tokens.

TTFT: prefill ≈ \(2\cdot7.5\text{e}9\cdot2000+2\cdot32\cdot4096\cdot2000^2\approx3.1\text{e}13\) FLOPs; at 50% MFU ≈ 63 ms (+ queueing). TPOT: bytes per step = 16.06 GB of weights + \(64\times2250\times128\) KiB ≈ 18.9 GB of cache ≈ 35 GB; at 80% of 3.35 TB/s ≈ 13 ms, so ≈ 77 tokens/s per user. E2E: ≈ 0.063 + 499 × 0.013 ≈ 6.6 s. Throughput: 64/0.013 ≈ 4,900 output tokens/s. Load: Little's law gives λ = 64/6.6 ≈ 9.7 requests/s, and their prefills consume ≈ 0.6 s of GPU per second, so interference will lengthen TPOT unless prefill is chunked or disaggregated. Cost: $2.50/h ÷ (4,900 × 3,600) × 10⁶ ≈ $0.14 per million output tokens (more once prefill time is charged). Then name the levers: FP8 cache/weights, prefix caching, speculative decoding, batching policy.

Core What are MFU and MBU, and which should you report for prefill and for decode?

MFU (model FLOPs utilisation) = useful FLOPs performed per second ÷ peak FLOP/s, counting only the model's required FLOPs (not recomputation or padding). MBU (memory-bandwidth utilisation) = bytes that must be moved per second (weights + KV cache) ÷ peak bandwidth. Prefill is compute-bound, so MFU tells you how close to the limit you are (40–70% is good). Decode is memory-bound, so its MFU is necessarily tiny (often <5%) even when perfectly optimised; MBU is the meaningful metric (60–85% is good). Reporting decode MFU as "the GPU is only 3% utilised" is a classic interview mistake.
