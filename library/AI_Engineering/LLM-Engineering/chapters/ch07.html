Part II · The Machine — Chapter 7

GPU Programming for Mathematicians

How fast GPU code is actually written: from a first CUDA kernel to tiled matrix multiplication, parallel reductions, the online softmax, kernel fusion, Triton, and the compilers and libraries that generate most of the kernels an LLM runs.

Why this chapter

Chapter 6 kept arriving at the same conclusion. The element-wise operations are memory-bound, so fuse them. Matrix multiplication needs reuse, so tile it. Small kernels drown in launch overhead, so capture them in a graph. Each conclusion ends with an instruction to write better GPU code, and for a reader without a systems background that is the last black box left in the stack. You do not need to become a kernel engineer to be an excellent inference engineer, and most people in the field rarely write CUDA. But you do need to read kernels, judge whether one is likely to be good, and know what is and is not possible. FlashAttention (Chapter 9), PagedAttention (Chapter 10), fused MoE kernels (Chapter 19) and quantised GEMMs (Chapter 14) are all, at bottom, clever kernels, and their design choices make sense only if you know how kernels work.

This chapter teaches that skill through four worked programs of increasing sophistication: a vector addition, a tiled matrix multiplication, a parallel reduction, and a fused softmax. Each introduces one idea that matters for performance: launching parallel work, reusing data on-chip, cooperating across threads, and fusing operations so data stays on-chip. The mathematical heart of the chapter is the online softmax, an associative reformulation of a seemingly sequential computation. It is the key that unlocks FlashAttention. We then introduce Triton, the Python-embedded language in which most LLM kernels outside NVIDIA's libraries are now written, and finish with the tools that remove launch overhead and generate kernels automatically: CUDA Graphs, torch.compile and the newer kernel languages.

Learning objectives
  1. Read and write a simple CUDA kernel, and explain the role of the grid, block and thread indices.
  2. Explain memory coalescing and shared-memory bank conflicts, and why they decide whether a memory-bound kernel reaches peak bandwidth.
  3. Write a shared-memory tiled matrix multiplication, and derive its arithmetic intensity as a function of tile size.
  4. Implement a parallel reduction with warp shuffles, and explain why reductions need associativity.
  5. Derive the online softmax and its merge rule, and prove that the merge is associative.
  6. Explain kernel fusion quantitatively, and write fused kernels in Triton.
  7. Explain what CUDA Graphs, torch.compile, CUTLASS/CuTe and newer kernel languages each contribute.
  8. Time a GPU kernel correctly and convert the result into achieved bandwidth or FLOP/s.

7.1 A first kernel

We begin with the simplest possible parallel computation, \(z=x+y\) for vectors of length \(n\), because it shows every piece of the machinery without any algorithmic distraction. In CUDA, the C++ dialect for NVIDIA GPUs, the kernel is written from the point of view of one thread:

__global__ void add(const float* x, const float* y, float* z, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // this thread's global index
    if (i < n) z[i] = x[i] + y[i];                    // guard: the last block may overhang
}

// Host code: launch ceil(n / 256) blocks of 256 threads each.
add<<<(n + 255) / 256, 256>>>(x, y, z, n);

Three details carry over to every kernel. First, the __global__ qualifier marks a function that runs on the GPU and is launched from the CPU. Second, each thread computes its own index from three built-in variables: which block it is in (blockIdx), how large blocks are (blockDim) and its position within the block (threadIdx). This is the map-over-an-index-set of §5.2, written out explicitly. Third, the launch configuration <<<blocks, threads>>> chooses the grid. Here it is enough blocks of 256 threads to cover \(n\) elements, with a guard for the last, partial block.

How fast is it? Each element requires reading 8 bytes and writing 4 for one FLOP, an arithmetic intensity of \(1/12\) FLOPs per byte, so the kernel is as memory-bound as a kernel can be. Its runtime is \(12n/\beta\) at best, and the only question is whether it reaches that bound. It does, if two conditions hold. Enough threads must be in flight to cover memory latency (§5.1), which for large \(n\) is automatic. And consecutive threads must access consecutive addresses, the subject of the next section.

7.2 Coalescing and bank conflicts

When the 32 threads of a warp execute a load, the hardware does not fetch 32 separate values. It fetches whole aligned 32-byte sectors from memory, grouped into transactions of up to 128 bytes. If the 32 threads read 32 consecutive 4-byte floats, the warp needs exactly one 128-byte transaction, and every byte fetched is used. This is a coalesced access. If instead each thread reads an element 32 floats apart, for example walking down a column of a row-major matrix, the warp touches 32 different sectors. The hardware fetches 32 × 32 = 1,024 bytes to use 128, wasting seven-eighths of the bandwidth.

Figure 7.1 contrasts the two patterns. The left warp reads one contiguous 128-byte segment, and every byte fetched is used. The right warp reads 32 widely spaced floats, and the hardware fetches 32 sectors of 32 bytes each to deliver 128 useful bytes. For a memory-bound kernel this is an eightfold slowdown. Coalescing is therefore the first thing to check in any memory-bound kernel. It is also why data layout is a recurring theme in LLM systems: the KV cache layout in PagedAttention (Chapter 10), the "interleaved" storage of quantised weights (Chapter 14) and the head-major versus token-major ordering of attention tensors are all chosen so that the threads that run together read memory that sits together.

Shared memory has its own access rule. It is divided into 32 banks, each serving one 4-byte word per cycle, with consecutive words in consecutive banks. If the threads of a warp access 32 different banks, the access completes in one cycle. If several threads access different addresses in the same bank, their accesses are serialised, a bank conflict. The classic trap is a \(32\times32\) tile stored row by row and read by column: every element of a column lies in the same bank, so a warp reading one column suffers a 32-way conflict. The classic fix is to pad each row by one element (declare the tile as [32][33]), which shifts each row by one bank and spreads a column across all 32 banks. Modern kernels use more elaborate "swizzled" layouts for the same purpose, and the TMA engine of §5.5 can write tiles in swizzled form automatically.

Worked example — the cost of an uncoalesced read

A warp of 32 threads each reads one 4-byte float. Coalesced: the addresses are consecutive, so the 128 bytes fall in four 32-byte sectors of one cache line, and the memory system moves exactly 128 bytes. Strided by 32 floats: each thread's address lies in a different line, so the hardware fetches 32 sectors of 32 bytes, 1,024 bytes, to deliver 128 useful bytes: an eightfold waste of bandwidth. A kernel that reads a matrix column-wise from row-major storage in this way runs at one eighth of its bandwidth roofline, which is why kernels stage tiles through shared memory and transpose there (§7.2).

7.3 Tiled matrix multiplication

Matrix multiplication is where reuse becomes possible, and the shared-memory tiled GEMM is the canonical example of how to obtain it. Recall the argument of §5.4. Computing \(C=AB\) with \(A\in\mathbb R^{M\times K}\) and \(B\in\mathbb R^{K\times N}\) uses each element of \(A\) in \(N\) products and each element of \(B\) in \(M\). A kernel that fetches every operand from HBM for every multiply-add has constant intensity. The tiled kernel instead assigns each thread block a \(t\times t\) tile of \(C\). The block marches along the shared dimension \(K\) in steps of \(t\). At each step, its threads cooperatively load a \(t\times t\) tile of \(A\) and one of \(B\) into shared memory, synchronise, and then accumulate the tile product from shared memory:

#define TILE 32
__global__ void matmul(const float* A, const float* B, float* C, int M, int N, int K) {
    __shared__ float As[TILE][TILE], Bs[TILE][TILE];          // on-chip tiles
    int row = blockIdx.y * TILE + threadIdx.y;                 // this thread's output element
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.f;
    for (int k0 = 0; k0 < K; k0 += TILE) {                       // march along K
        As[threadIdx.y][threadIdx.x] = (row < M && k0 + threadIdx.x < K) ? A[row * K + k0 + threadIdx.x] : 0.f;
        Bs[threadIdx.y][threadIdx.x] = (k0 + threadIdx.y < K && col < N) ? B[(k0 + threadIdx.y) * N + col] : 0.f;
        __syncthreads();                                          // tiles fully loaded
        for (int k = 0; k < TILE; ++k)                            // TILE multiply-adds per loaded pair
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        __syncthreads();                                          // before overwriting tiles
    }
    if (row < M && col < N) C[row * N + col] = acc;
}
// Launch: dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE), block(TILE, TILE);

Notice how the loads are arranged. Thread \((y,x)\) loads element \((y,x)\) of each tile, so consecutive threads of a warp (consecutive \(x\)) read consecutive addresses of a row of \(A\) and of \(B\): coalesced. The two __syncthreads() barriers are essential. The first ensures no thread reads a tile before all threads have finished writing it. The second ensures no thread overwrites a tile while others are still reading it.

Figure 7.2 shows the data flow. The block that owns the green tile of \(C\) needs the whole block row of \(A\) (orange band) and block column of \(B\) (purple band), but it never needs them all at once. It streams them through shared memory one pair of tiles at a time, and each element brought on-chip is used in \(t\) multiply-adds. The intensity of the traffic between HBM (or L2) and the block is therefore

\[ I_{\text{block}} = \frac{2t^2t_k}{2t\,t_k\,b} = \frac{t}{b}\quad\text{FLOPs per byte}, \]

where \(t_k\) is the step along \(K\). This is a clean, important formula: intensity grows linearly with the tile width.

Figure 7.3 plots \(t/b\) for BF16, and it makes clear why one level of tiling is not enough on a modern GPU. Our 32-wide tiles give 16 FLOPs per byte. Even 256-wide tiles, about as large as on-chip memory allows, give 128, below the H100's HBM ridge of 295. Production GEMMs close the gap with two further levels of reuse. Across blocks, thread blocks that run concurrently are launched in an order (called rasterisation or swizzling) chosen so that they share rows of \(A\) and columns of \(B\). Most of their tile loads then hit in the 50 MB L2 cache, and each input element crosses from HBM only a few times. Within a block, each thread accumulates a small sub-tile of \(C\) in its registers rather than a single element, multiplying the reuse of every value read from shared memory. That keeps shared-memory bandwidth from becoming the binding constraint, the hierarchical-roofline effect of §6.2. Finally, the inner loop uses tensor-core instructions rather than scalar multiply-adds, and the tile loads are issued asynchronously (TMA, §5.5) into multi-stage buffers so that the next tiles arrive while the current ones are being multiplied. Each refinement is easy to state and hard to implement well, which is why almost nobody writes production GEMMs by hand: libraries such as cuBLAS and CUTLASS do it, tuned per GPU and per shape.

For the mathematician — synchronisation as a barrier

__syncthreads() is a barrier: no thread of the block proceeds past it until every thread has reached it. It imposes a partial order on events (all writes before the barrier happen before all reads after it), which is exactly what correctness requires when threads communicate through shared memory. Barriers exist only within a block, because blocks may run in any order and need not be resident at the same time. Algorithms that need global synchronisation must either end the kernel and start another, or use atomic operations.

Drill 7.2 — How much does a tile buy?

A GEMM kernel computes an \(M_t\times N_t\) output tile by streaming \(k\)-slices of the two input panels through shared memory, in BF16. Show that its arithmetic intensity with respect to the data it loads is \(2M_tN_t/((M_t+N_t)b)\), and evaluate it for \(128\times128\) and \(128\times256\) tiles. Is that enough to reach the H100 ridge point from HBM?

Solution. For each \(k\)-slice of width \(k_s\), the tile loads \((M_t+N_t)k_s\) elements and performs \(2M_tN_tk_s\) FLOPs, so the intensity is \(2M_tN_t/((M_t+N_t)b)\). For \(128\times128\): \(2\times16{,}384/(256\times2)=64\) FLOP/B; for \(128\times256\): \(2\times32{,}768/(384\times2)\approx85\) FLOP/B. Both are well below the ridge of about 295 FLOP/B, so tiling into shared memory alone does not make a GEMM compute-bound against HBM; the rest comes from L2-cache reuse, because neighbouring thread blocks that share input panels are scheduled together (rasterisation), so most panel loads hit L2 rather than HBM (§7.3, and the correction logged in REVIEW.md).

7.4 Reductions: computing sums in parallel

Many LLM operations reduce a vector to a scalar: the mean square in RMSNorm, the maximum and sum in softmax, the dot products in attention, the total in a top-\(p\) mass. Summing \(n\) numbers looks inherently sequential, \(((x_1+x_2)+x_3)+\cdots\), but because addition is associative, the sum can be computed as a balanced binary tree in \(\lceil\log_2 n\rceil\) parallel steps. At step \(s\), each of the \(n/2^{s}\) active threads adds a pair of partial sums.

Figure 7.4 shows eight values summed in three steps. On a GPU the tree is implemented at two levels. Within a warp, threads exchange register values directly with shuffle instructions, which take no shared memory and no synchronisation:

__device__ float warp_sum(float v) {                 // every lane returns the sum over the warp
    for (int offset = 16; offset > 0; offset /= 2)
        v += __shfl_xor_sync(0xffffffff, v, offset);   // add the value held by lane (id XOR offset)
    return v;
}

Five shuffle steps reduce 32 values. Across warps, each warp writes its partial sum to shared memory, and one warp reduces those partials. Across thread blocks, which cannot synchronise, partial results are written to HBM and combined by a second kernel or by atomic additions. The reduction order determines the floating-point result bit for bit, which is why the batch-dependent choice between these strategies causes the nondeterminism of §4.8.

The essential requirement is associativity. A tree reduction computes \((x_1\oplus x_2)\oplus(x_3\oplus x_4)\) rather than \(((x_1\oplus x_2)\oplus x_3)\oplus x_4\), and these agree only if \(\oplus\) is associative. Addition and maximum are associative, so sums and maxima parallelise directly. Softmax, at first sight, is not a reduction at all, which brings us to the most important idea of the chapter.

7.5 The online softmax

Softmax over a vector \(x\in\mathbb R^{n}\) is computed in a numerically safe way as

\[ \operatorname{softmax}(x)_i = \frac{e^{x_i-m}}{\ell},\qquad m=\max_j x_j,\qquad \ell=\sum_j e^{x_j-m}. \]

Subtracting the maximum prevents overflow: without it \(e^{x_i}\) overflows for \(x_i\gtrsim 88\) in FP32, or about 11 in FP16. But the formula seems to require three passes over the data: one to find \(m\), one to compute \(\ell\) given \(m\), and one to produce the outputs. For a memory-bound operation, three passes means three times the memory traffic. Worse, in attention the vector \(x\) is a row of the \(T\times T\) score matrix, which we would very much like never to store at all. Can the maximum and the normaliser be computed together, in one pass, from data seen piece by piece?

Milakov and Gimelshein (2018) showed that they can[1]. Maintain a running maximum \(m\) and a running normaliser \(\ell\) relative to that maximum. When a new element \(x\) arrives, the maximum may increase, and the old normaliser, which was computed relative to the old maximum, must be rescaled:

\[ m' = \max(m, x),\qquad \ell' = \ell\,e^{m-m'} + e^{x-m'} . \]

Starting from \(m=-\infty,\ \ell=0\), one pass produces exactly \(m=\max_j x_j\) and \(\ell=\sum_je^{x_j-m}\). More useful still, the same idea combines the summaries of two blocks of data. If block \(a\) has summary \((m_a,\ell_a)\) and block \(b\) has \((m_b,\ell_b)\), then the summary of their union is

\[ (m_a,\ell_a)\oplus(m_b,\ell_b) = \Big(m,\ \ell_a e^{m_a-m} + \ell_b e^{m_b-m}\Big),\qquad m=\max(m_a,m_b). \]
Proposition — the online-softmax merge is associative

Map each summary to the pair \((m,\ell)\) and observe that \(\ell e^{m}=\sum_{j\in\text{block}}e^{x_j}\) is invariant: it is the true sum of exponentials of the block, represented as a mantissa \(\ell\) relative to the exponent \(m\). The merge computes \(\max\) of the exponents and the sum of the represented quantities, \(\ell e^{m}=\ell_ae^{m_a}+\ell_be^{m_b}\), re-expressed relative to the new maximum. Since \(\max\) and \(+\) are associative and commutative, so is \(\oplus\). In exact arithmetic the result is independent of how the data are split into blocks and in what order the blocks are merged. ∎

Associativity is what makes the trick so powerful: softmax normalisation becomes a reduction, so it can be computed in a single pass, in parallel, over blocks processed in any order, by a tree of merges. The same merge extends to the output of attention. If each block also keeps a partial weighted sum of values \(o_a=\sum_{j\in a}e^{x_j-m_a}v_j\), then

\[ o = o_a e^{m_a-m} + o_b e^{m_b-m},\qquad \text{output} = o/\ell , \]

so attention over a long sequence can be computed block by block, never materialising the full row of scores. That single equation is the core of FlashAttention, which we derive in full in Chapter 9, and of FlashDecoding, which splits a long KV cache across thread blocks and merges their partial results with exactly this rule.

Figure 7.5 summarises the idea. Each block of a long row of scores is processed independently, perhaps by a different thread block or even a different GPU, and summarised by three quantities: its local maximum, its local normaliser and, for attention, its local weighted sum of values. The summaries then merge pairwise in any order. Nothing larger than a block is ever held, and every input is read exactly once. This turns a three-pass, memory-hungry operation into a one-pass, streaming one, which is the kind of reformulation that separates a fast kernel from a slow one.

7.6 Kernel fusion

We can now make Chapter 6's advice to "fuse the element-wise operations" precise. Consider a chain of \(k\) element-wise operations applied to a tensor of \(S\) bytes, for example a residual addition, an RMSNorm scaling and a cast. If each runs as a separate kernel, each reads its input from HBM and writes its output back: \(2kS\) bytes in total. If they are fused into one kernel, the data are read once, transformed \(k\) times in registers, and written once: \(2S\) bytes. For memory-bound operations the time is proportional to the bytes, so fusion of \(k\) operations is worth a factor of \(k\), and it also saves \(k-1\) kernel launches.

Figure 7.6 shows the linear growth of unfused traffic against the flat cost of a fused kernel. In an LLM the opportunities are everywhere. "Add the residual, then RMSNorm" is one kernel in every serious engine, as are "SiLU of the gate times the up-projection" in SwiGLU, "apply RoPE to \(q\) and \(k\), then write \(k\) and \(v\) into the paged cache", and "dequantise the weights inside the GEMM" for quantised models. The most valuable fusions put memory-bound operations into the prologue or epilogue of a matrix multiplication. A bias, activation or scaling applied to the output tile while it is still in registers costs essentially nothing. The deepest fusion of all is FlashAttention, which fuses the score matrix product, the softmax and the value product into one kernel so that the \(T\times T\) intermediate never touches HBM.

Fusion has limits. A fused kernel needs all its inputs at once, so operations that require a global synchronisation, such as a reduction across the whole tensor followed by a use of its result everywhere, may not fuse into one pass unless they can be reformulated, as the online softmax reformulates softmax. Fusing too much can exhaust registers and shared memory, lowering occupancy. And each fused kernel is specialised code that must be written, tested and maintained. That last cost is why compilers that fuse automatically (§7.8) matter so much.

7.7 Triton: kernels at the level of blocks

CUDA asks the programmer to think about individual threads, then coordinate them into warps and blocks by hand. Coalescing, bank conflicts, shuffles and barriers are all the programmer's responsibility. Tillet, Kung and Cox's Triton (2019)[2], now maintained by OpenAI, raises the level of abstraction. A Triton program describes what one block of work does, in terms of whole tiles of data (vectors and small matrices). The compiler decides how to map each tile onto threads, registers and shared memory, handling coalescing, vectorisation, shuffles and, for matrix products, tensor-core instructions. Triton is embedded in Python, which is one reason it has become the default way to write custom kernels in the LLM ecosystem, from vLLM and SGLang to torch.compile, which generates Triton code.

Here is a row-wise softmax in Triton. Each program instance handles one row, which fits in on-chip memory for typical widths:

import triton, triton.language as tl

@triton.jit
def softmax_kernel(out_ptr, in_ptr, n_cols, stride, BLOCK: tl.constexpr):
    row = tl.program_id(0)                                   # which row this program handles
    cols = tl.arange(0, BLOCK)                               # a whole vector of column indices
    mask = cols < n_cols
    x = tl.load(in_ptr + row * stride + cols, mask=mask, other=-float('inf'))
    x = x - tl.max(x, axis=0)                                # reduction: compiler emits shuffles
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(out_ptr + row * stride + cols, y, mask=mask)

# launch one program per row:
# softmax_kernel[(n_rows,)](out, x, n_cols, x.stride(0), BLOCK=triton.next_power_of_2(n_cols))

Compare this with what the equivalent CUDA would need: per-thread index arithmetic, a two-level reduction with shuffles and shared memory, and careful coalescing. In Triton the reductions are a single tl.max or tl.sum, and the masking of the ragged last block is a keyword argument. The kernel reads each row once and writes it once, so it is a fused softmax: three logical passes over the row, one pass over HBM. The fused residual-add-and-RMSNorm that every engine uses is equally short:

@triton.jit
def add_rmsnorm(x_ptr, res_ptr, w_ptr, out_ptr, d, eps, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK); mask = cols < d
    x = tl.load(x_ptr + row * d + cols, mask=mask, other=0.).to(tl.float32)
    r = tl.load(res_ptr + row * d + cols, mask=mask, other=0.).to(tl.float32)
    h = x + r                                                # residual add
    tl.store(res_ptr + row * d + cols, h.to(res_ptr.dtype.element_ty), mask=mask)   # updated residual stream
    rms = tl.sqrt(tl.sum(h * h, axis=0) / d + eps)           # one reduction, in FP32
    w = tl.load(w_ptr + cols, mask=mask, other=0.)
    tl.store(out_ptr + row * d + cols, (h / rms * w).to(out_ptr.dtype.element_ty), mask=mask)

Five HBM round-trips in an unfused implementation (add, square, mean, scale, multiply by \(\gamma\)) become one read of two tensors and two writes, with the arithmetic done in FP32 registers for accuracy. Triton also supports tiled matrix products through tl.dot, which compiles to tensor-core instructions, and an autotuner that tries several tile sizes and keeps the fastest for each problem shape. That is how one Triton kernel can approach cuBLAS-level performance across many shapes.

Figure 7.7 contrasts the two levels. In CUDA you program a thread and are responsible for everything that makes 32 of them cooperate efficiently. In Triton you program a tile, and the compiler handles that mapping. The trade-off is control. The very fastest kernels on new hardware (FlashAttention-3 on Hopper, FlashAttention-4 on Blackwell) depend on warp specialisation, explicit asynchronous pipelines and hardware features that a tile-level compiler may not expose or may not schedule optimally. Those are written in lower-level tools: CUDA with CUTLASS/CuTe, or the Python-embedded CuTe-DSL. For the large majority of LLM kernels, however, Triton gives most of the performance for a fraction of the effort.

7.8 Launch overhead, CUDA Graphs and compilers

A decode step of Llama 3 8B launches hundreds of kernels, and at small batch many of them run for only a few microseconds. Each launch costs the CPU a few microseconds to prepare and submit, so the GPU can spend much of its time waiting for the next kernel: the overhead regime of §3.4 and Figure 6.4. CUDA Graphs remove this cost. The engine runs the decode step once in "capture" mode, recording the sequence of kernels, their arguments and their dependencies as a graph. Thereafter it replays the whole graph with a single launch, and the GPU executes the recorded kernels back to back. The catch is that a captured graph has fixed shapes and fixed memory addresses. Engines therefore capture one graph per batch size in a set of buckets (for example 1, 2, 4, 8, 16, … 256), pad each actual batch up to the nearest bucket, and keep inputs in pre-allocated buffers whose addresses never change. Prefill, whose shapes vary freely, usually runs without graphs, where launch overhead matters little relative to its long kernels.

torch.compile (PyTorch 2, 2023)[3] automates much of the rest. It captures a model's Python code as a graph of operations (TorchDynamo), then compiles that graph (TorchInductor), fusing chains of element-wise and reduction operations into generated Triton kernels and calling library GEMMs for matrix products. It can also wrap the result in CUDA Graphs. Inference engines use it, often alongside hand-written kernels for attention and quantised matrix products, to get fusion without writing every fused kernel by hand.

At the other end of the spectrum, NVIDIA's CUTLASS is a C++ template library of building blocks for high-performance GEMMs and convolutions, and its core abstraction, CuTe, describes data layouts algebraically. A CuTe layout is a function from logical coordinates to memory offsets, given by a shape and a stride, and layouts can be composed, partitioned and tiled with algebraic operations. That makes the intricate data arrangements of tensor-core kernels expressible and checkable. CuTe-DSL brings the same abstractions to Python, and FlashAttention-4 is written in it. Research languages push further. ThunderKittens (2024)[4] treats \(16\times16\) register tiles as the primitive data type. TileLang and others offer tile-level programming with explicit control over pipelining. The trend across all of them is the same: as tensor cores become faster and more asynchronous, kernel languages move towards expressing tiles and pipelines rather than threads.

For the mathematician — a layout is a function

A CuTe layout with shape \((s_1,\dots,s_r)\) and stride \((d_1,\dots,d_r)\) is the map \(\mathbb Z_{s_1}\times\cdots\times\mathbb Z_{s_r}\to\mathbb Z\), \((c_1,\dots,c_r)\mapsto\sum_i c_id_i\). Row-major and column-major storage of a matrix are two such maps; a tile is the restriction of a layout to a sub-box; "swizzling" composes a layout with a bijection on offsets that spreads accesses across shared-memory banks. Kernel bugs that look mysterious often become transparent when the layouts are written down as functions and composed.

Worked example — launch overhead in a decode step

A decode step of Llama 3 8B launches roughly ten kernels per layer (normalisations, projections, attention, activation, residual adds) over 32 layers, about 320 launches. At 4–5 µs of CPU-side launch cost each, the launches alone take about 1.5 ms, and if the GPU finishes small kernels faster than the CPU issues them it idles between them. Against a 10 ms step at batch 64 that is a 15% loss; against a 2 ms step at batch 1 on a small model, it can exceed the GPU time. Capturing the step in a CUDA graph replaces the 320 launches with one, cutting the overhead to tens of microseconds, which is why engines capture decode steps in graphs for each batch-size bucket (§7.8, §12.2).

7.9 Timing a kernel correctly

Every claim in this chapter, that a fused kernel is faster or a layout coalesces, must eventually be checked by measurement. GPU timing has traps that catch almost everyone the first time, and most of them follow from one fact established in §5.2: kernel launches are asynchronous. When Python calls a GPU operation, the call returns as soon as the kernel is queued, long before it finishes. A naive timing loop therefore measures how fast the CPU can enqueue work, not how fast the GPU does it. The correct pattern records events on the GPU's own timeline and synchronises before reading them:

import torch

def time_gpu(fn, warmup=10, iters=100):
    for _ in range(warmup):                 # compile, autotune, warm caches and clocks
        fn()
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()                           # timestamps recorded on the GPU stream
    for _ in range(iters):
        fn()
    end.record()
    torch.cuda.synchronize()                 # wait for the GPU to finish
    return start.elapsed_time(end) / iters   # milliseconds per call

Four further cautions turn a measurement into evidence. Warm up. The first calls include one-off costs such as compilation, autotuning and memory allocation, and the GPU may still be raising its clock. Beware of caches. If the same small input is used on every iteration, it may stay in the 50 MB L2 cache, and a "memory-bound" kernel will appear to exceed HBM bandwidth. Benchmark on inputs larger than L2, or rotate among several buffers. Convert to a rate. Report achieved bandwidth (necessary bytes ÷ time) or FLOP/s alongside the time, and compare with the roofline. A vector addition of \(10^8\) floats should take about \(12\times10^8/3.35\times10^{12}\approx0.36\) ms on an H100. Measuring 0.45 ms means 80% of peak, which is excellent. Measuring 0.05 ms means the measurement is wrong. Measure the distribution. Report the median and spread over repetitions, because clock changes, other processes and power management add noise. Triton's triton.testing.do_bench implements most of these practices and is a good default.

The same principles apply at larger scale. When benchmarking a whole serving system (Chapter 28), asynchrony becomes queueing, cache effects become prefix-cache hit rates, and warm-up becomes the period before CUDA graphs are captured and memory pools are filled. The habit of predicting the answer from first principles before measuring, then explaining any gap, is the same.

Looking ahead

Part II is complete. We have built a model of the GPU (Chapter 5), a quantitative tool for predicting and measuring performance on it (Chapter 6), and the programming ideas with which fast kernels are written (this chapter): coalesced access, on-chip tiling, parallel reductions, the online softmax and fusion. With these in hand we can return to the problem that Part I identified as central. The KV cache grows with every token, dominates memory capacity, and at realistic context lengths dominates the bytes each decode step must read (§6.4–6.5). Part III attacks it from three directions: making the cache smaller (Chapter 8), reading it with IO-aware kernels built on exactly the online softmax derived here (Chapter 9), and managing it in memory as carefully as an operating system manages pages (Chapter 10).

Chapter summary

  • A CUDA kernel is written per thread; threads compute their index from blockIdx, blockDim and threadIdx. Memory-bound kernels such as vector addition reach peak bandwidth only with enough parallelism and coalesced access.
  • Coalescing: a warp reading 32 consecutive words uses one 128-byte transaction; strided access can waste 7/8 of the bandwidth. Shared memory has 32 banks; same-bank accesses serialise; padding or swizzling avoids conflicts.
  • Tiled GEMM: each block computes a \(t\times t\) output tile from tiles staged in shared memory, giving intensity \(t/b\). Practical tiles fall short of the HBM ridge, so real GEMMs add L2 reuse across blocks, register tiling, tensor cores and asynchronous pipelines (cuBLAS, CUTLASS).
  • Reductions use associativity to sum in \(\log n\) steps: warp shuffles inside a warp, shared memory across warps, multiple kernels or atomics across blocks. Reduction order determines bit-level results.
  • Online softmax: \(m'=\max(m,x)\), \(\ell'=\ell e^{m-m'}+e^{x-m'}\); block summaries merge associatively, and partial attention outputs merge the same way. This is the basis of FlashAttention and FlashDecoding.
  • Fusion of \(k\) memory-bound operations cuts HBM traffic from \(2kS\) to \(2S\). The best fusions put element-wise work into GEMM prologues and epilogues.
  • Triton programs tiles rather than threads; the compiler handles mapping, reductions and tensor cores, giving most of the performance with far less effort. The very fastest kernels use CUTLASS/CuTe or CuTe-DSL.
  • Timing: kernels launch asynchronously, so time with GPU events and synchronise; warm up, avoid L2-resident inputs, and report achieved bandwidth against the roofline.
  • CUDA Graphs remove launch overhead by replaying captured kernel sequences (fixed shapes, so engines bucket batch sizes). torch.compile captures and fuses automatically, generating Triton.

Warm-up Write a CUDA kernel for element-wise addition and explain the launch configuration. 
__global__ void add(const float* x, const float* y, float* z, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) z[i] = x[i] + y[i];
}
add<<<(n + 255) / 256, 256>>>(x, y, z, n);

Each thread handles one element; 256 threads per block (a multiple of the warp size) and enough blocks to cover \(n\), with a bounds check for the tail. Consecutive threads touch consecutive addresses, so loads and stores coalesce. Intensity is 1/12 FLOPs/byte, so the kernel is memory-bound at ≈ \(12n/\beta\); large \(n\) gives enough parallelism to saturate bandwidth. Improvements: vectorised loads (float4), grid-stride loops for very large \(n\).

Core What is memory coalescing, and how would you detect and fix uncoalesced access?

When a warp's threads access consecutive, aligned addresses, the hardware combines them into a few wide transactions (one 128-byte segment for 32 floats). Scattered or strided accesses need a separate 32-byte sector per thread, wasting bandwidth (up to 8× for 4-byte elements). Detect: Nsight Compute's sectors-per-request and achieved DRAM bandwidth versus useful bytes. Fix: change the data layout (transpose, struct-of-arrays), change the thread-to-data mapping so consecutive threads read consecutive elements, stage through shared memory (load coalesced, then read in any pattern), use vectorised loads.

Core Explain the shared-memory tiled GEMM and derive its arithmetic intensity.

Each thread block computes a \(t\times t\) output tile. It iterates along \(K\) in steps of \(t_k\); at each step the block's threads cooperatively (and coalescedly) load a \(t\times t_k\) tile of \(A\) and a \(t_k\times t\) tile of \(B\) into shared memory, synchronise, accumulate the tile product, and synchronise again before the next load. FLOPs per step: \(2t^2t_k\); bytes per step: \(2tt_kb\); intensity \(t/b\). For BF16 tiles of 128 that is 64, below the H100 HBM ridge, so production kernels add L2 reuse across blocks (rasterised scheduling), register tiling (each thread owns a sub-tile), tensor cores and asynchronous multi-stage pipelines. Shared memory and register capacity bound \(t\).

Core Derive the online softmax and explain why it matters for attention.

Safe softmax needs \(m=\max_jx_j\) and \(\ell=\sum_je^{x_j-m}\), seemingly two passes before the output pass. Online: keep \((m,\ell)\); for each new \(x\), \(m'=\max(m,x)\), \(\ell'=\ell e^{m-m'}+e^{x-m'}\). Blocks merge: \(m=\max(m_a,m_b)\), \(\ell=\ell_ae^{m_a-m}+\ell_be^{m_b-m}\). This is associative because \(\ell e^{m}\) represents the block's \(\sum e^{x_j}\) exactly and the merge adds those sums. With partial outputs \(o_a=\sum e^{x_j-m_a}v_j\) merged by the same rescaling, attention can be computed over blocks of keys in one pass without storing the \(T\times T\) score matrix: FlashAttention. Splitting a long KV cache across thread blocks and merging gives FlashDecoding.

Core Implement a fused residual-add + RMSNorm in Triton and explain what it saves.

See §7.7: one program per row loads \(x\) and the residual \(r\), computes \(h=x+r\) in FP32, stores \(h\) back as the new residual stream, computes \(\text{rms}=\sqrt{\operatorname{mean}(h^2)+\epsilon}\) with one tl.sum, and stores \(h/\text{rms}\cdot\gamma\). Savings: unfused there are separate kernels for the add, square, mean, rsqrt-scale and multiply by γ, each reading and writing the tensor (≈ 5 round-trips plus launches). Fused: read two tensors once, write two once. The operation is memory-bound, so time falls roughly in proportion to bytes, and launch overhead falls too. Accumulating in FP32 avoids precision loss in the reduction.

Core What are shared-memory bank conflicts and how do you avoid them?

Shared memory has 32 banks, each serving one 4-byte word per cycle, with consecutive words in consecutive banks. If several threads in a warp access different addresses in the same bank in one instruction, the accesses serialise (n-way conflict). Classic case: reading a column of a 32×32 float tile (stride 32 words means the same bank). Fixes: pad rows ([32][33]), use swizzled layouts (XOR-based permutation of columns per row), change access patterns, or let TMA write swizzled tiles. Broadcast (all threads reading the same address) is not a conflict.

Deep-dive Why does every LLM engine use CUDA Graphs for decode but not usually for prefill? What constraints do graphs impose?

Decode at small and medium batch launches hundreds of short kernels; per-launch CPU cost (microseconds) can rival kernel time, leaving the GPU idle. A CUDA graph records the whole step and replays it with one launch, eliminating that overhead. Prefill kernels are long and shapes vary with prompt length, so launch overhead is negligible and capturing every shape is impractical. Constraints: fixed shapes (capture per batch-size bucket and pad), fixed memory addresses (persistent input and output buffers, static KV-cache tensors with block tables passed as data), no CPU-dependent control flow inside the captured region, and capture cost and memory per graph. Engines (vLLM, SGLang) capture a set of decode batch sizes at start-up.

Core When would you write a kernel in Triton versus CUDA/CUTLASS, versus relying on torch.compile?

torch.compile: first choice for fusing element-wise and reduction chains automatically with no kernel code; good for prototyping and many production paths. Triton: custom fused operations the compiler does not produce (fused RoPE + KV write, custom attention variants, quantised matmuls with unusual formats, MoE routing kernels), when you want near-library performance with Python productivity and portability. CUDA / CUTLASS / CuTe-DSL: when you need the last 10–30% on the newest hardware (warp specialisation, TMA/wgmma/tcgen05 pipelines, persistent kernels), or features the compiler does not expose. Always compare against vendor libraries (cuBLAS, cuDNN, FlashAttention) first.

Deep-dive Write a parallel sum reduction for a large array, describing all three levels.

(1) Thread level: grid-stride loop. Each thread sums many elements with coalesced (vectorised) loads into a register. (2) Warp level: for (off = 16; off > 0; off /= 2) v += __shfl_xor_sync(0xffffffff, v, off);, giving the warp's sum in every lane. (3) Block level: lane 0 of each warp writes to shared memory, __syncthreads(), and the first warp reduces those values. (4) Grid level: each block writes its partial sum to global memory; either a second kernel reduces the partials, or each block does atomicAdd (non-deterministic order). Accumulate in FP32 (or use Kahan summation) for accuracy; for reproducibility use a fixed-order two-pass approach.

Core Quantify the benefit of kernel fusion for a decode step and name the fusions every engine implements.

For memory-bound ops, time ∝ bytes; fusing \(k\) ops cuts traffic from \(2kS\) to \(2S\) and removes \(k-1\) launches. In decode the activations are small, so the bigger win is often launches (hundreds per step) plus avoiding extra passes over the KV cache or logits. Standard fusions: residual add + RMSNorm; QKV projection as one GEMM; RoPE fused with the KV-cache write (and often with the QKV GEMM epilogue); SiLU × up-projection (gate/up fused GEMM + activation epilogue); attention (FlashAttention / paged decode kernels); dequantisation inside the GEMM for quantised weights; fused MoE routing and expert GEMMs; fused sampling (penalties + temperature + top-k/p). Together with CUDA graphs these typically give large decode speed-ups over naive PyTorch.

Deep-dive Prove that the online-softmax merge is associative, and discuss its floating-point behaviour.

Represent a block by \(S=\sum_{j}e^{x_j}\) written as \(S=\ell e^{m}\) with \(m\) the block max. The merge outputs \(m=\max(m_a,m_b)\) and \(\ell=\ell_ae^{m_a-m}+\ell_be^{m_b-m}\), so \(\ell e^{m}=\ell_ae^{m_a}+\ell_be^{m_b}=S_a+S_b\). Since max and + are associative and commutative, any bracketing gives \((\max_jx_j,\ \sum_je^{x_j}/e^{\max_jx_j})\). In floating point: every exponent argument is \(\le0\), so no overflow; \(\ell\in[1, n]\), so it is well scaled; rounding errors depend on the merge order (non-associative addition), giving last-bit differences between tilings, harmless numerically but relevant to bit-reproducibility. Rescaling the running output \(o\) by \(e^{m_a-m}\le1\) is stable.

Warm-up What do CUTLASS and CuTe provide, and why would an inference engineer care?

CUTLASS is NVIDIA's open-source C++ template library of building blocks for high-performance GEMMs, convolutions and related kernels (tiling, pipelining, tensor-core MMA, epilogues). CuTe is its layout algebra: layouts as functions from coordinates to offsets that compose and tile, making tensor-core data arrangements tractable. Inference engineers care because custom GEMM variants (quantised weights with in-kernel dequantisation, grouped GEMMs for MoE, fused epilogues) and attention kernels (FlashAttention-3, FlashMLA) are built on them; CuTe-DSL exposes the same in Python (FlashAttention-4 uses it).

Design Your model has a custom attention variant with no optimised kernel, and decode is 3× slower than a standard model of the same size. Plan the work.

(1) Profile: confirm attention dominates and whether it is memory-bound (likely) or overhead-bound (many small kernels). (2) Write the roofline target: cache bytes per step / β. (3) Quick wins: torch.compile the variant to fuse element-wise parts; CUDA graphs. (4) If the variant is expressible as standard attention plus a mask or bias, use FlexAttention or FlashInfer's customisable interfaces. (5) Otherwise write a Triton decode kernel: one program per (sequence, head-group, KV split), loading K/V tiles coalescedly from the paged cache, computing scores, online softmax and partial outputs, then a merge kernel (FlashDecoding pattern); share KV loads across query heads in a group. (6) Autotune block sizes; validate against a reference for numerical error; measure MBU. (7) Only if needed, a CUTLASS/CuTe implementation for the last gains on the target GPU.

Core Why does a tiled GEMM need L2 reuse across blocks on an H100, and how is it obtained?

A block's traffic has intensity \(t/b\); with BF16 and practical tiles (128–256) that is 64–128 FLOPs/byte, below the HBM ridge (≈ 295). If every block fetched its tiles from HBM independently, the GEMM would be memory-bound. But many blocks need the same tiles: all blocks in a row of C share A's block row, all in a column share B's block column. Launching blocks in an order where concurrently resident blocks form a compact 2-D region (grouped rasterisation, swizzling) makes these shared tiles hit in the 50 MB L2, so each input crosses from HBM only a few times and the effective HBM intensity reaches the thousands. Persistent kernels and thread-block clusters with distributed shared memory (Hopper) or TMA multicast can share tiles even more explicitly.

Deep-dive What changes when writing kernels for Hopper and Blackwell compared with Ampere?

Ampere: synchronous warp-level MMA plus asynchronous global→shared copies (cp.async); classic multi-stage pipelines. Hopper: warpgroup-level asynchronous MMA (wgmma) consuming operands directly from shared memory; TMA for bulk asynchronous tile copies with hardware swizzling and multicast across clusters; thread-block clusters with distributed shared memory. High performance needs warp specialisation (producer warps issue TMA, consumer warpgroups issue wgmma), barriers on asynchronous transactions, and ping-pong scheduling to overlap softmax with MMA (FlashAttention-3). Blackwell: tcgen05 MMA with accumulators in dedicated tensor memory, two-CTA cooperative MMAs, FP4/FP6 and block-scaled formats, even larger tiles. Bottlenecks shift to exponentials, shared-memory bandwidth and synchronisation (FlashAttention-4 emulates part of exp on FMA units). Kernels must be re-architected, not just recompiled.
