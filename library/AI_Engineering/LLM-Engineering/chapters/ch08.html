Part III · Attention and Memory — Chapter 8

The KV Cache: Shrinking It

Four knobs control the size of the KV cache: how many heads it stores, how wide each entry is, how many tokens and layers it covers, and how many bits each number takes. This chapter turns each knob in turn, from multi-query attention to DeepSeek's latent attention.

Why this chapter

Every thread of Parts I and II led back to one object. The KV cache grows with every token (Chapter 3), limits how many sequences fit on a GPU (§3.3), and, beyond a critical context length of only a few hundred tokens, makes decoding memory-bound at every batch size (§6.4). For Llama 3 8B at batch 64 and 2,048-token contexts, reading the cache already costs more than reading the weights (§6.5). For reasoning models whose traces run to tens of thousands of tokens it dominates everything. If we could make the cache ten times smaller, we would fit ten times as many sequences, read ten times fewer bytes per step from the cache, and push decode back towards the compute-bound regime.

The cache's size is a product, \(s_{kv}\cdot T=2\,L\,n_{kv}\,d_h\,b_{kv}\,T\), and each factor is a knob. This chapter is organised around them. We can store fewer key/value heads (multi-query and grouped-query attention), or compress what each token stores into a low-dimensional latent (DeepSeek's multi-head latent attention). We can keep fewer tokens per layer (sliding windows and local/global hybrids) or share the cache across layers. We can use fewer bits per number (KV quantisation), or evict tokens the model is unlikely to need again. Each technique appeared in response to a specific pressure, from Shazeer's 2019 observation about decode bandwidth to the long-context and reasoning workloads of 2024–25, and each has a cost: in quality, in compute, or in the complexity of the serving system. By the end of the chapter you will be able to compute the cache of any modern architecture, explain why DeepSeek-V3 needs half the cache per token of Llama 3 8B despite being eighty times larger, and judge which compression is appropriate for a given workload.

Learning objectives
  1. Decompose KV-cache size into its factors and classify every compression technique by the factor it reduces.
  2. Explain MQA and GQA, their quality trade-offs, uptraining from MHA checkpoints, and their interaction with tensor parallelism.

  4. Compute the cache of sliding-window and local/global hybrid models, and of cross-layer sharing schemes.
  5. Explain KV-cache quantisation (FP8, INT4, KIVI's per-channel keys and per-token values) and its error model.

8.1 Four knobs

Write the cache of one sequence of length \(T\) as

\[ \text{KV} \;=\; \underbrace{L}_{\text{layers}}\ \times\ \underbrace{2\,n_{kv}\,d_h}_{\text{numbers per token per layer}}\ \times\ \underbrace{T}_{\text{tokens kept}}\ \times\ \underbrace{b_{kv}}_{\text{bytes per number}} . \]

Every method in this chapter reduces one of these factors. Reducing the second factor, the width of what each token stores, is the province of attention architecture: share keys and values across heads, or compress them into a latent. Reducing the number of tokens kept per layer is the province of attention patterns (windows) and eviction. Reducing the number of layers that store distinct caches is cross-layer sharing. Reducing the bytes per number is quantisation. The first three classes change the model and usually require training it that way. The last two can often be applied to an existing model at serving time, at some cost in accuracy.

Figure 8.1 lays out the taxonomy, and the factors multiply: a model can combine several techniques, and modern ones do. Character.AI's production models, for instance, combined multi-query attention, local attention in most layers and cache sharing between adjacent layers, and reported a reduction of more than 20× relative to a standard design[1]. We take the factors one at a time, starting with the one that has done the most work in practice.

8.2 Fewer heads: MQA and GQA

Chapter 2 introduced multi-query and grouped-query attention briefly (§2.4). We now examine them as compression techniques. In standard multi-head attention (MHA) every one of the \(n_h\) query heads has its own key and value heads, so each token stores \(2n_hd_h=2d\) numbers per layer, as many as the model width. Shazeer's 2019 paper[2] began from a measurement. On TPUs of the time, incremental decoding of an MHA Transformer was dominated by the memory bandwidth needed to load the cached keys and values, not by arithmetic. His remedy, multi-query attention (MQA), keeps \(n_h\) query heads but only one key head and one value head, shared by all queries. The cache shrinks by a factor of \(n_h\), and decode attention's intensity rises from 1 to \(n_h\) FLOPs per byte (§3.5), because each loaded key and value now serves every query head.

MQA was adopted by PaLM (2022) and Falcon, but it has two drawbacks. Quality suffers somewhat, because all heads must agree on a single representation of each token's keys and values. And training can be less stable. Ainslie et al. (2023)[3] proposed the interpolation that is now nearly universal, grouped-query attention (GQA). The \(n_h\) query heads are divided into \(n_{kv}\) groups of \(g=n_h/n_{kv}\), and each group shares one key/value head. MHA is the case \(g=1\) and MQA the case \(n_{kv}=1\). They also showed that an existing MHA checkpoint can be converted ("uptrained") to GQA by mean-pooling the key and value projections within each group and continuing training for about 5% of the original pre-training compute, recovering nearly all of the quality.

Figure 8.2 draws the per-token, per-layer storage of each variant to scale for a model shaped like Llama 3 70B. MHA would store 16,384 numbers per token per layer, the same as two copies of the residual vector. Llama 3 70B's actual GQA with eight KV heads stores 2,048, and MQA would store 256. MLA, which we derive next, stores 576 numbers per token per layer for DeepSeek's 128-head models, between GQA and MQA in size but with quality the DeepSeek team reports as better than MHA.

GQA and tensor parallelism

One systems interaction is worth noting before moving on. Under tensor parallelism (Chapter 18), attention heads are divided among GPUs. With \(n_{kv}=8\) KV heads and eight GPUs, each GPU holds one KV head and its group of query heads, and the cache divides cleanly. With sixteen GPUs, there are not enough KV heads to go round, so each KV head must be replicated on two GPUs, and the per-GPU cache stops shrinking. MQA is the extreme case: its single KV head must be replicated on every GPU. The degree of tensor parallelism that a GQA model supports efficiently is therefore bounded by \(n_{kv}\), one of several reasons the eight-KV-head design is so common.

8.3 Compressing: multi-head latent attention

GQA and MQA reduce the cache by forcing heads to share. DeepSeek-V2 (2024)[4] asked a different question. Must each token's keys and values for all heads really be stored at full dimension? Or do they lie in a low-dimensional subspace that can be stored instead? Multi-head latent attention (MLA) answers by caching one compressed vector per token and reconstructing every head's keys and values from it. The derivation is elegant, and its key step, weight absorption, is a favourite interview question.

Low-rank keys and values

Let \(h_t\in\mathbb R^{d}\) be the (normalised) input of token \(t\) to an attention layer. MLA first projects it down to a latent of dimension \(d_c\ll n_hd_h\), and then up to the keys and values of each head \(i\):

\[ c_t = W_{DKV}\,h_t\in\mathbb R^{d_c},\qquad k^{C}_{t,i} = W_{UK,i}\,c_t,\qquad v_{t,i} = W_{UV,i}\,c_t,\qquad W_{UK,i},W_{UV,i}\in\mathbb R^{d_h\times d_c}. \]

Only \(c_t\) is cached. In DeepSeek-V2 and V3, \(d_c=512\), against \(2n_hd_h=2\times128\times128=32{,}768\) numbers for MHA with the same 128 heads. Queries are also computed through a low-rank bottleneck to save parameters, but queries are not cached, so that does not affect the cache. Naively, MLA would reconstruct every head's keys and values from the latents at every step, a matrix product per cached token per head. That would make decode far more expensive in compute. The trick that avoids it is to never reconstruct them at all.

Proposition — weight absorption

Ignoring positions for the moment, the attention score of query head \(i\) at position \(t\) against cached token \(j\) is \[ q_{t,i}^{\top}k^{C}_{j,i} = q_{t,i}^{\top}W_{UK,i}\,c_j = \big(W_{UK,i}^{\top}q_{t,i}\big)^{\top}c_j =: \tilde q_{t,i}^{\top}c_j . \] So instead of reconstructing \(k^C_{j,i}\) for every cached token, we transform the query once per step into the latent space, \(\tilde q_{t,i}=W_{UK,i}^{\top}q_{t,i}\in\mathbb R^{d_c}\), and score it directly against the cached latents. Equivalently, \(W_{UK,i}\) is absorbed into the query projection. Similarly, the output of head \(i\) is \[ o_{t,i} = \sum_j p_{t,i,j}\,W_{UV,i}\,c_j = W_{UV,i}\Big(\sum_j p_{t,i,j}\,c_j\Big), \] so the weighted sum is taken over latents, and \(W_{UV,i}\) is applied once per step, or absorbed into the output projection \(W_O\). ∎

After absorption, decode-time MLA looks like multi-query attention with an unusual shape. All \(n_h\) heads attend over the same cached vectors \(c_j\), which play the role of a single shared key and value head of dimension \(d_c=512\). Each head has its own transformed query. Computationally this is excellent. Each cached latent, once loaded, is used by all 128 heads, so the arithmetic intensity of decode attention is in the hundreds of FLOPs per byte, close to the H100's ridge point, compared with \(g\le8\) for GQA (§3.5). It is the reason DeepSeek wrote dedicated decode kernels (FlashMLA) that are compute-bound rather than memory-bound.

Why RoPE must be decoupled

The absorption argument has a gap: it ignored positions. With rotary embeddings (§2.5), the key of token \(j\) is rotated by a matrix \(R_j\) that depends on its position, so the score becomes

\[ (R_tq_{t,i})^{\top}R_j\,W_{UK,i}\,c_j = q_{t,i}^{\top}R_{j-t}\,W_{UK,i}\,c_j . \]

The rotation \(R_{j-t}\) now sits between the query and \(W_{UK,i}\), and it depends on the cached token's position. \(W_{UK,i}\) can no longer be absorbed into a single fixed query transformation, because each cached token would need a different one. MLA's solution is to split each head's query and key into two parts. A content part of dimension \(d_h\) carries no positional rotation and goes through the latent, so it can be absorbed as above. A small positional part of dimension \(d_h^R=64\) is rotated by RoPE. For keys, the positional part \(k^R_t\in\mathbb R^{d_h^R}\) is computed directly from \(h_t\), shared across all heads, and cached alongside the latent. The score is the sum of the two parts, \(\tilde q_{t,i}^{\top}c_j+(q^R_{t,i})^{\top}k^R_j\), scaled by \(1/\sqrt{d_h+d_h^R}\).

Figure 8.3 assembles the pieces. On the left, each new token's input produces a latent \(c_t\) and a shared rotated key \(k^R_t\). These 576 numbers are all that is cached. On the right, each query head transforms its content query into the latent space once per step, scores it against every cached latent plus a positional term, and combines the latents with the resulting weights. A single up-projection per head (absorbed into the output projection) then returns to the model width. Nothing per-head is ever stored for past tokens.

Worked example — DeepSeek-V3's cache and attention intensity

Size. 61 layers × 576 numbers × 2 bytes = 70,272 bytes ≈ 68.6 KiB per token in BF16. MHA with 128 heads of dimension 128 would need \(61\times32{,}768\times2\) B ≈ 3.8 MiB per token, 57 times more. DeepSeek reports that MLA's cache is comparable to GQA with only about 2.25 groups, while its quality slightly exceeds MHA's.

Decode intensity. Per cached token per layer, the kernel reads \(576\times2=1{,}152\) bytes. Each of the 128 heads computes a 576-dimensional score (\(2\times576\) FLOPs) and accumulates a 512-dimensional latent (\(2\times512\)), for \(128\times2{,}176\approx2.8\times10^5\) FLOPs. Intensity ≈ 242 FLOPs per byte, roughly 60 times that of Llama 3 8B's GQA attention (4), and close to the H100's ridge (295).

Price. More arithmetic per cached byte, extra projection matrices, and a kernel that must be specially written. For decode-heavy serving this is an excellent trade.

Drill 8.2 — How small is MLA's cache?

DeepSeek-V3 has 61 layers and caches, per token and layer, a latent of \(d_c=512\) values plus a decoupled RoPE key of \(d_h^R=64\) values, in BF16. Compute its cache per token, and compare with standard multi-head attention for its 128 heads with 192-dimensional keys and 128-dimensional values.

Solution. MLA: \((512+64)\times2\) bytes = 1,152 bytes per layer, \(\times61\approx70{,}272\) bytes, 68.6 KiB per token. MHA with the same heads: \(128\times(192+128)\times2=81{,}920\) bytes per layer, about 5.0 MB per token over 61 layers, 71 times more. A 128k-token context would need 640 GB with MHA and 9 GB with MLA. Llama 3 8B's GQA cache, 128 KiB per token, is about twice MLA's despite a model eighty times smaller, the comparison promised in this chapter's opening.

8.4 Fewer tokens per layer: sliding windows and hybrids

A different route to a smaller cache is to let most layers attend only to recent tokens. In sliding-window attention, the query at position \(i\) attends only to keys at positions \(j\) with \(i-w<j\le i\), for a window size \(w\). That is a banded causal mask, used for efficient long-document Transformers since Longformer (2020) and adopted for an LLM by Mistral 7B (2023) with \(w=4096\)[5]. A sliding-window layer needs to cache only the last \(w\) tokens, so its cache stops growing once the sequence exceeds the window. It is typically stored as a ring buffer that overwrites the oldest entry. Information from further back can still reach the current token, but only indirectly, by being carried forward through the residual streams of intermediate positions across layers: with \(L\) layers, the theoretical receptive field is about \(Lw\).

Figure 8.4 contrasts the two masks. Under full causal attention (left), the last query attends to every earlier position, and the cache for that layer must hold them all. Under a sliding window (right), every query attends to a band of fixed width, and everything to the left of the band can be discarded. The quality risk is clear: a pure sliding-window model cannot directly retrieve a specific fact from far back in a long document. The modern answer is the local/global hybrid. Most layers use a short window, and every few layers a full ("global") attention layer gives direct access to the whole context. Gemma 2 alternated local and global layers one-to-one, with a 4,096-token window. Gemma 3 moved to five local layers per global layer with a window of only 1,024 tokens, and its report found that this ratio, and even 7:1, barely affected perplexity[6].

The cache saving of a hybrid is easy to compute. If a fraction \(\phi\) of layers are global, the cache relative to an all-global model with the same layer shapes is

\[ \frac{\text{KV}_{\text{hybrid}}}{\text{KV}_{\text{global}}} = \phi + (1-\phi)\,\frac{\min(T,w)}{T} \ \xrightarrow{\ T\to\infty\ }\ \phi . \]

Figure 8.5 plots this ratio for three designs. Up to the window size, every design stores the same cache as full attention. Beyond it, the all-sliding model's cache stops growing entirely, so its relative size falls as \(w/T\): to 3% at 128k tokens. The hybrids converge to their fraction of global layers, about one half for Gemma 2's alternation and one sixth for Gemma 3's 5:1 pattern. At 128k tokens Gemma 3's design stores 17% of what full attention would. For serving, hybrids bring one complication: different layers now have caches of different lengths and lifetimes. The memory manager (Chapter 10) must handle ring-buffered local layers alongside growing global ones, and prefix caching must track both.

8.5 Fewer layers: sharing the cache across layers

If adjacent layers compute similar keys and values, perhaps they could share them. Cross-layer attention (CLA) (Brandon et al., 2024)[7] lets groups of adjacent layers reuse the key/value projections, and hence the cache, of the first layer in the group. Sharing across pairs halves the cache, at a small cost in quality when trained in from the start. Character.AI reported sharing caches across two or three neighbouring layers in its production models[1]. YOCO ("You Only Cache Once", Sun et al., 2024)[8] takes the idea to its limit. The first half of the network uses efficient local attention, and a single global cache, produced once at the midpoint, is attended to by every layer of the second half. That brings the cache close to that of a single layer, and also allows the prefill of the second half to be skipped for most of the prompt.

Figure 8.6 shows the simplest form, sharing between pairs of layers. Each pair computes keys and values once and both layers attend to them, so the number of distinct caches halves. As with the other architectural knobs, the saving must be trained into the model. Unlike them, it also reduces the work of producing the cache, since half the layers no longer compute key and value projections at all.

8.6 Fewer bits: quantising the cache

The architectural knobs must be chosen before training. The last two families can be applied to a model that already exists. The simplest is to store the cache in fewer bits. Chapter 14 treats quantisation in general. Here we need only its basic form: replace each number \(x\) by a low-precision code from which an approximation \(\hat x\) can be recovered, typically \(\hat x = s\cdot\operatorname{round}(x/s)\) with a scale \(s\) shared by a group of numbers.

FP8 caches (8-bit floating point, E4M3) are the standard first step. They halve the cache with a per-tensor or per-head scale and usually negligible quality loss, and every major engine supports them. They double the number of sequences that fit and halve the cache-read time of decode, which by §6.4 doubles the critical context length. Going further, to 4 or even 2 bits, requires care, because the errors in keys and values affect attention differently. An error \(\delta k\) in a key changes the score by \(q^{\top}\delta k\), which the softmax exponentiates, so key errors can change which tokens are attended to. An error in a value changes the output linearly in proportion to its attention weight. Keys also turn out to have a few channels (coordinates of \(d_h\)) with consistently large magnitudes. A scale shared across a whole token vector is then dominated by those outlier channels, and the small channels lose all their precision.

KIVI (Liu et al., 2024)[9] built its method on exactly these observations. It quantises keys per channel (each coordinate gets its own scale, computed over a group of tokens) and values per token. It keeps the most recent tokens in full precision until a group is complete, and reaches 2-bit caches with little accuracy loss, a 2.6× reduction in peak memory for Llama 2 7B. KVQuant and others refined the approach with non-uniform codebooks and by quantising keys before RoPE, since the rotation mixes outlier channels with others. The serving cost of aggressive cache quantisation is in the kernel. Attention must dequantise on the fly while reading, which is cheap relative to memory traffic but must be fused into the attention kernel (Chapter 9) to realise the bandwidth savings.

Drill 8.1 — How far does quantisation move the frontier?

Llama 3 8B on one H100 with 16 GB of BF16 weights and 60 GB available for cache. At 8k-token contexts, how many sequences fit with BF16, FP8 and 4-bit caches?

Solution. Per sequence: \(8192\times128\) KiB = 1 GiB in BF16, 0.5 GiB in FP8, 0.25 GiB in 4-bit (ignoring scale overhead). Sequences: about 56, 112 and 224. Since decode at these contexts is cache-dominated, step time at full occupancy is set by roughly the same total cache bytes in each case, so throughput rises nearly in proportion to the batch size, about 4× from BF16 to 4-bit, provided quality holds.

Worked example — FP8 cache for Llama 3 8B at 32k context

Setup. Llama 3 8B, \(s_{kv}=128\) KiB per token in BF16, serving 32k-token contexts on one H100. We budget about 72 GB of the 80 GB for weights and cache (the rest goes to the runtime and activations), which leaves \(72-16.06\approx56\) GB for the cache. Bandwidth efficiency is 80%, so 2.68 TB/s.

BF16 cache. One sequence of 32,768 tokens needs \(32{,}768\times128\) KiB = 4 GiB ≈ 4.29 GB, so 13 sequences fit. A decode step reads \(16.06+13\times4.29\approx71.9\) GB in 26.8 ms: 485 output tokens per second in total, 37 per user.

FP8 cache. At one byte per element, \(s_{kv}\) halves to 64 KiB and 26 sequences fit. A full batch of 26 reads the same 71.9 GB, so the step time is unchanged at 26.8 ms and throughput doubles to 970 tokens per second. Alternatively, keeping the batch at 13 cuts the bytes to \(16.06+27.9=44\) GB and the step to 16.4 ms, so each user is 1.6 times faster.

Consequence. At long context the cache, not the weights, dominates the bytes of a step (here 78% of them), so halving the cache is worth almost as much as halving everything. The quality cost of FP8 KV with per-head scales is small (§8.6), which is why it has become a default in long-context serving.

8.7 Fewer tokens: eviction and selection

The final family keeps the model and the precision but discards, or declines to read, cached tokens that seem unimportant. The motivating observation is that attention is often sparse: most of a query's probability mass falls on a small subset of positions. If we could identify that subset, we could store or read only it.

A first discovery set the constraints. Xiao et al. (2023) noticed that simply keeping a sliding window of recent tokens in a model trained with full attention causes quality to collapse as soon as the earliest tokens are evicted[10]. The reason is that models learn to dump large amounts of attention on the first few tokens, which act as attention sinks: a place to put probability mass when nothing else is relevant, because softmax weights must sum to one. Keeping just the first four tokens plus a recent window (StreamingLLM) restores stable generation over effectively unlimited lengths. It does not, however, restore the ability to recall evicted content.

Figure 8.7 compares three policies on a 24-token sequence with a budget of about a third of the tokens. A pure window keeps only recent tokens and collapses. Sinks plus a window keeps generation stable. Sinks, heavy hitters and a short window keep the tokens that past queries attended to most. H2O (Zhang et al., 2023)[11] introduced the heavy-hitter policy, with cumulative attention scores as the importance signal. SnapKV (Li et al., 2024)[12] compresses a long prompt once, after prefill: it uses the attention of the last few prompt tokens (an "observation window") to vote for the positions each head will need, a good fit for long-document question answering, where the question comes last. PyramidKV allocates larger budgets to lower layers, which attend more broadly. A different line declines to evict anything and instead reads selectively. Quest (Tang et al., 2024)[13] keeps the full cache but stores, for each page of cached keys, element-wise minima and maxima, uses them to bound each page's possible score for the current query, and loads only the top-scoring pages. That reduces bytes read without losing information permanently.

All of these methods share a weakness, and it has grown more serious with the reasoning workloads of §1.12. They estimate future importance from past attention. A token that seemed irrelevant when evicted may become essential later, and once evicted it cannot be recovered. Long-input workloads, where the prompt is fixed and compressed once, tolerate this reasonably well. Long-output workloads, where a model reasons for tens of thousands of tokens and repeatedly returns to earlier steps, tolerate it badly. Recent studies report that methods designed for long inputs are often ineffective in the long-output regime, and propose learned or lookahead importance estimates in response[14]. Selective reading (Quest, and the trained sparse attention of DeepSeek's V3.2; Chapter 21) avoids the irrecoverability problem at the cost of still storing everything. For production systems, the safe order of adoption is: architectural reduction (choose a GQA/MLA/hybrid model), then FP8 cache quantisation, then selective reading, and only then eviction, validated on the actual workload.

8.8 Putting it together

How much do these techniques achieve in practice? The chart below places a range of real models by their parameter count and their cache bytes per token, coloured by attention type.

Figure 8.8 shows that cache size per token has become almost decoupled from model size. Llama 2 7B, a small MHA model, stores more per token than the 540-billion-parameter PaLM with MQA. A hypothetical MHA version of Llama 3 70B would store eight times more than the real GQA model. The two DeepSeek models, with 236 and 671 billion parameters, store the least of all. The trend from 2019 to 2025 has been to decouple capacity, the parameters that hold knowledge, from state, the per-token memory that inference must carry. Combined with FP8 caches, windowed layers and careful memory management, modern architectures carry roughly one to two orders of magnitude less state per token than a naive design of the same size.

A free serving-time change, the FP8 cache, doubles it again. Either a latent-attention architecture or a local/global hybrid gives roughly another fourfold improvement. And because, at these context lengths, decode step time is dominated by reading caches, fitting more users in memory translates almost directly into more throughput at a given latency (§6.6). The difference between the first and last rows is the difference between a product that is uneconomic to serve and one that is profitable. Architectural choices about the cache are therefore as much business decisions as modelling ones, which is why every major open-model release since 2023 has led with them.

A design question you should be ready for

"You are designing a 30B model for 128k-context serving. How would you size its KV cache?" A strong answer computes the MHA baseline, proposes GQA with \(n_{kv}\) matched to the intended tensor-parallel degree (or MLA if the team can build the kernels), adds a local/global hybrid for the long-context layers, plans for an FP8 cache at serving, quantifies each step's saving and quality risk, and states the resulting concurrency on the target GPU, for example via the critical-context-length formula of §6.4.

Looking ahead

This chapter made the cache smaller. However small it becomes, it must still be read: at every decode step for every sequence, and, during prefill, as part of an attention computation whose naive form writes a \(T\times T\) matrix to memory. The next question is how to read the cache, and compute attention over it, with as little memory traffic as possible. Chapter 9 answers it with FlashAttention, which applies the online softmax of §7.5 to compute exact attention in tiles that never leave on-chip memory, and follows its evolution across four GPU generations, together with the decode-time kernels (FlashDecoding, FlashInfer, FlashMLA) that read compressed and paged caches at full bandwidth.

Chapter summary

  • KV size = \(L\times2n_{kv}d_h\times T\times b_{kv}\). Techniques reduce one factor each: width per token (MQA, GQA, MLA), tokens per layer (windows, hybrids, eviction), layers with distinct caches (CLA, YOCO), or bits (quantisation).
  • MQA shares one KV head across all query heads (cache ÷ \(n_h\)); GQA shares one per group (cache ÷ \(g\)), recovering quality, and MHA checkpoints can be uptrained to GQA with ~5% extra compute. Tensor parallelism beyond \(n_{kv}\) forces KV replication.
  • MLA caches a latent \(c_t=W_{DKV}h_t\) (\(d_c=512\)) plus a shared RoPE key (64). Weight absorption (\(q^{\top}W_{UK}c=(W_{UK}^{\top}q)^{\top}c\), and \(W_{UV}\) into \(W_O\)) lets all heads attend directly over latents. RoPE is decoupled because rotations do not commute with absorption. DeepSeek-V3: ≈ 68.6 KiB per token, decode intensity ≈ 240 FLOPs/byte.
  • Sliding windows bound each local layer's cache at \(w\) tokens; hybrids converge to the fraction of global layers \(\phi\) (Gemma 3: 1/6, window 1,024).
  • Cross-layer sharing divides distinct caches by the group size; YOCO caches once for the whole second half of the network.
  • FP8 caches halve the cache almost for free. 2–4-bit caches need per-channel key and per-token value quantisation (KIVI) and fused dequantisation.
  • Eviction must keep attention sinks; heavy-hitter (H2O) and observation-window (SnapKV) policies keep important tokens; Quest reads selectively without evicting. Eviction is risky for long-output reasoning workloads.

Warm-up What are MQA and GQA, and why were they introduced?

Both reduce the KV cache by sharing key/value heads among query heads. MQA (Shazeer, 2019) uses one KV head for all \(n_h\) query heads: the cache shrinks by \(n_h\) and decode attention's intensity rises to ≈ \(n_h\), but quality and stability can suffer. GQA (Ainslie et al., 2023) uses \(n_{kv}\) KV heads, each shared by a group of \(g=n_h/n_{kv}\) query heads, recovering near-MHA quality with a \(g\)-fold smaller cache; MHA checkpoints can be uptrained to GQA. Motivation: decode is bound by the bandwidth of reading cached K/V, and the cache limits concurrency. Attention FLOPs are unchanged.

Core Derive multi-head latent attention and the weight-absorption trick.

Cache a latent \(c_t=W_{DKV}h_t\in\mathbb R^{d_c}\) (\(d_c=512\)) instead of per-head K/V; reconstruct \(k^C_{t,i}=W_{UK,i}c_t\), \(v_{t,i}=W_{UV,i}c_t\). Absorption: \(q_{t,i}^{\top}W_{UK,i}c_j=(W_{UK,i}^{\top}q_{t,i})^{\top}c_j\), so compute \(\tilde q_{t,i}=W_{UK,i}^{\top}q_{t,i}\) once per step (or fold \(W_{UK}\) into the query projection) and score against latents directly. Output: \(\sum_jp_jW_{UV,i}c_j=W_{UV,i}\sum_jp_jc_j\), so \(W_{UV}\) folds into \(W_O\). RoPE: rotations would sit between \(q\) and \(W_{UK}\) and depend on \(j\), breaking absorption, so add a small decoupled RoPE part: queries get a per-head rotated part, keys a shared rotated part \(k^R_t\in\mathbb R^{64}\), cached with \(c_t\). Score = \(\tilde q^{\top}c_j+q^{R\top}k^R_j\). Cache: 576 numbers per token per layer. All heads attend over the same latents, like MQA with head dim 576/512, giving decode intensity ≈ 240 FLOPs/byte.

Core Compute the KV cache per token for Llama 3 70B and DeepSeek-V3, and explain the difference.

Llama 3 70B (GQA): \(2\times80\times8\times128\times2\) B = 327,680 B = 320 KiB. DeepSeek-V3 (MLA): \(61\times(512+64)\times2\) B = 70,272 B ≈ 68.6 KiB. DeepSeek is ~10× larger in parameters but needs ~4.7× less cache per token: MLA stores one 576-dim latent per layer shared by 128 heads, whereas GQA stores 8 heads × (K+V) × 128 = 2,048 numbers per layer. A 128k-token context needs ≈ 40 GiB for Llama 3 70B and ≈ 8.6 GiB for DeepSeek-V3.

Core How do sliding-window and local/global hybrid models reduce the cache, and what do they cost?

A window layer attends to the last \(w\) tokens and caches only those (a ring buffer), so its cache is bounded. With a fraction \(\phi\) of global layers, cache ratio = \(\phi+(1-\phi)\min(T,w)/T\to\phi\) (Gemma 3: 1 global per 6, \(w=1024\), ≈ 17% at 128k). Costs: weaker direct long-range retrieval in local layers (mitigated by global layers); training must include the pattern; serving complexity, because layers have different cache lengths and lifetimes, affecting paging, prefix caching and kernel dispatch; and attention kernels must support windowed masks efficiently, which they generally do.

Core Explain KV-cache quantisation and why keys and values are quantised differently.

Store cached K/V at lower precision with scales (FP8 E4M3 with per-tensor/per-head scales is near-lossless; INT4/INT2 need finer grouping). Keys exhibit a few outlier channels with large magnitude, so per-token scaling wastes precision; quantising keys per channel isolates them. Values have no such channel structure and are quantised per token. Key errors also matter more because scores are exponentiated by the softmax. KIVI implements this asymmetric scheme, keeping the most recent tokens in full precision until a group fills, reaching 2-bit caches with small accuracy loss. Practical points: fuse dequantisation into the attention kernel; consider quantising keys pre-RoPE (KVQuant); validate on long-context and reasoning tasks.

Deep-dive What are attention sinks, and what do they imply for KV eviction and streaming?

Trained LMs place large attention mass on the first few tokens regardless of content: softmax must allocate probability somewhere, and early tokens, visible to every query, become a learned "no-op" target. Evicting them shifts that mass elsewhere and destabilises outputs; StreamingLLM found that perplexity explodes when a window passes the initial tokens. Keeping ≈ 4 sink tokens plus a recent window gives stable generation over unlimited length, but does not let the model recall evicted content. Implications: eviction policies must pin sinks; models can be trained with a dedicated learnable sink token; with RoPE, sinks and window tokens must keep consistent positions (StreamingLLM assigns positions within the cache rather than in the original text).

Deep-dive Compare H2O, SnapKV and Quest. When would you use each, and what are the risks?

H2O: during decoding keep sinks, recent tokens and "heavy hitters" with high cumulative attention; continuous eviction under a budget. Risk: past attention is a poor predictor of future need. SnapKV: one-shot compression of the prompt after prefill, using the attention of the last few prompt tokens to vote per head for positions to keep. Good for long-document QA where the question is at the end; less robust when later queries need different parts. Quest: no eviction; per-page key min/max give upper bounds on scores, and only the top pages are read per step. It saves bandwidth but not memory, and is safe against irreversible loss. For reasoning or agentic workloads prefer selective reading or architectural reductions over eviction, and always evaluate on the target tasks (long-output benchmarks, needle retrieval, multi-hop QA).

Core How does GQA interact with tensor parallelism?

Tensor parallelism splits attention heads across GPUs. With \(n_{kv}\) KV heads and TP degree \(p\le n_{kv}\) (dividing evenly), each GPU holds \(n_{kv}/p\) KV heads and their query groups: the cache divides by \(p\) and no communication is needed inside attention. If \(p>n_{kv}\), KV heads must be replicated (each on \(p/n_{kv}\) GPUs), so per-GPU cache stops shrinking and K/V projections are duplicated. MQA (\(n_{kv}=1\)) must replicate on every GPU. This is one reason \(n_{kv}=8\) matches common 8-GPU servers, and why very large deployments combine TP with other parallelism (data-parallel attention, expert parallelism) rather than raising TP further.

Design Design the attention and KV-cache strategy for a 30B model that must serve 128k contexts efficiently on H100s.

Baseline MHA (say \(L=60\), \(d=6144\), 48 heads × 128): \(2\times60\times6144\times2\) B ≈ 1.4 MiB/token, 180 GiB per 128k sequence, untenable. Steps: (1) GQA with \(n_{kv}=8\) (6× smaller, ≈ 240 KiB/token), matched to TP ≤ 8; or MLA if kernels are available (≈ 70 KiB/token). (2) A local/global hybrid, e.g. 1 global per 4–6 layers with \(w=1024\)–4096 (cache ≈ 20% at 128k). (3) FP8 cache at serving (2×). Result: ≈ 240 KiB × 0.2 × 0.5 ≈ 24 KiB/token effective, ≈ 3 GiB per 128k sequence, enough for many concurrent long sequences per GPU alongside 30 GB of FP8 weights. Validate long-context retrieval (needle, RULER) and reasoning quality; ensure the serving stack (paging, prefix caching, attention kernels) supports mixed window layers.

Core Why does MLA make decode attention close to compute-bound, and what does that mean for kernel design?

After absorption, all \(n_h=128\) heads attend over the same cached latent (576 numbers). Each byte loaded is used by 128 heads: per cached token per layer ≈ 128 × (2·576 + 2·512) ≈ 2.8 × 10⁵ FLOPs over 1,152 bytes, ≈ 240 FLOPs/byte, near the H100 ridge (295). So the kernel must use tensor cores efficiently (batched matmuls over heads × latents) rather than streaming like a GQA decode kernel; DeepSeek's FlashMLA does this, with paged latent caches. A consequence: MLA trades memory for compute, and the trade is good precisely because decode had spare compute.

Warm-up List the families of KV-cache reduction and the factor each attacks.

KV = L × 2·n_kv·d_h × T × b. Width per token: MQA, GQA, MLA (and low-rank post-hoc compression). Tokens per layer: sliding windows, local/global hybrids, eviction (StreamingLLM, H2O, SnapKV, PyramidKV), merging tokens. Layers with distinct caches: cross-layer attention, YOCO, KV sharing. Bytes per number: FP8, INT4/INT2 (KIVI, KVQuant). Selective reading (Quest, trained sparse attention) reduces bytes read without reducing storage.

Deep-dive Can you convert a trained GQA model to MLA without retraining from scratch? What would you expect?

Partially. GQA's K/V projections already factor through a low-dimensional space (\(2n_{kv}d_h=2048\) for Llama-70B-like models), so a GQA layer can be rewritten exactly as an MLA-like layer with \(d_c=2048\) and up-projections that select and replicate heads. Further compression requires a low-rank approximation of the stacked K/V projections (SVD of \(W_K\), \(W_V\) jointly, or of their activations), and RoPE must be handled by keeping a decoupled rotated part, since rotation does not commute with the compression. Expect some quality loss proportional to the discarded spectrum, mostly recoverable with a modest amount of continued training (several research works, such as TransMLA-style conversions, report this). Serving gains require MLA kernels and engine support.

Core By how much does an FP8 KV cache improve decode throughput, and when is it most valuable?

It halves cache bytes: (1) twice as many sequences fit; (2) per-step cache-read time halves; (3) \(t_{\text{crit}}\) doubles. When the cache dominates the step (long contexts, large batches, small GQA groups), throughput at a fixed TPOT nearly doubles (Figure 6.7). When weights dominate (short contexts, small batch), the gain is small. Most valuable for long-context chat, RAG, reasoning traces and agents. Quality impact is usually negligible with E4M3 and sensible scales, but must be validated, especially on retrieval-heavy tasks.

Design A customer's agent workload has 100k-token contexts and 10k-token reasoning outputs. Your engineers propose H2O eviction to triple concurrency. What do you advise?

Caution. Long-output reasoning revisits earlier context and intermediate steps; importance estimated from past attention is unreliable, and evicted tokens cannot be recovered, so accuracy failures will be silent and task-dependent. Prefer, in order: (1) FP8 (or carefully validated INT4) cache, a reliable 2–4×; (2) selective reading (Quest-like or a natively sparse-attention model) to cut bandwidth without loss; (3) hierarchical offload of cold cache to CPU (Chapter 10); (4) a model with MLA or hybrid attention if model choice is open; (5) prefix caching for shared context across agent steps. If eviction is still desired, A/B test on the real agent tasks with end-to-end success metrics, keep sinks and generous budgets, and consider lookahead or learned importance methods designed for long outputs.

Core Why does Shazeer's 2019 observation still matter more on today's GPUs than it did on 2019 TPUs?

Shazeer observed decode was bound by reading K/V, not by FLOPs. Since then compute has grown much faster than bandwidth (the memory wall; ridge points rose from ~150 to ~300+ in BF16 and higher in FP8/FP4), and contexts grew from ~2k to 128k+ tokens, with reasoning traces adding long outputs. Cache reads grow with context while weight reads are amortised by batching, so the cache's share of decode time has grown, and \(t_{\text{crit}}=2N_{\text{mm}}/(I^*s_{kv})\) has fallen as \(I^*\) rose. Reducing \(s_{kv}\) is therefore more valuable now than when MQA was proposed, which explains the progression MQA → GQA → MLA and the adoption of FP8 caches.
