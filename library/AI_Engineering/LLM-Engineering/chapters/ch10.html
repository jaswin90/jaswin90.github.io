Part III · Attention and Memory — Chapter 10

Memory Management: PagedAttention and Prefix Caching

How a 60-year-old idea from operating systems, virtual memory, turned the KV cache from a source of waste into a shared, reusable and tiered resource.

Why this chapter

Chapters 8 and 9 shrank the KV cache and made reading it fast. One problem remains, and it is not about arithmetic or bandwidth at all: where in memory should each sequence's cache live? The question sounds mundane, but in 2023 it turned out to be worth a factor of two to four in serving throughput. Sequences grow one token at a time, to lengths nobody knows in advance. A server that reserves each request's maximum possible length up front wastes most of what it reserves. A server that packs caches tightly cannot grow them without copying. Kwon et al. measured that systems of the day used only 20–38% of the memory they reserved for KV caches to store actual tokens[1]. And since Chapter 3 showed that KV capacity limits batch size and batch size limits throughput, wasted memory is directly wasted money.

The solution, PagedAttention and the vLLM system built around it, borrowed the idea operating systems have used since the 1960s to give programs the illusion of contiguous memory on top of scattered physical pages. Once the cache is paged, three further capabilities follow almost for free, and this chapter develops each. Several sequences can share pages, for parallel sampling, beam search and common prompts. Caches can be kept and reused across requests, so a system prompt or document is processed once and served many times: prefix caching. And pages can be moved between GPU memory, CPU memory, SSDs and remote stores, a memory hierarchy for the KV cache. We end with the economics: when is it cheaper to load a cached prefix than to recompute it? The answer, for most models and most storage tiers, is "almost always".

Learning objectives
  1. Identify the three kinds of memory waste in contiguous KV allocation and quantify them.
  2. Explain virtual memory and paging, and map each concept onto PagedAttention's block tables.
  3. Analyse the block-size trade-off between internal fragmentation, kernel efficiency and sharing granularity.
  4. Explain copy-on-write sharing for parallel sampling and beam search, and preemption by swapping or recomputation.
  5. Compare hash-based and radix-tree prefix caching, eviction policies, and cache-aware scheduling.
  6. Decide when loading a cached prefix from CPU, SSD or the network beats recomputing it.

10.1 The allocation problem

A KV cache is written one token at a time. When a request arrives, the server knows its prompt length but not its output length. The model will decide when to stop, anywhere from one token to the request's maximum, often thousands. Early serving systems such as FasterTransformer, and the first versions of Orca, handled this the way a C programmer allocates an array whose final size is unknown: they reserved a contiguous buffer large enough for the maximum length, prompt plus maximum output, for every request. A contiguous buffer is convenient because the attention kernel can find token \(t\)'s keys at a fixed offset. It also wastes memory in three distinct ways.

  • Reserved but unused. If a request is allowed 2,048 output tokens but stops after 200, about 90% of its output reservation is never written. Since output lengths vary widely, the expected waste is large: with lengths uniform between zero and the maximum, half of every reservation is wasted on average.
  • Internal fragmentation in the future. Even for a request that will eventually use its whole reservation, the part not yet generated sits empty for most of the request's lifetime.
  • External fragmentation. As requests of different sizes arrive and finish, free memory becomes scattered into gaps between live buffers. A new request may need more contiguous space than any single gap provides, even when the total free memory would suffice.

Figure 10.1 shows a stretch of GPU memory under contiguous allocation. Each request's buffer contains a used part, the prompt and the tokens generated so far, and a large reserved part that may never be used. Between buffers lie gaps left by finished requests, which together could hold another request but individually cannot. The consequence is that the server admits far fewer concurrent requests than its memory could support. By Chapter 3's analysis, fewer concurrent requests means lower throughput at the same latency. The waste is not a minor inefficiency. It is a 2–5× loss in the resource that decides serving cost.

Worked example — the cost of reserving the maximum length

An engine serving Llama 3 8B reserves a contiguous cache of max_model_len = 8,192 tokens for each request, 1 GiB at 128 KiB per token, while requests average 1,500 tokens of prompt and output. With 55 GB of cache memory, the engine admits 51 requests, although they use only about 9.6 GB of cache between them: 82% of the reserved memory holds nothing. Allocating in 16-token blocks as tokens arrive lets the same memory hold about 290 requests of average length, nearly six times the batch, and since decode throughput grows almost linearly with batch in the memory-bound regime, nearly six times the throughput. That is the case for PagedAttention (§10.3).

10.2 An old idea: virtual memory

Operating systems faced exactly this problem in the 1960s. Programs want to believe they have one large contiguous address space, but physical memory is shared by many programs that start, grow and finish unpredictably. The solution, first implemented in the Atlas computer at Manchester (1962) and universal today, is virtual memory with paging.

For the mathematician — paging as a function

Divide physical memory into fixed-size frames (pages), typically 4 KiB. Give each program a virtual address space divided into pages of the same size. A per-program page table is a partial function \(\tau:\{\text{virtual page numbers}\}\to\{\text{physical frame numbers}\}\). A virtual address \((p,\text{offset})\) refers to physical address \((\tau(p),\text{offset})\). Frames are allocated on first use, so memory a program never touches costs nothing. Any free frame can serve any page, so there is no external fragmentation, and the only waste is the unused tail of each program's last page (internal fragmentation of at most one page). Two programs can map the same frame, sharing it read-only. On a write, the system copies the frame first ("copy-on-write"). Frames can be moved to disk and back ("swapping") by updating \(\tau\).

Every property in that box solves one of the problems of §10.1, once "program" is read as "sequence", "virtual page" as "logical block of tokens" and "physical frame" as "physical block of KV memory". On-demand allocation removes reservation waste. Fixed-size frames remove external fragmentation. Shared frames enable sharing between sequences. Swapping enables offloading. The insight of Kwon et al. was to apply this mapping to the KV cache, and to write attention kernels that follow the page table.

10.3 PagedAttention

In vLLM, the KV cache of every layer is a pool of fixed-size blocks, each holding the keys and values of a fixed number of tokens (16 by default). Each sequence has a block table, its page table, listing which physical block holds each of its logical blocks: tokens 0–15, 16–31, and so on. When a sequence's last block fills, the memory manager takes any free block from the pool and appends its number to the table. When a sequence finishes, its blocks return to the pool. The attention kernel receives, for each sequence, its block table and length. To read token \(t\)'s keys it looks up physical block \(\text{table}[\lfloor t/16\rfloor]\) and offset \(t\bmod16\), one extra level of indirection.

Figure 10.2 shows two sequences sharing a pool of eight physical blocks. Sequence A's three logical blocks live in physical blocks 7, 1 and 4, which are not adjacent and not in order. Sequence B's two live in blocks 2 and 6. Only the last block of each sequence is partly empty. Every other block is full, and the free blocks 0, 3 and 5 can serve any sequence that needs to grow. The waste per sequence is therefore less than one block: on average about half a block, or eight tokens with the default size. For a sequence of hundreds or thousands of tokens that is under 1%, compared with the 60–80% waste measured in contiguous systems. In the vLLM paper this translated into 2–4× higher throughput than FasterTransformer and Orca at the same latency, purely by fitting more sequences into the same memory.

Choosing the block size

The block size is a trade-off with three terms. Internal fragmentation grows with block size: the expected waste per sequence is about \((b_{\text{blk}}-1)/2\) tokens for block size \(b_{\text{blk}}\). Kernel efficiency improves with block size: each block is a contiguous chunk the attention kernel can read with coalesced, vectorised loads, and fewer, larger blocks mean less indirection overhead. Sharing granularity (§10.4 and §10.6) gets coarser with block size: prefixes can be shared only in whole blocks.

Figure 10.3 plots the expected waste fraction, \(\frac{(b_{\text{blk}}-1)/2}{\bar t+(b_{\text{blk}}-1)/2}\), for two mean sequence lengths. With 16-token blocks, waste is 1.5% for 500-token sequences and 0.2% for 4,000-token ones. Even 64-token blocks, which some kernels prefer (FlashMLA uses 64), waste under 6% for short sequences. The curve is so flat in the practical range that block size is usually chosen for kernel efficiency and sharing granularity rather than fragmentation. The point of paging is not the exact block size but the move from reservation-proportional waste to block-proportional waste.

Drill 10.1 — How many more sequences fit?

An H100 has 60 GB available for Llama 3 8B's cache. Requests have 1,000-token prompts and a 2,000-token output limit, but actual outputs are uniformly distributed between 0 and 2,000 tokens. Compare the average number of concurrent sequences under contiguous max-length reservation and under paging with 16-token blocks.

Solution. Contiguous: each request reserves 3,000 tokens × 128 KiB ≈ 393 MB, so about 152 requests fit, regardless of how much they actually use. Paged: a request's live cache grows from 1,000 tokens to its final length. Weighting by how long each request spends at each length, with final lengths uniform on [1,000, 3,000], the time-averaged live length is \(\mathbb E[(F^2-1000^2)/2]/\mathbb E[F-1000]\approx1{,}670\) tokens (≈ 218 MB) plus half a block of waste, so about 275 requests fit on average, roughly 1.8 times as many. In practice the gain is larger, because contiguous systems also suffer external fragmentation, and servers must cap them conservatively to avoid running out of contiguous space.

10.4 Sharing blocks: copy-on-write

Paging makes sharing natural. Several sampling methods create sequences with a common prefix. An API request asking for \(n\) completions of one prompt, best-of-\(N\) reranking, and beam search (§4.2) all start \(n\) sequences from the same prompt and then diverge. With contiguous buffers, each would need its own copy of the prompt's cache. With paging, all \(n\) block tables can point at the same physical blocks for the shared prefix. Each physical block carries a reference count, the number of block tables that point to it. A block is freed only when its count falls to zero.

Sharing is safe for full blocks, which are never written again. The one subtlety is the last, partly filled block of the shared prefix: when the sequences diverge, each wants to append its own next token into that block. vLLM handles this with copy-on-write. When a sequence is about to write into a block whose reference count exceeds one, the memory manager first copies the block to a fresh physical block, points that sequence's table at the copy, and decrements the original's count. Only the partly filled block is ever copied, so the cost is at most one block per diverging sequence.

Figure 10.4 shows two samples of one prompt that fills two and a half blocks. Both block tables point at the same full blocks P0 and P1, whose reference counts are two. When sample 2 writes its first generated token, it finds P2 shared, so P2 is copied to P2′ and sample 2's table is updated. From then on the two samples share the full prompt blocks and own their own tails. For \(n\) samples of a long prompt, the prompt's cache is stored once rather than \(n\) times, a saving that grows with \(n\) and prompt length. Beam search uses the same mechanism more intensively. Beams fork and die at every step, and reference counting reclaims the blocks of pruned beams automatically.

10.5 When memory runs out: preemption

Paging lets a server admit requests on the basis of their current sizes rather than their maximums. But current sizes grow. If the server admits aggressively, the running requests may collectively need more blocks than exist before any of them finishes. The server must then preempt some requests, freeing their blocks so that others can continue. vLLM implements two ways to do this. Swapping copies the preempted request's blocks to CPU memory over PCIe and brings them back when space frees up. Recomputation discards the blocks and, when the request resumes, recomputes its cache by running a prefill over the prompt plus the tokens generated so far.

Which is cheaper? Swapping costs two transfers of the request's cache over PCIe. Recomputation costs a prefill whose duration Chapter 3 modelled. For Llama 3 8B with 4,096 tokens of context, swapping out and back moves 2 × 512 MiB, about 17 ms at 64 GB/s, while recomputation takes about 130 ms at 50% MFU. Swapping is cheaper per request, but it consumes PCIe bandwidth and CPU memory, and it must be overlapped with GPU work to avoid stalling the batch. For short sequences, recomputation is simpler and comparably fast, and it is vLLM's default in recent versions. A more important point is that preemption is a scheduling event as well as a memory event. Which request to preempt, and how aggressively to admit new requests so that preemption is rare, are policy questions that Chapter 11 takes up. The block manager provides the mechanism. The scheduler decides when to use it.

10.6 Prefix caching: reusing work across requests

Paging and reference counting were designed to share caches within a request. The same machinery allows sharing across requests, and this has become one of the largest optimisations in production serving. A remarkable fraction of prompts begin with text the server has already processed. A chat assistant prefixes every conversation with the same system prompt, often thousands of tokens. A multi-turn conversation resends its entire history every turn. An agent re-reads the same tool descriptions at every step. A retrieval application may process the same popular documents for many users. Few-shot prompts repeat their examples. In each case the prompt's prefix produces exactly the same keys and values every time, by the exactness argument of §3.2, provided it appears at the same positions. Recomputing it is pure waste.

Prefix caching keeps the blocks of finished requests in the pool, marked as reusable, and lets new requests whose prompts start with the same tokens point their block tables at them instead of recomputing. Only the uncached suffix of the prompt needs a prefill. Two data structures for finding matching prefixes have emerged.

Hash-chained blocks (vLLM's automatic prefix caching). Each full block is identified by a hash of its own tokens and of the hash of the block before it, so a block's identity encodes the entire prefix up to and including it. A new prompt is split into blocks, each hashed, and looked up in a table from hashes to physical blocks. The longest run of hits from the start gives the reusable prefix. Free blocks with zero reference count stay in the table until evicted, by least-recently-used order, when memory is needed. vLLM V1 made this lookup cheap enough to enable by default (reporting under 1% throughput loss even at a 0% hit rate)[2].

Radix trees (SGLang's RadixAttention, Zheng et al., 2024)[3]. All cached token sequences are stored in a radix tree, a trie whose edges are labelled with runs of tokens, and each node points to the KV blocks for its edge's tokens. Finding the longest cached prefix of a new prompt is a walk down the tree. Inserting a finished request adds or extends a branch. Eviction removes least-recently-used leaves, so shared ancestors (system prompts) outlive the unique tails of individual conversations. SGLang also makes the scheduler cache-aware: among waiting requests it prefers those with the longest cached prefixes, raising the hit rate, and programs written in its frontend language expose their prefix structure explicitly.

Figure 10.5 shows a small radix tree from a chat and agent workload. Every request shares the 2,000-token system prompt at the root's child. User A's first turn and answer form a branch beneath it, and A's second turn needs a prefill only for its new message, because 2,600 tokens of history are already cached. An agent re-reading the same 3,000 tokens of tool documentation reuses them at every step. The economics are striking. In the chat workload of §6.6, where prefill was 38% of each request's GPU time, a cached 1,500-token system prompt removes three-quarters of that prefill. That is about 28% of all GPU time, plus a corresponding cut in time to first token. This is why API providers now discount cached input tokens heavily, often by 50–90% relative to uncached input: the work genuinely is not being done.

Pitfalls of prefix caching

A cached block is reusable only by a prompt that matches it exactly, token for token, from the very first token, at the same positions (cached keys are already rotated by RoPE; §2.5). Prompt templates that put a timestamp, user name or random identifier at the start destroy reuse. Good practice puts stable content first and variable content last. In a multi-replica deployment, a request benefits only if it is routed to the replica that holds its prefix, so routers must be prefix-aware (Chapter 27). Requests that ask for prompt log-probabilities may bypass the cache, because the cached state does not include logits. And caches of different models, adapters (LoRA) or tokenisers must never be mixed, which hash keys must encode.

Worked example — what a cached system prompt is worth

A service on Llama 3 8B receives 100 requests per second, each with a 1,500-token system prompt and 500 tokens of user input. Without prefix caching, prefill processes 2,000 tokens per request, \(2{,}000\times1.6\times10^{10}=3.2\times10^{13}\) FLOPs, about 54 ms of an H100 at 60% utilisation, so prefill alone occupies about 5.4 GPUs. With the system prompt cached, only 500 tokens are prefilled (attending to the cached 1,500), about 14 ms per request, about 1.4 GPUs: four GPUs saved, and TTFT cut by about 40 ms per request. The saving holds only if the cached prefix is byte-identical across requests, which is why a timestamp at the top of a system prompt is expensive (§10.6).

10.7 Beyond GPU memory: KV hierarchies

A prefix cache is limited by GPU memory, and GPU memory is the most expensive and most contended storage in the system. Most cached prefixes are not needed this second, but might be within minutes: a conversation whose user is reading the last answer, a document that will be queried again. They could live in a cheaper, larger tier and be brought back on demand. This creates a memory hierarchy for the KV cache, mirroring the hardware hierarchy of Chapter 5: GPU HBM (tens of GB per GPU), CPU DRAM (hundreds of GB to terabytes per server, about 64 GB/s per GPU over PCIe), local NVMe SSDs (many terabytes, roughly 7–14 GB/s per drive), and remote memory or storage pools shared across servers over RDMA networks (tens of GB/s per GPU). Systems such as LMCache, Mooncake Store (Moonshot AI's KV-centric architecture for Kimi; Chapter 13)[4] and CachedAttention[5] implement such tiers and plug into vLLM or SGLang as cache backends.

Whether a tier is worth using comes down to one comparison: is it faster to load a cached prefix of \(T\) tokens over a link of bandwidth \(\beta_{\text{link}}\), or to recompute it with a prefill? Loading takes \(T\,s_{kv}/\beta_{\text{link}}\). Recomputing takes \((2N_{\text{mm}}T+2LdT^2)/(\text{MFU}\cdot\pi)\) (§3.7). Per token, ignoring the quadratic term, the ratio is

\[ \frac{t_{\text{recompute}}}{t_{\text{load}}} \approx \frac{2N_{\text{mm}}/(\text{MFU}\cdot\pi)}{s_{kv}/\beta_{\text{link}}} = \frac{2N_{\text{mm}}\,\beta_{\text{link}}}{\text{MFU}\cdot\pi\,s_{kv}} . \]

Loading wins whenever this exceeds 1. The quadratic attention term only makes recomputation more expensive at long contexts.

Figure 10.6 makes the comparison for our running example. Recomputing a prefix (orange) costs about 30 ms per thousand tokens at short lengths and grows superlinearly. Loading it from CPU memory over PCIe (blue) costs about 2 ms per thousand tokens, roughly 15 times less, and loading over a 50 GB/s network is similar. Even a single local SSD (yellow) is faster than recomputation at every length, by about 1.6× at short prefixes and 5× at 128k tokens. The formula above says the advantage grows with model size, because FLOPs per token grow faster than cache bytes per token. For Llama 3 70B the PCIe ratio is about 55×, and for MLA models with tiny caches it is larger still. Two caveats keep this from being a blanket rule. Loads must be overlapped with computation, or a request waits on its transfer while the GPU idles. And transfers consume link bandwidth that tensor-parallel communication or other loads may need. Within those constraints, the conclusion of the 2024–25 systems literature is clear: KV caches are worth keeping, and worth keeping in large, cheap tiers. A frontier provider's prefix cache is better thought of as a distributed storage system than as a GPU buffer.

Drill 10.2 — Sizing a CPU tier

A server with 8 H100s serves Llama 3 8B (one replica per GPU) and has 2 TB of CPU memory. Conversations average 6,000 tokens of history, and users return after a median of 2 minutes. How many idle conversations can the CPU tier hold, and how long does restoring one take?

Solution. Per conversation: 6,000 × 128 KiB ≈ 786 MB in BF16, or ≈ 393 MB in FP8. 2 TB holds about 2,500 (BF16) or 5,000 (FP8) idle conversations, versus a few hundred in all eight GPUs' HBM. Restoring one at 64 GB/s takes about 12 ms (BF16), against about 210 ms to recompute it. The tier turns returning users' TTFT from hundreds of milliseconds into tens.

10.8 Variations and alternatives

Paging has costs. Every attention kernel must follow block tables, an extra indirection that complicates kernel design and can reduce efficiency. Every new kernel, whether a new attention variant, a quantised cache format or a new GPU generation, must be written in a paged form. vAttention (Prabhu et al., 2024)[6] proposed keeping the KV cache virtually contiguous and letting the GPU's own virtual-memory hardware do the paging. Using CUDA's low-level virtual memory APIs, it reserves a large contiguous virtual range per sequence and maps physical memory pages into it on demand. Unmodified, non-paged attention kernels then work, and fragmentation is still avoided. The trade-offs are the GPU's large page granularity (megabytes rather than 16 tokens) and the cost of mapping calls, which vAttention mitigates by allocating ahead and in the background.

Newer architectures complicate paging in other ways. Local/global hybrids (§8.4) have layers whose caches are bounded ring buffers alongside layers whose caches grow, so different layers need different allocation policies. Engines now support multiple "KV cache groups" with different block managers. MLA models (§8.3) cache a single latent per token instead of per-head keys and values, so their blocks have a different shape. State-space and linear-attention hybrids (Chapter 22) have a fixed-size recurrent state per sequence rather than a per-token cache, which pages poorly and complicates prefix caching, because the state after a prefix must be checkpointed explicitly. The general principle, managing cache memory as fixed-size, reference-counted, movable units, has survived all of these. The details are where much current engine engineering effort goes.

10.9 Operating a KV memory manager

The mechanisms of this chapter are invisible to users when they work and very visible when they do not, so production teams watch a small set of quantities. Understanding how an engine sizes its pool, and what each metric reveals, is part of the practical craft.

Sizing the pool. At start-up, an engine such as vLLM loads the weights, runs a profiling forward pass at the largest batch it will use to measure peak activation memory, and then allocates a fraction of the remaining GPU memory to the KV block pool. A configuration parameter (in vLLM, gpu_memory_utilization, typically 0.9) sets how much of the device the engine may use in total. The number of blocks is then fixed for the life of the process. For Llama 3 8B on an 80 GB H100 at 0.9 utilisation: \(0.9\times80\approx72\) GB, minus 16 GB of weights, a few GB of activations and CUDA graphs, leaves about 52–54 GB, roughly 25,000 blocks of 16 tokens (each block is \(16\times128\) KiB = 2 MiB), about 400,000 tokens of cache. That single number, cache tokens available, bounds the sum of all live sequence lengths and is the most useful capacity figure an engine reports.

Watching the pool. KV-cache utilisation (the fraction of blocks in use) tells you whether memory or something else is limiting batch size. A server whose utilisation sits near 100% with requests waiting is memory-bound in capacity, and an FP8 cache or a smaller-cache model will raise throughput. One whose utilisation is low while requests wait is limited elsewhere, by a configured maximum batch size, the TPOT target, or CPU overhead. The preemption rate tells you whether admission is too aggressive: occasional preemptions are healthy, but frequent ones waste work and inflate tail latency. The prefix-cache hit rate, the fraction of prompt tokens served from cache, measures how much prefill is avoided. For chat with a shared system prompt it is often well above 50%. For agents with stable tool descriptions it can exceed 90%. A sudden drop usually means a prompt-template change broke prefix stability, one of the commonest silent regressions in production.

Reading TTFT through the cache. With prefix caching, TTFT becomes bimodal. Requests that hit the cache prefill only their new suffix and see low TTFT, while misses pay the full prefill. A median TTFT that looks fine can hide a slow tail of misses, so TTFT should be monitored separately for hits and misses, and the miss tail examined for patterns, such as new users, rare prompts or evicted conversations, that a larger CPU tier or a pinning policy could fix. These operational signals connect this chapter's mechanisms to the scheduling and capacity decisions of Part IV and Chapter 28.

Drill 10.3 — What does the capacity figure allow?

The engine above reports 400,000 cache tokens. The workload has a mean live context of 2,500 tokens per request (prompt plus partial output). What is the maximum mean concurrency, and by Little's law, what arrival rate can it sustain if requests last 8 s on average?

Solution. Concurrency ≤ 400,000 / 2,500 = 160 sequences (less in practice, to leave headroom and avoid preemption, say ~150). Little's law: \(\lambda=\bar n/W\approx150/8\approx19\) requests per second per GPU, provided the TPOT target is met at that batch size (§6.6). If the TPOT target is binding first, the cache will sit partly unused and the right optimisation is speed, not memory.

Looking ahead

Part III is complete. The KV cache is now small (Chapter 8), read efficiently (Chapter 9), stored without waste, shared within and across requests, and spread across a hierarchy of storage tiers (this chapter). What we have not yet asked is which requests run when. The block manager can admit a request, grow it, share it, swap it or recompute it, but every one of those actions is a decision taken by a scheduler, step by step, under uncertainty about output lengths and arrival times, and against competing goals of throughput, latency and fairness. Part IV turns from memory to time. Chapter 11 develops batching and scheduling, from Orca's iteration-level scheduling, which made paging necessary in the first place, to chunked prefill and SLO-aware policies.

Chapter summary

  • Contiguous max-length KV reservation wastes memory through unused reservations, not-yet-used space and external fragmentation; measured utilisation was only 20–38%.
  • Virtual memory maps fixed-size logical pages to arbitrary physical frames on demand: no external fragmentation, at most one partial page per program, sharing, copy-on-write and swapping.
  • PagedAttention: per-layer pools of fixed-size blocks (16 tokens by default), per-sequence block tables, kernels that follow the table. Waste is about half a block per sequence (< 2%), giving 2–4× throughput over contiguous systems.
  • Reference counts and copy-on-write let parallel samples and beams share prompt blocks; only the last partial block is copied.
  • Preemption frees blocks by swapping to CPU (two PCIe transfers) or recomputation (a prefill); the scheduler decides when.
  • Prefix caching reuses exact prefixes across requests, via hash-chained blocks (vLLM) or radix trees with LRU leaf eviction and cache-aware scheduling (SGLang). Stable content must come first in prompts; routing must be prefix-aware.
  • Load versus recompute: ratio ≈ \(2N_{\text{mm}}\beta_{\text{link}}/(\text{MFU}\,\pi\,s_{kv})\): about 15× for Llama 3 8B over PCIe and about 55× for 70B. CPU, SSD and remote tiers (LMCache, Mooncake Store) are worth using when transfers are overlapped.
  • Operations: the pool is sized at start-up from memory left after weights and activations (≈ 400k tokens for Llama 3 8B on an H100); monitor KV utilisation, preemption rate and prefix hit rate, and track TTFT separately for cache hits and misses.
  • Alternatives and complications: vAttention uses GPU virtual memory for contiguous virtual caches; hybrids, MLA and SSM states need specialised cache managers.

Warm-up What is PagedAttention, and what problem does it solve?

PagedAttention (vLLM, 2023) manages the KV cache like OS virtual memory. KV memory is a pool of fixed-size blocks (e.g. 16 tokens). Each sequence has a block table mapping its logical blocks to arbitrary physical blocks, allocated on demand as it grows, and attention kernels read KV through the table. It solves memory waste in contiguous max-length reservation (unused reservations, unfilled space, external fragmentation; only 20–38% utilisation was measured), reducing waste to under half a block per sequence. More sequences fit, so batches are larger and throughput higher (2–4× in the paper). It also enables sharing (copy-on-write), prefix caching, and swapping/offloading.

Core Map the concepts of OS virtual memory onto PagedAttention.

Process ↔ sequence. Virtual address space ↔ the sequence's token positions. Virtual page ↔ logical KV block (16 tokens). Physical frame ↔ physical KV block in the GPU pool. Page table ↔ block table. Demand paging ↔ allocate a block when the last one fills. No external fragmentation ↔ any free block serves any sequence. Internal fragmentation ↔ the unfilled tail of the last block. Shared pages and copy-on-write ↔ parallel samples and beams sharing prompt blocks, copying the last partial block on first write. Swapping ↔ moving blocks to CPU memory under pressure. Page-replacement policy ↔ LRU eviction of cached blocks. TLB/address translation ↔ block-table lookups inside the attention kernel.

Core How would you choose the KV block size?

Trade-offs: (1) internal fragmentation ≈ \((b-1)/2\) tokens per sequence, tiny for typical lengths (16-token blocks waste < 2% at 500 tokens); (2) kernel efficiency: larger blocks give longer contiguous reads, better coalescing and vectorisation, and fewer table lookups; some kernels prefer 64 or 128 (FlashMLA uses 64); (3) sharing granularity: prefix caching and copy-on-write work in whole blocks, so larger blocks share less of a partially matching prefix; (4) metadata size and hashing cost per block; (5) alignment with quantisation group sizes and with TMA-friendly tile shapes. In practice choose the smallest size at which the attention kernel reaches near-peak bandwidth (often 16–64), and measure end-to-end throughput and prefix-hit rates.

Core Explain copy-on-write in the KV cache with an example.

A request asks for 4 samples of a 40-token prompt (blocks of 16: two full blocks plus one with 8 tokens). After one prefill, all 4 sequences' block tables point to the same three physical blocks, with reference count 4. When sample 1 generates its first token, it must write into the third (partial) block; since its refcount is above 1, the manager copies it to a new block, updates sample 1's table, and decrements the original's count. Samples 2 and 3 do the same; sample 4 can write in place once the count reaches 1. Full blocks are never copied. Memory: ≈ 40 tokens of shared prompt plus 4 small tails, instead of 4 × 40. Beam search applies the same rule at every fork; pruned beams decrement counts, and blocks free at zero.

Core Compare vLLM's hash-based prefix caching with SGLang's RadixAttention.

vLLM APC: each full block's key = hash(previous block's hash, this block's tokens, extra keys such as LoRA id or multimodal hashes). A global hash table maps keys to physical blocks; free blocks with refcount 0 remain cached in an LRU list. Lookup splits the prompt into blocks and finds the longest matching run from the start. It is simple, works at block granularity, and has negligible overhead (V1 enables it by default). SGLang RadixAttention: a radix tree over token sequences; nodes hold KV for their edge's tokens; longest-prefix match is a tree walk; eviction removes LRU leaves, preserving shared ancestors; the scheduler is cache-aware (prefers requests with long cached prefixes) and the frontend exposes program structure (forks, few-shot templates). Both reuse exact prefixes; differences are in data structure, eviction granularity and scheduler integration.

Deep-dive Derive when loading a cached prefix beats recomputing it, and give numbers for Llama 3 8B and 70B.

Load: \(T s_{kv}/\beta_{\text{link}}\). Recompute: \((2N_{\text{mm}}T+2LdT^2)/(\text{MFU}\cdot\pi)\). Ignoring the quadratic term, ratio = \(2N_{\text{mm}}\beta_{\text{link}}/(\text{MFU}\,\pi\,s_{kv})\). Llama 3 8B: \(N_{\text{mm}}=7.5\)B, \(s_{kv}=128\) KiB, MFU 0.5, π = 989 TFLOP/s: PCIe (64 GB/s) ≈ 15×, 50 GB/s network ≈ 11.6×, 7 GB/s SSD ≈ 1.6×. Llama 3 70B: \(N_{\text{mm}}=69.5\)B, \(s_{kv}=320\) KiB: PCIe ≈ 55×. The quadratic attention term raises recompute cost further at long contexts (at 128k for 8B: 13 s recompute vs 0.27 s PCIe). MLA models (tiny \(s_{kv}\)) and FP8 caches raise the ratio further. So loading almost always wins if transfers overlap with computation and links are not saturated.

Design Design a multi-tier KV cache for a chat service with millions of daily users.

Tiers: GPU HBM (hot: running requests plus very recent prefixes), CPU DRAM per server (warm: conversations idle for seconds to minutes), local NVMe (cool: hours), and optionally a distributed pool over RDMA (Mooncake Store / LMCache) for cross-server reuse. Keys: hash(model, adapter, tokeniser, token blocks, positions). Policies: LRU or frequency-aware eviction per tier, with system prompts and popular documents pinned. Prefetch: when a user's next message arrives, the router sends it to the replica or server holding its cache (prefix-aware routing); start loading cache blocks while tokenising and queueing, overlapped with other GPU work. Store caches in FP8 to double capacity. Sizing: conversations × average history × \(s_{kv}\); e.g. 6k tokens × 128 KiB ≈ 0.8 GB each (BF16), so 2 TB of CPU memory holds ≈ 2,500 per server. Monitoring: hit rate per tier, load latency, TTFT for cache hits versus misses, link utilisation. Correctness: invalidate on model or adapter updates; tenant isolation for privacy.

Core What happens when a paged engine runs out of KV blocks mid-generation?

The scheduler must preempt some running requests to free blocks. Options: (1) swap their blocks to CPU memory (PCIe transfer out, and back later), preserving work; (2) discard their blocks and recompute later via a prefill over prompt plus generated tokens; (3) with prefix caching, partially preserve shared blocks. Victim selection is typically the most recently admitted or lowest-priority requests (to protect old requests' latency), possibly preempting whole groups such as parallel samples together. Prevention: admission control based on current sizes plus headroom, watermark thresholds, and output-length estimates. Preemption hurts the victim's latency and wastes work, so frequent preemption signals over-admission.

Deep-dive Why does prefix caching require exact token and position matches, and how do engines handle near-matches?

KV at position \(j\) depends on all tokens \(\le j\) through every layer (§3.2), and keys are stored after RoPE rotation by absolute position. Any difference in an earlier token, or a shift in positions, changes every later K/V, so reuse requires the identical token prefix from position 0. Near-matches (same document at a different offset, slightly different system prompts) cannot be reused exactly. Approaches: canonicalise prompts (stable content first, deterministic formatting), structure applications so shared content forms a common prefix, and research methods that reuse non-prefix chunks (e.g. caching document KV independently and "blending" or partially recomputing cross-attention, as in CacheBlend-style work), which trade exactness for reuse and must be validated.

Core How does PagedAttention change attention kernels, and what does it cost?

Kernels take per-sequence block tables and lengths instead of contiguous pointers; each thread block computes physical addresses via table lookups, reading each KV block as a contiguous chunk. Costs: an extra indirection (index loads, address arithmetic); non-contiguous access across blocks (fine if blocks are large enough for coalesced reads); harder use of hardware copy engines (TMA needs regular tensors, mitigated by gather variants and by aligning block sizes); every new kernel (new attention variants, quantised caches, new GPUs) must support paging. Well-optimised paged kernels (FlashInfer, vLLM's, FlashMLA) reach near-peak bandwidth, so the overhead is small relative to the memory savings.

Design An agent framework sends 30 requests per task, each with the same 8k-token tool description and a growing scratchpad. How do you serve it efficiently?

(1) Make the prompt prefix-stable: tool descriptions first (identical bytes and tokens every call), then the scratchpad appended monotonically, then the new instruction. Avoid timestamps or ids at the start. (2) Enable prefix caching; each call then prefills only the new scratchpad delta, so prefill cost falls by roughly 8k + previous-scratchpad tokens per call. (3) Prefix-aware routing so all calls of a task (and all tasks sharing tools) hit the same replica; pin the tool prefix in cache. (4) Offload idle tasks' caches to CPU between calls if think-time is long. (5) Cascade attention for many concurrent tasks sharing the same tool prefix. (6) Measure: hit rate, TTFT per call, GPU-time per task. Expect TTFT and cost reductions of an order of magnitude for later calls in a task.

Warm-up Why do API providers price cached input tokens lower, and what should application developers do about it?

When a prompt's prefix matches a cached one, the provider reuses stored KV instead of running prefill for those tokens, saving GPU time (prefill can be a third or more of serving cost) and cutting TTFT. They pass on part of the saving as discounts. Developers should structure prompts so that long stable content (system prompts, instructions, tool schemas, documents, few-shot examples) comes first and is byte-identical across calls; put variable content (user message, timestamps, ids) at the end; reuse conversation history verbatim; and batch related calls close together in time (caches expire).

Deep-dive How do local/global hybrid models and MLA affect KV memory management?

Hybrids: local layers need only the last \(w\) tokens (ring buffers whose old blocks can be freed or reused) while global layers grow; a single block table per sequence no longer fits all layers. Engines create separate KV-cache groups per layer type with different block managers and freeing rules. Prefix caching must store local layers' state at the boundary (the window's contents), and a cached prefix is reusable only if the needed window is retained. MLA: one latent plus RoPE key per token per layer (576 numbers), so block shapes differ from per-head K/V, kernels are specialised (FlashMLA, 64-token blocks), and the cache per token is much smaller, making offload and prefix caching cheaper. SSM hybrids add fixed-size states that must be checkpointed for prefix reuse.

Core What is vAttention and how does it differ from PagedAttention?

vAttention keeps each sequence's KV cache virtually contiguous and uses CUDA's virtual memory management APIs to back that virtual range with physical GPU pages allocated on demand. Kernels see an ordinary contiguous tensor, so existing non-paged attention kernels (and their latest optimisations) work unchanged; fragmentation is still avoided because physical pages are allocated incrementally. Differences: physical page granularity is large (MB-scale versus 16-token blocks), so internal fragmentation per sequence is larger, mitigated by allocating ahead; mapping calls have latency, so they are overlapped in the background; sharing and prefix caching at fine granularity are harder. PagedAttention requires paged kernels but offers fine-grained sharing.

(1) Paging versus contiguous max-length reservation: if contiguous allowed only ~40% memory utilisation, paging fits ≈ 2–2.5× more sequences; in the memory-bound regime throughput rises by roughly 1.6–2× (sublinear because cache reads per step also grow), cutting decode cost per token by ~40–50%. (2) Prefix caching a 1,500-token system prompt removes ~75% of prefill, ≈ 28% of total GPU time, and cuts TTFT for most requests.
