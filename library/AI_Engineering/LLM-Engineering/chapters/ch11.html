Part IV · Serving Systems — Chapter 11

Batching and Scheduling

Requests arrive at random, want different amounts of work, and finish at unpredictable times. Deciding, every few milliseconds, which of them to run and how much of each, is what turns a fast model into a fast service.

Why this chapter

Parts I to III built a model of a single forward pass and made it as cheap as possible. A serving system does not run one forward pass. It runs a continuous stream of them on behalf of requests that arrive at random times, with prompts of different lengths and outputs whose lengths nobody knows in advance. Chapter 3 showed that throughput comes from batching, since every weight read from memory can serve many sequences at once. It also showed that batching costs latency, since each step does more work, and that memory caps the batch (§3.6). Chapter 6 turned this into an operating point on a latency–throughput frontier (§6.6). What it did not say is how a server actually achieves that operating point when requests come and go.

That is the job of the scheduler, the component that decides at every step which requests participate and with how many tokens each. This chapter follows its evolution through four problems, each revealed by solving the last. Static batching wastes most of the GPU, because a batch is only as fast as its longest member. Continuous batching (Orca, 2022) fixes that by scheduling one step at a time, which immediately made KV memory the binding constraint, the problem PagedAttention solved (Chapter 10). Continuous batching then exposed prefill–decode interference: a newcomer's long prompt stalls everyone else's generation. Chunked prefill (Sarathi-Serve, 2024) splits prompts into pieces that fit in the spare capacity of decode steps. Finally, with the mechanics in place, we turn to policy: who to admit, who to preempt, and in what order to serve, so that the most requests meet their latency targets.

Learning objectives

11.1 The scheduling problem

At every iteration the scheduler faces the same decision. There is a set of running requests, each with a KV cache in memory and an unknown number of tokens still to generate. There is a queue of waiting requests, each with a prompt to prefill. The scheduler must choose which requests take part in the next forward pass and, for prompts being prefilled, how many of their tokens to process. Its constraints are hard ones. The KV blocks of all participants must fit in memory, the step must not be so large that it delays everyone's next token beyond the latency target, and the batch must fit the kernels and CUDA graphs available. Its objective is a combination of throughput (tokens per second, which sets cost) and latency (TTFT and TPOT percentiles, which set user experience), usually expressed as goodput, the rate of requests completed within their SLOs (§1.13).

Two facts make the problem hard. First, output lengths are unknown: a request may finish after three tokens or after three thousand, which makes both memory planning and ordering difficult. Second, prefill and decode tokens cost different amounts. A decode token adds little arithmetic to a memory-bound step but needs its own KV read, while a prefill token is almost pure arithmetic. Every scheduler design in this chapter is a different way of coping with these two facts.

11.2 Static batching and its waste

The simplest scheduler forms a batch of \(B\) requests, runs prefill for all of them together, then runs decode steps until every request in the batch has finished, and only then starts the next batch. This was how early transformer serving systems, such as FasterTransformer behind a request queue, operated. It is simple, and it matches the fixed-shape kernels of the time. It is also enormously wasteful, for a reason anyone who has waited for a group to finish dinner will recognise: the batch is only as fast as its slowest member. Requests that finish early leave their slots empty, but those slots cannot be refilled until the batch ends.

Figure 11.1 makes the waste visible. On the left, four requests start together. The short ones finish early, and their slots stay grey, idle, until the longest request finishes. Only then can the next batch begin. How large is the waste? If the \(B\) requests in a batch have output lengths \(n_1,\dots,n_B\), the batch runs for \(\max_k n_k\) steps but does \(\sum_k n_k\) useful token-steps, so the fraction of slot-steps doing useful work is

\[ \eta_{\text{static}} = \frac{\mathbb E\big[\sum_k n_k\big]}{B\,\mathbb E\big[\max_k n_k\big]} = \frac{\mathbb E[n]}{\mathbb E[\max_k n_k]} . \]

For output lengths with a long tail this is dismal. If lengths are exponentially distributed, a reasonable model for many chat workloads, the expected maximum of \(B\) independent draws is \(\mathbb E[n]\cdot H_B\), where \(H_B=1+\tfrac12+\cdots+\tfrac1B\approx\ln B+0.577\) is the harmonic number. So \(\eta=1/H_B\).

Figure 11.2 plots \(\eta\) for two length distributions. With uniform lengths, utilisation falls towards one half. With exponential lengths it keeps falling, to 21% at a batch of 64. That is a cruel irony: the large batches that Chapter 3 said were needed for throughput are exactly the ones static batching wastes most. A static-batching server at batch 64 does about a fifth of the useful work its GPU could do. Real servers fared worse still, because a single runaway request that generated up to its maximum length held its whole batch hostage.

11.3 Dynamic batching

Before LLMs, model servers such as NVIDIA's Triton Inference Server addressed a different inefficiency: requests arrive one at a time, but GPUs like batches. Dynamic batching holds arriving requests for a short time, up to a configured maximum delay of a few milliseconds, and launches them as one batch when either the batch is full or the delay expires. For models that run a single forward pass per request, such as image classifiers, embedding models or rerankers, this is exactly right. The only waste is the brief queueing delay, which trades a little latency for much better utilisation, and it remains the standard approach for those workloads. For autoregressive generation it does not help with the real problem: once the batch starts generating, its members still finish at different times. The fix had to happen inside the generation loop itself.

11.4 Continuous batching: scheduling every iteration

Yu et al.'s Orca (OSDI 2022)[1] made the decisive change: schedule at the granularity of a single iteration (one forward pass) rather than a whole request. After every decode step, the scheduler removes requests that have finished, admits waiting requests into the freed capacity, and runs the next step on the new set. On the right of Figure 11.1, slot 4's short request finishes and a new request takes its place at the very next step. No slot ever waits for another request to finish. This iteration-level scheduling, now universally called continuous batching, reported up to 36.9× higher throughput than FasterTransformer at the same latency for a GPT-3-scale model. Later engine benchmarks have reported order-of-magnitude gains over naive static batching on typical chat traffic.

Continuous batching posed a technical problem that Orca also solved. In a continuously changing batch, requests are at different positions: one is being prefilled with 900 prompt tokens, another is decoding its 12th token, a third its 400th. How can they share one forward pass? Orca's answer was selective batching. Every operation that acts on tokens independently (the QKV and output projections, the FFN, the norms) is batched by simply concatenating all tokens from all requests into one long ragged matrix, so the weights are read once for the whole step regardless of where each request is. Only attention, which mixes tokens within a request and needs each request's own KV cache, is computed per request. Modern ragged attention kernels (§9.8) do this in a single launch, with per-request offsets and paged KV.

Figure 11.3 shows one iteration in which request A is processing a 512-token piece of its prompt while B and C each decode one token. For the projections and FFN, the three requests' 514 tokens form a single matrix multiplied by each weight once. For attention, the batch is split: A attends causally over its new tokens and its cached prefix, while B and C each attend over their own caches. Continuous batching also has a less obvious consequence, which tied it to the previous chapter. Because requests are now admitted whenever any capacity frees up, the server holds many requests of different, growing lengths at once, exactly the situation in which contiguous KV allocation wastes most of its memory. Iteration-level scheduling created the need for PagedAttention, and the two together became the foundation of vLLM.

11.5 Prefill–decode interference

Continuous batching admits new requests at every step, and admitting a request means prefilling its prompt. In early implementations, including vLLM's original scheduler, a step either ran a prefill for newly admitted requests or ran a decode step for running ones. Prefills were prioritised so that newcomers would get their first token quickly. Consider what that does to everyone else. A 4,096-token prompt for Llama 3 8B takes about 130 ms to prefill on an H100 (§3.7). During those 130 ms, the 64 requests that were decoding at about 10 ms per token produce nothing. Each of them experiences a single inter-token gap of 130 ms or more, a visible stutter in their stream and a TPOT tail that violates any reasonable SLO. With frequent arrivals the stalls repeat constantly. Agrawal et al. named this the problem of generation stalls[2].

Figure 11.4 contrasts the two schedules. In the top timeline, a newly arrived 4k-token prompt is prefilled in one 130 ms step, and every running request waits through it. The alternative, decode-prioritising, would protect TPOT but leave newcomers waiting indefinitely under load, wrecking TTFT. Neither extreme is acceptable, and the way out comes from looking at the roofline again.

11.6 Chunked prefill and stall-free scheduling

Recall the decomposition of §3.4. A decode step at moderate batch is memory-bound: its time is set by reading weights and caches, while its tensor cores are mostly idle. For Llama 3 8B at batch 64 and 2k contexts, a decode step reads about 33 GB (9.9 ms at full bandwidth) but needs only about 1 ms of compute. A prefill token is the opposite, nearly pure computation, about 15 GFLOPs, or 0.015 ms of H100 time. So a decode step has room for roughly \((9.9-1)/0.015\approx590\) prefill tokens' worth of compute without getting any slower, because the step is waiting on memory anyway. Prefill tokens added to a decode step are almost free, up to the point where the step becomes compute-bound.

Sarathi (Agrawal et al., 2023) and its successor Sarathi-Serve (OSDI 2024)[2] turned this observation into a scheduler. Prompts are split into chunks. Every iteration has a fixed token budget, the total number of tokens the step may process. The scheduler first adds one token for every running decode, then fills the remaining budget with prefill chunks from waiting requests ("piggybacking" them on the decodes). A long prompt is therefore prefilled over several consecutive steps, each step stays close to the length of a pure decode step, and running requests never stall. Sarathi-Serve called this stall-free scheduling and reported several-fold higher serving capacity under tight TPOT targets. vLLM V1 adopted the same design as its only scheduling mode: every step has a token budget, and each request is simply allotted some number of tokens, whether it is prefilling or decoding (§12.2).

Figure 11.5 quantifies the trade-off with the idealised roofline model of §3.6. The blue curve is the duration of a step that carries 64 decodes plus a prefill chunk of the given size. It stays flat at 9.9 ms until the chunk reaches about 590 tokens, where the step becomes compute-bound, and then rises linearly. The orange curve is the newcomer's TTFT, the number of steps needed to prefill its 4,096 tokens times the step time. With tiny chunks the prompt takes many steps and TTFT suffers (317 ms at 128 tokens per step). With huge chunks TTFT is optimal (63 ms) but running requests' TPOT jumps to 63 ms, the stall of §11.5 again. Around 512 tokens per step, both are near their best: TPOT unchanged at 9.9 ms and TTFT 79 ms, only 25% above the minimum. This is why typical token budgets are a few hundred to a few thousand tokens, tuned to the model, the hardware and the SLOs. Larger models and faster-compute GPUs can absorb more prefill per step, and tighter TPOT targets call for smaller budgets.

Drill 11.1 — The free prefill capacity of a decode step

Llama 3 70B on 4×H100 with tensor parallelism serves 64 decodes at 2k context, with a step time of about 17.6 ms (Drill 3.2). How many prefill tokens can each step absorb before becoming compute-bound?

Solution. Per GPU, a prefill token costs \(2\times69.5\times10^{9}/4\approx3.5\times10^{10}\) FLOPs, about 0.035 ms at peak (0.044 ms at 80% MFU). The decode work itself uses about \(64\times0.035\approx2.2\) ms of compute. The spare compute is about \(17.6-2.2=15.4\) ms, enough for roughly 350–440 prefill tokens per step. A token budget of about 512 is a reasonable start, to be tuned against the TPOT target.

Chunking is not free

Each chunk of a prompt attends to all earlier chunks' cached keys and values, so later chunks re-read the growing prefix cache. A prompt split into \(k\) chunks reads its own cache about \(k/2\) times in total rather than computing attention in one pass. For very long prompts this extra traffic, plus the overhead of more steps, makes chunked prefill somewhat less efficient than a single large prefill. Engines therefore use large chunks when no decodes are waiting, and for very long prompts some systems move prefill to separate machines altogether. That is disaggregation, Chapter 13.

Worked example — choosing the chunk size

Setup. Llama 3 8B on one H100 is decoding 64 sequences at 2k context, as in §3.8. A step reads \(16.06+17.2\approx33.3\) GB, 12.4 ms at 80% of peak bandwidth. A new 4,096-token prompt arrives. How large a prefill chunk can ride along with each decode step?

Compute per token. Each token costs about \(2\times7.5\times10^9=1.5\times10^{10}\) FLOPs in the matrix products (prefill attention is small at this length and we ignore it). At 50% MFU, 494 TFLOP/s, that is about 30 µs per token. A step that processes \(64+C\) tokens takes roughly \(\max(12.4\text{ ms},\,(64+C)\times30\text{ µs})\).

The free region. The two terms are equal when \(64+C\approx410\), so a chunk of up to about \(C=345\) tokens costs almost nothing: the step was waiting on memory anyway. With \(C=256\) the prompt is consumed in 16 steps (about 0.2 s of TTFT from chunking) while TPOT stays at 12.4 ms.

Beyond it. With \(C=2048\), the step costs \(2112\times30\) µs ≈ 64 ms: TTFT for this prompt improves to two steps, but all 64 users see a TPOT five times larger during those steps. The best token budget is therefore near the knee where the step turns compute-bound, adjusted for the TPOT SLO. Budgets of a few hundred to a couple of thousand tokens are typical in production engines, and the right value is a property of the model, GPU and SLO, not a universal constant.

11.7 Policy: admission, preemption and order of service

Continuous batching and chunked prefill are mechanisms. They do not say which waiting request to admit next, or which running request to preempt when memory runs out (§10.5). Those are policy decisions, and they change latency distributions dramatically even at the same throughput.

First come, first served (FCFS) is the default in most engines: admit waiting requests in arrival order, and preempt the most recently admitted request when memory runs short, so the oldest requests finish first. It is simple and fair in one sense, but queueing theory tells us it is far from optimal for mean latency when job sizes vary. A long request at the head of the queue delays every short one behind it, the convoy effect. For a single server, the policy that minimises mean completion time is shortest job first (or its preemptive version, shortest remaining processing time). LLM servers cannot know job sizes exactly, since output lengths are unknown, but they can predict them. Fu et al. (2024)[3] showed that a small model trained to rank requests by expected output length, rather than predict it exactly, is enough to approximate shortest-job-first and substantially reduce latency under load. Prompt length, which is known, is a useful proxy for prefill cost.

SJF has a well-known pathology: long requests can starve. Production schedulers therefore combine prediction with ageing, so that a request's priority rises with its waiting time, or with explicit priorities set by the application (interactive users ahead of batch jobs, paid tiers ahead of free ones). Multi-tenant services add fairness. Sheng et al.'s Virtual Token Counter (OSDI 2024)[4] tracks the service each client has received, measured in weighted prompt and output tokens, and always serves the client who has received least. That guarantees that a heavy user cannot crowd out light ones, with provable bounds on the service gap.

For the mathematician — what queueing theory says

Model the server as a queue with arrival rate \(\lambda\) and random job sizes \(S\), and let utilisation \(\rho=\lambda\mathbb E[S]\) (with capacity normalised to 1). For FCFS on one server with Poisson arrivals, the Pollaczek–Khinchine formula gives mean waiting time \(\mathbb E[W]=\frac{\lambda\,\mathbb E[S^2]}{2(1-\rho)}\). Two lessons transfer directly. First, waiting time blows up as \(\rho\to1\), so servers must run below full load to meet latency SLOs, and the margin needed grows with variability. Second, waiting time depends on \(\mathbb E[S^2]\): heavy-tailed job sizes, such as long reasoning outputs, inflate it, which is precisely when size-aware policies (SJF, SRPT) help most. Continuous batching makes an LLM server behave more like a processor-sharing system than a single FCFS queue, but the qualitative lessons hold.

11.8 SLO-aware scheduling and goodput

A service rarely has one latency target. Interactive chat may need TTFT under 500 ms and TPOT under 50 ms. A code-completion endpoint needs end-to-end latency under 300 ms. A batch summarisation API cares only about finishing within hours. An agent pipeline may care about end-to-end time per multi-step task. SLO-aware schedulers use these targets directly. They estimate, for each waiting and running request, how close it is to violating its target, and prioritise accordingly, for example by earliest deadline first. They also adjust the token budget dynamically: smaller when many tight-TPOT requests are decoding, larger when the queue holds requests near their TTFT deadline. When load exceeds what the system can serve within SLOs, they can shed or defer requests, preferring to serve 90% of requests well rather than 100% badly. Research systems have explored predicting each request's remaining work, migrating requests between replicas to rebalance memory (Llumnix), and optimising users' perceived quality of experience while streaming (Andes).

The common objective is goodput: the request rate at which a target fraction of requests meet all their SLOs. Its practical meaning is captured by the operating-point analysis of §6.6, extended to a mixed and stochastic workload. Every mechanism in this chapter raises the curve. Continuous batching removes idle slots. Paging (Chapter 10) admits more requests. Chunked prefill removes stalls that would otherwise violate TPOT. Good policies keep the queue moving in the right order. The next chapter shows how a real engine puts them together.

11.9 A scheduler, in code

The following pseudocode captures the core loop of a modern token-budget scheduler in the style of vLLM V1. It is simplified, with no speculative decoding, multi-step scheduling or disaggregation, but it shows how the mechanisms of Chapters 10 and 11 interact.

def schedule_step(running, waiting, kv, token_budget):
    batch, budget = [], token_budget
    # 1. Running requests first: each needs 1 decode token (or its next prefill chunk).
    for req in running:
        need = min(req.remaining_prompt, budget) if req.prefilling else 1
        while not kv.can_append(req, need):          # out of KV blocks?
            victim = pick_victim(running)                 # e.g. lowest priority / newest
            kv.free_or_swap(victim); running.remove(victim); waiting.push_front(victim)
            if victim is req: break
        else:
            kv.append(req, need); batch.append((req, need)); budget -= need
    # 2. Admit waiting requests into the remaining budget (policy decides the order).
    for req in order_by_policy(waiting):              # FCFS, priority, predicted-SJF, fair share ...
        if budget == 0: break
        cached = kv.match_prefix(req.prompt)              # prefix cache hit: skip these tokens
        chunk = min(len(req.prompt) - cached, budget)
        if not kv.can_allocate(req, cached + chunk, headroom=WATERMARK):
            break                                         # admission control
        kv.allocate(req, cached + chunk); req.start(cached)
        batch.append((req, chunk)); budget -= chunk
        waiting.remove(req); running.append(req)
    return batch    # one ragged forward pass over all (request, n_tokens) pairs

Notice how much of the book this loop touches. The token budget implements chunked prefill (§11.6). kv.can_append and free_or_swap are PagedAttention and preemption (§10.3, §10.5). match_prefix is prefix caching (§10.6). order_by_policy is the policy of §11.7. The returned batch is executed as one ragged forward pass with selective batching (§11.4), paged attention kernels (§9.8) and, for the decode-only parts, CUDA graphs (§7.8). The watermark is the headroom that keeps preemption rare.

The loop is easier to reason about as a state machine on individual requests, which is what Figure 11.7 draws. A request enters waiting. Admission moves it to running only if the token budget has room and the KV allocator can give it blocks with a safety margin (the watermark). While running, it first consumes its prompt in chunks and then decodes one token per step. Two arrows leave the running state. The normal one goes to finished, which returns its blocks to the allocator (or leaves them in the prefix cache). The other goes to preempted when a running request cannot append a token because memory is exhausted; the victim's blocks are freed (recompute) or copied to host memory (swap), and it re-enters the front of the waiting queue so that it is not starved. Every scheduler policy of §11.7 is a choice about which arrow to take and in which order to examine the waiting queue; the state machine itself does not change.

11.10 From scheduler to capacity plan

A scheduler determines how well one replica uses its GPU. An operator must also decide how many replicas to run for a given traffic level, and that decision combines this chapter's queueing view with the operating-point analysis of §6.6. The most common mistake is to size a deployment so that every GPU runs at its maximum sustainable throughput. Queueing theory explains why that fails.

Think of each replica as a server with a maximum sustainable rate of requests within its TPOT target, \(\lambda_{\max}\), found as in §6.6 from the operating point and the mean request size. For the chat workload of §3.8 on one H100, that was roughly 10 requests per second. If requests arrive at random, as a Poisson process is a good first model for many independent users, then the replica's utilisation is \(\rho=\lambda/\lambda_{\max}\), and the time requests spend waiting to be admitted grows as \(\rho/(1-\rho)\) times the typical service time. That holds for exponential job sizes, and more with heavier tails, by the Pollaczek–Khinchine formula of §11.7. Since waiting time adds directly to TTFT, a TTFT target translates into a utilisation ceiling.

Figure 11.6 shows the shape of this law, and it is the most important picture in capacity planning. Below about 60% utilisation, waiting is short relative to service. Beyond about 80%, it climbs steeply, and at 95% the mean wait is nineteen service times even for well-behaved job sizes, and much worse for heavy-tailed ones such as reasoning traces of wildly varying length. Continuous batching softens the picture somewhat, since a replica serves many requests at once and behaves more like a processor-sharing system than a single queue. Bursty arrivals make it worse. The qualitative rule is robust, and a practical consequence follows directly: provision for a target utilisation, not for peak throughput. Interactive services commonly target 50–75% of each replica's SLO-constrained capacity, accepting the idle headroom as the price of predictable tail latency.

Worked example — sizing a chat deployment

Expected peak traffic is 600 requests per second of the §3.8 chat workload. Each H100 replica of Llama 3 8B sustains \(\lambda_{\max}\approx10\) requests per second within the TPOT target. The P90 TTFT target leaves room for waiting of about two mean service times, and traffic is somewhat heavy-tailed. Reading Figure 11.6, that allows utilisation of roughly 0.45–0.65 depending on the tail; take \(\rho=0.6\). Required replicas: \(600/(0.6\times10)=100\) GPUs, against the naive \(600/10=60\). Prefix caching of the 1,500-token system prompt raises \(\lambda_{\max}\) by roughly a quarter (§6.6, §10.6), to about 12.5 requests per second, and cuts the deployment to 80 GPUs. An FP8 cache, by raising the batch at the same TPOT (Figure 6.7), could reduce it further. Each optimisation from earlier chapters shows up as fewer machines.

The example also shows why scheduling and capacity are not separate problems. A better scheduler, with chunked prefill and good admission and ordering, raises \(\lambda_{\max}\) and also reduces the variance of service, which lowers the curve of Figure 11.6. A size-aware policy reduces the waiting of short requests at a given utilisation. Load balancing across replicas (Chapter 27) determines whether the fleet behaves like 100 separate queues, each with its own unlucky bursts, or like one large pool. Pooling reduces waiting dramatically, a classical result of queueing theory: many servers sharing one queue need far less headroom than the same number of servers with separate queues.

Drill 11.2 — The cost of tight tails

Using the exponential curve of Figure 11.6, by what factor does mean waiting grow if a team raises utilisation from 0.6 to 0.85 to save money, and how many GPUs does it save in the example above (without prefix caching)?

Solution. Waiting grows from 1.5 to 5.7 mean service times, about 3.8×, likely breaking the TTFT target. GPUs fall from 100 to \(600/(0.85\times10)\approx71\), a 29% saving bought with a nearly fourfold increase in queueing delay. The usual better answer is to raise \(\lambda_{\max}\) (caching, quantisation, scheduling) rather than utilisation.

Looking ahead

We now have all the ingredients of a serving engine: a memory manager, a scheduler, and the kernels it launches. Real engines combine them under further pressures that this chapter has ignored. The CPU must tokenise, schedule, sample and stream without becoming the bottleneck. Model execution must be overlapped with the next step's scheduling. Engines must support dozens of model architectures, quantisation formats and parallelism schemes, and expose an API that applications can rely on. Chapter 12 opens up vLLM, SGLang and their peers to show how these pieces fit together in practice, and why their designs changed between 2023 and 2025.

Chapter summary

  • The scheduler decides at every step which requests run and how many tokens each processes, under memory and latency constraints, to maximise goodput. Unknown output lengths and the different costs of prefill and decode tokens make it hard.
  • Static batching wastes the slots of finished requests: utilisation \(\mathbb E[n]/\mathbb E[\max n]\), which is \(1/H_B\) (about 21% at \(B=64\)) for exponential lengths.
  • Dynamic batching (wait briefly, then batch) suits single-pass models but not generation.
  • Continuous batching (Orca): schedule every iteration, refilling freed slots immediately. Selective batching concatenates all tokens for token-wise operations and splits only attention. It made memory the bottleneck, motivating PagedAttention.
  • Prefill–decode interference: a long prefill stalls all running decodes (≈ 130 ms gap for a 4k prompt on Llama 3 8B).
  • Chunked prefill with a token budget (Sarathi-Serve, vLLM V1): memory-bound decode steps have spare compute for ≈ 590 prefill tokens (Llama 3 8B, batch 64, H100), so chunks of a few hundred tokens remove stalls with modest TTFT cost.
  • Policies: FCFS is simple but suffers convoys; predicted shortest-job-first (learning to rank) reduces mean latency; ageing and priorities prevent starvation; VTC enforces fair sharing. Queueing theory: waiting time ∝ \(\mathbb E[S^2]/(1-\rho)\).
  • Capacity planning: waiting grows like \(\rho/(1-\rho)\) (more with heavy tails), so provision for a target utilisation (often 50–75%), not peak throughput. Pooling queues and raising \(\lambda_{\max}\) beat running hotter.
  • SLO-aware scheduling prioritises by deadline, adapts the token budget, and sheds load to maximise goodput.

Warm-up What is continuous batching and why does it raise throughput so much?

Continuous (iteration-level) batching, introduced by Orca (2022), schedules at every forward pass: finished requests leave the batch and waiting requests join immediately, instead of waiting for a whole static batch to finish. Static batching wastes the slots of finished requests until the longest one ends; with heavy-tailed output lengths its utilisation is \(1/H_B\) (≈ 21% at batch 64). Continuous batching keeps slots full, so effective batch size, and hence throughput in the memory-bound decode regime, is much higher at the same latency (Orca reported up to 36.9×). Implementation relies on selective batching (concatenate tokens for linear layers, per-request attention), ragged kernels, and paged KV memory to hold many sequences of varying length.

Core Explain prefill–decode interference and how chunked prefill fixes it.

When a new request's long prompt is prefilled as a separate step, all running decodes wait for it, so their inter-token latency spikes (a 4k-token prefill on Llama 3 8B ≈ 130 ms, versus a 10 ms decode step). Prioritising decodes instead starves newcomers' TTFT. Chunked prefill (Sarathi-Serve, vLLM V1) splits prompts into chunks and gives each step a token budget: every running decode gets one token, and the remainder goes to prefill chunks. Because decode steps are memory-bound with idle tensor cores, chunks of a few hundred tokens add little time (for Llama 3 8B at batch 64, up to ≈ 590 tokens add almost nothing). Running requests keep a steady TPOT while newcomers are prefilled over several steps. Trade-off: chunk size versus TTFT and extra KV re-reads.

Core Derive the utilisation of static batching for exponential output lengths.

A batch of \(B\) requests with i.i.d. lengths \(n_k\sim\text{Exp}(\mu)\) runs for \(\max_kn_k\) steps and does \(\sum_kn_k\) useful token-steps. Utilisation \(=\mathbb E[\sum n_k]/(B\,\mathbb E[\max n_k])=\mathbb E[n]/\mathbb E[\max n]\). For exponentials, the maximum of \(B\) draws has expectation \(\mu^{-1}H_B\) (sum of spacings: \(\frac1{B\mu}+\frac1{(B-1)\mu}+\cdots+\frac1\mu\)), so utilisation \(=1/H_B\approx1/(\ln B+0.577)\): 0.48 at B = 4, 0.30 at 16, 0.21 at 64. Heavy tails (reasoning outputs) are worse.

Core How would you choose the token budget (max batched tokens) for a deployment?

Start from the roofline: spare compute per decode step ≈ memory time − decode compute; dividing by compute per prefill token gives the "free" budget (≈ 590 tokens for Llama 3 8B at batch 64, 2k context on H100; ≈ 350–440 per GPU for 70B with TP = 4). Then account for SLOs: a tighter TPOT target means a smaller budget; TTFT pressure (long prompts, bursts) argues for a larger one. Consider CUDA-graph and kernel efficiency at different token counts, and attention re-reads for long chunked prompts. Tune empirically: sweep the budget under a realistic load test, measuring P90/P99 TTFT and TPOT and goodput, and pick the best. Some engines adapt the budget dynamically to queue state.

Deep-dive Why is FCFS suboptimal for LLM serving, and how can you approximate SJF without knowing output lengths?

With highly variable job sizes, FCFS creates convoys: short requests queue behind long ones, inflating mean and tail latency. Pollaczek–Khinchine shows waiting time grows with \(\mathbb E[S^2]\). SJF/SRPT minimises mean completion time but needs sizes. Approximations: (1) known prefill size (prompt length) for TTFT ordering; (2) predicted output length from features or a small model; (3) learning-to-rank (Fu et al.): train a model to order requests by length, which suffices for SJF; (4) ageing to prevent starvation; (5) a multi-level feedback queue: start everyone at high priority, demote requests that have generated many tokens (a size-oblivious SRPT approximation). Evaluate on goodput and tail latency, and watch for fairness regressions.

Core What is selective batching?

Orca's technique for executing a batch whose requests are at different positions and phases. Token-wise operations (QKV and output projections, FFN, norms, activations) concatenate all tokens from all requests into one ragged matrix, so each weight is read once for the whole step. Attention, which mixes tokens within a sequence and needs each request's own KV cache, is split per request (originally separate calls; now a single ragged, paged attention kernel with per-request offsets and block tables). It removes padding and makes iteration-level scheduling efficient.

Design Design the scheduler for a service with interactive chat (tight TPOT) and a batch summarisation API (throughput only) on the same GPUs.

Use priority classes. Interactive requests get high priority for admission and are never preempted for batch work; batch requests fill leftover capacity. Use a token budget sized for the interactive TPOT target; when no interactive requests wait, raise the budget or let batch prefills use larger chunks. Preemption victims are batch requests first (swap or recompute), with watermarks reserving headroom for interactive bursts. Per-class SLO monitoring. Optionally a separate pool or disaggregation for batch prefill (Chapter 13). Prefix caching for shared system prompts (interactive) and repeated documents (batch). Fairness within classes (VTC) for multi-tenant traffic. Evaluate: interactive P99 TPOT/TTFT under batch load; batch throughput and completion time.

Core What are generation stalls, and how would you detect them in production?

Generation stalls are long inter-token gaps for running requests caused by the scheduler running long prefills (or other heavy work) in steps that exclude or delay decodes. Detection: per-request ITL distributions, not just mean TPOT; P99/P999 ITL spikes correlated with arrivals of long prompts; traces showing step durations by composition. Fixes: chunked prefill with an appropriate token budget, disaggregated prefill, limiting prefill tokens per step, prioritising decodes for latency-sensitive classes.

Deep-dive Model the step time of a mixed batch with B decodes and c prefill tokens, and derive the free prefill capacity.

Memory time ≈ \((Nb_w+B\bar ts_{kv}+\text{prefill KV writes and reads})/\beta\); compute time ≈ \((2N_{\text{mm}}(B+c)+\text{attention FLOPs})/\pi\). Step ≈ max of the two (plus overhead). While memory dominates, adding \(c\) prefill tokens adds ≈ \(2N_{\text{mm}}c/\pi\) to compute but almost nothing to memory, so the step time is unchanged until \(2N_{\text{mm}}(B+c)/\pi\approx\) memory time, i.e. \(c^{*}\approx\pi\,t_{\text{mem}}/(2N_{\text{mm}})-B\). For Llama 3 8B, \(t_{\text{mem}}=9.9\) ms, \(B=64\): \(c^{*}\approx9.9\text{e-}3\times989\text{e}12/1.5\text{e}10-64\approx590\). With realistic MFU in mixed steps and the attention FLOPs of the chunk, the practical value is somewhat lower. Beyond \(c^{*}\), step time grows linearly with \(c\).

Core How do continuous batching, paging and prefix caching interact in a scheduler?

Continuous batching decides membership each step; paging lets it admit by current rather than maximum size; prefix caching reduces the prefill work and memory a newcomer needs. In the loop: running requests first get their decode token (allocating a new block if the last one is full, preempting if none is free); then waiting requests are considered in policy order; for each, find the longest cached prefix, allocate blocks for the uncached chunk if memory (with headroom) allows, and give it part of the token budget. Cache-aware ordering (prefer long cached prefixes) raises hit rates. Preempted requests can often resume cheaply because their prefix may still be cached.

Design Traffic is bursty: arrivals triple for a few minutes each hour. How do you keep TTFT SLOs?

(1) Capacity planning with headroom: by queueing theory, keep steady-state utilisation well below 1 so bursts do not explode queues; size for peak goodput, or (2) autoscale replicas ahead of known bursts (Chapter 27; model loading is slow, so pre-warm). (3) Scheduler: SLO-aware admission (earliest-deadline-first for waiting prefills), temporarily larger token budgets to drain prefill queues if TPOT has slack, and priority for interactive traffic. (4) Load shedding or deferral of low-priority or batch work during bursts; graceful degradation (shorter max outputs). (5) Prefix caching to cut prefill work. (6) Disaggregated prefill pools that can be scaled independently (Chapter 13). Monitor queue length and P99 TTFT, and alert on queue growth.

Warm-up Static vs dynamic vs continuous batching: one sentence each.

Static: form a fixed batch and run it until every member finishes, so slots of early finishers sit idle. Dynamic: wait briefly to accumulate arriving requests into a batch, then run it; ideal for single-pass models. Continuous: reschedule at every iteration, so finished generations leave and new ones join immediately; the standard for LLM generation.

Deep-dive What is a multi-level feedback queue, and why might it suit LLM scheduling?

An MLFQ has several priority queues. New jobs start in the highest; a job that consumes its quantum (here, a number of generated tokens) is demoted to a lower queue with a larger quantum, and higher queues are served first. It approximates shortest-remaining-time-first without knowing job sizes: short jobs finish while still at high priority; long jobs sink. For LLMs, quanta measured in output tokens give short answers low latency and keep long generations from blocking others; ageing or periodic boosts prevent starvation. Costs: more preemption (KV swapping or recompute, so prefer demotion without eviction when memory allows) and possible unfairness to long but important requests (combine with priorities).

Core How does output-length uncertainty affect admission control, and how can it be mitigated?

Admission based on current sizes may over-commit memory as sequences grow, causing preemptions; admission based on maximum lengths under-utilises memory. Mitigations: headroom watermarks; per-request max-token limits; output-length prediction to estimate future KV demand; reserving capacity per priority class; fast preemption (recompute for short contexts, swap for long); prefix caching so recomputation after preemption is cheaper; monitoring preemption rate and tuning admission thresholds. With paging, mild over-commitment plus occasional preemption usually beats conservative reservation.

Design Write (in pseudocode) the step loop of a continuous-batching engine and explain each phase. 
while True:
    new = receive_requests(); waiting.extend(tokenize(new))
    batch = schedule_step(running, waiting, kv, token_budget)   # §11.9
    inputs = build_ragged_inputs(batch)          # token ids, positions, block tables, offsets
    logits = model.forward(inputs)               # one ragged forward pass (graphs for decode-only)
    tokens = sample(logits, params_of(batch))    # fused sampler (Chapter 4)
    for req, tok in zip(decoding(batch), tokens):
        req.append(tok); stream(req, detokenize(req))
        if req.finished(): kv.release(req, keep_for_prefix_cache=True); running.remove(req)

Phases: ingest and tokenise (often in a separate process); schedule (membership, token allocation, preemption, prefix matching); prepare metadata; execute; sample; post-process (append, stop checks, streaming, freeing). Modern engines overlap CPU phases of step k+1 with GPU execution of step k to hide overhead (Chapter 12).

Deep-dive How should chunked prefill be adapted for 128k-token prompts?

A 128k prefill takes ≈ 13 s on one H100 for Llama 3 8B. Chunked at 512 tokens it would need 256 steps, each re-reading the growing prefix cache (later chunks attend over up to 128k cached tokens, making chunk attention cost grow linearly), so total traffic and latency rise noticeably and TTFT becomes tens of seconds. Options: (1) use much larger chunks when few decodes are running, and adapt the budget dynamically; (2) give long prompts their own prefill capacity (dedicated replicas or disaggregated prefill, Chapter 13) so they do not interfere with interactive decodes; (3) context or sequence parallelism to spread a single long prefill across GPUs (Chapter 18); (4) prefix caching for repeated long documents; (5) admission control so only a few very long prefills run at once; (6) set user expectations (streaming progress). The token-budget scheduler remains the mechanism; the policy must recognise long prompts as a separate class.

Core How does GQA (or MLA) change the free prefill capacity of a decode step?

Free capacity ≈ (memory time − decode compute) / compute per prefill token. Smaller caches (larger GQA groups, MLA, FP8 KV) reduce decode memory time at a given batch and context, so for the same batch they reduce the spare compute, making steps closer to compute-bound and leaving less room for free prefill. But they also allow a much larger batch within memory, and a larger batch raises decode compute and throughput. The net effect: with efficient caches, steps are more balanced between compute and memory, which is good for utilisation, and the token budget for chunked prefill should be retuned (often smaller per step relative to the batch). MLA's compute-heavy decode attention (≈ 240 FLOPs/byte) pushes steps towards compute-bound even sooner.
