Part IV · Serving Systems — Chapter 12

Inside an Inference Engine

How vLLM, SGLang, TensorRT-LLM and their peers assemble the kernels, memory manager and scheduler of the previous chapters into software that serves real traffic, and why their designs changed so much between 2023 and 2025.

Why this chapter

We have now met every component of a serving engine on its own. There are attention kernels that read paged caches (Chapter 9), a block manager that allocates, shares and caches them (Chapter 10), a scheduler that chooses each step's batch (Chapter 11), a sampler (Chapter 4), and the GPU programming techniques that make each piece fast (Chapter 7). An inference engine is the program that combines them. It accepts requests over the network, turns them into tokens, runs the step loop, and streams text back, for hundreds of model architectures, a dozen quantisation formats and several kinds of parallelism. For an inference engineer, an engine is what you deploy, configure, profile and, increasingly, modify. Interviewers expect you to know how the major engines are organised and to reason about where their time goes.

The story of engines between 2023 and 2025 is the story of a bottleneck moving. The first engines were built around a new memory manager and a new scheduler, and the GPU work was the obvious cost. As kernels improved and models grew more efficient per token, the CPU side, meaning Python scheduling, tokenisation, sampling bookkeeping and the gaps between GPU kernels, became a large fraction of every step. SGLang's developers reported that an unoptimised engine could spend up to half its time on CPU overhead[1]. The second generation of engines (vLLM V1, SGLang's overlap scheduler, TensorRT-LLM's PyTorch backend) was largely a response to this. This chapter dissects that architecture, compares the major engines, describes the API surface they expose, and ends with a practical guide to configuring one.

12.1 Anatomy of an engine

Every modern engine, whatever its implementation language and history, has the same logical components, because every request must pass through the same stages. A request arrives at the API server, usually an HTTP server implementing the OpenAI chat-completions interface. The server applies the model's chat template to turn a list of messages into a prompt string, and the tokeniser turns the string into token ids. The request then enters the engine core, which owns the scheduler and the KV-cache manager. At every step the scheduler selects a batch (Chapter 11), the cache manager allocates blocks and matches prefixes (Chapter 10), and the model runner on each GPU worker executes one forward pass over the ragged batch, using paged attention kernels and, for decode-only steps, CUDA graphs. The sampler turns logits into tokens (Chapter 4). Finally the output processor appends tokens, checks stop conditions, detokenises incrementally and streams text back to the client.

Figure 12.1 places the components in a row and traces one request through them. Two things about this picture determine engine design. First, only the right-hand box runs on the GPU. Everything else is CPU work, and some of it happens on every step for every request: the scheduler's decisions, building the next step's input tensors and block tables, bookkeeping of sampled tokens, stop-string checks, detokenisation. Second, these components operate at very different rates. The API server handles bursts of arrivals, the engine core runs once per step, every few milliseconds, and the GPU executes kernels continuously if it is kept fed. How these components are mapped onto processes and threads, and how their work is overlapped, separates a fast engine from a slow one.

For the mathematician — processes, threads and the GIL

A process is a running program with its own memory; a thread is a sequence of instructions within a process, sharing its memory with other threads. Python's reference interpreter has a global interpreter lock (GIL): only one thread can execute Python code at a time, so CPU-heavy Python work in several threads does not run in parallel. To truly parallelise Python work, engines use several processes, communicating by message passing (for example over ZeroMQ sockets) or shared memory. That is why modern engines split the API server, tokenisation and detokenisation, and the scheduling loop into separate processes.

12.2 Where the CPU time goes, and how to hide it

To see why CPU overhead became a central problem, recall the time of a decode step (§3.6, §6.5). For Llama 3 8B on an H100 at moderate batch it is about 10 ms of GPU time, and less for smaller models, smaller batches or tensor-parallel shards. Now count the CPU work between two steps in a straightforward Python engine. The scheduler iterates over hundreds of requests and updates their states. Input tensors (token ids, positions, block tables, sampling parameters) are rebuilt and copied to the GPU. Sampled tokens are copied back, appended and checked against stop conditions, and new text is detokenised and sent. At a few microseconds per request per operation, this easily adds up to a few milliseconds per step. If the CPU work runs between GPU steps, the GPU idles for that time on every step, the overhead regime of §3.4.

Figure 12.2 quantifies the effect with a deliberately simple model: \(t_{\text{cpu}}=3\) ms of CPU work per step and a GPU step of \(t_{\text{gpu}}\) milliseconds. If the CPU work runs between GPU steps, throughput is \(t_{\text{gpu}}/(t_{\text{gpu}}+t_{\text{cpu}})\) of ideal: 77% for a 10 ms step, and only 40% for a 2 ms step such as a small model or a tensor-parallel shard. If the CPU work for step \(k+1\) can run while the GPU executes step \(k\), throughput is \(t_{\text{gpu}}/\max(t_{\text{gpu}},t_{\text{cpu}})\), which is 100% whenever the GPU step is longer than the CPU work. That is why overlapping matters most for small models and large tensor-parallel degrees, exactly what SGLang reported for its overlap scheduler.

Engines attack the problem with three techniques. Process separation moves work that need not be on the critical path (HTTP handling, tokenisation, detokenisation, streaming) into processes of their own, so it neither competes for the GIL nor delays the step loop. Incremental state means that the GPU workers keep a persistent copy of the batch's metadata and receive only changes each step, a few requests added or removed and new tokens appended, rather than rebuilding everything. Overlapped (asynchronous) scheduling lets the engine core schedule step \(k+1\) while the GPU runs step \(k\). The difficulty is that step \(k+1\)'s inputs include the tokens sampled at step \(k\), which are not yet known. The solution is to schedule with placeholders ("future tokens") that the GPU fills in from step \(k\)'s output buffer when step \(k+1\) actually executes, with CUDA events enforcing the ordering. The cost is that some decisions, such as noticing that a request has produced its end-of-sequence token, are made one step late, so a finished request may run one wasted step.

Figure 12.3 contrasts the two timelines. In the serial engine the GPU sits idle during every scheduling phase. In the overlapped engine the scheduling of the next step runs underneath the current one, and the GPU's timeline is continuous. With CUDA graphs removing kernel-launch gaps within each step (§7.8), and overlapped scheduling removing gaps between steps, a well-built engine keeps the GPU busy almost all the time. The bottleneck then returns to where Chapters 3 and 6 say it should be: memory bandwidth and compute.

Drill 12.1 — When is tensor parallelism too much?

Llama 3 8B serves 64 decodes at 2k context. Compare one H100 (TP = 1) with eight H100s (TP = 8), assuming \(t_{\text{cpu}}=3\) ms of CPU work per step and about 15 µs per all-reduce. What fraction of the GPU time is useful in each case, with and without overlapped scheduling?

Solution. At TP = 1 a step reads 16.06 GB of weights plus \(64\times2048\times128\) KiB \(\approx17.2\) GB of cache, about 33.3 GB, which takes \(t_{\text{gpu}}\approx9.9\) ms at 3.35 TB/s. Serial efficiency is \(9.9/12.9\approx77\%\), and overlapped it is 100%. At TP = 8 each GPU reads one eighth of both, about 4.2 GB, or 1.24 ms, plus \(2\times32=64\) all-reduces at 15 µs, about 1 ms, so \(t_{\text{gpu}}\approx2.2\) ms. Serial efficiency is \(2.2/5.2\approx42\%\). Even overlapped it is only \(2.2/3\approx73\%\), because the CPU now takes longer than the GPU. The eight GPUs deliver well under eight times the throughput of one, and for an 8B model eight independent replicas would be far better. Overlap hides CPU work only while there is GPU work long enough to hide it behind.

An engine-level trade-off: CUDA-graph buckets

CUDA graphs require fixed shapes (§7.8), so engines capture graphs for a set of batch sizes and pad each step's batch up to the next captured size. Which sizes to capture is a real trade-off. Each graph costs capture time at start-up and some GPU memory, while coarse buckets waste work on padding.

Figure 12.4 shows the waste for two bucket schemes. With powers of two, a batch just above a boundary (33, 65, 129) is padded almost to double its size, so nearly half the step's work is wasted on dummy sequences. Decode at these batch sizes is memory-bound, so padded rows cost little bandwidth for weights but do cost attention work and metadata. Buckets every eight sequences keep the waste below 10% once batches are large. vLLM's default capture sizes follow this pattern (1, 2, 4, then multiples of 8 up to a maximum). Some engines add "piecewise" graphs, which capture the parts of the model whose shapes are fixed and run attention outside the graph, so that one set of graphs can serve batches with arbitrary mixes of prefill and decode.

12.3 vLLM: from V0 to V1

vLLM began in 2023 as the reference implementation of PagedAttention[2]. Its first architecture, retrospectively "V0", was a single Python process wrapping the scheduler, block manager and model runner, with an asynchronous front end (AsyncLLMEngine) feeding requests into the step loop. It scheduled prefill and decode as separate kinds of step (with chunked prefill added later as an option), and grew a large set of features: dozens of model architectures, quantisation methods, speculative decoding, LoRA adapters, multimodal inputs and tensor and pipeline parallelism. By 2024 its throughput was increasingly limited by its own CPU overhead and by the complexity of interactions between features.

vLLM V1, released in alpha in January 2025 and the default since, re-architected the core[3][4]. Its main design choices map directly onto the problems of §12.2. The API server process handles HTTP and tokenisation and communicates with one or more engine core processes over ZeroMQ sockets. Each engine core runs a busy loop that schedules and dispatches work to GPU worker processes, one per GPU. The scheduler is unified: there is no distinction between prefill and decode steps. Every step has a token budget, and each request is assigned some number of tokens, which implements chunked prefill as the only mode (§11.6) and extends naturally to speculative decoding. Workers keep persistent batch state and receive only incremental updates each step. Prefix caching was rewritten to be cheap enough to enable by default, with under 1% throughput loss reported even at a 0% hit rate. The model runner uses torch.compile with piecewise CUDA graphs. Later releases added data-parallel coordination across engine cores, disaggregated prefill connectors (Chapter 13) and expert parallelism for MoE models (Chapter 19). Gordić's "Inside vLLM" (2025)[5] is an excellent walk through the V1 code, from a single offline call to multi-node serving.

Figure 12.5 shows the V1 layout. The separation is a direct application of the GIL discussion of §12.1. Front-end work scales with the number of concurrent connections and can be parallelised across API-server processes. The engine core is a single tight loop whose only job is to keep the GPUs fed. The workers execute whatever the engine core sends them, maintaining their own copy of the batch so that each step's message is small. The same structure accommodates data parallelism, with several engine cores each owning a model replica, and disaggregation, with prefill and decode engine cores connected by a KV-transfer channel.

12.4 SGLang: a language and a runtime

SGLang (Zheng et al., 2024)[6] started from a different observation. Many applications are not single prompt-and-response exchanges but programs that call an LLM many times: generate a plan, then fork into several branches, constrain one output to JSON, select among options, feed results into the next call. SGLang provides a Python-embedded frontend language for such programs, with primitives like gen, fork, select and regular-expression constraints, and a runtime that exploits the structure those programs reveal. Its best-known contribution is RadixAttention (§10.6). Because the runtime sees that several calls share a prefix (the forks of one program, the few-shot examples of many), it caches and reuses their KV automatically, and its scheduler orders requests to maximise cache hits. It also introduced compressed finite-state machines for faster constrained decoding, with jump-forward decoding (§4.7).

Figure 12.6 shows the kind of program SGLang was designed for: one long shared context, three parallel generations against it, and a final constrained call that combines their results. Written as four independent API calls to a conventional server, this would prefill the document four times. In SGLang the runtime sees the structure and prefills it once. On the runtime side, SGLang v0.4 (December 2024) introduced a zero-overhead batch scheduler, the overlapped scheduling of §12.2, borrowing the idea from the NanoFlow research system. It reported about 1.1× higher throughput in general and larger gains for small models and high tensor-parallel degrees. SGLang has also been a leader in serving large MoE models such as DeepSeek-V3, with data-parallel attention for MLA, expert parallelism and prefill–decode disaggregation (Chapters 13 and 19).

12.5 The wider landscape

vLLM and SGLang are the most widely used open-source engines for GPU serving, but several others matter, and each embodies a distinct design philosophy.

TensorRT-LLM (NVIDIA, 2023) originally took a compiled approach. A model was defined in a Python API and built ahead of time into a TensorRT engine, an optimised graph with fused kernels and hand-tuned "plugins" for attention and GEMMs, specialised to the GPU, precision and maximum shapes. The build step gave excellent performance, especially with NVIDIA's latest FP8 and FP4 kernels, at the cost of a rebuild for every configuration change. Its runtime introduced "in-flight batching", NVIDIA's name for continuous batching, with paged KV and chunked context. Since 2025 it has also offered a PyTorch backend that serves Hugging Face models without compilation and includes an overlap scheduler of the same kind as SGLang's. It is integrated with NVIDIA's Triton Inference Server and Dynamo (Chapter 13).

Text Generation Inference (TGI, Hugging Face, 2023) paired a Rust router, handling queueing, batching and streaming, with Python model servers. It was one of the first open engines with continuous batching and became the backend of Hugging Face's inference products, later supporting multiple backends including TensorRT-LLM and vLLM. LMDeploy (from the InternLM team) built its own C++ engine, TurboMind, with persistent batching and strong quantisation support. At the other end of the spectrum, llama.cpp (Gerganov, 2023) is a dependency-light C/C++ implementation designed to run on laptops, phones and servers alike, on CPUs, Apple Silicon (Metal), CUDA and other back ends. It introduced the GGUF single-file format, which bundles weights (in many quantisation schemes), tokeniser and metadata, and ships llama-server with an OpenAI-compatible API and parallel slots. Ollama and many desktop applications are built on it (Chapter 29). MLC-LLM compiles models with Apache TVM for phones, browsers (WebGPU) and diverse accelerators.

The engines are converging. They share kernels, too: FlashInfer, FlashAttention and FlashMLA are used across engines. The differences that remain are in maturity for particular models and hardware, in CPU-side efficiency, in how quickly new techniques land, and in ecosystem fit. The right choice for a deployment is usually made by benchmarking the two or three plausible engines on the actual model, hardware and traffic (Chapter 28).

12.6 The API surface

Applications talk to engines through an HTTP API, and in practice that means the OpenAI-compatible interface. Its main endpoint, /v1/chat/completions, accepts a list of messages with roles (system, user, assistant, tool), sampling parameters (temperature, top-p, max tokens, stop sequences, seed, penalties, \(n\), log-probabilities), optional tool definitions and response-format constraints. It returns either a complete response or a stream. Every engine in §12.5 implements this interface so that applications can switch engines without code changes. Several engine responsibilities sit behind it and are easy to get wrong.

Chat templates. A model is trained on a specific textual format for conversations, with special tokens marking each turn's role and end. The engine must convert messages to exactly that format, typically with a Jinja template shipped with the model's tokeniser. A template error, such as a missing generation prompt or a wrong end-of-turn token, silently degrades quality, a common cause of "the model is worse on engine X". Streaming. Responses are streamed as server-sent events: one HTTP response that stays open, delivering a small JSON message per chunk of new text and a final message with usage counts. The stop-string and detokenisation subtleties of §4.9 live here. Tool calls and structured outputs. When tools are offered, the model may emit a tool call in a model-specific syntax. The engine must parse it into structured JSON, often incrementally while streaming, and may use grammar-constrained decoding (§4.7) to guarantee validity. Usage accounting. Responses report prompt tokens, cached prompt tokens (prefix-cache hits; §10.6) and completion tokens, which is the basis of billing.

For the mathematician — server-sent events

HTTP is a request–response protocol: the client sends a request and the server sends one response. Server-sent events (SSE) keep that response open and let the server write a sequence of messages into it over time, each a line beginning data: followed by a JSON payload, separated by blank lines. The client reads them as they arrive. It is the simplest way to stream tokens: one-directional, text-based, and compatible with ordinary HTTP infrastructure.

12.7 Configuring an engine

Most of an inference engineer's interaction with an engine is through its configuration, and every important setting corresponds to a decision analysed earlier in this book. Using vLLM's names (other engines have equivalents), the main knobs are the following. tensor_parallel_size (and pipeline or data parallel sizes) decides how many GPUs hold one replica (Chapter 18). gpu_memory_utilization sets the fraction of GPU memory the engine may use, and hence the size of the KV pool (§10.9). max_num_seqs caps the number of concurrent sequences, an upper bound on decode batch size. max_num_batched_tokens is the token budget of chunked prefill (§11.6). kv_cache_dtype set to FP8 halves cache bytes (§8.6). enable_prefix_caching is on by default in V1. block_size is the KV block size (§10.3). max_model_len caps context length, which affects memory planning and CUDA-graph capture. Quantisation options load FP8, INT4 (AWQ, GPTQ) or FP4 weights (Chapter 14). Speculative-decoding settings choose a draft method (Chapter 20). CUDA-graph capture sizes are discussed in §12.2.

Worked example — configuring the chat service of §3.8

Llama 3 8B on one H100, 2,000-token prompts (1,500 shared), 500-token outputs, TPOT target 20 ms. Parallelism: TP = 1; the model fits on one GPU, and more replicas beat sharding for an 8B model. Memory: gpu_memory_utilization=0.9 leaves ≈ 52 GB, ≈ 400k BF16 cache tokens (§10.9). Cache dtype: FP8, doubling capacity to ≈ 800k tokens and moving the frontier (Figure 6.7). Batch cap: the TPOT target allows ≈ 270 sequences with an FP8 cache at 2k context (§6.6), and memory allows ≈ 350 at a mean live length of ≈ 2,250, so set max_num_seqs≈256. Token budget: ≈ 512–1,024 (§11.6), tuned by load test against P99 TPOT. Prefix caching: on, with the system prompt placed first and byte-identical. Context cap: max_model_len=8192 if the product allows, which shrinks worst-case planning. Then benchmark with an open-loop load generator at the target arrival rate and adjust.

The example illustrates a general method. Every number comes from a calculation in an earlier chapter, and the configuration is a set of hypotheses to be confirmed by measurement. Engines change quickly, and defaults and names vary across versions and engines, so the reasoning matters more than the specific settings. The questions behind each knob are always the same: what limits batch size (memory or TPOT), how much prefill can be absorbed per step, how much prefix reuse the workload offers, and whether the model's size justifies splitting it across GPUs.

Drill 12.2 — Configuring Llama 3 70B on four H100s

Repeat the worked example for Llama 3 70B with TP = 4, the same workload and a 20 ms TPOT target. Estimate the KV pool, the memory-limited and TPOT-limited batch sizes, and propose max_num_seqs.

Solution. Each GPU holds \(141/4\approx35.3\) GB of BF16 weights. With gpu_memory_utilization=0.9 and about 3 GB for activations and graphs, each GPU has about 34 GB left for cache, so the pool is about 136 GB across four GPUs. At 320 KiB per token in BF16 that is about 415k tokens, or about 830k with an FP8 cache. At a mean live length of 2,250 tokens, memory allows about 370 sequences with FP8. For TPOT, each GPU reads 35.3 GB of weights plus \(B\times2250\times160\text{ KiB}/4\approx B\times92\) MB of FP8 cache per step, and the 160 all-reduces cost about 2 ms. At full bandwidth the remaining 18 ms carries about 60 GB, which allows \(B\approx270\). At a more realistic 80% of peak bandwidth it carries about 48 GB, which allows only \(B\approx140\). The weights consume most of the per-step budget, so the TPOT-limited batch is very sensitive to achieved bandwidth. A sensible start is max_num_seqs=128 to 192, a token budget of about 512 (Drill 11.1), and a load test to settle the value.

12.8 Observing an engine: metrics and profiles

A configuration is a hypothesis, and testing it needs measurements. Suppose an engine serving Llama 3 8B delivers half the throughput a calculation predicts. The cause could be the scheduler admitting too few requests, the KV pool filling up and forcing preemptions, the prefix cache missing because a timestamp sits at the top of every system prompt, or the GPU idling between steps while Python works. Each has a different fix, and guessing wastes days. Engines therefore expose two kinds of evidence: metrics, which summarise the engine's state over time, and profiles, which record exactly what the CPU and GPU were doing during a short window.

The metrics are aggregated counters and histograms, exposed on an HTTP endpoint (conventionally /metrics) in the Prometheus text format and scraped every few seconds by a monitoring system. The essential ones correspond to quantities defined earlier in the book. On the latency side there are histograms of time to first token, time per output token (or inter-token latency), end-to-end latency and queueing time (§3.7, §11.8). On the state side there are the numbers of running and waiting requests, KV-cache usage as a fraction of the pool, the prefix-cache hit rate (§10.6), the number of preemptions (§10.5) and the distribution of tokens per step. Read together, they localise problems quickly. A long queue with low KV usage means the scheduler is limited by max_num_seqs or the token budget, not by memory. KV usage near 100% with frequent preemptions means memory is the limit, so an FP8 cache, a shorter max_model_len or more GPUs would help. A low hit rate on a workload that should share prefixes points at the prompts, not at the engine.

A profile answers the next question: when the engine is busy, is the GPU busy? The tool is a timeline profiler such as NVIDIA Nsight Systems or the PyTorch profiler. It records every kernel launch and every kernel execution with timestamps, together with CPU activity, and draws them as parallel tracks. The signature of CPU overhead is unmistakable. GPU kernels arrive in dense bursts, one per step, separated by empty stretches during which the CPU track is full of Python. A well-overlapped engine instead shows a continuous GPU track. Within a step, the profile also shows which kernels dominate: GEMMs, attention, all-reduces, or a surprising elementwise kernel that should have been fused (§7.6).

For the mathematician — why "GPU utilisation" misleads

The utilisation that nvidia-smi reports is the fraction of sampling intervals during which at least one kernel was running. A single small kernel occupying one SM out of 132 counts as 100%. It is therefore an indicator of idleness (a value well below 100% proves the GPU is waiting), not of efficiency. The quantities that measure efficiency are those of Chapter 6: model FLOP/s utilisation for compute-bound phases and model bandwidth utilisation (MBU) for memory-bound ones, computed from the bytes or FLOPs a step must do and the time it actually took.

Worked example — diagnosing a slow decode

Llama 3 8B on one H100 runs a steady batch of 128 decodes at 2k context, and the measured step time is 24 ms. Required bytes: 16.06 GB of weights plus \(128\times2048\times128\) KiB \(\approx34.4\) GB of cache, 50.4 GB in total, which needs 15.0 ms at 3.35 TB/s. MBU: \(15.0/24\approx63\%\). This is low for a large memory-bound batch, where good kernels reach 80–90%. Profile: Nsight shows each step's kernels taking 18 ms, followed by a 6 ms gap with the GPU idle. Within the kernels, MBU is \(15/18\approx83\%\), which is healthy. Diagnosis: the missing quarter of throughput is CPU overhead between steps, not slow kernels. Fixes, in order: make sure the engine version uses overlapped scheduling; look for per-request options that add CPU work on every step (log-probabilities for many candidates, many stop strings, per-token callbacks); and check that the batch sizes hit captured CUDA graphs. Removing the gap would raise throughput by \(24/18\approx1.33\times\) without changing a single kernel.

The example shows the order in which to look. First, compute what the step should cost from the roofline model of Chapter 6. Second, compare it with the measured step time. Third, use a profile to split the shortfall between gaps (CPU and scheduling) and slow kernels (kernel choice, shapes, fusion). Only the third step requires tools beyond a calculator, and the first two often settle the question. Measurements tell us whether the engine runs fast. They do not tell us whether it computes the right thing, and that question has subtleties of its own.

12.9 Correctness: when engines disagree

A common and disconcerting experience is to move a model from one engine to another, or from a reference implementation to a serving engine, and find that its outputs change. Sometimes the change is harmless, and sometimes evaluation scores drop by several points. An inference engineer must be able to tell the two apart and find the cause, because users notice quality regressions long before anyone reads a profile. The causes fall into a small number of classes, and they are worth knowing because each has a characteristic signature.

The first class is input formatting. The chat template may differ from the one the model was trained with (§12.6), the tokeniser may add a beginning-of-sequence token that the template has already inserted, so the model sees two of them, or a whitespace or special-token convention may differ. These bugs change every response, often subtly, and they are the most common cause of large quality drops. The second class is sampling defaults. Model repositories often ship a generation configuration with a recommended temperature, top-\(p\) or repetition penalty. One engine may apply it while another uses its own defaults, so "the same request" is sampled from different distributions (Chapter 4). The third class is numerics. Different kernels sum in different orders, and floating-point addition is not associative, so logits differ in the last bits. Batch composition also changes which kernels run and how work is split, so even one engine is not deterministic across batch sizes unless it uses batch-invariant kernels (§4.10). Once two engines sample different tokens at one position, the continuations diverge entirely, even though neither is wrong. The fourth class is approximation: a quantised checkpoint, an FP8 KV cache or a different attention approximation changes the model itself, by an amount that must be measured rather than assumed (Chapter 14).

Testing must therefore separate divergence from degradation. Comparing sampled texts is nearly useless, because tiny numerical differences legitimately produce different texts. Three tests are informative. A greedy prefix test decodes a set of prompts with temperature zero in both systems and records how many tokens agree before the first difference. Long agreement is expected, and divergence at the first token signals a formatting bug. A teacher-forced log-probability test feeds the same token sequences to both systems and compares the per-position distributions, for example by the mean Kullback–Leibler divergence. This measures the numerical gap directly, free of the butterfly effect of sampling. Finally, an evaluation suite on the tasks that matter to the product measures the effect users would see. Engines run the first two kinds of test in their own continuous integration for every supported model, which is part of why adding a new architecture to an engine is real work.

12.10 Beyond one GPU

Engines also coordinate multiple GPUs, a subject Part VI develops fully. Within a replica, tensor parallelism runs one worker per GPU, each holding a shard of every weight matrix and its share of the KV heads, with collective communication after each sub-layer. The engine core broadcasts each step's schedule to all workers, which must stay in lockstep. Pipeline parallelism assigns layers to GPUs and keeps several micro-batches in flight to fill the pipeline. Across replicas, data parallelism runs several engine cores behind a load balancer, which for MoE models may coordinate so that expert-parallel layers see synchronised batches. Large deployments use a distributed framework such as Ray or Kubernetes operators to place workers across nodes. Increasingly, the "engine" is not one process but a cluster of specialised services: prefill and decode workers, KV stores, routers and autoscalers. That is the architecture of disaggregated serving, the subject of the next chapter.

Looking ahead

An engine schedules prefill and decode together on the same GPUs, and chunked prefill (§11.6) makes that coexistence tolerable. But the two phases want fundamentally different things. Prefill is compute-bound and wants large batches of tokens and maximal FLOP/s. Decode is memory-bound and wants large batches of sequences, maximal bandwidth and steady, low-latency steps. Running them on the same hardware forces compromises in both. Chapter 13 asks the natural question: what if they ran on different machines, each tuned for its phase, with the KV cache sent from one to the other? That idea, disaggregated serving, reshaped large-scale deployments in 2024–25.

Chapter summary

  • An engine comprises an API server (templates, tokenisation, streaming), an engine core (scheduler, KV manager), GPU workers (model runner, sampler) and an output processor (detokenisation, stop checks).
  • CPU overhead per step (scheduling, input preparation, bookkeeping, detokenisation) can cost a large fraction of throughput when GPU steps are short: \(t_{\text{gpu}}/(t_{\text{gpu}}+t_{\text{cpu}})\) serial versus \(t_{\text{gpu}}/\max(t_{\text{gpu}},t_{\text{cpu}})\) overlapped. It is hidden by process separation, incremental state and overlapped scheduling with future-token placeholders.
  • CUDA-graph buckets trade capture cost against padding waste; fine-grained buckets (every 8) keep padding below 10% at large batch.
  • vLLM: V0 (single process, PagedAttention) → V1 (2025: API server ↔ engine core over ZMQ, one worker per GPU, unified token-budget scheduler, persistent batch, default-on prefix caching, torch.compile with piecewise CUDA graphs).
  • SGLang: frontend language for LLM programs, RadixAttention with cache-aware scheduling, compressed FSMs, zero-overhead overlap scheduler, strong MoE/MLA serving.
  • TensorRT-LLM (compiled engines, plugins, NVIDIA's newest kernels, now a PyTorch backend), TGI (Rust router), LMDeploy, llama.cpp (GGUF, local and edge), MLC-LLM. Engines are converging on the same techniques.
  • The OpenAI-compatible API: chat templates (a frequent source of silent quality loss), SSE streaming, tool-call parsing, structured outputs, usage with cached tokens.
  • Configuration knobs map to earlier analyses: parallel sizes, memory utilisation, max sequences, token budget, KV dtype, prefix caching, block size, max context, quantisation, speculation. Set them by calculation, then confirm by load test.
  • Observability: Prometheus metrics (TTFT, TPOT, queue time, running and waiting counts, KV usage, hit rate, preemptions) localise the limiting resource; a timeline profile splits a shortfall into inter-step gaps (CPU) and slow kernels. nvidia-smi utilisation measures idleness, not efficiency.
  • Engines disagree for four reasons: input formatting (templates, duplicated BOS), sampling defaults, numerics (summation order, batch dependence) and approximation (quantisation). Test with greedy-prefix agreement, teacher-forced KL and task evaluations, not by comparing sampled text.

Warm-up Trace a chat request through an inference engine, from HTTP to streamed text.

The API server receives a /v1/chat/completions request, validates its parameters, applies the model's chat template to turn the messages into a prompt string, and tokenises it. The request enters the engine core's waiting queue. At each step the scheduler decides whether to admit it under the token budget and memory limits; the KV-cache manager matches its prefix against cached blocks and allocates new ones. The model runner on each GPU worker executes a forward pass over the ragged batch (prefill chunks plus decodes), using paged attention kernels and, where shapes allow, CUDA graphs; the sampler turns the last position's logits into a token. The output processor appends the token, checks stop conditions, detokenises incrementally and sends a server-sent event to the client. When the request finishes, its blocks are freed or left in the prefix cache, and a final event reports usage counts including cached prompt tokens.

Warm-up What is the OpenAI-compatible API and why does every engine implement it?

It is the de facto HTTP interface for LLM serving: /v1/chat/completions (and the older /v1/completions) taking role-tagged messages, sampling parameters, tool definitions and response-format constraints, returning either a whole response or an SSE stream with a final usage record. Because applications, SDKs and agent frameworks are written against it, an engine that implements it can be swapped in without code changes. The interface hides real engine responsibilities: applying the right chat template, parsing model-specific tool-call syntax into JSON (incrementally while streaming), enforcing structured outputs with grammar-constrained decoding, handling stop strings across token boundaries, and accurate usage accounting.

Core Why did CPU overhead become a first-class problem for inference engines around 2024?

Two trends shrank the GPU's share of each step. Kernels got much better (FlashAttention, FlashInfer, fused GEMMs, FP8), and serving moved to smaller, efficient models and to tensor-parallel shards whose steps are only a few milliseconds. Meanwhile a Python engine does per-request work every step: scheduling, rebuilding token-id, position and block-table tensors, copying them to the GPU, copying sampled tokens back, stop checks, detokenisation and streaming. A few microseconds per request per operation adds up to milliseconds at batch sizes of hundreds. With CPU time \(t_{\text{cpu}}\) run serially between GPU steps of length \(t_{\text{gpu}}\), throughput is \(t_{\text{gpu}}/(t_{\text{gpu}}+t_{\text{cpu}})\): 3 ms of CPU work costs 23% at a 10 ms step and 60% at a 2 ms step. SGLang reported unoptimised engines spending up to half their time on overhead. The second generation of engines (vLLM V1, SGLang's overlap scheduler, TensorRT-LLM's PyTorch backend) was largely a response.

Core Explain overlapped (zero-overhead) scheduling. What is the hard part and what does it cost?

The engine core schedules and prepares step \(k+1\) while the GPU executes step \(k\), so the GPU timeline is continuous and throughput becomes \(t_{\text{gpu}}/\max(t_{\text{gpu}},t_{\text{cpu}})\) instead of \(t_{\text{gpu}}/(t_{\text{gpu}}+t_{\text{cpu}})\). The hard part is a data dependency: step \(k+1\)'s inputs include the tokens sampled in step \(k\), which do not exist yet when scheduling happens. Engines schedule with placeholder (future) tokens; when step \(k+1\) runs, the GPU reads the real tokens from step \(k\)'s output buffer, with CUDA events ordering the two. The costs: decisions that depend on sampled tokens, such as stopping at end-of-sequence or a stop string, are made one step late, so a finished request may run one wasted step and its blocks are freed a step later; the code is more complex, particularly with speculative decoding and structured outputs, whose next-step constraints depend on the current token. The gain is largest for small models and high TP degrees, where \(t_{\text{gpu}}\) is short.

Core Describe vLLM V1's architecture and the problem each design choice addresses.

(1) Process separation: API-server processes handle HTTP, templating and tokenisation; an engine-core process runs the scheduling loop; one worker process per GPU runs the model. They communicate over ZeroMQ. This avoids GIL contention and keeps front-end bursts off the critical path. (2) Unified scheduler: every step has a token budget and each request gets some number of tokens, so chunked prefill is the only mode and speculative tokens fit the same abstraction; this removes the separate prefill and decode paths of V0. (3) Persistent batch / incremental updates: workers keep batch metadata and receive only diffs, cutting per-step CPU and messaging. (4) Cheap prefix caching (under 1% loss at zero hit rate), so it is on by default. (5) torch.compile with piecewise CUDA graphs: fixed-shape parts are captured while attention runs outside, so mixed batches still benefit. The structure extends to data parallelism (several engine cores), disaggregation (KV connectors) and expert parallelism.

Core What are CUDA-graph buckets, and how would you choose them?

A CUDA graph replays a recorded sequence of kernels with fixed shapes and addresses, eliminating per-kernel launch overhead, which matters for short decode steps. Because shapes are fixed, the engine captures graphs for a set of batch sizes and pads each step up to the next captured size. Coarse buckets (powers of two) waste up to nearly half the step on padding just above a boundary (65 → 128); fine buckets (every 8) keep waste below about 10% at large batch but each graph costs capture time at start-up and GPU memory. A good choice is dense small sizes (1, 2, 4, 8), then every 8 or 16 up to the largest batch the configuration actually reaches (set by max_num_seqs), and no graphs beyond it. Above the largest size, or for prefill-heavy mixed steps, engines fall back to eager execution or piecewise graphs. Check in a profile that steady-state batch sizes hit graphs.

Core Compare vLLM, SGLang and TensorRT-LLM. When would you pick each?

All three now have paged KV, continuous batching with chunked prefill, prefix caching, CUDA graphs, FP8, speculative decoding, disaggregation and an OpenAI API, so the differences are of emphasis. vLLM: broadest model and hardware support, large community, V1's clean multi-process core; the default general-purpose choice. SGLang: RadixAttention with cache-aware scheduling and a frontend for multi-call programs; zero-overhead scheduling; strong performance for structured and agentic workloads and for large MoE/MLA models such as DeepSeek-V3. TensorRT-LLM: NVIDIA's newest kernels (FP8/FP4 on Hopper and Blackwell) and compiled engines, now also a PyTorch backend; often the fastest on NVIDIA hardware for supported models, integrated with Triton and Dynamo, but historically less flexible. In practice: shortlist by model support and hardware, then benchmark on your traffic, because results are workload-specific and change with every release.

Core What is RadixAttention and how does SGLang's scheduler exploit it?

RadixAttention stores cached KV blocks in a radix tree keyed by token sequences, so any request whose prompt shares a prefix with earlier ones can reuse their KV without recomputation (§10.6); leaves are evicted LRU when memory is needed. The scheduler adds cache awareness: among waiting requests it prefers those with the longest cached prefix match (roughly a longest-prefix-first order), which increases the hit rate and also keeps related requests together while their shared blocks are resident. The frontend language makes sharing explicit: forks of one program and few-shot templates reveal common prefixes. The risk is starvation of requests with no shared prefix, so practical schedulers bound waiting time or mix policies.

Deep-dive Your engine's step time is 24 ms for a workload where the roofline predicts 15 ms. How do you find the cause?

First compute MBU: \(15/24\approx63\%\), well below the 80–90% achievable for memory-bound decode at large batch. Then check metrics to make sure the batch is what you think it is (running count, tokens per step, preemptions). Then take a timeline profile (Nsight Systems or the PyTorch profiler) over a few steps and split the 24 ms into time with kernels running and gaps. If kernels take 18 ms and gaps 6 ms, kernel MBU is about 83% and the problem is CPU overhead: confirm the version uses overlapped scheduling, look for per-request options that add per-step CPU work (many logprobs, many stop strings, logits processors, structured-output masks computed on the CPU), check that batch sizes hit captured CUDA graphs, and consider reducing TP degree. If instead kernels take 23 ms, look inside them: which kernels dominate, whether attention uses the right backend for the head layout and dtype, whether an unfused elementwise kernel appears, and whether all-reduces are slow (topology, NCCL settings). Fix the largest bucket first and re-measure.

Deep-dive Why can two correct engines produce different outputs for the same prompt and model? How do you test that an engine is correct?

Four classes of cause. Input formatting: different chat templates, a duplicated BOS token, special-token or whitespace conventions; these change every response and often degrade quality. Sampling defaults: one engine applies the model's generation config (temperature, top-p, repetition penalty) and another does not. Numerics: kernels sum in different orders and floating-point addition is not associative, and batch composition changes kernel choice and splits, so logits differ in low bits; a single flipped argmax then sends continuations apart (unless batch-invariant kernels are used). Approximation: quantised weights or an FP8 KV cache change the model. Tests: greedy-prefix agreement (long agreement expected; first-token divergence indicates a formatting bug), teacher-forced per-position KL or log-prob differences on fixed sequences (measures the numerical gap directly), and task evaluations on what matters to the product (measures degradation). Comparing sampled texts proves nothing.

Deep-dive How does an engine handle stop strings and incremental detokenisation correctly while streaming?

Tokens do not align with characters or with stop strings. A multi-byte UTF-8 character may span tokens, and a stop string such as "\n\nUser:" may be split across several tokens or appear in the middle of one. The output processor therefore keeps a detokenisation state per request: it decodes a small window of recent tokens and emits only the text that is now stable (for example, not ending in an incomplete UTF-8 sequence, and with leading-space conventions respected). For stop strings it holds back any suffix of the emitted text that is a prefix of some stop string, until enough further text arrives to confirm or rule out a match; on a match it truncates and finishes the request. All of this is per request per step on the CPU, so many stop strings or long ones add overhead, and with overlapped scheduling the stop is detected a step late, so one extra token may be generated and discarded.

Deep-dive What does tensor parallelism require of the engine, and why can it be counter-productive for small models?

With TP, each worker holds a shard of every weight matrix and its share of KV heads; after attention and after the FFN each worker's partial results are combined by an all-reduce. The engine core must broadcast each step's schedule to all workers, which execute in lockstep; any worker's delay stalls all, and CPU work per step is unchanged by TP. For a small model the per-GPU step shrinks roughly as \(1/\text{TP}\) but the number of all-reduces (two per layer) does not, and each has a latency floor of order 10 µs. For Llama 3 8B at batch 64 and 2k context, TP = 8 turns a 9.9 ms step into about 1.2 ms of memory traffic plus about 1 ms of all-reduces, and with 3 ms of CPU work even perfect overlap gives only about 73% GPU efficiency. Eight replicas at TP = 1 would give nearly eight times the throughput. TP is justified when the model or its KV does not fit, or when latency targets need the aggregate bandwidth of several GPUs.

Design Configure an engine for Llama 3 70B on 4×H100 serving chat with 2k-token prompts, 500-token outputs and a 20 ms TPOT target. Justify each setting.

TP = 4: the 141 GB of BF16 weights need at least two GPUs, and four leave room for cache and give the bandwidth needed for TPOT. gpu_memory_utilization≈0.9: about 34 GB per GPU of KV after 35.3 GB of weights and activations, about 136 GB in total. FP8 KV cache: about 830k tokens instead of 415k, and half the per-step cache bytes. max_num_seqs: memory allows about 370 sequences at a mean live length of 2,250, but TPOT allows roughly 140–270 depending on achieved bandwidth (weights dominate the per-step bytes), so start at 128–192. Token budget ≈ 512, from the free prefill capacity of a decode step (Drill 11.1), tuned against P99 TPOT. Prefix caching on, with a byte-identical system prompt first. max_model_len set to what the product needs. Consider FP8 weights (Chapter 14), which would halve weight bytes and roughly double the TPOT-limited batch, and speculative decoding for latency (Chapter 20). Validate with an open-loop load test at the target arrival rate, watching TTFT and TPOT percentiles, KV usage and preemptions.

Design Design the monitoring and alerting for a production LLM service.

Scrape each engine's Prometheus metrics and the gateway's request logs. User-facing SLIs: TTFT and TPOT (or inter-token latency) percentiles, end-to-end latency, error and timeout rates, all per model and per tenant; alert on SLO burn rates, not single spikes. Capacity signals: running and waiting counts, queue time, KV-cache usage, preemptions per second, tokens per step, prefix-cache hit rate, GPU memory and power; a rising queue with KV usage near 100% predicts TTFT breaches before they happen and drives autoscaling. Efficiency: tokens per second per GPU and estimated MBU/MFU from step times, to detect regressions after upgrades. Quality: periodic canary prompts with greedy-prefix and log-prob checks against a reference, plus sampled evaluation; catch template or tokeniser regressions immediately after deploys. Keep a way to capture an Nsight or PyTorch profile on demand from a live replica for diagnosis.

Design You must add support for a new model architecture to an engine. What work is involved?

Implement the model's forward pass in the engine's modelling framework, using the engine's parallel linear layers (column and row parallel for TP), attention backend and fused kernels rather than reference PyTorch; map the checkpoint's weight names and shapes, including fused QKV or gate-up layouts and sharding for TP and EP. Handle anything novel: a new attention variant (sliding windows, MLA, linear attention) may need new kernels and a new KV-cache layout and block-manager support; a new positional encoding or normalisation; MoE routing with expert parallelism; multimodal encoders and their placeholders in the token stream. Register the tokeniser, chat template, tool-call parser and generation-config defaults. Make it work with CUDA graphs or torch.compile, quantisation formats and speculative decoding. Finally test correctness against the reference implementation (greedy prefixes, teacher-forced log-probs, evals) and performance against the roofline, and add both to CI.

Design A team reports that the same model "is worse" on your engine than on the provider's API. How do you investigate?

First make the comparison fair: same checkpoint and precision, same sampling parameters (explicitly set temperature, top-p, penalties, max tokens), same system prompt. Then test formatting: render the prompt your engine actually feeds the model (template output and token ids) and compare with the model card's reference; look for a duplicated or missing BOS, a missing generation prompt, wrong end-of-turn tokens, or tool-definition formatting. Run greedy-prefix tests against a reference implementation: divergence at the first tokens points at formatting, late divergence at numerics. Run teacher-forced log-prob comparisons to quantify numerical differences, and check for quantisation or FP8 KV settings. Finally run the team's evaluation on both systems with enough samples to separate noise from a real gap. In practice, template and sampling-default mismatches explain most such reports.

Core What metrics would tell you whether a serving deployment is limited by memory, by the scheduler or by compute?

Memory-limited: KV-cache usage near 100%, preemptions or swaps occurring, the running count below max_num_seqs, and a growing waiting queue; remedies are an FP8 cache, a shorter maximum context, better prefix reuse or more GPUs. Scheduler-limited: a long queue while KV usage is moderate and the running count sits at max_num_seqs, or tokens per step pinned at the token budget; remedies are raising the caps if TPOT allows. Compute-limited: prefill-heavy steps with high MFU and TTFT growing with prompt length; remedies are more compute, prefix caching, or disaggregating prefill (Chapter 13). Latency-limited by bandwidth: TPOT at its target with step time close to the roofline prediction; only fewer bytes per step (quantisation, MLA/GQA) or more bandwidth help. Low MBU with gaps in a profile indicates CPU overhead instead.
