Part V · Making Models Smaller — Chapter 14

Quantisation

Decode reads every weight once per step, so its speed is set by the number of bytes in the model. This chapter asks how few bits per number a model can use without losing what it knows: the number formats, the error analysis, the outlier problem that made language models hard to quantise, the algorithms that solved it between 2022 and 2024, and what actually becomes faster on real hardware.

Why this chapter

Part IV ended with a remark that is the starting point of Part V. Every serving technique we have studied works around the bytes of the model: batching shares each weight read among many sequences, paging packs caches tightly, disaggregation moves caches to where they are used. None of them reduces the bytes themselves. Yet decode is memory-bound (Chapter 6), so its time is close to the number of bytes read divided by the bandwidth, and Llama 3 8B in BF16 reads 16.06 GB per step however cleverly it is scheduled. Halve the bytes and, to first order, decode runs twice as fast, the model fits on half as many GPUs, and twice as much memory is left for the KV cache.

Quantisation represents weights, activations or caches with fewer bits per number: 8 instead of 16, or 4, or fewer. It is a lossy approximation, so the questions are how much accuracy is lost, how to lose as little as possible, and which of the savings in bytes turn into savings in time. Language models turned out to be unusually hard to quantise. In 2022, Dettmers and colleagues found that models above a few billion parameters develop a handful of activation features with enormous magnitudes, and that naive 8-bit quantisation destroys them[1]. The methods that followed, SmoothQuant, GPTQ, AWQ and rotation methods, each found a different way around this obstacle. By 2025, 8-bit floating point was the default for serving on Hopper GPUs, 4-bit weights were routine for latency-bound and local inference, and Blackwell GPUs had made 4-bit floating point a first-class format.

The subject has a pleasing mathematical core. A quantiser is a map onto a lattice, its error has a simple statistical model, the effect of outliers can be computed exactly, the best-known weight quantiser is a greedy algorithm for a closest-vector problem, and the cure for outliers is an orthogonal change of basis. We develop each of these in turn, then return to engineering: which formats the hardware supports, what each scheme does to the roofline, and how to choose.

  6. Choose a quantisation scheme for a given model, hardware and workload, and evaluate its accuracy properly.

14.1 Why fewer bits means faster

Three kinds of number are candidates for quantisation, and they behave differently. Weights are fixed after training, can be analysed offline with as much computation as we like, and dominate the bytes read at small batch. Activations, the inputs to each matrix product, change with every token, must be quantised on the fly, and matter because quantising both operands of a matrix product lets the tensor cores run at a lower precision, which is faster. The KV cache is a stored activation, read at every decode step, and dominates bytes at large batch and long context (§8.6). A scheme is described by what it quantises and to how many bits: W4A16 means 4-bit weights with 16-bit activations, W8A8 means both operands in 8 bits, and a KV4 suffix adds a 4-bit cache.

The two kinds of saving act on the two sides of the roofline. A decode step with \(B\) sequences reads the weights once and performs about \(2NB\) FLOPs, so with weight bytes \(N b_w\) and the hardware's peak compute \(\pi_x\) at the precision \(x\) of the matrix product, its time is roughly

\[ t_{\text{step}}\;\approx\;\max\!\Big(\frac{N\,b_w}{\beta},\;\frac{2NB}{\pi_x}\Big), \]

ignoring the cache for now. Weight-only quantisation reduces \(b_w\), the first term. Quantising activations as well lets the product run on lower-precision tensor cores, raising \(\pi_x\), the second term: on an H100, FP8 tensor cores deliver 1,979 TFLOP/s against 989 for BF16. The batch size at which a step turns compute-bound is \(B^{*}=\pi_x b_w/(2\beta)\), which for BF16 is the familiar 295.

Figure 14.1 plots this model for Llama 3 8B. At batch 1, throughput is set by weight bytes alone, so 4-bit weights (4.125 bits including their scales) run almost four times faster than BF16, and FP8 twice as fast. As the batch grows, each curve rises linearly until it meets its compute ceiling. The W4A16 curve meets the BF16 ceiling early, at a batch of about 76, because its weights are cheap to read but its arithmetic is still done in BF16. Beyond that point, 4-bit weights buy nothing in speed. W8A8 in FP8 doubles the ceiling, so it helps at every batch size. Combining 4-bit weights with FP8 compute gets the best of both, which is why NVIDIA's newest formats do exactly that. Real kernels fall short of these ideal curves, especially for 4-bit weights, which must be unpacked and converted before the tensor cores can use them, and real contexts add cache bytes that weight quantisation does not touch. But the picture is the right first approximation, and it already says something an interviewer will probe: weight-only 4-bit quantisation is a latency technique for small batches, while FP8 is a throughput technique.

The memory savings are equally important. A model that fits on fewer GPUs needs less tensor parallelism and its communication, and memory freed from weights becomes KV cache, which raises the batch size that memory allows. Before we can choose a scheme, though, we need to know what an 8-bit or 4-bit number actually is.

14.2 Number formats

A number format is a finite set of representable values together with an encoding. Two families matter. An integer format with \(n_b\) bits represents the \(2^{n_b}\) integers from \(-2^{n_b-1}\) to \(2^{n_b-1}-1\), and a real tensor is mapped onto them by a scale: \(x\approx\Delta\,(q-\zeta)\), where \(q\) is the stored integer, \(\Delta\) the step and \(\zeta\) an optional zero point. The representable values are equally spaced. A floating-point format splits its bits into a sign, an exponent field of \(e\) bits and a mantissa field of \(m\) bits, and represents \(\pm2^{E}\times(1.f)\), so its values are spaced uniformly within each power of two (a binade) and geometrically across binades. Relative precision is roughly constant, about \(2^{-m}\), over a range of about \(2^{2^e}\).

Figure 14.2 lays out the formats in use. BF16, the training and serving default since about 2020, keeps FP32's eight exponent bits and so its range, at the cost of precision: seven mantissa bits, about three significant decimal digits. The two 8-bit formats standardised in 2022[2] make different trade-offs. E4M3 has three mantissa bits and a maximum of 448, and is used for weights and activations; E5M2 has the range of FP16 with only two mantissa bits, and is used for gradients in training. FP4 in its E2M1 form has just sixteen codes: zero and the seven magnitudes 0.5, 1, 1.5, 2, 3, 4 and 6, each with either sign.

With so few values, a 4-bit or 8-bit format cannot cover the range of a whole tensor, so every practical scheme pairs the elements with scales: blocks of \(n_g\) consecutive elements share one higher-precision scale factor, and the stored element is the value divided by its block's scale. The scale granularity is part of the format. The Open Compute Project's microscaling (MX) specification of 2023[3] standardised block-scaled formats with \(n_g=32\) and an 8-bit power-of-two scale (E8M0); MXFP4 is E2M1 elements in such blocks, and MXFP8 and MXFP6 are analogous. NVIDIA's NVFP4, introduced with Blackwell, uses blocks of 16 E2M1 elements with an FP8 (E4M3) scale, plus one FP32 scale per tensor. The cost of the scales is easy to count: a block of \(n_g\) elements with an \(s\)-bit scale costs \(n_b+s/n_g\) bits per element, so MXFP4 costs \(4+8/32=4.25\) bits and NVFP4 \(4+8/16=4.5\).

Figure 14.3 compares the two 4-bit grids over the same interval. Both have eight non-negative magnitudes, but INT4 spreads them evenly while FP4 concentrates them near zero and leaves a large gap between 4 and 6. Which is better depends on the distribution being quantised. For uniformly distributed values, INT4 is optimal; for the bell-shaped, heavy-tailed distributions of trained weights, where most values are small and a few are large, FP4's allocation matches the data better. To make "better" precise we need an error model.

14.3 The error of rounding

Consider the simplest quantiser: a uniform grid of step \(\Delta\), with each value rounded to the nearest grid point. If the values are spread over many steps and are not aligned with the grid, the rounding error \(\epsilon=\hat x-x\) is well modelled as uniformly distributed on \([-\Delta/2,\Delta/2]\), independent of \(x\), with mean zero and variance

\[ \mathbb E[\epsilon^2]\;=\;\frac1\Delta\int_{-\Delta/2}^{\Delta/2}\epsilon^2\,d\epsilon\;=\;\frac{\Delta^2}{12}. \]

This is the classical model of quantisation noise from signal processing, and it is accurate except for very coarse grids. Now suppose a block of values with root-mean-square \(\sigma\) and maximum magnitude \(M\) is quantised symmetrically with \(n_b\) bits, using the absmax scale that maps \(\pm M\) to the ends of the grid. There are about \(2^{n_b}\) levels across a range of \(2M\), so \(\Delta\approx2M/2^{n_b}\), and the signal-to-quantisation-noise ratio is

\[ \text{SQNR}\;=\;\frac{\sigma^2}{\Delta^2/12}\;=\;\frac{3\cdot2^{2n_b}}{r_c^2},\qquad r_c=\frac{M}{\sigma}, \]

or, in decibels, \(\text{SQNR}\approx6.02\,n_b+4.77-20\log_{10}r_c\). Each extra bit buys about 6 dB, a factor of four in noise power. The second term is the crux of the whole subject. The quantity \(r_c\), the crest factor of the block, measures how far its largest value lies above its typical value, and every factor of ten in \(r_c\) costs 20 dB, more than three bits. For a block of 4,096 Gaussian values the maximum is about \(\sqrt{2\ln4096}\approx4.1\) standard deviations, so \(r_c\approx4\). A single value a hundred times the typical magnitude raises \(r_c\) to about 54 and costs 22 dB, almost four bits, of precision for every other value in the block, because the scale must accommodate the outlier and the step grows accordingly.

Figure 14.4 plots the formula for 8 and 4 bits. At the crest factor of well-behaved Gaussian data, 8 bits gives about 38 dB, a relative error near 1%, and 4 bits about 17 dB, near 14%. As the crest factor grows the lines fall together, and at \(r_c=100\) a 4-bit block is pure noise. The rest of this chapter can be read as a sequence of answers to one question: how do we keep the crest factor of whatever we quantise small?

The first and simplest answer is granularity. The crest factor is a property of a block, so smaller blocks have smaller crest factors: an outlier spoils only its own block. A scale can be shared by a whole tensor (per-tensor), by each row or column (per-channel for weights, per-token for activations), or by each group of \(n_g\) consecutive elements (per-group or block-wise). Finer granularity means more scales to store and apply, and, for activations, scales that must be computed at run time.

Figure 14.5 shows the three granularities on a small weight matrix. The trade-off can be measured. We quantised a 512 × 4096 matrix of heavy-tailed values (Student's \(t\) with five degrees of freedom, a reasonable stand-in for trained weights) with absmax scales at various group sizes, and recorded the relative root-mean-square error.

Figure 14.6 shows three regularities. Error grows steadily with group size, because a larger block is more likely to contain a large value; going from per-row scaling (4,096) to groups of 128 halves the INT4 error. FP4 is more accurate than INT4 at every group size on this heavy-tailed data, for the reason Figure 14.3 suggested. And the two block-scaled FP4 formats differ noticeably: MXFP4's scales are powers of two, so a block's maximum generally cannot be mapped exactly onto the top code and some range is wasted, while NVFP4's FP8 scales and smaller blocks bring it close to the exact-scale curve. These are the considerations behind the industry convention of INT4 weights in groups of 128 with FP16 scales (4.125 or 4.25 bits per weight with zero points) and behind NVIDIA's choices for NVFP4.

Worked example — the size of Llama 3 8B in each format

Count bits per weight including scales, then multiply by \(N=8.03\times10^{9}\). BF16: 16 bits, 16.06 GB. FP8 per-channel: 8 bits plus one scale per 4,096-element row, 8.03 GB. INT4, \(n_g=128\), FP16 scale: 4.125 bits, 4.14 GB; with an FP16 zero point as well, 4.25 bits, 4.27 GB. MXFP4: 4.25 bits, 4.27 GB. NVFP4: 4.5 bits, 4.52 GB. Embeddings and the LM head (about 1.05B parameters together) are often kept in higher precision because they are sensitive and cheap to keep, which adds about 1.6 GB to the 4-bit figures. At batch 1 the 4-bit model reads about a quarter of the bytes, and Figure 14.1's factor of four becomes something closer to 3× in practice.

Granularity tames moderate outliers in weights. It is much less help for activations, for a structural reason. A matrix product \(Y=XW\) sums over the shared inner dimension, so a scale can be factored out of the sum only if it is constant along that dimension: per-token scales for \(X\) (one per row) and per-output-channel scales for \(W\) (one per column) are free, because they become a rescaling of the output. A scale per input channel of \(X\), which is what an outlier feature would need, cannot be pulled out of the sum. As we now see, the outliers of language models live exactly in input channels.

14.4 The outlier problem

In August 2022, Dettmers, Lewis, Belkada and Zettlemoyer published LLM.int8()[1], the first method to quantise models of 175 billion parameters to 8 bits without degradation. Its most influential contribution was an empirical finding. In Transformers above about 6.7 billion parameters, a small number of hidden-state dimensions, the same few dimensions for almost every token and in most layers, carry values tens of times larger than the rest. These emergent outlier features appear abruptly with scale, and they are not noise: zeroing them devastates the model's perplexity. When the activation matrix \(X\) entering a linear layer is quantised per tensor or per token, these columns set the scale, the crest factor of every row is huge, and Figure 14.4 tells us what happens to everything else.

LLM.int8()'s remedy was a mixed-precision decomposition. For each matrix product, the columns of \(X\) containing any value above a threshold (6 in the paper) are separated out, together with the corresponding rows of \(W\), and multiplied in FP16; the remaining columns, more than 99.9% of them, are quantised to INT8 with per-token scales for \(X\) and per-channel scales for \(W\), and multiplied in integer arithmetic. The two partial products are summed. This preserved accuracy at every scale tested and halved memory, which made 175B-parameter models runnable on a single server and opened large models to a generation of researchers. It was, however, slower than FP16 for inference, because splitting each product and gathering outlier columns is awkward on GPUs. The memory saving was real; the speed-up was not.

Two asymmetries explain why outliers make activations hard and weights comparatively easy. First, weights are fixed, so their outliers can be found offline and handled by fine-grained grouping or special treatment at no run-time cost; activations change with every input, so their scales must be computed on the fly or calibrated in advance. Second, weight distributions are roughly bell-shaped with moderate crest factors, while activation outliers are systematic and concentrated in particular channels, the one place where per-element scaling is impossible. Later work traced the outliers to how trained Transformers implement "no-op" attention and very large residual-stream features, but for inference the important point is practical: activation outliers are channel-structured, predictable and very large. The methods of the next two sections exploit the first two properties.

14.5 SmoothQuant: moving the difficulty

SmoothQuant (Xiao et al., 2022)[4] starts from an observation about the matrix product. For any positive diagonal matrix \(D=\operatorname{diag}(u_1,\dots,u_k)\),

\[ Y\;=\;XW\;=\;\big(XD^{-1}\big)\big(DW\big). \]

Dividing column \(j\) of \(X\) by \(u_j\) and multiplying row \(j\) of \(W\) by \(u_j\) leaves the product unchanged. If channel \(j\) of the activations is an outlier, choosing \(u_j\) large shrinks it, at the price of enlarging row \(j\) of the weights. The difficulty of quantisation is transferred from the activations, which are hard to quantise, to the weights, which can absorb it. And the transformation is free at run time, because \(D^{-1}\) can be folded into the parameters of the normalisation layer that produces \(X\), and \(D\) into \(W\), both offline.

Figure 14.7 shows the effect on a toy activation profile. How large should the \(u_j\) be? Let \(a_j=\max_t|X_{tj}|\) be the calibrated maximum of activation channel \(j\) and \(w_j=\max_i|W_{ji}|\) the maximum of the matching weight row. After smoothing, these become \(a_j/u_j\) and \(u_jw_j\). SmoothQuant sets

\[ u_j\;=\;\frac{a_j^{\alpha_s}}{w_j^{\,1-\alpha_s}}, \]

with a migration strength \(\alpha_s\in[0,1]\). With \(\alpha_s=0.5\) the two maxima become equal, \(a_j/u_j=u_jw_j=\sqrt{a_jw_j}\), so the difficulty is shared evenly between the operands; larger \(\alpha_s\) pushes more onto the weights, which is needed for models with especially severe activation outliers. The equalisation is per channel, so after smoothing, per-token scales for \(X\) and per-channel scales for \(W\) see moderate crest factors, and standard INT8 GEMMs apply. SmoothQuant quantised models up to 530 billion parameters to W8A8 with negligible accuracy loss and reported up to 1.56× speed-up and a halving of memory over FP16, and it became the standard recipe for INT8 inference on Ampere-class GPUs.

Smoothing is a diagonal change of basis that rescales channels but cannot mix them. It works at 8 bits, where moderate crest factors are tolerable; at 4 bits, Figure 14.4 demands crest factors near the Gaussian value, and rescaling alone cannot get there. Before turning to the more powerful non-diagonal transformations that can, we look at the other half of the problem: quantising weights to 4 bits and below, where rounding itself must become smarter.

14.6 GPTQ: rounding with error compensation

Round-to-nearest, quantising each weight independently, is optimal if the goal is to make \(\hat W\) close to \(W\). But that is not the goal. What matters is that the layer's output is preserved on the inputs it actually sees, and errors in different weights can cancel in the output. Consider one output neuron of a linear layer, with weight row \(w\in\mathbb R^{1\times k}\), and a calibration set of inputs stacked as the columns of \(X\in\mathbb R^{k\times m}\). The squared output error of a quantised row \(\hat w\) is

\[ \big\|wX-\hat wX\big\|^2\;=\;(w-\hat w)\,\Sigma\,(w-\hat w)^\top,\qquad\Sigma=XX^\top. \]

The geometry is that of a quadratic form: errors along directions in which the inputs vary strongly are expensive, errors along directions the inputs rarely visit are cheap. Choosing \(\hat w\) on the quantisation grid to minimise this form is a closest-vector problem in the lattice defined by \(\Sigma\), which is NP-hard in general. GPTQ (Frantar, Ashkboos, Hoefler and Alistarh, 2022)[5] solves it approximately with a greedy procedure inherited from the Optimal Brain Surgeon pruning method of the early 1990s.

The key step is this. Suppose we round coordinate \(q\) of \(w\) to its grid value, changing it by \(c=\operatorname{quant}(w_q)-w_q\), and we are free to adjust the not-yet-quantised coordinates to compensate. The best total change \(\delta\) solves

\[ \min_{\delta}\;\delta\,\Sigma\,\delta^\top\quad\text{subject to}\quad\delta e_q=c, \]

where \(e_q\) is the \(q\)-th unit column vector. A Lagrange multiplier gives \(2\Sigma\delta^\top=\mu e_q\), so \(\delta^\top\propto\Sigma^{-1}e_q\), and the constraint fixes the constant:

\[ \delta\;=\;\frac{c}{[\Sigma^{-1}]_{qq}}\;e_q^\top\Sigma^{-1},\qquad\text{with error}\quad\delta\Sigma\delta^\top=\frac{c^2}{[\Sigma^{-1}]_{qq}}. \]

The \(q\)-th component of \(\delta\) is \(c\), which performs the rounding, and the other components spread a compensating correction across the remaining weights, weighted by the inverse second-moment matrix. GPTQ applies this step to the columns in a fixed order, left to right, so that the same sequence of \(\Sigma^{-1}\) updates serves every row of the weight matrix at once; after each step, the quantised coordinate is removed and the inverse of the remaining submatrix is needed, which a Cholesky factorisation of \(\Sigma^{-1}\) provides directly and stably. Updates are applied lazily in blocks of 128 columns so that the work is done as matrix products, and a small multiple of the mean diagonal is added to \(\Sigma\) for numerical stability. The result quantised OPT-175B and BLOOM-176B to 3 or 4 bits in about four GPU-hours, with far smaller accuracy loss than round-to-nearest.

Figure 14.8 shows one step. The procedure has a clean interpretation for the mathematically inclined: processing coordinates in order, rounding each and projecting the residual onto the remaining coordinates is the nearest-plane heuristic of lattice decoding (Babai's algorithm), applied to the lattice whose Gram matrix is \(\Sigma\). Like that algorithm it is greedy and not optimal, as Drill 14.2 shows, but it is fast and good. GPTQ needs only a few hundred calibration sequences and no gradients, and it produces standard group-wise INT4 weights that any W4A16 kernel can use. Its weakness is that it can overfit the calibration set, and its column order matters; the "act-order" variant quantises columns with the largest diagonal of \(\Sigma\), the most active input channels, first, while the most freedom to compensate remains.

Drill 14.1 — Bits and bytes

Compute the bits per weight and the weight memory of Llama 3 70B (70.6B parameters) in INT4 with \(n_g=128\), an FP16 scale and an FP16 zero point; in MXFP4; and in NVFP4. How many H100s does each need for weights alone, compared with BF16?

Solution. INT4: \(4+32/128=4.25\) bits, \(70.6\times10^{9}\times4.25/8\approx37.5\) GB. MXFP4: 4.25 bits, 37.5 GB. NVFP4: 4.5 bits, 39.7 GB. Each fits on one 80 GB H100, leaving roughly 35–40 GB for cache and activations (NVFP4 needs Blackwell hardware to compute in that format, though). BF16 needs 141 GB, so two GPUs at least, and in practice four once the cache is included. Quantisation to 4 bits changes the deployment from a tensor-parallel group to a single GPU, which also removes all tensor-parallel communication.

Drill 14.2 — GPTQ by hand, and why greedy is not optimal

A two-input neuron has weights \(w=(0.6,\;0.65)\), the quantisation grid is the integers, and the calibration inputs have \(\Sigma=\begin{pmatrix}2&1\\1&2\end{pmatrix}\). Compare round-to-nearest, one pass of GPTQ (column 1 first), and the best grid point, using the error \(d\,\Sigma\,d^\top\) with \(d=\hat w-w\).

Solution. The error is \(2d_1^2+2d_1d_2+2d_2^2\). Round-to-nearest gives \((1,1)\), \(d=(0.4,0.35)\), error \(0.32+0.28+0.245=0.845\). GPTQ: \(\Sigma^{-1}=\tfrac13\begin{pmatrix}2&-1\\-1&2\end{pmatrix}\); rounding \(w_1\) to 1 gives \(c=0.4\) and \(\delta=\frac{0.4}{2/3}\cdot(\tfrac23,-\tfrac13)=(0.4,-0.2)\), so \(w_2\) becomes 0.45 and rounds to 0. The result \((1,0)\) has \(d=(0.4,-0.65)\) and error \(0.32-0.52+0.845=0.645\), better than round-to-nearest because the positively correlated inputs let the two errors partly cancel. But \((0,1)\) has \(d=(-0.6,0.35)\) and error \(0.72-0.42+0.245=0.545\), better still. GPTQ's greedy order committed to \(\hat w_1=1\) too early. Ordering heuristics and refinements such as later lattice-based methods try to close this gap.

14.7 AWQ: protecting the weights that matter

GPTQ treats all weights through the lens of \(\Sigma\), but a simpler observation captures much of the same information. Lin and colleagues (2023)[6] noticed that keeping just 1% of weight channels in FP16 recovered most of the accuracy lost by 4-bit round-to-nearest, but only if those channels were chosen by the magnitude of their activations, not their weights. A weight multiplying a large input contributes a large share of the output, so its rounding error is amplified. Mixed precision is unattractive in kernels, however, so activation-aware weight quantisation (AWQ) protects salient channels by scaling instead.

Multiply input channel \(j\) of the weights by \(u_j>1\) before quantising, and divide the corresponding activation by \(u_j\): the product \(Q(w_ju_j)\,x_j/u_j\) is the same as before up to rounding. If scaling one channel does not change its group's maximum much, the step \(\Delta\) stays about the same, so the rounding error of \(w_ju_j\) is about the same in absolute terms, and after division by \(u_j\) its contribution to the output shrinks by a factor \(u_j\). Large-activation channels are thus quantised relatively more finely, at the cost of slightly coarser steps for others when a scaled weight becomes the group maximum. AWQ chooses \(u_j=\bar a_j^{\,\alpha}\), where \(\bar a_j\) is the mean activation magnitude of channel \(j\) on calibration data, and searches the single exponent \(\alpha\in[0,1]\) per layer to minimise the output error. The division by \(u_j\) is folded into the previous layer, exactly as in SmoothQuant, whose formula this resembles. The difference is the purpose: SmoothQuant moves difficulty onto the weights so that activations can be quantised, while AWQ uses activation statistics to decide which weights deserve precision.

AWQ needs no backpropagation and no reconstruction of weights, only activation statistics and a small grid search, so it generalises well beyond its calibration data and works for instruction-tuned and multimodal models. It received the MLSys 2024 best paper award, and with its kernels (and the later Marlin kernels[7], which reach close to the ideal 4× speed-up of 4-bit weights at batch sizes up to about 16–32 on Ampere and Hopper) it became, with GPTQ, the standard way to produce 4-bit weight-only checkpoints for local and latency-bound serving. Both methods, though, stop at the weights. To quantise activations and caches to 4 bits, the outliers themselves must go.

14.8 Rotations: removing outliers by a change of basis

SmoothQuant's identity \(XW=(XD^{-1})(DW)\) holds for any invertible \(D\), not only diagonal ones. Take \(D^{-1}=R\) orthogonal, so that \(XW=(XR)(R^\top W)\). An orthogonal transformation preserves Euclidean norms but can redistribute a vector's energy across coordinates. A vector with one huge coordinate, \(x=(100,\epsilon_2,\dots,\epsilon_d)\), has a large crest factor; after multiplication by a random orthogonal matrix, or by a normalised Hadamard matrix \(\mathcal H_d/\sqrt d\) whose entries are all \(\pm1/\sqrt d\), every coordinate receives a share of the outlier, and the result looks like a Gaussian vector with the same norm. Rotation does not shrink the outlier; it dissolves it.

Worked example — the crest factor before and after a Hadamard rotation

Let \(x\in\mathbb R^{4096}\) have one coordinate equal to 100 and the others independent standard normals. Then \(\|x\|^2\approx10^4+4095\), so \(\|x\|\approx118.8\) and \(\operatorname{rms}(x)=\|x\|/\sqrt{4096}\approx1.86\). Before rotation \(r_c\approx100/1.86\approx54\). After \(x\mapsto x\mathcal H_d/\sqrt d\), each coordinate is \(\pm100/64\) plus a sum of 4,095 terms \(\pm\epsilon_j/64\), approximately Gaussian with standard deviation about 1.0, so the rotated coordinates are near-Gaussian with rms 1.86 and maximum about \(4.1\times1.86\approx7.6\): \(r_c\approx4\). The gain is \(20\log_{10}(54/4)\approx23\) dB, nearly four bits of SQNR, from a transformation that costs \(O(d\log d)\) operations with a fast Walsh–Hadamard transform.

Figure 14.9 makes the point visually. The remaining question is where the rotations go, since applying \(R\) at run time to every activation would cost a matrix product per layer. QuaRot (Ashkboos et al., 2024)[8] observed that most of them can be folded into the weights offline, thanks to a property it called computational invariance. RMSNorm divides a vector by its norm, and orthogonal transformations preserve norms, so \(\operatorname{RMSNorm}(xR)=\operatorname{RMSNorm}(x)\,R\) once the norm's learned gain is folded into the next weight matrix. Rotating the entire residual stream by one \(R\), by multiplying the embedding table by \(R\), the input weights of every block by \(R^\top\) on the left and the output weights by \(R\) on the right, therefore leaves the network's function exactly unchanged while every activation entering a linear layer is rotated. A few places, such as the input to the FFN's down projection and the keys and values for cache quantisation, need small online Hadamard transforms, which fast kernels make cheap. With rotated activations of near-Gaussian crest factor, QuaRot quantised weights, activations and KV cache all to 4 bits (W4A4KV4) with modest accuracy loss on Llama 2 models. SpinQuant (Liu et al., 2024)[9] went further and learned the rotations, optimising \(R\) over the orthogonal group (with the Cayley parametrisation, an elegant use of manifold optimisation) to minimise the quantised network's loss, and found that learned rotations beat random Hadamard ones substantially at 4 bits.

Rotations completed the theoretical picture: outliers are a property of the basis, not of the model, and an orthogonal change of basis that the network does not notice can remove them. In practice, though, the most widely deployed low-precision serving of 2025 did not use 4-bit activations on Hopper GPUs, because Hopper has no 4-bit tensor cores and the gains would not appear. What hardware supports decides what is worth doing.

14.9 Quantisation in practice

By 2025 a fairly stable set of practices had emerged, organised by hardware generation. On Hopper (H100, H200), FP8 W8A8 is the default for serving large models: E4M3 weights with per-channel or block scales, and E4M3 activations with per-token or per-tensor scales computed on the fly, running on FP8 tensor cores at twice BF16 throughput. Because E4M3 is a floating-point format, its relative precision is nearly uniform across its range, so moderate outliers are tolerated without smoothing. A large evaluation by Kurtic and colleagues (2024), covering hundreds of thousands of model evaluations[10], found FP8 W8A8 essentially lossless across tasks and model sizes, INT8 W8A8 within one to three per cent when carefully tuned, and 4-bit weight-only quantisation competitive for most tasks, with the best choice depending on deployment. DeepSeek-V3 was trained in FP8 with fine-grained scaling, 1 × 128 tiles for activations and 128 × 128 blocks for weights, so it is served in FP8 natively[11].

W4A16 (GPTQ or AWQ weights with Marlin-style kernels) is the choice when latency at small batch matters most, or when memory is the binding constraint, as in local inference on a single consumer GPU or a laptop (Chapter 29). As Figure 14.1 predicts, its advantage fades at large batch, where FP8 overtakes it. On Blackwell (B200, GB200), FP4 tensor cores double FP8 throughput again, and MXFP4 and NVFP4 become formats for both weights and activations. Accuracy at 4 bits is harder to keep than at 8, so models are increasingly trained or fine-tuned with FP4 in the loop (quantisation-aware training) rather than quantised after the fact. OpenAI's gpt-oss models of 2025, for example, were released with their MoE weights in MXFP4. For the KV cache, FP8 is common and nearly free in accuracy, doubling cache capacity (§8.6), with 4-bit caches in more specialised settings.

Two lessons of practice are as important as any algorithm. The first is about evaluation. Perplexity on a generic corpus is a blunt instrument: a quantised model can match its perplexity closely and still fail more often on long-context retrieval, multi-step reasoning, code or less common languages, where small errors compound over many tokens. A credible evaluation compares the quantised and reference models on the tasks the product needs, with enough samples to resolve differences of a point or two, and checks per-task rather than averaged scores, using the teacher-forced divergence tests of §12.9 to separate implementation bugs from genuine quantisation error. The second is about what is quantised. Embeddings, the LM head, normalisation parameters and sometimes the first and last blocks are sensitive and contribute little to bytes per step, so they are usually kept in higher precision; MoE experts, which dominate parameter count but are each read only when routed to, are the most profitable targets.

Worked example — choosing a scheme for Llama 3 70B

Serve Llama 3 70B for chat on H100s with a 20 ms TPOT target. BF16, TP = 4: 35.3 GB of weights per GPU; the TPOT-limited batch is about 140–270 (Drill 12.2). FP8 W8A8, TP = 2: 35.3 GB of weights per GPU again, now on half as many GPUs, so twice the throughput per GPU at the same per-GPU bytes; with an FP8 cache (160 KiB per token), about 34 GB per GPU of cache, roughly 415k tokens per replica. Accuracy is essentially unchanged. W4A16, TP = 1: about 37.5 GB of weights on one GPU, leaving about 31 GB for an FP8 cache (about 190k tokens), with no tensor-parallel communication; per-step weight bytes are about the same as the FP8 TP = 2 configuration on each of its GPUs, but the arithmetic runs in BF16 on one GPU, so the step becomes compute-bound at a batch of about 78. Decision: FP8 at TP = 2 for throughput-oriented serving; W4A16 on one GPU for low-concurrency, latency-sensitive or cost-constrained deployments, after validating accuracy on the product's tasks.

The example illustrates the general method: compute the bytes per step and the compute ceiling for each candidate, check what fits in memory and how much cache remains, and only then compare accuracy on the workload. Quantisation is rarely a single decision; it interacts with parallelism, batch size, cache precision and hardware, which is why every chapter of Part IV has quantisation knobs among its configuration options.

Drill 14.3 — Where does W4A16 stop helping?

For Llama 3 8B on an H100, at what batch size does a W4A16 decode step become compute-bound (weights only), and what is the speed-up over BF16 at batch 32 and at batch 512?

Solution. With \(b_w=4.125/8\) bytes and BF16 compute, \(B^{*}=\pi b_w/(2\beta)=989\times10^{12}\times0.516/(2\times3.35\times10^{12})\approx76\). At batch 32 both are memory-bound: BF16 takes \(16.06/3.35=4.8\) ms and W4A16 \(4.14/3.35=1.24\) ms, a 3.9× speed-up in the ideal model. At batch 512 both are compute-bound at \(2\times8.03\times10^{9}\times512/989\times10^{12}\approx8.3\) ms, so the speed-up is 1×, and in practice W4A16 is slightly slower because of dequantisation work. FP8 W8A8 would take about 4.2 ms at batch 512.

Looking ahead

Quantisation keeps every parameter and stores it more cheaply. Its error is spread thinly over all weights, and the analysis of this chapter shows that below about four bits the noise grows quickly however cleverly we round. A different way to shrink a model is to remove parts of it altogether: individual weights, structured blocks of weights, attention heads, whole layers, or, most radically, to train a smaller model to imitate the large one. Each of these trades accuracy for bytes and FLOPs in a different way, and only some of them translate into speed on GPUs. Chapter 15 takes up pruning, sparsity and distillation, asks which kinds of sparsity the hardware can exploit, and explains why distillation has become the way small models are made.

Warm-up Why does quantisation speed up LLM decode? When does it not?

Decode at small and moderate batch is memory-bound: each step reads all weights (and the KV cache) once, so step time is about bytes divided by HBM bandwidth. Storing weights in 8 or 4 bits reads 2× or almost 4× fewer bytes. It does not speed things up when the step is compute-bound: at large batch, weight-only 4-bit quantisation still multiplies in BF16, so beyond \(B^{*}=\pi b_w/(2\beta)\) (about 76 for Llama 3 8B on H100) it is no faster, and dequantisation adds overhead. Quantising activations as well (W8A8 FP8) raises the compute ceiling, so it helps at large batch too. Quantising weights also does nothing for cache bytes, which dominate at long contexts; that needs KV quantisation. Separately, smaller models fit on fewer GPUs and leave more memory for cache, which helps throughput indirectly.

Warm-up Explain FP8 E4M3 versus E5M2 and where each is used.

Both are 8-bit floating-point formats from the 2022 FP8 specification. E4M3 has 4 exponent bits and 3 mantissa bits, a maximum of 448 and relative precision of about 1/8 per binade; it is used for weights and activations in inference (and forward passes in training), where precision matters more than range. E5M2 has 5 exponent bits and 2 mantissa bits, the range of FP16 (max 57,344) but coarser precision; it is used for gradients in training, which span a wide dynamic range. Both are used with scales (per-tensor, per-channel, per-token or per-block) to map tensors into range. Hopper and Blackwell tensor cores execute FP8 products at about twice BF16 throughput.

Core Derive the SQNR of a uniform quantiser and explain the role of the crest factor.

With step \(\Delta\) and values not aligned to the grid, rounding error is approximately uniform on \([-\Delta/2,\Delta/2]\), so its variance is \(\Delta^2/12\). An absmax scale over a block with maximum \(M\) and rms \(\sigma\), using \(2^{n_b}\) levels over \([-M,M]\), gives \(\Delta\approx2M/2^{n_b}\). Then \(\text{SQNR}=\sigma^2/(\Delta^2/12)=3\cdot2^{2n_b}/r_c^2\) with \(r_c=M/\sigma\), or \(6.02n_b+4.77-20\log_{10}r_c\) dB. Bits buy 6 dB each; the crest factor costs 20 dB per decade. A Gaussian block of 4,096 values has \(r_c\approx4\); one 100× outlier raises it to about 54, costing almost four bits for every value in the block, because the scale must stretch to cover the outlier. Hence the whole field's focus on reducing crest factors: finer groups, smoothing, rotations, and mixed precision for outliers.

Core What are emergent outlier features, and why do they make activation quantisation hard?

Dettmers et al. (LLM.int8(), 2022) found that Transformers above roughly 6.7B parameters develop a few hidden dimensions whose values are tens of times larger than typical, consistently across tokens and in most layers; removing them destroys performance. In a matrix product \(Y=XW\) these are input channels of \(X\). Per-token scales (rows of \(X\)) and per-output-channel scales (columns of \(W\)) can be factored out of the sum, but per-input-channel scales cannot, so one outlier channel inflates the scale of every token's row and crushes the precision of the other channels. Weights do not have this problem to the same extent: they are fixed, roughly bell-shaped and can be quantised offline with fine groups. Remedies: keep outlier channels in high precision (LLM.int8()), move the range into the weights (SmoothQuant), or rotate the basis to dissolve them (QuaRot, SpinQuant); FP8's floating-point grid also tolerates moderate outliers.

Core Explain SmoothQuant and derive its choice of scales.

For any positive diagonal \(D\), \(XW=(XD^{-1})(DW)\). Choosing \(D=\operatorname{diag}(u_j)\) divides activation channel \(j\) by \(u_j\) and multiplies weight row \(j\) by \(u_j\). With calibrated maxima \(a_j\) (activations) and \(w_j\) (weights), the new maxima are \(a_j/u_j\) and \(u_jw_j\). SmoothQuant sets \(u_j=a_j^{\alpha_s}/w_j^{1-\alpha_s}\); with \(\alpha_s=0.5\) both become \(\sqrt{a_jw_j}\), splitting the difficulty evenly; larger \(\alpha_s\) moves more onto the weights for models with severe activation outliers. \(D^{-1}\) is folded into the preceding LayerNorm/RMSNorm gain and \(D\) into \(W\) offline, so there is no run-time cost, and standard INT8 GEMMs with per-token and per-channel scales apply. It enabled accurate W8A8 up to 530B parameters, with up to 1.56× speed-up and half the memory. Its limit: a diagonal transformation cannot mix channels, so it is not enough for 4-bit activations.

Core Compare GPTQ and AWQ.

Both produce 4-bit (or 3-bit) group-wise weight-only checkpoints from a small calibration set, without retraining. GPTQ minimises each layer's output error \((w-\hat w)\Sigma(w-\hat w)^\top\), quantising columns in order and compensating each rounding error by adjusting remaining weights with the Optimal-Brain-Surgeon update \(\delta=c\,e_q^\top\Sigma^{-1}/[\Sigma^{-1}]_{qq}\), using a Cholesky factorisation and blocked updates; it is a second-order, error-feedback method and can overfit calibration data. AWQ observes that weights multiplying large activations matter most, and scales those input channels up by \(u_j=\bar a_j^{\alpha}\) before round-to-nearest (folding \(1/u_j\) into the previous layer), choosing \(\alpha\) per layer by grid search; it uses only activation statistics, so it generalises well and is cheap. In accuracy they are close; they can even be combined. Both serve the W4A16 use case with fast kernels such as Marlin.

Core How do block-scaled formats like MXFP4 and NVFP4 work, and how do they differ?

Elements are stored in a tiny format (FP4 E2M1: magnitudes 0, 0.5, 1, 1.5, 2, 3, 4, 6), and each block of \(n_g\) consecutive elements shares a scale, so the block's values are mapped into the element format's range. MXFP4 (OCP Microscaling, 2023) uses blocks of 32 and an 8-bit power-of-two (E8M0) scale: 4.25 bits per element, cheap to apply (an exponent add) but coarse, since a block maximum generally cannot map exactly to the top code. NVFP4 (Blackwell) uses blocks of 16 with an FP8 E4M3 scale and a per-tensor FP32 scale: 4.5 bits per element, with smaller blocks and finer scales, hence lower error (about 9% versus 13% relative RMS error in our heavy-tailed simulation). Blackwell tensor cores multiply such blocks directly at about twice FP8 throughput, so these formats serve both weights and activations.

Deep-dive Derive the GPTQ update from first principles.

For weight row \(w\) and calibration inputs \(X\) (columns), the output error of \(\hat w\) is \(\|(w-\hat w)X\|^2=(w-\hat w)\Sigma(w-\hat w)^\top\), \(\Sigma=XX^\top\). Suppose we fix coordinate \(q\) to its grid value, i.e. change it by \(c=\operatorname{quant}(w_q)-w_q\), and may change other unquantised coordinates freely. Minimise \(\delta\Sigma\delta^\top\) subject to \(\delta e_q=c\). The Lagrangian \(\delta\Sigma\delta^\top-\mu(\delta e_q-c)\) gives \(2\Sigma\delta^\top=\mu e_q\), so \(\delta^\top=(\mu/2)\Sigma^{-1}e_q\); the constraint gives \(\mu/2=c/[\Sigma^{-1}]_{qq}\). Hence \(\delta=c\,e_q^\top\Sigma^{-1}/[\Sigma^{-1}]_{qq}\), with error increase \(c^2/[\Sigma^{-1}]_{qq}\). After fixing \(q\), the problem restricts to the remaining coordinates, whose relevant inverse is the Schur-complement update of \(\Sigma^{-1}\); GPTQ obtains all of these at once from the Cholesky factor of \(\Sigma^{-1}\), processes columns in a fixed order shared by all rows, applies updates lazily in blocks of 128, and dampens \(\Sigma\) by adding a small multiple of its mean diagonal. This is the nearest-plane heuristic for a closest-vector problem with Gram matrix \(\Sigma\).

Deep-dive How do rotation methods (QuaRot, SpinQuant) enable 4-bit activations, and where do the rotations go?

For orthogonal \(R\), \(XW=(XR)(R^\top W)\). Rotating preserves norms but spreads a large coordinate across all coordinates: a 4,096-vector with one 100× outlier goes from crest factor about 54 to about 4, gaining about 23 dB, which 4-bit quantisation needs. Placement: RMSNorm commutes with orthogonal maps (\(\|xR\|=\|x\|\)) once its gain is folded into the following weights, so the whole residual stream can be rotated by one \(R\), absorbed offline by multiplying the embedding by \(R\), each block's input projections by \(R^\top\) and output projections by \(R\); the network computes exactly the same function. A few places need online Hadamard transforms (input to the FFN down-projection; keys and values for 4-bit KV), implemented with fast Walsh–Hadamard kernels at \(O(d\log d)\). QuaRot used random Hadamard rotations to reach W4A4KV4; SpinQuant learned \(R\) on the orthogonal manifold (Cayley optimisation) and improved 4-bit accuracy substantially. Benefit requires 4-bit tensor cores, which Hopper lacks.

Deep-dive Why did FP8 rather than INT8 become the default 8-bit inference format on Hopper?

Accuracy: FP8 E4M3 has roughly constant relative precision across its range, so moderate outliers and wide distributions are represented well without smoothing; INT8 has uniform absolute precision and needs per-channel/per-token scales plus SmoothQuant to cope with activation outliers. Large evaluations found FP8 W8A8 essentially lossless and INT8 within 1–3% when tuned. Hardware: Hopper's tensor cores run FP8 at the same rate as INT8 (about 2× BF16), and FP8 integrates naturally with BF16 accumulation and with FP8 training (DeepSeek-V3 was trained in FP8 with fine-grained scales). Engineering: dynamic per-token activation scales are cheap, calibration is simpler, and the same format serves the KV cache. INT8 remains relevant on Ampere and CPUs.

Deep-dive When is W4A16 slower than FP8 W8A8, and why?

W4A16 reads about 4.1 bits per weight but performs the matrix product in BF16 after dequantising in registers. At small batch, decode is memory-bound and W4A16 reads half the bytes of FP8, so it is faster (up to about 2× over FP8, 4× over BF16, ideal). As batch grows, arithmetic grows linearly while weight bytes are fixed; W4A16 becomes compute-bound at \(B^{*}\approx\pi_{\text{BF16}}b_w/(2\beta)\approx76\) for Llama 3 8B on H100, whereas FP8 W8A8 becomes compute-bound at about 295 and its compute ceiling is twice as high. Above roughly 150 sequences FP8 is faster, and at 512 it is about twice as fast. Dequantisation (unpacking, scale multiply, layout shuffles) adds overhead that grows with batch. Long contexts also shift bytes to the KV cache, which weight quantisation does not reduce.

Deep-dive How would you evaluate whether a quantised model is good enough to ship?

Reference: the unquantised model with identical serving settings. Implementation checks first: teacher-forced per-token KL or log-prob differences on held-out text, and greedy-prefix agreement, to catch kernel or packing bugs (§12.9). Then task evaluation on what the product uses: instruction following, reasoning (GSM8K, MATH-style), code (pass@k), long-context retrieval, multilingual, tool calling and structured output validity, with enough samples for confidence intervals of about a point, and per-task results rather than an average. Check generation-level behaviour: answer length, refusals, repetition; long generations, where errors compound; and the tails (worst-case prompts). Compare at realistic sampling settings and also greedy. Include latency and throughput on the target batch sizes, since a quantisation that does not speed up the actual workload is not worth its risk. Finally, run an online A/B or shadow test where possible.

Design Choose a quantisation strategy for serving a 70B dense model on 8×H100 for high-throughput chat, and for the same model on a single 48 GB workstation GPU.

8×H100, throughput: FP8 W8A8 (per-channel weights, dynamic per-token activations) with an FP8 KV cache. Weights are 70.6 GB, so TP = 2 replicas (four of them) each have about 34 GB per GPU for cache, high batch sizes and FP8's doubled compute ceiling; accuracy is essentially unchanged. Keep embeddings and LM head in BF16. Optionally test FP8 attention and speculative decoding. Avoid W4A16 here: at large batch it is compute-bound in BF16 and slower than FP8. Single 48 GB GPU, latency: 4-bit weights (AWQ or GPTQ, groups of 128, about 37.5 GB) leave about 8 GB for cache and activations, so use an FP8 or 4-bit KV cache and modest context; batch is small, so W4A16 kernels (Marlin) give close to the memory-bound ideal. Validate accuracy on the target tasks; if quality is short, try mixed precision (keep sensitive layers at 8 bits) or a smaller model distilled for the task (Chapter 15).

Design Design a quantisation pipeline for a model provider that releases new models monthly.

Inputs: BF16 checkpoint, target hardware (Hopper, Blackwell, consumer GPUs), target formats (FP8, NVFP4/MXFP4, INT4 W4A16). Steps: (1) calibration data representative of real traffic (chat, code, long documents, multilingual), a few hundred to a few thousand sequences; (2) per-format recipes: FP8 with per-channel weight scales and dynamic activation scales; INT4 with AWQ or GPTQ, groups of 128, act-order; FP4 with block scales, rotations where activations are quantised, and quantisation-aware fine-tuning when PTQ loses too much; (3) layer sensitivity analysis to keep sensitive layers (embeddings, LM head, some attention projections) at higher precision; (4) automated evaluation against BF16 on a fixed suite with confidence intervals and per-task gates, plus KL on held-out text; (5) kernel and engine compatibility tests (vLLM, SGLang, TensorRT-LLM, llama.cpp formats) and performance benchmarks at several batch sizes; (6) publish checkpoints with metadata (format, scales, calibration set, measured deltas). Automate end to end so each release ships quantised variants within days.

Design Your team wants to run DeepSeek-V3-class MoE models cheaply. Where would you apply quantisation, and why?

MoE parameters are dominated by experts, each read only when routed, so expert weights are the most profitable target: FP8 (the model's native training format) at minimum, and 4-bit experts (MXFP4/NVFP4 on Blackwell, or W4A16-style on Hopper at small expert batches) to cut memory, which lets the model fit on fewer GPUs and reduces expert-parallel communication volume. Attention and shared layers are small and sensitive, so keep them in FP8 or BF16. The KV cache is already compact with MLA but can be FP8. Because expert batch sizes per GPU are often small in decode, expert GEMMs are memory-bound, which is exactly where 4-bit weights pay. Validate carefully: routing can be sensitive to small numerical changes in gate logits, so keep the router in high precision and check load balance and accuracy.

Core What is quantisation-aware training, and when is it necessary?

Post-training quantisation (PTQ) quantises a trained model using a small calibration set (GPTQ, AWQ, SmoothQuant, FP8 scaling). Quantisation-aware training (QAT) instead simulates quantisation during training or fine-tuning: the forward pass uses quantised weights (and possibly activations), and gradients flow through the rounding with a straight-through estimator (treating rounding as identity in the backward pass), so the network learns weights that are robust to the grid. It costs training compute and data, but recovers accuracy that PTQ cannot, and is increasingly necessary at 4 bits for weights and activations (FP4 on Blackwell) or below. Model providers increasingly release QAT checkpoints (for example 4-bit variants of open models), and some models are trained natively in low precision (DeepSeek-V3 in FP8, gpt-oss MoE weights released in MXFP4).
