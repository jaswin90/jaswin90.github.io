Part VI · Distributed Inference — Chapter 17

Distributed Computing Fundamentals

When a model or its cache does not fit on one GPU, the GPUs must exchange data, and every exchange costs time. This chapter builds the vocabulary and the cost model of that exchange: collective operations described as linear algebra, the α–β model, ring and tree algorithms and why the ring is bandwidth-optimal, the interconnects that carry the bytes, the software that drives them, and the art of hiding communication behind computation.

Why this chapter

Every chapter so far has, in the end, reasoned about one GPU: its compute, its memory bandwidth, its memory capacity. That is the right starting point, because the economics of inference are set per GPU. But the largest models do not fit on one. Llama 3 70B needs 141 GB of BF16 weights, almost twice an H100's memory; DeepSeek-V3 needs 671 GB even in FP8; and even when weights fit, a latency target may require more memory bandwidth per request than one GPU provides. Part VI is about splitting a model across GPUs, and before we can compare the ways of splitting it (Chapter 18) or route tokens between experts (Chapter 19), we need to know what it costs to move data between GPUs.

That cost has a structure as clean as the roofline. Communication in parallel programs is almost always organised into a handful of collective operations, in which every GPU contributes a buffer and receives a result: sum the buffers, gather them, scatter them, or exchange them all-to-all. Each collective has a precise mathematical definition, a minimum number of bytes that any algorithm must move, and a family of algorithms that approach that minimum to different degrees. A simple two-parameter model, a fixed latency per message plus a time per byte, predicts their cost well enough to make engineering decisions. With it, we can say when tensor parallelism will be limited by latency rather than bandwidth, why the all-reduce inside an 8-GPU server costs microseconds while the same all-reduce across servers costs ten times more, and why the most important optimisation in distributed inference is not a faster collective but one that runs at the same time as useful work.

The material in this chapter comes from high-performance computing, where it was developed for scientific simulation decades before LLMs. We present it in the language of linear algebra, which makes the definitions short, and we evaluate everything on the hardware of the running examples: the NVLink-connected 8-GPU H100 server and the InfiniBand network between servers (§5.7).

Learning objectives
  1. Identify the communication patterns of inference: tensor-parallel all-reduce, pipeline point-to-point, expert all-to-all and KV transfer.
  2. Define broadcast, reduce, all-reduce, reduce-scatter, all-gather and all-to-all as operations on a block matrix of buffers.
  3. Use the α–β model to predict the time of a collective, and identify latency- and bandwidth-dominated regimes.
  4. Derive the ring all-reduce, prove that its bandwidth term is optimal, and compare it with tree, recursive halving–doubling and one-shot algorithms.
  5. Describe NVLink, NVSwitch, PCIe, InfiniBand and RoCE, rail-optimised topologies, hierarchical collectives and in-network reduction.
  6. Explain the roles of NCCL, NVSHMEM and custom kernels, and quantify the benefit of overlapping communication with computation.

17.1 Why GPUs must talk

Suppose we split Llama 3 70B across eight GPUs, each holding one eighth of every weight matrix. This is tensor parallelism, the subject of Chapter 18, and its essential fact for now is that after each attention sub-layer and each FFN sub-layer, every GPU holds a partial sum of the layer's output, and the partial sums must be added together, with the result made available to every GPU, before the next sub-layer can begin. That operation, an all-reduce, happens twice per layer, 160 times per forward pass for an 80-layer model. In decode with a batch of 64 sequences, each all-reduce sums a buffer of \(B\times d\times2=64\times8192\times2\) bytes, exactly 1 MiB, across eight GPUs. Whether that takes 5 µs or 50 µs decides whether communication is a rounding error or a third of the step.

Other ways of splitting a model create other patterns. Pipeline parallelism assigns consecutive layers to different GPUs, and the only communication is point-to-point: one GPU sends its activations to the next. Expert parallelism places different experts of a mixture-of-experts model on different GPUs, and each token's hidden state must be sent to the GPUs holding its chosen experts and the results sent back, an all-to-all exchange. Data parallelism replicates the whole model and needs no communication during inference at all, except for coordination. And disaggregated serving (Chapter 13) moves KV caches point to point between machines. Each pattern has its own volume and its own sensitivity to latency, and to compare them we first need precise definitions.

17.2 Collectives as linear algebra

Consider \(n_p\) GPUs, called ranks and numbered \(0,\dots,n_p-1\). Each rank holds a buffer of \(\nu\) bytes, which we think of as a vector, and it is convenient to split each buffer into \(n_p\) equal blocks. Arrange the blocks in an \(n_p\times n_p\) matrix \(A\), where \(A_{ij}\) is block \(j\) of rank \(i\)'s buffer, so that rank \(i\) holds row \(i\). The standard collectives are then simple operations on this matrix.

Definition — the collective operations

Broadcast from rank \(r\): every rank receives row \(r\). Reduce to rank \(r\): rank \(r\) receives the column sums \(\sum_iA_{ij}\) for all \(j\), i.e. the sum of all buffers. All-reduce: every rank receives the sum of all buffers. Reduce-scatter: rank \(j\) receives only block \(j\) of the sum, \(\sum_iA_{ij}\). All-gather: each rank starts with one block (rank \(i\) has \(A_{ii}\)) and every rank receives all of them. All-to-all: rank \(j\) receives column \(j\), the blocks \(A_{0j},\dots,A_{n_p-1,j}\); the block matrix is transposed.

Figure 17.1 shows four of the collectives on four ranks. Two relations among them organise everything that follows. First, an all-reduce is a reduce-scatter followed by an all-gather: after the reduce-scatter, rank \(j\) holds block \(j\) of the sum, and gathering those blocks gives every rank the whole sum. Second, all-gather and reduce-scatter are duals: running an all-gather's communication backwards, with sums in place of copies, is a reduce-scatter, so they have the same cost. All-to-all is different in kind. It moves every block to a different rank, with no reduction, and its volume is fixed by the data: each rank sends \((n_p-1)/n_p\) of its buffer and receives the same amount, whatever the algorithm.

For the mathematician — SPMD programs and ranks

Distributed GPU programs are almost always written in the single program, multiple data style: the same program runs on every GPU, parameterised by its rank \(i\in\{0,\dots,n_p-1\}\), and each instance works on its own part of the data. A collective is a call that all ranks make together; it returns only when the rank's part of the result is ready. Mathematically, the program is a function applied to a tuple of local states, and a collective is a fixed map from the tuple of buffers \((A_{0\cdot},\dots,A_{n_p-1,\cdot})\) to a new tuple, such as \(A\mapsto(\mathbf 1^\top A)\otimes\mathbf 1\) for all-reduce, where \(\mathbf 1^\top A\) is the vector of column sums. Correctness depends on every rank calling the same collectives in the same order, which is one reason tensor-parallel workers must run in lockstep (§12.8).

17.3 The α–β cost model

To compare algorithms for these collectives we need a model of what sending a message costs. The standard one, used throughout high-performance computing, has two parameters. Sending a message of \(\nu\) bytes from one rank to another takes

\[ t(\nu)\;=\;\alpha+\frac{\nu}{\beta_{\text{link}}}, \]

where \(\alpha\) is a fixed latency per message, covering software overhead, synchronisation and the time for the first byte to arrive, and \(\beta_{\text{link}}\) is the bandwidth of the link in one direction. We also assume that a rank can send one message and receive one message at the same time, on different links or the two directions of one link, at full bandwidth each.

The two terms define two regimes, divided by the message size \(\nu^*=\alpha\beta_{\text{link}}\) at which they are equal. Messages much smaller than \(\nu^*\) are latency-bound: their cost is essentially \(\alpha\), and an algorithm should minimise the number of sequential messages. Messages much larger are bandwidth-bound: their cost is the bytes over the bandwidth, and an algorithm should minimise the bytes each rank sends and receives. This is the communication counterpart of the roofline, with the latency \(\alpha\) playing the role of fixed overhead and \(\beta_{\text{link}}\) the role of memory bandwidth. For NVLink on an H100, with \(\beta_{\text{link}}=450\) GB/s per direction and a per-step latency of order 1 µs, \(\nu^*\approx450\) KB. For a 400 Gb/s InfiniBand link, with \(\beta_{\text{link}}=50\) GB/s and a latency of a few microseconds, \(\nu^*\approx150\) KB. Inference messages are often near or below these sizes: the 1 MiB all-reduce of §17.1 is only twice \(\nu^*\) on NVLink, so neither term can be ignored.

The model is deliberately simple. It ignores contention between messages sharing a link, the finite number of messages a GPU can have in flight, and the fact that α itself has components (kernel launch, synchronisation, network hops) that algorithms can sometimes avoid. But it captures the decisive trade-off between the number of steps and the bytes per step, and with it we can analyse the most important collective of all.

17.4 All-reduce algorithms

The naive all-reduce sends every buffer to one rank, which sums them and broadcasts the result. That rank receives \((n_p-1)\nu\) bytes and sends as many, so its links are a bottleneck that grows with \(n_p\), while every other link is mostly idle. Good algorithms spread the work so that every link is busy. The classic one, the ring all-reduce, arranges the ranks in a cycle \(0\to1\to\dots\to n_p-1\to0\) and implements the two phases of §17.2 by passing blocks around the ring.

In the reduce-scatter phase, at step \(s=1,\dots,n_p-1\), rank \(i\) sends one block to rank \(i+1\), which adds it to its own copy of that block. The schedule is arranged so that the block arriving at each rank is always a partial sum that has not yet included that rank. After \(n_p-1\) steps, each block has travelled around the ring collecting every rank's contribution, and rank \(i\) holds the complete sum of one block. In the all-gather phase, the completed blocks travel around the ring again for \(n_p-1\) steps, this time copied rather than added, until every rank holds all of them. Each step sends one block of \(\nu/n_p\) bytes per rank, and all ranks send simultaneously, so every link carries traffic in every step.

Figure 17.2 traces the reduce-scatter on four ranks. With \(2(n_p-1)\) steps of \(\nu/n_p\) bytes each, the α–β model gives the ring's time as

\[ t_{\text{ring}}\;=\;2(n_p-1)\,\alpha\;+\;\frac{2(n_p-1)}{n_p}\cdot\frac{\nu}{\beta_{\text{link}}}. \]

The bandwidth term is remarkable: as \(n_p\) grows it approaches \(2\nu/\beta_{\text{link}}\), independent of the number of ranks. Adding GPUs to a ring does not increase the time to all-reduce a buffer of fixed size, apart from latency. And this bandwidth term cannot be improved.

Proposition 16.1 — A lower bound for all-reduce

Suppose additions are performed only by the ranks, data is sent uncompressed, each rank's contribution to each block is arbitrary, and each block of the sum is completed at one rank. Then the ranks together must send at least \(2(n_p-1)\nu\) bytes, so some rank sends at least \(2(n_p-1)\nu/n_p\) bytes, and any all-reduce takes at least \(2(n_p-1)\nu/(n_p\beta_{\text{link}})\). The ring achieves this bound.

Proof. Let rank \(i\) complete \(k_i\) of the \(n_p\) blocks, so \(\sum_ik_i=n_p\). Reduction traffic: every block that rank \(i\) does not complete depends on rank \(i\)'s arbitrary contribution to it, so information about that contribution, at least \(\nu/n_p\) bytes per block, must leave rank \(i\): at least \((n_p-k_i)\nu/n_p\) bytes. Summed over ranks this is \((n_p^2-n_p)\nu/n_p=(n_p-1)\nu\). Distribution traffic: every rank must end with all \(n_p\) completed blocks, so rank \(i\) must receive the \(n_p-k_i\) blocks completed elsewhere, again \((n_p-1)\nu\) bytes in total, all of which some rank must send. These are different data (contributions before summation versus completed sums), so total sends are at least \(2(n_p-1)\nu\), and the busiest of the \(n_p\) ranks sends at least the average, \(2(n_p-1)\nu/n_p\), which takes at least \(2(n_p-1)\nu/(n_p\beta_{\text{link}})\). \(\square\)

The rigorous treatment, for general topologies and including the latency term, is due to Patarasuk and Yuan (2009)[2] and Chan et al. (2007). The bound's first assumption matters: if the network itself can add, the reduction traffic can be combined in transit (Drill 17.2).

The ring's weakness is its latency term, \(2(n_p-1)\alpha\), which grows linearly with the number of ranks. For small messages on many ranks, it dominates. Other algorithms trade bandwidth optimality for fewer steps. Recursive halving and doubling (Rabenseifner's algorithm; see Thakur, Rabenseifner and Gropp, 2005[1]) pairs ranks at distance \(n_p/2\), then \(n_p/4\), and so on, exchanging and summing halves of the buffer each time, then reverses the pattern for the all-gather. It achieves the same bandwidth term in only \(2\log_2n_p\) steps, but needs a topology in which those pairs can communicate at full speed. Tree algorithms, such as the double binary trees NCCL introduced in 2019, also have logarithmic latency and are preferred at large scale for small and medium messages. At the other extreme, on a fully connected switch such as NVSwitch, a one-shot all-reduce lets every rank read all other ranks' buffers directly and sum them locally: one step of latency, but \((n_p-1)\nu\) bytes received per rank, \(n_p/2\) times the minimum. A two-shot all-reduce performs the reduce-scatter and the all-gather each as one direct exchange, reaching the optimal bandwidth term in two steps.

Figure 17.3 evaluates these algorithms for eight GPUs on NVSwitch. Below about 100 KB, every algorithm is latency-bound, and the one-shot algorithm, with a single step, is fastest by an order of magnitude over the ring. Above about 10 MB, every algorithm is bandwidth-bound, and the one-shot algorithm's extra bytes make it four times slower than the others. In between, at the 1 MiB of our decode example, the two-shot algorithm is about three times faster than the ring. This is exactly why inference engines such as vLLM and TensorRT-LLM ship their own "custom all-reduce" kernels for small messages within a node, using one-shot or two-shot algorithms that read peer GPUs' memory directly over NVLink, and fall back to NCCL's ring and tree algorithms for large messages and across nodes. The general rule is the one the α–β model predicts: choose the algorithm by message size and topology.

Worked example — the communication cost of tensor-parallel decode

Llama 3 70B on eight H100s with tensor parallelism, batch 64, 2k context. Per step: 160 all-reduces of 1 MiB each. Ring: 14 latency steps of 1 µs plus \(1.75\times1.05\) MB at 450 GB/s (4.1 µs), about 18 µs each, 2.9 ms per step. Two-shot: \(2+4.1\approx6\) µs each, about 1.0 ms per step. Computation: each GPU reads \(141/8=17.6\) GB of weights and \(64\times2048\times320\,\text{KiB}/8\approx5.4\) GB of cache, about 6.9 ms at 3.35 TB/s. Communication is therefore 30% of the step with the ring algorithm and 13% with two-shot, if it is not overlapped. The same calculation with a 512-token prefill chunk gives 8 MiB buffers, for which both algorithms take about 35–47 µs, and the step is compute-bound for much longer, so communication is a smaller fraction. Decode is where communication latency matters most.

The example explains a pattern that Chapter 18 will develop. For tensor-parallel decode, all-reduce time is dominated by latency rather than bandwidth, so reducing the number of collectives, or their steps, matters more than raw link speed; and the fraction of time spent communicating rises as the per-GPU computation shrinks, which is why tensor parallelism has diminishing returns. Before that, we need to know what the links in the model actually are, because \(\alpha\) and \(\beta_{\text{link}}\) differ by an order of magnitude between them.

17.5 Interconnects and topologies

GPU systems have two tiers of interconnect, usually called scale-up and scale-out. The scale-up tier is NVLink: a point-to-point link between GPUs, designed for memory-like traffic, with high bandwidth and low latency. On Hopper, each GPU has 18 NVLink links totalling 900 GB/s bidirectional (450 GB/s each way); in an 8-GPU HGX or DGX server, four NVSwitch chips connect every GPU to every other at that full rate (§5.7). Blackwell doubles the per-GPU NVLink bandwidth to 1.8 TB/s, and its NVL72 rack extends one switched NVLink domain to 72 GPUs, which changes what can be done with tensor and expert parallelism without leaving NVLink (Chapters 18 and 19). The scale-out tier is the data-centre network: InfiniBand (NDR at 400 Gb/s, XDR at 800 Gb/s per port) or Ethernet with RDMA (RoCE), typically one network adapter per GPU, so about 50 GB/s per GPU on H100 systems, nine times less than NVLink. Below both tiers, PCIe connects GPUs to their host CPUs at about 64 GB/s per direction (Gen5).

Figure 17.4 shows how the two tiers are wired in a typical large cluster. Each server's eight network adapters connect to eight different leaf switches, one per GPU position, called rails, and a spine layer connects the rails. Traffic between GPU \(k\) of one server and GPU \(k\) of another crosses a single leaf switch, with low latency and no contention with the other seven rails. The design anticipates hierarchical collectives, which match the algorithm to the topology. A hierarchical all-reduce across \(n_s\) servers of eight GPUs proceeds in three stages: a reduce-scatter inside each server over NVLink, leaving each GPU with one eighth of its server's sum; an all-reduce of those eighths across servers, one per rail, over the network; and an all-gather inside each server over NVLink. Each GPU sends only \(\nu/8\) bytes' worth of data through the slow network, and all eight adapters work in parallel.

Figure 17.5 compares the hierarchical algorithm with a single ring over all 32 GPUs that ignores the topology, in which every step waits for the slowest hop. The hierarchical algorithm is about five times faster for large buffers and also has far less latency, because only six of its steps cross the network. Real libraries are more sophisticated than either model, running several rings or trees concurrently over all the adapters, but the lesson is general: across servers, the network is the bottleneck, and the algorithm should push as much of the work as possible onto NVLink. Two hardware features push further. In-network reduction, InfiniBand's SHARP and its NVLink counterpart NVLS on Hopper's NVSwitch, performs the summation inside the switches: each GPU sends its buffer once and receives the result once, which halves the bytes each GPU must move compared with the ring's bound, because the bound of Proposition 16.1 assumed that only GPUs could add. And for collectives that do not reduce, notably the all-to-all of expert parallelism, there is no such shortcut: every byte must cross the network, which is why large expert-parallel deployments care so much about network bandwidth and topology (Chapter 19).

17.6 Communication software

Three layers of software sit between an inference engine and the links. The workhorse is NCCL (the NVIDIA Collective Communications Library)[3], which implements all the collectives of §17.2 for NVIDIA GPUs. NCCL discovers the topology at start-up (NVLink, NVSwitch, PCIe, network adapters), builds rings and trees that use it well, splits each collective across several channels that run in parallel on different SMs and links, and selects an algorithm and protocol by message size. Its collectives are GPU kernels launched on a CUDA stream, so they order correctly with surrounding computation and can be captured in CUDA graphs (§7.8). Its performance is usually reported as bus bandwidth, the algorithm bandwidth \(\nu/t\) multiplied by \(2(n_p-1)/n_p\) for all-reduce, which normalises out the algorithm-independent factor so that the result can be compared directly with the link speed.

NCCL's collectives are two-sided and launched from the host: every rank calls the same collective, and the library coordinates the transfer. For irregular, fine-grained or latency-critical communication this model is restrictive. NVSHMEM provides the alternative: a partitioned global address space in which each GPU can read or write another GPU's memory directly from inside a running kernel, with one-sided put and get operations and lightweight synchronisation. Within a node, these operations go over NVLink as ordinary memory instructions; across nodes, they use GPU-initiated RDMA, in which the GPU itself posts requests to the network adapter without involving the CPU. One-sided, device-initiated communication is what makes it possible to fuse communication into compute kernels, to send each token to its expert as soon as it is routed, or to implement the one-shot all-reduce of §17.4 as a few memory reads.

The third layer is custom kernels written for specific patterns in inference. The custom all-reduce kernels of vLLM and TensorRT-LLM exploit NVSwitch's full connectivity for small messages; DeepSeek's DeepEP library[4] (2025) implements the dispatch and combine all-to-all of expert parallelism, with a high-throughput mode for prefill and a low-latency mode for decode that uses device-initiated RDMA and avoids occupying SMs while waiting. These kernels exist because general-purpose libraries optimise for the bandwidth-bound regime of training, while inference lives largely in the latency-bound regime of Figure 17.3.

For the mathematician — two-sided and one-sided communication

In two-sided communication, a transfer is a pair of matching events: rank \(i\) executes send(x, to j) and rank \(j\) executes receive(into y, from i), and the data moves only when both have happened, a rendezvous. Collectives are coordinated sets of such pairs. In one-sided communication, rank \(i\) alone executes put(x, into y on j); rank \(j\) does not participate and learns that the data has arrived only through a separate synchronisation, such as a flag that rank \(i\) sets after the put or a barrier. One-sided communication separates data movement from synchronisation, which lets many small transfers proceed without a rendezvous each, at the price of the programmer reasoning explicitly about memory ordering: when may rank \(j\) safely read \(y\)?

17.7 Hiding communication behind computation

The α–β model prices communication as if nothing else were happening. But a GPU has separate engines for computation and data movement: links can carry bytes while the SMs multiply matrices. If the communication of one piece of work can proceed while the GPU computes another, independent piece, its cost disappears from the critical path. With computation time \(t_{\text{comp}}\) and communication time \(t_{\text{comm}}\), serial execution takes \(t_{\text{comp}}+t_{\text{comm}}\), while perfect overlap takes \(\max(t_{\text{comp}},t_{\text{comm}})\): the same structure as overlapped scheduling in §12.2 and layer-wise KV transfer in §13.4.

Figure 17.6 shows the obstacle and the most common remedy. In tensor-parallel inference, each all-reduce depends on the GEMM just before it, and the next GEMM depends on the all-reduce, so within one sequence of operations there is nothing to overlap. Independent work must be created. The simplest way is to split the batch into two micro-batches and interleave them, so that one micro-batch's communication runs during the other's computation; DeepSeek's inference system uses this "two-batch overlap" to hide expert-parallel all-to-all behind attention and expert computation[5], and SGLang and vLLM adopted it. A finer-grained method decomposes a single GEMM and its collective into pieces, starting to communicate the first tiles of the output while later tiles are computed; this "collective matmul" or asynchronous tensor parallelism[6] needs no change in batching. A third method fuses communication into the compute kernel itself with one-sided writes, so that each tile of output is sent the moment it is ready.

Overlap has costs that the max-formula hides. Computation and communication compete for resources: NCCL kernels occupy SMs that would otherwise compute, and both use memory bandwidth. Splitting a batch halves the size of each GEMM, which for memory-bound decode means reading the weights twice unless the halves are arranged cleverly, and shrinks messages towards the latency-bound regime. And the dependence structure must allow it: overlap requires that the two pieces really are independent. When these costs are small, overlap is the single most effective optimisation in distributed inference, because it attacks the communication term without making the network any faster.

Drill 17.1 — The crossover message size

Using the α–β model with \(n_p=8\), find the buffer size at which a one-shot all-reduce and a ring all-reduce take equal time, for \(\alpha=1\) µs and \(\beta_{\text{link}}=450\) GB/s. Which should an engine use for the 1 MiB buffers of 70B decode at batch 64, and for a 512-token prefill chunk?

Solution. One-shot: \(\alpha+7\nu/\beta\). Ring: \(14\alpha+1.75\nu/\beta\). Equal when \(13\alpha=5.25\nu/\beta\), i.e. \(\nu=13\times10^{-6}\times450\times10^{9}/5.25\approx1.1\) MB. At 1 MiB the two are almost equal (about 17–18 µs), and the two-shot algorithm, at about 6 µs, beats both. For a 512-token chunk, \(\nu=512\times8192\times2=8\) MiB, far above the crossover, so a bandwidth-optimal algorithm (ring or two-shot, about 35–47 µs) is right and one-shot (about 130 µs) is wrong. An engine should switch algorithms by message size, which is what custom all-reduce implementations do.

Drill 17.2 — In-network reduction

With SHARP or NVLS, a switch adds the buffers in transit. In the α–β model, each GPU sends its \(\nu\) bytes once and receives the \(\nu\)-byte result once, in a small constant number of steps. Compare its bandwidth term with the ring's for \(n_p=8\) and for \(n_p\to\infty\), and explain why this does not contradict Proposition 16.1.

Solution. In-network reduction sends and receives \(\nu\) bytes per GPU; with full-duplex links the time is about \(\nu/\beta_{\text{link}}\). The ring's bandwidth term is \(2(n_p-1)\nu/(n_p\beta_{\text{link}})=1.75\nu/\beta_{\text{link}}\) at \(n_p=8\), approaching \(2\nu/\beta_{\text{link}}\): in-network reduction is about 1.75–2× faster. The proposition assumed that only the ranks themselves can add; its argument counted the bytes each rank must send for blocks it cannot sum itself and then receive for blocks completed elsewhere. When the network adds, a rank's data is combined in the switch, and the rank need only send its input and receive the output once each.

Drill 17.3 — The cost of an expert-parallel all-to-all

A mixture-of-experts layer with hidden size \(d=7168\) (DeepSeek-V3) runs expert parallelism over 32 GPUs in four servers. In decode, each GPU holds 128 tokens, each routed to 8 experts, spread uniformly over all GPUs. Estimate the bytes each GPU sends in the dispatch all-to-all with BF16 activations, and the time over a 50 GB/s network per GPU, ignoring latency. What changes with FP8 dispatch, and why is in-network reduction no help?

Solution. Each GPU sends \(128\times8=1024\) token copies of \(7168\times2\) bytes, about 14.7 MB, of which the fraction destined for other servers is \(24/32\), about 11 MB (the rest crosses NVLink). At 50 GB/s that is about 0.22 ms for dispatch, and the combine costs as much again, so about 0.44 ms per MoE layer, which over 58 MoE layers would be about 26 ms per step, far too slow without remedies. Dispatching in FP8 halves the bytes. Deduplicating tokens routed to several experts on the same server, sending each token once per destination server and fanning out over NVLink, cuts inter-server traffic further, which is what DeepSeek's node-limited routing and DeepEP's hierarchical kernels do. In-network reduction cannot help, because all-to-all moves distinct data to distinct places and has nothing to add. The remaining cost must be hidden by overlap, the subject of Chapter 19.

Worked example — MoE all-to-all for DeepSeek-V3 decode

Setup. DeepSeek-V3 is served with expert parallelism across many nodes. Each GPU holds 256 tokens in a decode step; each token is routed to 8 experts with hidden size \(d=7168\). Dispatch sends activations in FP8 (1 byte), and combine returns them in BF16 (2 bytes). We take the pessimistic case in which every routed copy leaves the node, over InfiniBand at \(\beta=50\) GB/s per GPU and \(\alpha=3\) µs.

Bytes per MoE layer. Dispatch: \(256\times8\times7168\times1\approx14.7\) MB. Combine: twice that, 29.4 MB. At 50 GB/s these take 0.29 ms and 0.59 ms; the latency terms (a few message rounds of 3 µs) are negligible at this size. One MoE layer therefore spends about 0.88 ms communicating.

Per step. With 58 MoE layers the total is about 51 ms per decode step, more than the time the step spends computing. Without help, decode would be communication-bound by a wide margin.

What is done about it. Three measures attack the 51 ms. Node-limited routing (each token\'s experts live on at most 4 nodes) and deduplication send one copy per destination node, not per expert, then forward over NVLink, cutting inter-node bytes several-fold. FP8 dispatch already halves them. Finally, splitting the batch into two micro-batches lets one compute while the other communicates (§17.7), so that what remains is hidden rather than added. The example shows why MoE serving systems are designed around the network first.

17.8 A cost model for distributed inference

We can now assemble the pieces into a template that Chapters 18 and 19 will fill in. For any way of splitting a model across \(n_p\) GPUs, the time of one step is approximately

\[ t_{\text{step}}\;\approx\;\max\!\Big(\frac{\text{bytes per GPU}}{\beta},\;\frac{\text{FLOPs per GPU}}{\pi}\Big)\;+\;(1-o)\sum_{\text{collectives}}\big(k\,\alpha+c\,\nu/\beta_{\text{link}}\big), \]

where the first term is the per-GPU roofline of Chapter 6, each collective contributes \(k\) latency steps and \(c\) "byte-units" of transfer according to its algorithm, and \(o\in[0,1]\) is the fraction of communication hidden by overlap. Every parallelism strategy is a different trade between these terms. Splitting more ways reduces the per-GPU bytes and FLOPs in the first term, while the second term stays the same or grows: the number of collectives per step is fixed by the model's structure, their latency steps grow with \(n_p\) for some algorithms, and their messages shrink towards the latency-bound regime. The point at which the second term stops being negligible is the point at which further splitting stops paying, and finding it is the subject of the next chapter.

The template also shows why topology is so important. The constants \(\alpha\) and \(\beta_{\text{link}}\) differ by roughly an order of magnitude between NVLink and the network, so a strategy that keeps its frequent, latency-sensitive collectives inside an NVLink domain and sends only infrequent or large transfers across the network can scale where a topology-oblivious one cannot. This is the reasoning behind the most common layout of 2023–25: tensor parallelism within a server, and pipeline, data or expert parallelism across servers. Rack-scale NVLink domains such as NVL72 relax the constraint by making the fast domain nine times larger, which is one of the main reasons they were built.

Looking ahead

We now have a language for communication and a way to price it. Chapter 18 uses them to analyse the strategies for splitting a dense model: tensor parallelism, which splits each matrix and needs two all-reduces per layer; pipeline parallelism, which splits the layer stack and needs only point-to-point transfers but creates bubbles; sequence and context parallelism, which split long prompts; and data parallelism, which splits nothing. For each, we will compute the per-GPU roofline term and the communication term, find where each strategy stops scaling, and derive the configurations used to serve models like Llama 3 70B and 405B in practice.

Chapter summary

  • Inference communication patterns: tensor-parallel all-reduce (two per layer, latency-sensitive), pipeline point-to-point, expert-parallel all-to-all, and KV transfer. Data parallelism needs none.
  • Collectives on an \(n_p\times n_p\) block matrix of buffers: broadcast, reduce, all-reduce (everyone gets the sum), reduce-scatter (rank \(j\) gets block \(j\) of the sum), all-gather, all-to-all (transpose). All-reduce = reduce-scatter + all-gather; the two halves are duals.
  • α–β model: \(t=\alpha+\nu/\beta_{\text{link}}\); latency-bound below \(\nu^*=\alpha\beta_{\text{link}}\) (≈ 450 KB on NVLink), bandwidth-bound above. Inference messages are often near \(\nu^*\).
  • Ring all-reduce: \(2(n_p-1)\alpha+2(n_p-1)\nu/(n_p\beta_{\text{link}})\); its bandwidth term is optimal (each rank must send and receive \((n_p-1)\nu/n_p\)). Trees and halving–doubling cut latency to \(O(\log n_p)\); one-shot uses one step but \(n_p/2\) times the bytes; two-shot gets both on a full switch.
  • Interconnects: NVLink/NVSwitch (450 GB/s per direction on H100; 900 on Blackwell; NVL72 racks), InfiniBand or RoCE at 400–800 Gb/s per GPU, PCIe Gen5 ≈ 64 GB/s. Rail-optimised networks and hierarchical collectives keep most traffic on NVLink; in-network reduction (SHARP, NVLS) halves all-reduce bytes.
  • Software: NCCL (topology-aware rings and trees, channels, bus bandwidth), NVSHMEM (one-sided, device-initiated puts and gets), custom kernels (one-shot/two-shot all-reduce, DeepEP all-to-all).
  • Overlap turns \(t_{\text{comp}}+t_{\text{comm}}\) into about \(\max(t_{\text{comp}},t_{\text{comm}})\) when independent work exists: two-batch overlap, collective matmul, fused communication.
  • Template: step time ≈ per-GPU roofline + un-hidden collective time; splitting more shrinks the first term while the second stays or grows, which bounds useful parallelism.

Warm-up Define all-reduce, reduce-scatter, all-gather and all-to-all, and say where each appears in LLM inference.

With \(n_p\) ranks each holding a buffer split into \(n_p\) blocks: all-reduce gives every rank the elementwise sum of all buffers (tensor parallelism, after attention and FFN sub-layers); reduce-scatter gives rank \(j\) only block \(j\) of the sum (sequence-parallel variants of TP, and the first half of an all-reduce); all-gather gives every rank all ranks' blocks (gathering sharded activations or logits, the second half of an all-reduce); all-to-all sends block \(j\) of rank \(i\) to rank \(j\), transposing the block matrix (expert-parallel dispatch and combine, and context parallelism variants). Pipeline parallelism uses point-to-point send/receive, and disaggregated serving uses point-to-point KV transfers.

Warm-up What is the α–β model, and what are typical values on NVLink and InfiniBand?

It prices a message of \(\nu\) bytes at \(\alpha+\nu/\beta_{\text{link}}\): \(\alpha\) is a fixed per-message latency (software, synchronisation, first-byte delay) and \(\beta_{\text{link}}\) the link bandwidth per direction. It separates latency-bound messages (below \(\nu^*=\alpha\beta_{\text{link}}\)), where the number of steps matters, from bandwidth-bound ones, where bytes per rank matter. Typical: NVLink on H100, \(\beta_{\text{link}}=450\) GB/s per direction, \(\alpha\) of order a microsecond per step, \(\nu^*\approx450\) KB; 400 Gb/s InfiniBand, 50 GB/s, \(\alpha\) a few microseconds, \(\nu^*\) about 150 KB. Inference messages (for example 1 MiB TP all-reduces in decode) sit near these thresholds, so both terms matter.

Core Explain the ring all-reduce and derive its cost.

Arrange ranks in a cycle and split each buffer into \(n_p\) blocks. Reduce-scatter phase: in each of \(n_p-1\) steps, each rank sends one block to its successor, which adds its own contribution; the schedule ensures each travelling partial sum has not yet visited the receiver, so after \(n_p-1\) steps each rank holds one fully summed block. All-gather phase: \(n_p-1\) more steps circulate the completed blocks until all ranks have all of them. Each step moves \(\nu/n_p\) bytes per rank, all ranks in parallel, so \(t=2(n_p-1)\alpha+2(n_p-1)\nu/(n_p\beta_{\text{link}})\). The bandwidth term approaches \(2\nu/\beta_{\text{link}}\) and is optimal; the latency term grows linearly in \(n_p\), which motivates trees or halving–doubling at scale and one-/two-shot algorithms for small messages on switches.

Core Prove that no all-reduce can beat the ring’s bandwidth term (without in-network computation).

Assume only ranks add, data is uncompressed, contributions are arbitrary, and each block's sum is completed at one rank; let rank \(i\) complete \(k_i\) blocks, \(\sum k_i=n_p\). Reduction: for each block rank \(i\) does not complete, its contribution must leave rank \(i\): at least \((n_p-k_i)\nu/n_p\) bytes; summed, \((n_p-1)\nu\). Distribution: rank \(i\) must receive the \(n_p-k_i\) completed blocks it lacks; summed, another \((n_p-1)\nu\) bytes sent by someone. These are distinct data, so total sends are at least \(2(n_p-1)\nu\), and the busiest rank sends at least \(2(n_p-1)\nu/n_p\), taking at least \(2(n_p-1)\nu/(n_p\beta_{\text{link}})\), exactly the ring's bandwidth term. With switch-based reduction (SHARP, NVLS), the first assumption fails, and each GPU only needs to send and receive \(\nu\) once.

Core Compare ring, tree/halving–doubling, one-shot and two-shot all-reduce. When would you use each?

Ring: \(2(n_p-1)\) steps, optimal bytes; best for large messages on ring-like topologies, poor latency at scale. Recursive halving–doubling and trees: \(O(\log n_p)\) steps with (near) optimal bytes; best for small-to-medium messages on many ranks (NCCL uses double binary trees at scale). One-shot (each rank reads all peers' buffers and sums locally): 1 step but \((n_p-1)\nu\) bytes received, \(n_p/2\) times the minimum; best for tiny messages on a fully connected switch (NVSwitch). Two-shot (direct reduce-scatter then direct all-gather): 2 steps with optimal bytes on a full switch; best for small and medium messages within a node. With \(\alpha=1\) µs and 450 GB/s on 8 GPUs, a 1 MiB all-reduce takes about 18 µs ring, 17 µs one-shot, 6 µs two-shot; at 8 MiB, about 47, 131 and 35 µs.

Core Explain hierarchical all-reduce and why topology-aware algorithms matter across servers.

Inside a server, NVLink gives about 450 GB/s per GPU per direction; between servers, each GPU has about 50 GB/s of network. A flat ring over all GPUs is limited at every step by the slowest (network) hop. A hierarchical all-reduce first reduce-scatters within each server over NVLink (each GPU holds 1/8 of its server's partial sum), then all-reduces those eighths across servers, one ring or tree per rail, so all eight network adapters work in parallel on 1/8 of the data each, and finally all-gathers within each server over NVLink. Network bytes per GPU fall eightfold and network latency steps fall too; in our model it was about five times faster than a flat ring for 4 servers. Rail-optimised networks are designed for exactly this pattern.

Core What do NCCL, NVSHMEM and custom kernels each provide?

NCCL: the standard GPU collective library; topology discovery, rings and trees across NVLink, PCIe and network, multiple channels on parallel SMs and links, algorithm and protocol selection by size, stream-ordered kernels compatible with CUDA graphs; optimised especially for bandwidth-bound collectives. NVSHMEM: a partitioned global address space with one-sided put/get and signalling callable from inside kernels, using NVLink loads/stores within a node and GPU-initiated RDMA across nodes; enables fine-grained and fused communication without host involvement. Custom kernels: specialised implementations for inference patterns, such as one-shot/two-shot all-reduce over NVSwitch for small TP messages (vLLM, TensorRT-LLM) and DeepEP for MoE dispatch/combine with low-latency decode modes. Inference uses all three because its messages are smaller and more latency-critical than training's.

Deep-dive Estimate the communication overhead of tensor-parallel decode for Llama 3 70B on 8 H100s and propose ways to reduce it.

Per step: 2 all-reduces per layer × 80 layers = 160, each of \(B\cdot d\cdot2\) bytes = 1 MiB at batch 64. Ring: \(14\alpha+1.75\nu/\beta\approx14+4.1=18\) µs each, about 2.9 ms per step. Per-GPU compute (memory-bound): weights 17.6 GB plus cache 5.4 GB at 3.35 TB/s ≈ 6.9 ms. So communication is about 30% of the step if serial. Remedies: use a latency-optimised two-shot or one-shot kernel (≈ 6 µs, total ≈ 1 ms); fuse the all-reduce with the following residual add and normalisation to save kernel launches; overlap communication of one micro-batch with computation of another; use in-switch reduction (NVLS) to halve bytes; reduce TP degree (TP = 4 with 2 replicas, if latency targets allow, halves the number of ranks per collective and doubles per-GPU work); or quantise activations for communication. Re-measure: the right TP degree is where marginal latency gain no longer justifies the communication.

Deep-dive Why are inference collectives often latency-bound while training collectives are bandwidth-bound?

Training all-reduces gradients, buffers of hundreds of megabytes to gigabytes (whole parameter shards), so \(\nu\gg\nu^*\) and the bandwidth term dominates; libraries optimise bus bandwidth. Inference tensor parallelism all-reduces activations, \(B\times d\times2\) bytes per sub-layer: with \(d=8192\) and decode batches of 1–256, 16 KiB to 4 MiB, around \(\nu^*\approx450\) KB on NVLink; and there are 2 per layer per step, in the critical path. Expert-parallel decode sends a few tokens' hidden states to each expert GPU, again small. Hence inference favours algorithms with few steps (one-/two-shot, trees), kernel fusion, CUDA-graph capture of communication, device-initiated transfers and overlap, while training favours rings, large chunks and bandwidth.

Deep-dive Explain in-network reduction (SHARP, NVLS) and quantify its benefit.

Switches with arithmetic units perform the summation as data passes through: each GPU sends its buffer once to the switch, the switch aggregates contributions from all GPUs, and sends the result back (or multicasts it). Per GPU, about \(\nu\) bytes are sent and \(\nu\) received, overlapping on full-duplex links, so time is about \(\nu/\beta_{\text{link}}\) plus a small constant number of latencies, versus the ring's \(2(n_p-1)\nu/(n_p\beta_{\text{link}})\), a gain approaching 2× for large \(n_p\), and latency independent of \(n_p\). It does not contradict the lower bound, which assumed only ranks add. InfiniBand SHARP does this in network switches across servers; NVLink SHARP (NVLS) does it in Hopper's NVSwitch within a node. It also frees GPU SMs from reduction work. It cannot help all-to-all, which has no reduction.

Deep-dive How does two-batch overlap work in MoE inference, and what does it cost?

Expert-parallel layers need an all-to-all dispatch (tokens to expert GPUs) and combine (results back) around the expert computation, with dependencies that serialise them within one batch. Two-batch overlap splits the batch into two micro-batches A and B and staggers them: while A's tokens are being dispatched or combined over the network, the GPU computes attention or experts for B, and vice versa, so communication is largely hidden if per-micro-batch computation and communication times are comparable. DeepSeek reported using it in prefill and decode for V3; SGLang and vLLM implement it. Costs: each micro-batch is half size, so expert GEMMs are smaller and less efficient and weights may be read twice per step; communication kernels compete with compute for SMs and memory bandwidth (DeepEP's low-latency mode avoids occupying SMs); and the schedule is more complex to implement and capture in CUDA graphs.

Design You are deploying a 400B dense model on two 8×H100 servers. How do you lay out parallelism given the interconnects?

Weights in BF16 are about 800 GB, in FP8 about 400 GB, so one server (640 GB) cannot hold BF16 weights plus cache; FP8 might fit on one server with little cache. With two servers: keep the frequent, latency-sensitive collectives on NVLink. Tensor parallelism of degree 8 within each server, and pipeline parallelism of degree 2 across servers (one point-to-point transfer of \(B\times d\) activations per micro-batch per step crossing InfiniBand), rather than TP = 16 across servers, which would put 2 all-reduces per layer on the 50 GB/s network with its higher latency. Use multiple micro-batches to fill the pipeline (Chapter 18), FP8 weights and cache to free memory, latency-optimised all-reduce kernels within servers, and overlap. Alternatively, if FP8 weights fit in one server, two independent TP = 8 replicas (data parallelism) avoid inter-server communication entirely and usually give higher throughput.

Design A team proposes tensor parallelism of 16 across two servers to cut decode latency for a 70B model. Evaluate.

Splitting 16 ways halves per-GPU bytes relative to TP = 8 (about 3.5 ms instead of 6.9 ms of memory time at batch 64), but every one of the 160 all-reduces per step now spans the network. Even hierarchically, each includes inter-server steps at a few microseconds of latency and 50 GB/s, so each all-reduce costs tens of microseconds, adding several milliseconds per step, which can exceed the compute saved; tail latency also worsens with network jitter. Better options: TP = 8 within a server with a latency-optimised all-reduce and overlap; FP8 weights to halve bytes; speculative decoding (Chapter 20) to cut per-token latency; or, if the hardware allows, a larger NVLink domain (NVL72) where TP = 16 stays on NVLink. Core What is the difference between two-sided and one-sided communication, and why does it matter for MoE and fused kernels?

Two-sided communication pairs a send on one rank with a matching receive on another (a rendezvous); collectives are coordinated sets of such pairs, launched by all ranks together. One-sided communication lets one rank write (put) or read (get) another's memory without the other's participation, with separate synchronisation (flags, fences, barriers) to tell the target when data is ready. One-sided, device-initiated communication (NVSHMEM, GPU-initiated RDMA) lets a kernel send each token to its expert as soon as routing is known, overlap fine-grained transfers with computation in the same kernel, and avoid host round-trips, which reduces latency for the many small, irregular messages of MoE decode. The cost is explicit reasoning about memory ordering and synchronisation.

Core Write the step-time template for distributed inference and explain what limits useful parallelism.

\[t_{\text{step}}\approx\max\Big(\frac{\text{bytes/GPU}}{\beta},\frac{\text{FLOPs/GPU}}{\pi}\Big)+(1-o)\!\sum_{\text{coll.}}\!\big(k\alpha+c\,\nu/\beta_{\text{link}}\big),\]with \(k\) latency steps and \(c\) byte-units per collective depending on the algorithm, and \(o\) the overlapped fraction. Splitting the model over more GPUs shrinks the first term roughly as \(1/n_p\), but the number of collectives per step is fixed by the architecture (for TP, \(2L\)), their latency steps may grow with \(n_p\), and their messages do not shrink (TP all-reduces are \(B\times d\) regardless of \(n_p\)). So the communication term becomes a growing fraction, and beyond some \(n_p\) latency stops improving. Keeping collectives on NVLink (small \(\alpha\), large \(\beta_{\text{link}}\)) and overlapping them pushes that point out.
