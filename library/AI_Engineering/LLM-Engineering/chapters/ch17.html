Part VI · Distributed Inference — Chapter 18

Parallelism Strategies for Inference

A dense model can be spread over many GPUs in four basic ways: replicate it, split each matrix, split the stack of layers, or split the sequence. Each reduces a different per-GPU cost and pays a different communication price. This chapter derives both sides for each strategy, shows why tensor parallelism cuts latency while pipeline parallelism does not, how long prompts are split across devices, and how to choose a configuration for a given model, cluster and latency target.

Why this chapter

Chapter 17 gave us the price of moving data: the α–β model, the collectives and their algorithms, the gap of an order of magnitude between NVLink and the network, and a template for step time as a per-GPU roofline term plus a communication term. This chapter fills in the template for the strategies used to serve dense models. They were mostly invented for training, Megatron-LM's tensor parallelism in 2019 and GPipe's and PipeDream's pipelines in 2019–21, and the trade-offs change in inference, where there is no backward pass, decode is memory-bound and the latency of a single token matters. Pope and colleagues' analysis of serving PaLM 540B on TPUs (2022)[1] was the first systematic treatment of these trade-offs for inference, and its reasoning is the model for ours.

The central questions are concrete. Llama 3 70B in BF16 needs at least two H100s; should it run on two, four or eight, and in what arrangement? Why does every production deployment use tensor parallelism within a server, and why does pipeline parallelism appear only across servers? How does a million-token prompt get prefilled in reasonable time, when attention over it would take minutes on one GPU? And when is the best answer not to split a model at all, but to quantise it and replicate it? By the end of the chapter we will be able to answer each with a calculation.

Learning objectives
  1. Explain data parallelism (replication) and why it is the default when a model fits.
  2. Derive Megatron-style tensor parallelism for the MLP and attention, including the treatment of GQA key/value heads, and compute its per-GPU bytes and communication.
  3. Show that pipeline parallelism increases capacity and throughput but not single-token latency, and that in memory-bound decode it re-reads weights once per micro-batch.
  4. Explain context parallelism for long prompts (Ring Attention, Ulysses), derive the block size at which ring attention hides its communication, and state their limits.
  5. Choose a parallel configuration for a model and cluster from the latency–throughput frontier, including the interaction with quantisation.

18.1 The space of strategies

A forward pass of a dense Transformer is a computation indexed by four things: the requests in the batch, the tokens of each sequence, the layers, and the coordinates within each layer (heads, hidden units). Each parallelism strategy splits one index across GPUs. Data parallelism splits the batch: each GPU, or group of GPUs, holds a full copy of the model and serves its own requests. Tensor parallelism (TP) splits the coordinates within each layer, so each GPU holds a slice of every weight matrix. Pipeline parallelism (PP) splits the layers, so each GPU holds a contiguous block of them. Context parallelism (CP), also called sequence parallelism in some papers, splits the tokens of a long sequence. A fifth strategy, expert parallelism, splits the experts of a mixture-of-experts model and is the subject of Chapter 19.

Figure 18.1 shows the four side by side, with the communication each requires. The strategies compose: a deployment might use tensor parallelism of degree \(n_{\text{TP}}=8\) within a server, pipeline parallelism of degree \(n_{\text{PP}}=2\) across two servers, and data parallelism of degree \(n_{\text{DP}}\) across many such groups, for \(n_{\text{TP}}n_{\text{PP}}n_{\text{DP}}\) GPUs in all. Each choice moves the deployment along three axes: how much memory each GPU needs, how fast a single token can be produced, and how many tokens per second each GPU delivers.

The simplest strategy deserves to be stated first, because it is so often the right one. If a model fits on one GPU with enough room for its KV cache, replicating it is optimal for throughput per GPU: every GPU works independently, there is no communication at all, and the cost per token is exactly that of one GPU. Llama 3 8B is served this way almost everywhere. The other strategies exist because a model does not fit, or because one GPU cannot meet a latency target, and every one of them gives up some per-GPU efficiency to fix that. With that in mind, the first and most important of them is tensor parallelism.

18.2 Tensor parallelism

Tensor parallelism splits each layer's weight matrices across \(n_{\text{TP}}\) GPUs so that each GPU computes part of each matrix product. The question is how to split them so that communication is minimal, and the answer, due to Shoeybi and colleagues in Megatron-LM (2019)[2], uses a simple fact about block matrices. Consider the SwiGLU FFN of §2.6, \(Y=\big(\operatorname{SiLU}(XW_1)\odot XW_3\big)W_2\). Split \(W_1\) and \(W_3\) by columns into \(n_{\text{TP}}\) blocks, and \(W_2\) by the matching rows:

\[ W_1=\big[W_1^{(1)}\,\cdots\,W_1^{(n_{\text{TP}})}\big],\quad W_3=\big[W_3^{(1)}\,\cdots\,W_3^{(n_{\text{TP}})}\big],\quad W_2=\begin{bmatrix}W_2^{(1)}\\ \vdots\\ W_2^{(n_{\text{TP}})}\end{bmatrix}. \]

GPU \(r\) computes \(H^{(r)}=\operatorname{SiLU}(XW_1^{(r)})\odot XW_3^{(r)}\), a block of the hidden activation, using only its own weights and the full input \(X\). Because the nonlinearity acts elementwise, the columns of the hidden layer are independent, so no communication is needed for this step. GPU \(r\) then multiplies its block by its rows of \(W_2\), and the output is a sum over GPUs,

\[ Y\;=\;\sum_{r=1}^{n_{\text{TP}}}H^{(r)}W_2^{(r)}, \]

which a single all-reduce delivers to every GPU. A column-parallel layer followed by a row-parallel layer thus needs one all-reduce, and the pattern is the key to the whole method. Attention splits the same way along heads. Each GPU takes \(n_h/n_{\text{TP}}\) query heads, the corresponding columns of \(W_Q\), and the key and value heads they need from \(W_K\) and \(W_V\), computes attention for its heads entirely locally, and multiplies by its rows of \(W_O\); one all-reduce sums the partial outputs. The whole Transformer block needs exactly two all-reduces, and the residual additions and normalisations are computed redundantly on every GPU.

Figure 18.2 traces the FFN on two GPUs. The construction has a consequence for grouped-query attention that matters in practice. Llama 3 70B has 64 query heads and 8 key/value heads. With \(n_{\text{TP}}=8\), each GPU takes 8 query heads and exactly one key/value head, and the KV cache divides evenly across GPUs, so each GPU stores one eighth of every token's cache. With \(n_{\text{TP}}=16\), there are not enough key/value heads to go round, and each must be replicated on two GPUs, so the per-GPU cache stops shrinking: tensor parallelism beyond \(n_{kv}\) divides the weights further but not the cache. DeepSeek's latent attention, which has a single shared latent rather than separate heads, has the same issue in its extreme form, which is why MLA models are usually served with data-parallel attention rather than tensor-parallel attention (Chapter 19).

We can now price tensor parallelism with the template of §17.8. In decode with batch \(B\) at context \(t\), each GPU reads \(1/n_{\text{TP}}\) of the weights and \(1/n_{\text{TP}}\) of the cache (while \(n_{\text{TP}}\le n_{kv}\)), and the step performs \(2L\) all-reduces of \(B\times d\times b\) bytes each:

\[ t_{\text{step}}\;\approx\;\frac{N b_w+B\,t\,s_{kv}}{n_{\text{TP}}\,\beta}\;+\;2L\Big(\alpha_{\text{ar}}+\frac{2(n_{\text{TP}}-1)}{n_{\text{TP}}}\cdot\frac{B\,d\,b}{\beta_{\text{link}}}\Big), \]

where \(\alpha_{\text{ar}}\) is the latency of one all-reduce, about 5 µs for a latency-optimised kernel within a server (two steps plus launch overhead; §17.4). The first term falls as \(1/n_{\text{TP}}\); the second does not fall at all, because the number of all-reduces is fixed by the depth of the model and their size by the batch and width. So latency improves with tensor parallelism until the communication term dominates, and throughput per GPU falls steadily, since each GPU is idle during communication.

Figure 18.3 plots this model for Llama 3 70B, with each curve tracing batch sizes from 1 to 256 for one configuration. Read it as a menu. Moving along a curve, larger batches raise per-GPU throughput at the cost of TPOT, as in §6.6. Moving between curves, more tensor parallelism shifts the curve left, to lower latency, and down, to lower throughput per GPU: at batch 64, BF16 with TP = 8 has 45% lower TPOT than TP = 4 but about 10% less throughput per GPU. For a TPOT target of 20 ms, BF16 TP = 4 at batch 128 delivers about 1,700 tokens/s per GPU; for a target of 10 ms, TP = 8 is required. The FP8 curves lie above and to the left of their BF16 counterparts at the same tensor-parallel degree, because halving the bytes halves the memory term; FP8 with TP = 2 matches the latency of BF16 with TP = 4 at twice the throughput per GPU. This is the quantitative content of the advice in Chapter 14: quantise first, then parallelise only as much as the latency target requires.

Worked example — the cost of TP at batch 1

Llama 3 70B in BF16, one sequence. TP = 2: each GPU reads 70.6 GB, 21.1 ms, plus 160 all-reduces of 16 KiB at about 5 µs, 0.8 ms: TPOT ≈ 22 ms. TP = 8: 17.6 GB per GPU, 5.3 ms, plus the same 0.8 ms: TPOT ≈ 6.1 ms, 3.6× faster with 4× the GPUs. Communication has grown from 4% to 13% of the step. TP = 16 across two servers: the memory term halves again to 2.6 ms, but each all-reduce now includes inter-server steps at several microseconds each; at about 11 µs per all-reduce, communication is 1.8 ms, and TPOT ≈ 4.4 ms, a gain of only 28% for twice the GPUs. Tensor parallelism across the network rarely pays.

Two refinements are standard. Sequence parallelism in the sense of Korthikanti et al. (2022) replaces each all-reduce by a reduce-scatter, performs the normalisation and residual add on each GPU's slice of the tokens, and then all-gathers before the next column-parallel layer; the bytes are the same, but the redundant work and activation memory are divided by \(n_{\text{TP}}\), and the split collectives create more opportunities for overlap. And because each all-reduce sits between a GEMM and the next, engines fuse it with the residual addition and normalisation that follow, and overlap it with independent micro-batches when they exist (§17.7). Tensor parallelism is the strategy of choice inside an NVLink domain. Across domains, its frequent, latency-bound collectives become too expensive, and a strategy with less frequent communication is needed.

18.3 Pipeline parallelism

Pipeline parallelism splits the model into \(n_{\text{PP}}\) stages of consecutive layers, one per GPU or per tensor-parallel group, and passes activations from each stage to the next. Communication is minimal: one point-to-point transfer of the hidden states, \(B\times d\times b\) bytes per stage boundary per step, instead of two all-reduces per layer. For Llama 3 70B at batch 64 that is 1 MiB once per stage, which crosses even a 50 GB/s network in about 20 µs. This is why pipeline parallelism is the natural way to span servers.

The cost is that a single sequence's forward pass is sequential across stages. While stage 2 processes a batch, stage 1 has nothing to do unless a different batch is ready. In training, GPipe (Huang et al., 2019) and PipeDream (Narayanan et al., 2019–21)[3] filled the pipeline by splitting each batch into micro-batches and scheduling forward and backward passes to minimise the idle "bubble". In inference with continuous batching the idea is simpler: keep \(n_\mu\ge n_{\text{PP}}\) independent micro-batches of sequences in flight, so that each stage always works on some micro-batch while the others are elsewhere in the pipeline.

Figure 18.4 shows four stages with four micro-batches. After the fill, every stage is busy, so throughput is good. But consider one sequence in micro-batch A. Its token must pass through all four stages before its next token can begin, so its time per output token is the sum of the four stage times. If each stage holds a quarter of the layers and takes a quarter of the time a single GPU would need for the whole model, the sum is the full single-GPU time. Pipeline parallelism, unlike tensor parallelism, does not reduce the latency of one token; it only increases how many tokens can be in flight. For a memory-bound model, the batch-1 TPOT under pipeline parallelism is essentially \(Nb_w/\beta\) plus small transfer times, however many stages there are.

Figure 18.5 makes the contrast stark. At batch 1, tensor parallelism cuts TPOT from 22 ms on two GPUs to 6 ms on eight, while pipeline parallelism stays at 42 ms whatever the number of GPUs, the time for one GPU to read the whole model. Pipeline parallelism has a second, subtler cost in memory-bound decode. Each stage reads its weights once for each micro-batch that passes through it. With \(n_\mu\) micro-batches of \(B/n_\mu\) sequences each, producing one token for all \(B\) sequences requires reading the weights \(n_\mu\) times, whereas tensor parallelism with one batch of \(B\) reads them once. In bytes per round of tokens, across the whole group of GPUs,

\[ \text{PP: } n_\mu\,Nb_w+B\,t\,s_{kv},\qquad\text{TP: } Nb_w+B\,t\,s_{kv}. \]

The weight term is multiplied by the number of micro-batches. When the cache dominates, at long contexts and large batches, the difference is small; when weights dominate, at short contexts, pipeline parallelism wastes bandwidth. These two facts explain the standard practice. Pipeline parallelism is used across servers, where tensor parallelism's all-reduces would be too slow, and with micro-batches large enough that weight re-reads are amortised; it is also attractive for prefill, which is compute-bound and where re-reading weights costs nothing extra. Within a server, tensor parallelism is used. Llama 3.1 405B in BF16 (810 GB) on two 8-GPU servers, for example, is typically served with \(n_{\text{TP}}=8\) within each server and \(n_{\text{PP}}=2\) across them.

Drill 18.1 — Pipeline or tensor parallelism across two servers

Llama 3.1 405B in BF16 on two 8×H100 servers, decode at batch 32 and 4k context (BF16 cache, 126 layers, 8 KV heads of dimension 128, so \(s_{kv}=504\) KiB). Compare TP = 8 × PP = 2 (with two micro-batches) against TP = 16, using 5 µs per intra-server all-reduce, 15 µs per inter-server all-reduce, and 25 µs per pipeline transfer.

Solution. Weights are 810 GB; cache is \(32\times4096\times504\,\text{KiB}\approx67.6\) GB. TP = 8 × PP = 2: each stage's GPU holds 50.6 GB of weights and 4.2 GB of cache, and processes a micro-batch of 16 sequences. A stage step reads 50.6 GB plus 2.1 GB of its micro-batch's cache, about 15.7 ms, plus 126 all-reduces at about 5 µs, 0.6 ms: 16.3 ms per stage. A token for one micro-batch passes both stages, so TPOT ≈ 32.7 ms plus 25 µs for the transfer, and the pipeline produces 32 tokens every 32.7 ms. TP = 16: each GPU reads 50.6 GB of weights and 4.2 GB of cache, 16.4 ms, plus 252 all-reduces at 15 µs, 3.8 ms: TPOT ≈ 20.2 ms for all 32 sequences. With TP = 16, KV heads must also be replicated (16 > 8), which raises per-GPU cache to 8.4 GB and the step to about 21.4 ms. TP = 16 has lower latency and higher throughput here, because weight re-reads in the pipeline double the dominant term, but it is very sensitive to inter-server all-reduce latency; at 40 µs per all-reduce, TP = 16 would take about 28 ms and most of its advantage would be gone. FP8 weights on a single server (405 GB) with TP = 8 would beat both.

18.4 Splitting the sequence: context parallelism

Tensor and pipeline parallelism divide the model. For very long prompts, the problem is the sequence. Prefilling a prompt of \(n_{\text{in}}\) tokens costs \(2Nn_{\text{in}}\) FLOPs in the linear layers and about \(2Ldn_{\text{in}}^2\) in attention (§2.9), so attention, quadratic in length, dominates beyond a few tens of thousands of tokens for models of this size. A million-token prompt to Llama 3 70B requires about \(1.4\times10^{17}\) FLOPs for the linear layers and about \(1.3\times10^{18}\) for attention, over half an hour on one H100 at 60% utilisation. Tensor parallelism can spread this over eight GPUs, but not more without leaving the server, and it does not reduce the activation memory of a long sequence enough. Context parallelism instead gives each of \(n_{\text{CP}}\) devices a contiguous chunk of \(T_c=n_{\text{in}}/n_{\text{CP}}\) tokens.

Every operation except attention is independent across tokens, so each device processes its chunk's linear layers alone. Attention is the exception: each query must see the keys and values of all earlier tokens, which live on other devices. Ring Attention (Liu, Zaharia and Abbeel, 2023)[4] solves this by passing key/value blocks around a ring of devices. In each of \(n_{\text{CP}}\) steps, every device computes blockwise attention between its own queries and the key/value block it currently holds, accumulating the result with the online softmax of FlashAttention (§9.3), while sending that block to the next device and receiving the next one. After \(n_{\text{CP}}\) steps every query has seen every key, and the result is exact.

Figure 18.6 shows the ring on four devices. The essential question is whether the transfers can hide behind the computation, and the answer is a short calculation. In one step, a device computes attention between \(T_c\) queries and \(T_c\) keys in one layer: \(4T_c^2d\) FLOPs (two matrix products of \(T_c\times d\) by \(d\times T_c\), over all heads). It sends a key/value block of \(2T_cn_{kv}d_hb\) bytes. Overlap is perfect when the computation takes at least as long as the transfer, \(4T_c^2d/\pi\ge2T_cn_{kv}d_hb/\beta_{\text{link}}\), which with \(d=n_hd_h\) and \(g=n_h/n_{kv}\) simplifies to

\[ T_c\;\ge\;\frac{b\,\pi}{2\,g\,\beta_{\text{link}}}. \]

For Llama 3 70B (\(g=8\)) in BF16 on H100s, with \(\pi_{\text{eff}}\approx600\) TFLOP/s, this is about 170 tokens over NVLink and about 1,500 tokens over a 50 GB/s network. Any prompt long enough to need context parallelism has chunks far larger than this, so ring attention's communication can be hidden almost entirely. Grouped-query attention helps by a factor of \(g\), since fewer key/value heads mean fewer bytes per block. One practical complication is causality. With the causal mask, the first device's queries attend to almost nothing and the last device's to everything, so contiguous chunks give a badly unbalanced load; implementations reorder tokens, giving each device two chunks from opposite ends of the sequence, so that every device has the same amount of attention work.

A second approach, DeepSpeed-Ulysses (Jacobs et al., 2023)[5], uses all-to-all instead of a ring. Before attention, an all-to-all converts the layout from "each device holds all heads for some tokens" to "each device holds some heads for all tokens"; each device then computes ordinary attention for its heads over the full sequence, and a second all-to-all converts back. Its communication per device is constant as the number of devices grows, but its parallelism is limited by the number of heads, and with GQA by the number of key/value heads, eight for Llama 3. Ring attention has no such limit. Meta's context-parallel inference for Llama 3 405B combined these ideas with tensor parallelism and reported prefilling a million-token prompt in about 77 seconds on 128 H100s[6].

Context parallelism is a prefill technique. In decode, a single new query must attend to a cache spread over many devices, and the work per step is small; the natural method is the split-KV approach of Flash-Decoding (§9.6) across devices, with a final reduction of partial softmax results, which is cheap in bytes but adds a latency-bound collective per layer. Long-context decode is therefore usually served with the cache distributed by tensor parallelism and the prefill accelerated by context parallelism, a split that maps naturally onto disaggregated prefill and decode pools (Chapter 13).

Drill 18.2 — Ring attention block size

Derive the minimum chunk length \(T_c\) for ring attention to hide its transfers for Llama 3 8B (\(g=4\)) in BF16 over NVLink and over a 50 GB/s network, with \(\pi_{\text{eff}}=600\) TFLOP/s. Why does MLA change the calculation?

Solution. \(T_c\ge b\pi/(2g\beta_{\text{link}})\). Over NVLink: \(2\times600\times10^{12}/(2\times4\times450\times10^{9})\approx333\) tokens. Over the network: \(2\times600\times10^{12}/(2\times4\times50\times10^{9})=3{,}000\) tokens. With fewer query heads per KV head, Llama 3 8B needs larger chunks than 70B for the same overlap. With MLA, what is passed around is the compressed latent (\(d_c+d_h^R=576\) values per token per layer for DeepSeek-V3) rather than per-head keys and values, so the bytes per block fall sharply relative to the attention FLOPs, and the threshold drops accordingly; attention computation, which works on up-projected heads, stays large.

Worked example — a 512k-token prompt for Llama 3 8B

Memory. At \(s_{kv}=128\) KiB per token, a 524,288-token prompt needs 64 GiB ≈ 68.7 GB of cache. Together with 16.06 GB of weights that is 85 GB, more than an H100 holds, before activations. One GPU cannot serve this request at all.

Compute. The matrix products cost \(2\times7.5\times10^9\times524{,}288\approx7.9\times10^{15}\) FLOPs. Causal attention costs about \(2T^2d\) per layer, \(32\times2\times(524{,}288)^2\times4096\approx7.2\times10^{16}\) FLOPs, nine times as much: at this length attention is almost the whole prefill. At 50% MFU on one H100 the total of \(8.0\times10^{16}\) FLOPs would take about 160 s.

Context parallelism over 8 GPUs. Each GPU holds 65,536 tokens of the sequence, 8.6 GB of cache, which fits easily. With causal load balancing (each GPU takes one chunk from the front and one from the back of the sequence, so that all do equal work), the prefill takes about \(160/8=20\) s. The ring passes every KV chunk around the other seven GPUs, so each GPU sends about \(7\times8.6\approx60\) GB over the whole prefill: 0.13 s at 450 GB/s over NVLink, or 1.2 s at 50 GB/s over InfiniBand, either way small beside 20 s of attention, so overlap hides it.

Consequence. Attention compute grows as \(T^2\) while the KV traffic grows as \(T\), so the longer the prompt, the easier context parallelism\'s communication is to hide. That is the opposite of tensor-parallel decode, where small messages and latency dominate, and it is why long-context prefill is the one place where spreading a single request across nodes pays.

18.5 Choosing a configuration

With the costs of each strategy in hand, choosing a configuration becomes a constrained optimisation, which Pope et al. framed as finding the Pareto frontier of latency and cost for each model and chip. Their PaLM 540B study found layouts reaching a 29 ms per-token latency at small batch with INT8 weights and 76% model FLOPs utilisation in large-batch prefill, by choosing partitionings separately for each phase and batch size. The general procedure has four steps.

First, memory: the configuration must hold the weights and the cache for the target batch and context. This sets a minimum number of GPUs per replica, which quantisation reduces. Second, latency: for the target TPOT, find the configurations whose frontier (Figure 18.3) reaches that latency, using tensor parallelism within an NVLink domain to cut the memory term, and remembering that pipeline parallelism does not help latency. Third, throughput: among the feasible configurations, choose the one with the highest tokens per second per GPU at the target latency, which usually means the smallest tensor-parallel degree that meets the target, because every extra GPU in a replica adds communication. Fourth, replicate: serve the required load with data parallelism over as many replicas as needed, with a router in front (Chapter 27). Prefill and decode may want different answers, which is one more argument for disaggregation (Chapter 13).

Worked example — serving Llama 3 70B on one 8×H100 server

Target: TPOT ≤ 15 ms at 2k context, maximum throughput. Option A, BF16, one replica with TP = 8: from Figure 18.3, the 15 ms target allows batch 256, about 2,100 tokens/s per GPU, 17,000 for the server. Option B, BF16, two replicas with TP = 4: the target allows batch 64 per replica (15.1 ms), about 1,060 tokens/s per GPU, 8,500 for the server; TP = 4 is worse here because its weights use more of each GPU's step. Option C, FP8, two replicas with TP = 4: at 14.7 ms, batch 256 per replica, about 4,350 tokens/s per GPU, 35,000 for the server. Option D, FP8, four replicas with TP = 2: at 14.9 ms, batch 64 per replica (memory allows about 200), about 2,150 tokens/s per GPU. Choice: option C, twice option A's throughput at the same latency, after checking FP8 accuracy. With a looser target of 20 ms, option D at batch 128 (18.5 ms, about 3,460 tokens/s per GPU) would come close to C, with more, smaller replicas that are easier to load-balance.

The example illustrates a pattern that holds widely. The interaction between quantisation and parallelism is strong, because halving the bytes per weight has the same effect on the memory term as doubling the tensor-parallel degree, without the communication. Larger batches always help throughput until the latency target binds. And the number of GPUs per replica should be the smallest that meets memory and latency, with the rest of the cluster used for replicas. Deviations from this pattern are usually driven by memory, as with 405B-class dense models, or by the very different structure of mixture-of-experts models, whose experts invite a parallelism strategy of their own.

Drill 18.3 — Replicas versus tensor parallelism for an 8B model

For Llama 3 8B on eight H100s at batch 64 per replica and 2k context (BF16), compare eight TP = 1 replicas with one TP = 8 replica serving batch 512, using the model of §18.2 (5 µs per all-reduce, 64 all-reduces per step).

Solution. Eight replicas: each step reads 16.06 GB plus \(64\times2048\times128\,\text{KiB}\approx17.2\) GB, 9.9 ms, for 64 tokens per GPU: about 6,460 tokens/s per GPU at 9.9 ms TPOT. One TP = 8 replica at batch 512: each GPU reads 2.0 GB of weights and 17.2 GB of cache, 5.7 ms, plus 64 all-reduces of \(512\times4096\times2=4\) MiB at about \(5+16=21\) µs, 1.3 ms: TPOT ≈ 7.1 ms, \(512/(7.1\,\text{ms}\times8)\approx9{,}000\) tokens/s per GPU. At the same total concurrency, TP wins in this model, because one large batch reads the weights once per step instead of eight times. The step is still memory-bound (its compute, 512 tokens × 16 GFLOPs ≈ 8.2 TFLOPs, is about 1.7 ms per GPU at 600 TFLOP/s, below the 5.7 ms of memory time), but the margin is smaller than it looks: CPU overhead per step is the same for one large engine as for each small one (Drill 12.1), and each replica could instead run a larger batch of its own. The lesson is to compute rather than assume: replicas avoid communication, tensor parallelism amortises weight reads over a larger batch, and which wins depends on the ratio of weight bytes to cache bytes and on the overheads the roofline omits.

18.6 Parallelism in real engines

The strategies of this chapter appear in every serving engine as a handful of configuration options, and it is worth seeing how the analysis maps onto them. In vLLM, tensor_parallel_size and pipeline_parallel_size set \(n_{\text{TP}}\) and \(n_{\text{PP}}\) for one engine, and data_parallel_size runs several engine cores, each with its own scheduler and KV cache, behind one API server (§12.3); SGLang and TensorRT-LLM have equivalents. The engines place tensor-parallel ranks on GPUs connected by NVLink when they can, and use Ray or a similar framework to place pipeline stages on different servers. Within a tensor-parallel group, the engine core broadcasts each step's schedule to all workers, which run in lockstep; the custom all-reduce kernels of §17.4 handle small messages and NCCL the large ones, and both are captured in CUDA graphs so that the 160 collectives of a 70B decode step do not each pay a launch overhead.

Two refinements are worth knowing because they are asked about in interviews. The first is data-parallel attention, introduced for MLA models such as DeepSeek-V3. Tensor-parallel attention would replicate the single shared latent cache on every GPU, wasting memory, so instead each GPU runs attention for its own subset of requests, with its own cache, while the FFN or expert layers are parallelised across GPUs; the activations are redistributed between the two parts with all-gather or all-to-all. This mixes data parallelism and model parallelism within one layer, choosing for each sub-layer the split that suits its state: per-request state (the cache) is partitioned by request, shared state (the weights) is partitioned by coordinate. The second refinement is that prefill and decode can use different degrees even within one engine: some engines run long prefills with context parallelism and decode with plain tensor parallelism on the same GPUs, and disaggregated deployments (Chapter 13) make the separation explicit.

Operational concerns also shape the choice. A tensor-parallel group is a single failure domain: if one GPU fails, the whole replica stops, so very large groups make failures more disruptive, and smaller replicas make load balancing and rolling upgrades easier. Pipelines add queueing between stages and are sensitive to imbalance between them, since the slowest stage sets the pace. And every configuration must be validated end to end, because the roofline-plus-α–β model omits kernel efficiency at small shapes, CPU overhead and scheduler effects. The calculations of this chapter tell us which few configurations deserve a load test; the load test decides.

Looking ahead

Every strategy in this chapter assumed a dense model, in which every token uses every weight. Mixture-of-experts models break that assumption: DeepSeek-V3 has 671 billion parameters but uses only 37 billion per token, spread across 256 experts per layer of which each token visits eight. Its weights are too large for tensor parallelism to be efficient, its per-token work too small for each expert to see large batches, and its routing creates a communication pattern, the all-to-all, that none of the dense strategies uses. Chapter 19 develops expert parallelism, load balancing and the deployment architectures that made trillion-parameter MoE models economical to serve.

Chapter summary

  • Four ways to split a dense model: data (requests, no communication), tensor (matrix coordinates, two all-reduces per layer), pipeline (layers, point-to-point) and context (sequence, KV exchange). They compose, e.g. TP within servers × PP across servers × DP across groups. If a model fits on one GPU, replication is best for per-GPU throughput.
  • Megatron TP: column-parallel then row-parallel matrices, so each FFN and each attention block needs one all-reduce. KV heads split across GPUs only up to \(n_{\text{TP}}=n_{kv}\); beyond that they are replicated and the per-GPU cache stops shrinking.
  • TP step time ≈ \((Nb_w+Bts_{kv})/(n_{\text{TP}}\beta)+2L(\alpha_{\text{ar}}+\dots)\): latency falls with \(n_{\text{TP}}\) until communication dominates, while per-GPU throughput falls steadily. Across servers TP rarely pays.
  • PP sends \(B\times d\) activations per stage boundary, ideal across servers, but does not reduce per-token latency (stages run in sequence for each token), and in memory-bound decode it re-reads weights once per micro-batch: \(n_\mu Nb_w\) versus \(Nb_w\).
  • Context parallelism for long prefill: Ring Attention passes KV blocks around a ring with the online softmax, hiding transfers when \(T_c\ge b\pi/(2g\beta_{\text{link}})\) (≈ 170 tokens on NVLink, ≈ 1,500 on 50 GB/s for 70B); load-balance causal masks by reordering chunks. Ulysses uses all-to-all and is limited by the number of (KV) heads.
  • Choosing: satisfy memory, then latency with the smallest TP that meets TPOT, then maximise throughput per GPU, then replicate. Quantisation halves the memory term without communication and usually beats extra TP.

Warm-up Explain Megatron-style tensor parallelism for a Transformer block.

In the FFN, split \(W_1\) and \(W_3\) by columns across \(n_{\text{TP}}\) GPUs and \(W_2\) by the matching rows. Each GPU computes its block of hidden units, \(\operatorname{SiLU}(XW_1^{(r)})\odot XW_3^{(r)}\), from the replicated input with no communication (the nonlinearity is elementwise), then multiplies by its rows of \(W_2\) to get a partial output; one all-reduce sums the partials. Attention is split by heads: each GPU takes \(n_h/n_{\text{TP}}\) query heads and the matching KV heads (columns of \(W_Q,W_K,W_V\)), computes attention locally, multiplies by its rows of \(W_O\), and one all-reduce sums. So each block needs two all-reduces; norms and residuals are replicated (or sharded with sequence parallelism). Each GPU stores \(1/n_{\text{TP}}\) of the weights and, while \(n_{\text{TP}}\le n_{kv}\), of the KV cache.

Warm-up Why does pipeline parallelism not reduce per-token latency?

A token's forward pass must go through the stages in order: stage 2 cannot start until stage 1 has finished that token's layers. If each of \(n_{\text{PP}}\) stages holds \(L/n_{\text{PP}}\) layers and takes \(1/n_{\text{PP}}\) of the single-device time, the sum over stages is the single-device time again, plus transfer latencies. Pipelining lets several micro-batches be in different stages at once, so throughput and capacity scale, but each sequence's time per output token does not improve. Tensor parallelism, by contrast, splits each layer's work so all GPUs work on the same token simultaneously, dividing the per-token time (until communication dominates).

Core Derive the decode step time under tensor parallelism and explain its diminishing returns.

Each GPU reads \(1/n_{\text{TP}}\) of the weights and (for \(n_{\text{TP}}\le n_{kv}\)) of the cache: \((Nb_w+Bts_{kv})/(n_{\text{TP}}\beta)\). Each step performs \(2L\) all-reduces of \(Bdb\) bytes: \(2L(\alpha_{\text{ar}}+2(n_{\text{TP}}-1)Bdb/(n_{\text{TP}}\beta_{\text{link}}))\). The memory term falls as \(1/n_{\text{TP}}\), but the communication term does not shrink: the count \(2L\) is fixed by depth, the message by batch and width, and \(\alpha_{\text{ar}}\) may even grow with more ranks. Example, Llama 3 70B BF16 at batch 1: TP = 2, 21.1 + 0.8 ms; TP = 8, 5.3 + 0.8 ms; TP = 16 across servers, 2.6 + 1.8 ms. Beyond \(n_{kv}\), KV replication also stops the cache term shrinking. Per-GPU throughput falls throughout because GPUs idle during communication.

Core Compare tensor and pipeline parallelism for decode in bytes per round of tokens.

Producing one token for each of \(B\) sequences: with TP, one batch passes once through all layers; weights are read once in total (split across GPUs): \(Nb_w+Bts_{kv}\) bytes across the group, with \(2L\) all-reduces. With PP and \(n_\mu\) micro-batches of \(B/n_\mu\), each micro-batch passes each stage separately, so each stage reads its weights \(n_\mu\) times: \(n_\mu Nb_w+Bts_{kv}\), with only \(n_{\text{PP}}-1\) point-to-point transfers per micro-batch. When weights dominate bytes (short contexts), PP wastes bandwidth and also does not cut latency; when cache dominates, the overhead is smaller. PP's advantage is its cheap, infrequent communication, which suits inter-server links, and it costs nothing extra in compute-bound prefill.

Core What is the interaction between GQA and tensor parallelism?

Attention is split by heads. With \(n_{kv}\) KV heads, TP up to \(n_{kv}\) gives each GPU whole KV heads, so the cache divides evenly and each query head finds its KV head locally. Beyond \(n_{kv}\) (for example TP = 16 with 8 KV heads), there are not enough KV heads to go round, so each is replicated on several GPUs: the per-GPU cache stops shrinking and cache memory is duplicated, reducing the memory-limited batch. That is one reason TP degrees above 8 are rare for Llama-class models. For MLA, with one shared latent per token, TP over attention would replicate the latent on every GPU, so MLA models typically use data-parallel attention (each GPU handles different requests' attention) with expert or tensor parallelism for the rest.

Core Explain Ring Attention and derive when its communication can be hidden.

Each of \(n_{\text{CP}}\) devices holds \(T_c\) contiguous tokens (queries and their KV). In each of \(n_{\text{CP}}\) steps, a device computes blockwise attention of its queries against the KV block it holds, merges into running outputs with the online-softmax recurrence, and simultaneously sends that block to the next device and receives another. Per step per layer: compute \(4T_c^2d\) FLOPs; transfer \(2T_cn_{kv}d_hb\) bytes. Overlap requires \(4T_c^2d/\pi\ge2T_cn_{kv}d_hb/\beta_{\text{link}}\); with \(d=n_hd_h\) and \(g=n_h/n_{kv}\): \(T_c\ge b\pi/(2g\beta_{\text{link}})\). For Llama 3 70B in BF16 at 600 TFLOP/s: about 170 tokens over NVLink, 1,500 over 50 GB/s. Long prompts have far larger chunks, so communication hides. Causal masks unbalance work; reorder chunks (each device takes one early and one late chunk) to balance.

Core Compare Ring Attention and DeepSpeed-Ulysses.

Both parallelise attention over a long sequence. Ring passes KV blocks around devices in \(n_{\text{CP}}\) steps, computing blockwise attention with online softmax; communication is point-to-point, overlappable, and scales to any number of devices, but each device's traffic grows with the total sequence and it needs load balancing under causal masks. Ulysses uses two all-to-alls per attention layer to switch from token-sharded to head-sharded layout, computes ordinary (Flash) attention over the whole sequence for its heads, and switches back; per-device communication is constant as devices grow, but parallelism is capped by the number of heads, and by \(n_{kv}\) for GQA without replication, and all-to-all is harder to overlap and sensitive to network bandwidth. Hybrids combine Ulysses within a node and Ring across nodes.

Deep-dive Llama 3.1 405B in BF16 must run on two 8×H100 servers. Compare TP = 8 × PP = 2 with TP = 16.

Weights 810 GB; at batch 32 and 4k context the BF16 cache is about 67.6 GB (504 KiB per token). TP8×PP2 with two micro-batches of 16: each GPU reads 50.6 GB of weights plus 2.1 GB of cache per stage step, about 15.7 ms plus 126 intra-server all-reduces (≈ 0.6 ms); TPOT ≈ 2 × 16.3 = 32.7 ms. TP16: each GPU reads 50.6 GB plus 4.2 GB (8.4 GB with KV-head replication), about 16.4–17.6 ms, plus 252 inter-server all-reduces at about 15 µs (3.8 ms): TPOT ≈ 21 ms, better on both latency and throughput because PP re-reads weights per micro-batch. But TP16 is fragile: at 40 µs per all-reduce it rises to about 28 ms. Better still: FP8 weights (405 GB) on one server with TP8 (≈ 19 ms) and use the second server as another replica.

Deep-dive How would you serve a one-million-token prompt to a 70B model?

Prefill costs about \(1.4\times10^{17}\) FLOPs in linear layers and \(1.3\times10^{18}\) in attention, about 40 minutes on one H100 at 600 TFLOP/s. Use context parallelism across many GPUs (for example 16 servers), with ring attention across servers (chunks of tens of thousands of tokens, far above the 1,500-token overlap threshold) and TP or Ulysses within servers, load-balanced chunk ordering for the causal mask, FlashAttention kernels, and FP8 where accuracy allows. The KV cache is 320 KiB × 10^6 ≈ 330 GB in BF16, so it must be distributed; decode then uses split-KV attention across devices with a softmax reduction per layer, or the cache is transferred to a decode pool. Consider prefix caching if documents recur, sparse or windowed attention variants if the model supports them, and disaggregating prefill (compute-heavy, CP) from decode (bandwidth- and memory-heavy). Meta reported about 77 s for a 1M-token prefill of 405B on 128 H100s with context parallelism.

Deep-dive What limits the useful tensor-parallel degree, and how do NVL72-class systems change it?

Three limits: (1) communication: \(2L\) all-reduces per step whose latency does not fall with TP, so communication becomes a growing fraction and across the network TP rarely pays; (2) KV heads: beyond \(n_{kv}\) the cache must be replicated; (3) efficiency: per-GPU GEMMs become thin (\(d/n_{\text{TP}}\)-wide slices at small batch), lowering kernel efficiency, and CPU overhead per step does not shrink (Drill 12.1). NVL72 puts 72 GPUs in one NVLink domain at 900 GB/s per direction, so all-reduces across more than 8 GPUs stay low-latency and high-bandwidth; this makes larger TP (or, more usefully, wide expert parallelism for MoE) practical for very large models, though limits (2) and (3) remain.

Deep-dive Why are prefill and decode often best served with different parallel configurations?

Prefill is compute-bound: TTFT for long prompts benefits from splitting FLOPs across many GPUs (TP within nodes, context parallelism across them); weight re-reads under PP cost nothing because compute dominates; communication volumes are large and bandwidth-bound, and overlap well with large GEMMs. Decode is memory-bound and latency-sensitive: the best per-GPU throughput comes from the smallest TP that meets TPOT, large batches, and avoiding PP's weight re-reads; communication is small and latency-bound. A single configuration compromises one of them. This is a further argument for disaggregation (Chapter 13), where prefill and decode pools can each use their own parallelism, as in DeepSeek's deployment with different unit sizes for the two phases.

Design Choose a configuration for Llama 3 70B on 16 H100s (two servers) for a chat product with TPOT ≤ 12 ms at peak 400 requests/s, 2k context, 400-token outputs.

Output demand: 400 × 400 = 160k tokens/s. Quantise to FP8 (weights and KV) after accuracy validation. From the frontier: FP8 TP = 4 at batch 128 gives about 10.4 ms and 3,080 tokens/s per GPU; TP = 8 at batch 256 gives 9.3 ms and 3,460 per GPU; TP = 2 cannot meet 12 ms. Four TP = 4 replicas (16 GPUs) deliver about 49k tokens/s; two TP = 8 replicas about 55k. Both fall far short of 160k: the target needs roughly 50 GPUs, so the plan must add hardware or relax constraints. Options: more GPUs (about 48–56 H100s as TP = 8 or TP = 4 replicas, with prefill handled by chunking or a disaggregated pool), speculative decoding to raise per-sequence speed at the same batch, or a smaller distilled model for part of the traffic. Never cross servers with TP; keep each replica inside one server.

Design A team plans to serve a 70B model with PP = 8 across eight single-GPU machines with 100 Gb/s Ethernet. Critique.

Memory works (each stage holds about 17.6 GB of BF16 weights), and PP's point-to-point transfers (1 MiB at batch 64) are fine over 12.5 GB/s (about 80 µs per hop). But latency: each token traverses eight stages sequentially, so TPOT is at least the single-device time to read all weights, about 42 ms in BF16, plus 7 hops of tens of microseconds plus network jitter; with \(n_\mu\) micro-batches the weights are re-read \(n_\mu\) times per round, so throughput per GPU is worse than TP. Pipeline bubbles appear whenever traffic is bursty or micro-batches are uneven, and any stage failure stops the whole pipeline. If the product needs low TPOT, this design cannot deliver. Better: put eight GPUs in one NVLink server with TP = 8 (about 6 ms at batch 1), or quantise to 4 bits and run on fewer GPUs per replica.

Design How would you build an automatic configuration search for an inference engine?

Inputs: model architecture (L, d, heads, KV heads, experts), precision options, hardware (GPU specs, NVLink domain size, network), workload (prompt and output distributions, prefix reuse, arrival rate) and SLOs (TTFT, TPOT percentiles). Enumerate configurations: precision × TP (up to the NVLink domain and \(n_{kv}\)) × PP × CP for prefill × batch caps × chunk sizes × disaggregation split. For each, check memory feasibility, then estimate step times with a roofline-plus-α–β model calibrated by microbenchmarks (GEMM efficiency, attention kernel throughput, all-reduce latency by size), and simulate the scheduler with the workload to estimate TTFT and TPOT distributions and per-GPU goodput. Keep the Pareto set of cost versus latency; validate the top few with real load tests, and feed measurements back to recalibrate. DistServe and Pope et al. used similar search-plus-simulation approaches.

Core What is sequence parallelism in the Megatron sense, and how does it differ from context parallelism?

Megatron sequence parallelism (Korthikanti et al., 2022) is an optimisation within tensor parallelism: the all-reduce after each sub-layer is split into a reduce-scatter, after which each GPU holds the summed output for a slice of the tokens and applies normalisation, dropout and residual additions only to that slice, and an all-gather before the next column-parallel layer. Bytes are unchanged, but redundant per-token work and activation memory fall by \(n_{\text{TP}}\). Context parallelism instead distributes the tokens of a long sequence across devices for the whole model, including attention, which requires KV exchange (ring) or head re-sharding (Ulysses). The names are often confused; the first is a TP implementation detail, the second a parallelism strategy for long sequences.

Core Why is data parallelism (replication) often the best choice, and when is it impossible?

Replicas need no inter-GPU communication, keep each GPU's work fully local and avoid the latency and efficiency losses of collectives, so per-GPU throughput is exactly that of one replica, and failures are isolated. Scaling is linear in GPUs with a load balancer. It is impossible or inefficient when the model plus a useful KV cache does not fit in one GPU (or one NVLink group), when a latency target requires more memory bandwidth per token than one GPU provides (TP divides the per-token bytes), or when very large MoE models need wide expert parallelism to give each expert large batches. Quantisation and distillation extend the range in which replication works, which is why they are usually tried first.
