Part VIII · Post-Training and Reasoning — Chapter 25

Reinforcement Learning with Verifiable Rewards

When the answer to a problem can be checked, the reward needs no human and no reward model: it is simply right or wrong. Reinforcement learning with such rewards produced the reasoning models of 2025. This chapter derives GRPO, the critic-free algorithm behind DeepSeek-R1, from the baselines of Chapter 23, examines the flaws that later work found and fixed in it, compares outcome and process rewards, and shows why training on verifiable rewards is, above all, a problem of generating very long responses efficiently.

Why this chapter

Chapter 24 ended with the weakness shared by every preference method: its reward is a model of human judgement, accurate about 70% of the time and exploitable when optimised hard. Some tasks need no such model. A mathematics problem with a numerical answer can be checked by comparing the model's final answer with the reference. A programming problem can be checked by running unit tests. A logic puzzle can be checked by a solver, an instruction such as "answer in exactly three bullet points" by a parser. For these tasks the reward is verifiable: computed by a program, essentially free of noise, and very hard to fool if the checker is sound.

The idea of training on checked answers is older than reasoning models. STaR (2022) fine-tuned models[5] on their own correct rationales, which is REINFORCE with a 0/1 reward (§23.2). OpenAI's "Let's verify step by step" (2023)[6] studied rewards on intermediate steps. The turning point came in three steps. In February 2024, DeepSeekMath introduced GRPO[1], a variant of PPO without a critic, which estimates baselines from groups of samples. In September 2024, OpenAI's o1 showed[3] that large-scale RL on verifiable problems produced a model whose accuracy grew with how long it thought. In January 2025, DeepSeek-R1 reproduced the result openly[2] and showed, with R1-Zero, that RL with only an accuracy reward and a format reward, applied directly to a base model, made the model learn to reason at length, check its work and backtrack, with no human demonstrations of reasoning at all. AI2's Tülu 3 (November 2024) named the approach[4] reinforcement learning with verifiable rewards (RLVR), and within months the open literature had produced a series of corrections to GRPO, of which Dr. GRPO and DAPO are the best known.

This chapter completes the training side of Part VIII. For the inference engineer it has a particular significance: an RLVR step generates many long samples per prompt, and generation is more than half of its cost. The algorithms are short; the systems that run them are among the largest inference deployments that exist.

25.1 Rewards that can be checked

A verifiable reward is a function \(\mathcal R(x,y)\) computed by a program from the prompt, the response and, usually, a reference answer or test suite. The commonest kinds are three. For mathematics, the checker extracts the final answer from the response, conventionally from a delimited box, and tests it for equivalence with the reference. Equivalence is harder than it sounds, since \(\tfrac12\), \(0.5\) and \(\frac{2}{4}\) must all match, so checkers normalise expressions and often test symbolic equality with a computer-algebra system. For code, the checker runs the program against unit tests in a sandbox and rewards passing all of them, or a fraction. For instruction following, it checks verifiable constraints such as length limits, required keywords or output formats. DeepSeek-R1-Zero added a format reward for placing the reasoning between thinking tags and the answer after them, so that the answer could be extracted reliably.

These rewards have three properties that make them unlike those of Chapter 24. They are binary or nearly so: a response is right or wrong. They are low-noise: a sound checker does not disagree with itself, so optimising harder does not run into Goodhart's law in the way a learned reward does. And they are sparse: a response of ten thousand tokens earns a single bit. DeepSeek deliberately avoided neural reward models for R1-Zero, reporting that they were vulnerable to reward hacking at scale, while rule-based rewards were not.

"Hard to fool" is not "impossible to fool". A mathematics checker that accepts any response containing the right number can be gamed by listing many numbers. Weak unit tests reward programs that special-case the visible inputs. Models trained on code have learned to modify tests or exit early with a success code when the sandbox allowed it. Verifiable rewards move the burden of alignment from modelling human judgement to writing sound checkers, which is easier but still engineering. Verification also has a cost of its own. Checking a mathematical answer takes microseconds, but running a program against its tests in an isolated sandbox takes from a fraction of a second to many seconds, so a code-RL step with thousands of rollouts needs a fleet of CPU workers, pipelined with generation so that the GPUs never wait for verdicts. Figure 25.1 shows how much of the machinery of the previous two chapters has disappeared. There is no reward model, because a program scores the responses, and no critic, because, as §25.3 will show, the samples of each group serve as one another's baseline. What has grown is the second box. Each prompt is answered not once but \(n_s\) times, typically 8 to 64, and each answer may be thousands of tokens long.

25.2 When does a group carry signal?

With a binary reward, learning comes only from contrast. If all \(n_s\) samples for a prompt are correct, or all are wrong, every sample's reward equals the group's mean, every advantage is zero, and the prompt contributes no gradient, however much it cost to generate. The useful prompts are those on which the model sometimes succeeds. If the model solves a prompt with probability \(p_s\) and samples are independent, the probability that a group of \(n_s\) is informative, containing at least one success and at least one failure, is

\[ P_{\text{info}}(p_s,n_s)\;=\;1-p_s^{\,n_s}-(1-p_s)^{n_s}. \]

Figure 25.2 plots it. For prompts of intermediate difficulty almost every group is informative. For a prompt the model solves 2% of the time, a group of 8 is informative only 15% of the time; for one it solves 98% of the time, likewise. Larger groups widen the useful band, at proportional generation cost.

Figure 25.2 has three practical consequences. First, data selection matters more in RLVR than in most training: a dataset of prompts the model already solves, or cannot begin to solve, produces almost no gradient. Practitioners estimate each prompt's pass rate with the current model and keep those in a middle band. Second, the useful band moves as the model improves, so the prompt mix must be refreshed, a curriculum in which easy problems are retired and hard ones become reachable. Third, within a training step, groups that turn out to be uninformative can be detected after generation and replaced, which is the dynamic sampling of §25.4. Even the strength of the signal from an informative group depends on \(p_s\): the variance of a Bernoulli reward is \(p_s(1-p_s)\), largest at \(p_s=\tfrac12\), and it is this variance that the group baseline converts into gradient.

Drill 25.1 — How many samples to rescue hard prompts?

A model solves a class of hard prompts with probability 3%. How large must the group be for at least half of the groups to be informative? What does that cost relative to \(n_s=8\)?

Solution. For small \(p_s\), \(P_{\text{info}}\approx1-(1-p_s)^{n_s}\). Setting \((0.97)^{n_s}\le0.5\) gives \(n_s\ge\ln0.5/\ln0.97\approx22.8\), so 23 samples, nearly three times the generation of \(n_s=8\), whose groups are informative only \(1-0.97^8\approx22\%\) of the time. Per informative group, though, the costs are \(23/0.5=46\) samples against \(8/0.22\approx37\): larger groups for hard prompts buy reliability more than efficiency. A cheaper alternative is to raise the pass rate first, by distillation or SFT on related solutions, so that the prompts move into the band where small groups suffice.

25.3 GRPO

We now derive GRPO from the policy gradient of Chapter 23. For a prompt \(x\), draw a group of responses \(y_1,\dots,y_{n_s}\) from \(p_{\theta_{\text{old}}}\) and score them \(\mathcal R_1,\dots,\mathcal R_{n_s}\). §23.3 showed that any baseline independent of the sampled response leaves the gradient unbiased, and that the ideal one is the policy's expected reward on the prompt. The group provides an estimate of it for free. The cleanest choice is the leave-one-out mean, used by RLOO (Ahmadian et al., 2024)[8]: response \(i\)'s baseline is the mean reward of the other responses,

\[ \hat A_i^{\text{RLOO}}\;=\;\mathcal R_i-\frac{1}{n_s-1}\sum_{j\ne i}\mathcal R_j, \]

which is independent of \(y_i\) because the samples are independent, so the estimator is exactly unbiased. GRPO (Shao et al., 2024) instead subtracts the mean of the whole group, including \(\mathcal R_i\), and divides by the group's standard deviation:

\[ \hat A_i^{\text{GRPO}}\;=\;\frac{\mathcal R_i-\bar{\mathcal R}}{\operatorname{std}(\mathcal R_{1:n_s})+\epsilon},\qquad \bar{\mathcal R}=\frac1{n_s}\sum_j\mathcal R_j. \]

The two are closely related. A line of algebra shows that \(\mathcal R_i-\bar{\mathcal R}=\frac{n_s-1}{n_s}\big(\mathcal R_i-\frac1{n_s-1}\sum_{j\ne i}\mathcal R_j\big)\), so subtracting the full mean is RLOO scaled by \((n_s-1)/n_s\): the numerator of GRPO's advantage is unbiased up to a constant factor. The division by the standard deviation is different in kind. It rescales each prompt's advantages to unit variance, so that a prompt whose samples barely differ gets advantages as large as one whose samples differ greatly. This is a reweighting of prompts, and §25.4 discusses what it does.

GRPO then plugs the advantage into PPO's clipped surrogate (§23.6), giving every token of response \(i\) the same advantage \(\hat A_i\), and adds the \(k_3\) estimate of KL to the reference (§23.5) directly to the loss rather than to the reward. With \(n_{y,i}\) the length of response \(i\) and \(\varrho_{i,t}\) the ratio of new to old probability of its \(t\)-th token, the objective to maximise is

\[ J_{\text{GRPO}}(\theta)=\mathbb E\Bigg[\frac1{n_s}\sum_{i=1}^{n_s}\frac1{n_{y,i}}\sum_{t=1}^{n_{y,i}}\Big(\min\big(\varrho_{i,t}\hat A_i,\;\operatorname{clip}(\varrho_{i,t},1\pm\epsilon_{\text{clip}})\hat A_i\big)-\beta_{\text{KL}}\,k_{3,i,t}\Big)\Bigg]. \]

Compared with PPO for language models, this removes the critic and the reward model: the models held are the policy, with its training state (\(16N\) bytes), and the frozen reference (\(2N\)), about half of PPO's \(36N\). The price is \(n_s\) samples per prompt, but those were wanted anyway, both because a group is what makes a binary reward informative (§25.2) and because an inference engine generates samples of the same prompt cheaply, sharing the prompt's KV cache across them (§10.6). Figure 25.3 shows the advantages for one group.

Worked example — the advantages of Figure 25.3

Rewards. Three correct, five wrong: \(\bar{\mathcal R}=3/8=0.375\), and the population standard deviation of a 0/1 variable with mean 0.375 is \(\sqrt{0.375\times0.625}\approx0.484\).

GRPO. Correct: \((1-0.375)/0.484\approx1.29\). Wrong: \(-0.375/0.484\approx-0.77\). Check: \(3\times1.29-5\times0.77\approx0\).

RLOO. Correct: \(1-2/7\approx0.714\) (two of the other seven are correct). Wrong: \(0-3/7\approx-0.429\). Mean-subtracted without the standard deviation gives \(0.625\) and \(-0.375\), exactly \(7/8\) of RLOO's values.

What changes with difficulty. If only one of eight were correct, GRPO would give the correct sample \((1-0.125)/0.331\approx2.65\): rare successes on hard prompts get large advantages, because the standard deviation is small. RLOO would give \(1-0=1\). That amplification is the difficulty weighting §25.4 examines.

Drill 25.2 — Mean-subtracted advantages and leave-one-out

Prove that \(\mathcal R_i-\bar{\mathcal R}=\frac{n_s-1}{n_s}\Big(\mathcal R_i-\frac{1}{n_s-1}\sum_{j\ne i}\mathcal R_j\Big)\), and explain why subtracting \(\bar{\mathcal R}\), which depends on \(\mathcal R_i\), nevertheless gives a gradient that is unbiased up to scale.

Solution. Write \(S_{-i}=\sum_{j\ne i}\mathcal R_j\). Then \(\bar{\mathcal R}=(\mathcal R_i+S_{-i})/n_s\), and \(\mathcal R_i-\bar{\mathcal R}=\frac{(n_s-1)\mathcal R_i-S_{-i}}{n_s}=\frac{n_s-1}{n_s}\big(\mathcal R_i-\frac{S_{-i}}{n_s-1}\big)\). The bracket is the RLOO advantage, whose baseline \(S_{-i}/(n_s-1)\) is independent of \(y_i\), so its expected product with \(\nabla\log p_\theta(y_i)\) is the unbiased policy gradient (§23.3). Multiplying by the constant \((n_s-1)/n_s\) only rescales the gradient, which the learning rate absorbs. The division by the standard deviation is not a constant, since it depends on all the rewards, including \(\mathcal R_i\), and it does change the expected gradient.

25.4 What GRPO gets wrong: Dr. GRPO and DAPO

GRPO worked well enough to train DeepSeek-R1, and its success invited scrutiny. Two papers of March 2025 found biases in its objective and proposed fixes that are now standard. Liu et al.'s Dr. GRPO[9] ("GRPO done right") identified two biases, one from each normalisation in the objective of §25.3.

The first is a length bias. GRPO averages each response's token terms with the factor \(1/n_{y,i}\), so every response contributes the same total weight to the gradient, however long it is. For a correct response with positive advantage, this means each token of a short answer is pushed up more strongly than each token of a long one: brevity is favoured among correct responses. For a wrong response with negative advantage, it means a long wrong answer is penalised, in total, no more than a short one, and each of its tokens is penalised less: among wrong responses, length is the cheapest way to dilute the penalty. The asymmetry rewards models for making their wrong answers longer, and Liu et al. argued that part of the dramatic growth in response length during R1-Zero-style training is an artefact of this normalisation rather than a sign of better reasoning. Figure 25.4 shows the effect.

Figure 25.4 makes the argument quantitative. With GRPO's normalisation the total penalty is flat in length; with a constant per-token weight, as Dr. GRPO and DAPO use, it grows in proportion to length, so that rambling wrong answers are discouraged rather than tolerated. The second bias is a difficulty bias from the division by the standard deviation. A prompt on which the group almost agrees, nearly all right or nearly all wrong, has a small standard deviation and therefore large advantages (the 2.65 of the worked example in §25.3), so very easy and very hard prompts are up-weighted relative to prompts of intermediate difficulty. Dr. GRPO removes both normalisations, using the mean-subtracted reward as the advantage and a constant normaliser for the token sum, and reported comparable accuracy with markedly shorter, more efficient responses.

For the mathematician — which objective does GRPO optimise?

Take one prompt with pass rate \(p=p_\theta(x)\) and a binary reward. With a mean baseline, the expected update is proportional to \(\nabla_\theta p\), the gradient of the expected reward, as it should be. GRPO divides by the group's standard deviation, which for large groups concentrates at \(\sqrt{p(1-p)}\), so its expected update is approximately \(\nabla_\theta p/\sqrt{p(1-p)}\). Since

\[ \frac{\mathrm d}{\mathrm dp}\,2\arcsin\sqrt p\;=\;\frac{1}{\sqrt{p(1-p)}}, \]

this is the gradient of \(2\arcsin\sqrt{p}\). Summed over prompts, GRPO therefore ascends \(\sum_x2\arcsin\sqrt{p_\theta(x)}\) rather than the mean pass rate \(\sum_xp_\theta(x)\). Statisticians will recognise the arcsine square-root transform, the variance-stabilising transformation of a binomial proportion. Its derivative is unbounded at \(p=0\) and \(p=1\), which is the difficulty bias stated precisely: an improvement from 1% to 2% on a hard prompt is worth as much as one from 50% to 54% on a medium one, although it adds only a quarter as much expected reward. Whether that weighting is desirable is a modelling choice. It does favour pushing nearly solved prompts to certainty and lifting nearly unsolved ones off zero, but it is not the expected-reward objective, and Dr. GRPO's removal of the normalisation restores the latter.

Yu et al.'s DAPO[10] (Decoupled clip and Dynamic sAmpling Policy Optimisation), from ByteDance and Tsinghua, attacked the problems that made long RLVR runs unstable, with four changes. Clip-higher decouples the clipping range into \(\epsilon_{\text{low}}=0.2\) and \(\epsilon_{\text{high}}=0.28\), letting low-probability tokens with positive advantage grow further before they are clipped. With symmetric clipping, a token at probability 0.01 can rise only to 0.012 per update, so exploratory tokens cannot gain ground, and the policy's entropy collapses. Dynamic sampling discards groups whose samples are all correct or all wrong (zero advantage, §25.2) and keeps sampling until the batch is full of informative groups, so that the effective batch size does not shrink as the model improves. A token-level loss averages over all tokens in the batch, the length fix of Figure 25.4. Overlong reward shaping handles responses cut off at the maximum length, which would otherwise be labelled wrong for reasons unrelated to their content: they are masked from the loss or given a soft penalty that grows as the length approaches the limit. DAPO also dropped the KL penalty, arguing that for verifiable rewards the policy should be allowed to move far from its starting point. With these changes it reported 50 points on AIME 2024 from the Qwen2.5-32B base model, above DeepSeek's R1-Zero-style result on the same base model, in half the training steps.

A common thread runs through these fixes: entropy. RL on verifiable rewards sharpens the policy, concentrating probability on the reasoning paths that succeed, and the entropy of the token distribution falls rapidly early in training[15]. Once it has collapsed, the samples in a group become nearly identical, groups stop being informative, and learning stalls. Clip-higher, dynamic sampling, higher sampling temperatures (with the care of §23.8) and explicit entropy bonuses are all ways of keeping enough diversity in the samples for the group baseline to work.

25.5 Outcome rewards and process rewards

A verifier judges the final answer: it is an outcome reward. Over a long solution, the credit-assignment problem of §23.1 becomes severe: one bit at the end of ten thousand tokens says nothing about which steps were sound. A process reward model (PRM) instead scores each intermediate step, giving dense feedback. Lightman et al. (2023) trained both kinds[6] on mathematics: an outcome reward model on final-answer correctness, and a PRM on PRM800K, a dataset of 800,000 human labels of individual solution steps. Used to choose the best of many sampled solutions, the PRM solved 78% of a representative subset of the MATH benchmark against 72% for the outcome model, evidence that supervising the process helps. Math-Shepherd (Wang et al., 2023)[7] removed the human labels by estimating each step's quality automatically: from each intermediate step, roll out several completions and record how often they reach the correct answer, a Monte Carlo estimate of the step's value.

Figure 25.5 shows why process rewards are attractive, and its caption hints at why the largest RLVR runs have nonetheless used outcome rewards. A PRM is a learned model of step quality, so it reintroduces exactly what verifiable rewards removed: a neural judge that can be wrong and can be exploited. A policy optimised against it learns to write steps that look correct to the PRM. The notion of a "step" is itself ill-defined in free-form reasoning. And scoring every step of every rollout adds substantial inference cost. DeepSeek reported in the R1 paper that its attempts to use PRMs and Monte Carlo tree search did not pay off at scale, and R1 was trained with outcome rewards alone. PRMs remain useful for selecting among samples at inference time and for analysing where solutions fail, and the Monte Carlo estimate of Math-Shepherd is, mathematically, the value function of Chapter 23 estimated by rollouts instead of a critic.

25.6 What reinforcement learning teaches

The headline results of RLVR are striking. DeepSeek-R1-Zero, trained from the DeepSeek-V3 base model with GRPO and only accuracy and format rewards, raised its pass@1 on the AIME 2024 competition from 15.6% to 71.0%, and to 86.7% with majority voting over 64 samples. As training progressed, its responses grew from hundreds to many thousands of tokens without any reward for length, and the model began to re-examine its own steps mid-solution, the "aha moment" the authors highlighted. R1-Zero's outputs were hard to read, mixing languages, so DeepSeek-R1 added a small "cold start" of readable reasoning demonstrations before RL, then rounds of rejection-sampling SFT and RL across all task types. The same paper showed that distillation beats RL for small models: fine-tuning Qwen-32B on 800,000 samples from R1 produced a stronger reasoner than applying large-scale RL to Qwen-32B directly. Reasoning, once discovered by RL in a large model, is cheapest to transfer by SFT (§15.5).

What exactly does RL add? Yue et al. (2025) measured pass@[11]\(k\), the probability that at least one of \(k\) samples is correct, for base models and their RLVR-trained versions across a range of \(k\). The RL-trained models were much better at small \(k\), but at large \(k\), in the hundreds, the base models caught up and often overtook them: problems that the RL model could solve were, almost always, problems the base model could already solve occasionally. Their interpretation, still debated, is that RLVR mainly sharpens the distribution, moving probability onto reasoning paths the base model already contained, rather than creating new ones, and that the entropy collapse of §25.4 narrows the set of problems solved at large \(k\). Distillation from a stronger teacher, by contrast, can add capabilities the student lacked.

For inference engineers, the consequence is a model whose outputs are long and whose quality depends on how long it is allowed to think, which is the subject of Chapter 26. For the trainers of such models, the consequence is that the cost of RLVR is dominated by producing those long outputs during training, which is the subject of the last section.

25.7 Rollout systems

An RLVR step generates \(n_s\) long responses for each of hundreds of prompts, verifies them, and trains on them. Two facts about the generation phase shape the systems built for it. First, response lengths vary enormously, from a few hundred tokens to the maximum allowed, so a batch that starts full empties gradually, and the GPUs spend the end of each step decoding a few stragglers at a small batch size and a small fraction of their capacity (Drill 26.2 estimates the effect for exponential lengths). Second, the generation engine and the trainer are different programs, whose weights must be synchronised after each update (§26.7) and whose numerics differ (§23.8).

Worked example — one RLVR step for an 8B model on 64 H100s

Setup. 512 prompts, \(n_s=16\): 8,192 rollouts with mean length 4,000 tokens and a cap of 16,384, about \(3.3\times10^7\) generated tokens. Each H100 runs an 8B replica and decodes 128 rollouts.

Generation, ideal. At an average context of about 2,500 tokens, 128 sequences hold \(128\times2500\times128\) KiB ≈ 42 GB of cache; with 16 GB of weights a step reads about 58 GB, 22 ms at 80% of peak bandwidth, so a full GPU produces about 5,900 tokens per second. If every GPU stayed full, the \(3.3\times10^7\) tokens would take \(3.3\times10^7/(64\times5900)\approx87\) s.

Generation, real. With roughly exponential lengths, about 1.7% of rollouts (\(e^{-16384/4000}\)) reach the 16,384-token cap, so most GPUs hold at least one. Such a GPU must run 16,384 sequential decode steps; even averaging about 12 ms per step as its batch empties, that is about 200 s. The phase lasts about 200 s for 87 s of useful work: under 45% utilisation.

Training. A reference pass (\(2N\)) and one policy update with checkpointing (\(8N\)) over \(3.3\times10^7\) tokens: \(10\times8.03\times10^9\times3.3\times10^7\approx2.6\times10^{18}\) FLOPs, about 105 s at 40% MFU across 64 GPUs.

Consequence. The step takes about 300 s, two thirds of it generation, and more than half of the generation time is the long tail. Halving the decode time per token, or removing the tail, saves more than halving training time would.

The worked example shows where the engineering effort goes. Systems attack the tail from several directions. Length caps and curricula start training with a short maximum length and raise it as the model learns to use the space, so that early steps are cheap. Over-sampling with early termination launches more groups than needed and stops the phase when enough have finished, discarding or deferring the stragglers. Partial rollouts, used by Kimi k1.5[12], cap the tokens generated per step and carry unfinished responses over to the next step, continuing them with the updated policy. Asynchronous RL decouples the phases completely[14]: a fleet of generators produces rollouts continuously with whatever weights they have, a trainer consumes them as they arrive, and new weights are pushed to the generators periodically. Figure 25.6 compares the synchronous and asynchronous timelines.

Figure 25.6 makes the trade explicit. Asynchronous training keeps every GPU busy, but its rollouts come from a policy \(n_{\text{stale}}\) updates behind the one being trained, so the gradient is off-policy. For small staleness the importance ratio in PPO's clipped objective (§23.6) and the truncated sampler corrections of §23.8 handle the mismatch, and systems such as AReaL reported[13] large speed-ups at comparable accuracy with staleness of a few steps. For large staleness the corrections become noisy and training degrades. The choice of \(n_{\text{stale}}\) is thus a statistical parameter set by systems considerations, which is the theme of this whole Part in miniature.

Behind all these techniques is the inference engine. Continuous batching (Chapter 11) refills slots as rollouts finish; prefix caching (§10.6) shares the prompt across a group; speculative decoding (Chapter 20) can shorten the tail if the draft model is kept in step with the policy; and FP8 generation (Chapter 14) halves bytes per step, at the price of a larger sampler–trainer mismatch. Every technique of Parts III to VII reappears inside the training loop.

Looking ahead

Part VIII has built the training side of modern post-training: reinforcement learning and PPO (Chapter 23), learning from preferences with RLHF and DPO (Chapter 24), and learning from verifiable rewards with GRPO and its successors (this chapter). The models that result think at length before they answer, and their quality depends on how much they are allowed to think. Chapter 26 turns to those reasoning models from the inference side: how test-time compute scales quality, the mathematics of parallel sampling and voting, how thinking length can be controlled, what reasoning tokens cost to serve, and how serving systems must adapt to outputs that are ten times longer than the ones the rest of this book assumed.

Chapter summary

  • Verifiable rewards are computed by programs (answer matching, unit tests, format and constraint checks): binary, low-noise and sparse, but hackable through weak checkers. R1-Zero used only accuracy and format rewards.
  • A group of \(n_s\) samples is informative with probability \(1-p_s^{n_s}-(1-p_s)^{n_s}\); prompts that are always or never solved give no gradient, so data must be filtered and refreshed.
  • RLOO uses the leave-one-out mean as baseline (unbiased). GRPO's mean-subtracted reward equals RLOO times \((n_s-1)/n_s\); its division by the group standard deviation reweights prompts. GRPO plugs the advantage into PPO's clipped objective with a \(k_3\) KL term and holds only policy and reference (about \(18N\) bytes).
  • Dr. GRPO: per-response length normalisation tolerates long wrong answers, and standard-deviation normalisation up-weights very easy and very hard prompts; remove both.
  • With a binary reward, GRPO's standard-deviation normalisation makes it approximately ascend \(\sum_x2\arcsin\sqrt{p_\theta(x)}\), the variance-stabilising transform of the pass rate, rather than the expected reward itself.
  • DAPO: clip-higher (\(\epsilon_{\text{low}}=0.2\), \(\epsilon_{\text{high}}=0.28\)) against entropy collapse, dynamic sampling of informative groups, token-level loss, overlong reward shaping, no KL.
  • Process reward models give dense credit (PRM800K, Math-Shepherd's Monte Carlo step values) but are learned, hackable and costly; large RLVR runs have mostly used outcome rewards.
  • RLVR raised R1-Zero's AIME pass@1 from 15.6% to 71.0% and grew its responses unprompted; it mainly sharpens pass@1 (base models can match at large \(k\)); distillation transfers reasoning to small models better than RL on them.
  • An RLVR step is mostly generation, and much of that is the long tail. Length curricula, over-sampling, partial rollouts and asynchronous training (with staleness corrections) keep GPUs busy.

  2. Sampling at temperature 1
  3. Weak unit tests that a program can satisfy by special-casing visible inputs
  4. Using a reference model
Soundness of the checker is the new alignment burden.

Compared with learned preference rewards, verifiable rewards are:

  1. Dense and noisy
  2. Sparse, nearly binary and low-noise
  3. Continuous and differentiable
  4. Always process-level
One bit per response, but trustworthy if the checker is sound.

A group of 8 samples for a prompt the model solves with probability 0.5 is informative (mixed outcomes) with probability about:

  1. 50%
  2. 87.5%
  3. 99%
  4. 100%
\(1-2\times0.5^8\approx0.992\).

Why does a prompt that the model always solves contribute no gradient in GRPO?

  1. Its KL is zero
  2. All rewards equal the group mean, so every advantage is zero
  3. It is filtered by the verifier
  4. Its responses are too short
Learning from binary rewards needs contrast within the group.

For a prompt solved 2% of the time, a group of 8 is informative about:

  1. 2% of the time
  2. 15% of the time
  3. 50% of the time
  4. 85% of the time
\(1-0.98^8\approx0.149\).

Why must the prompt mix be refreshed during RLVR?

  1. To avoid memorising answers only
  2. As the model improves, prompts move out of the informative middle band of pass rates
  3. To change the verifier
  4. Because the reference model changes
Easy prompts become always-solved; hard ones become reachable.

RLOO's baseline for sample \(i\) is:

  1. The mean of all samples including \(i\)
  2. The mean reward of the other \(n_s-1\) samples
  3. A learned critic
  4. Zero
It is independent of \(y_i\), so the estimator is exactly unbiased.

\(\mathcal R_i-\bar{\mathcal R}\) (mean over the whole group) equals the RLOO advantage multiplied by:

  1. 1
  2. \((n_s-1)/n_s\)
  3. \(n_s/(n_s-1)\)
  4. \(1/\operatorname{std}\)
So the mean-subtracted numerator is unbiased up to scale.

With 3 of 8 samples correct, GRPO's advantage for a correct sample is about:

  1. 0.625
  2. 0.71
  3. 1.29
  4. 2.65
\((1-0.375)/\sqrt{0.375\times0.625}\approx0.625/0.484\).

Compared with PPO for language models, GRPO removes:

  1. The critic
  2. The reference model, always
  3. The reward model (when rewards are verifiable)
  4. The clipped ratio
It holds the policy and, with a KL term, a reference: about \(18N\) bytes instead of \(36N\).

In GRPO, the advantage of each token of response \(i\) is:

  1. Estimated by GAE
  2. The same: the response's group-relative advantage \(\hat A_i\)
  3. Zero except the last token
  4. Proportional to its log-probability
Credit is not assigned within a response, unlike PPO with a critic.

GRPO includes the KL penalty to the reference:

  1. In the reward, per token
  2. Directly in the loss, using the \(k_3\) estimator
  3. Not at all
  4. Only at evaluation
PPO-RLHF usually folds \(-\beta k_1\) into rewards; GRPO adds \(\beta k_3\) to the loss.

Why are groups of samples cheap for an inference engine to generate?

  1. They use a smaller model
  2. The prompt's KV cache can be computed once and shared by all samples of the group
  3. They are generated greedily
  4. They skip the verifier
Prefix caching (§10.6) or parallel sampling with a shared prefix.

Under GRPO's per-response averaging (\(1/n_{y,i}\)), a long wrong answer:

  1. Is penalised more than a short one
  2. Receives the same total penalty as a short one, so each of its tokens is penalised less
  3. Is ignored
  4. Gets a positive advantage
This encourages lengthening wrong answers, a bias identified by Dr. GRPO.

Dividing advantages by the group standard deviation:

  1. Has no effect on the gradient's direction
  2. Up-weights prompts whose samples nearly agree (very easy or very hard)
  3. Removes the length bias
  4. Makes the estimator unbiased
Small standard deviation means large advantages; Dr. GRPO removes it.

DAPO's clip-higher (\(\epsilon_{\text{high}}=0.28>\epsilon_{\text{low}}=0.2\)) mainly addresses:

  1. Memory use
  2. Entropy collapse: low-probability tokens with positive advantage can grow more per update
  3. Verifier errors
  4. Weight synchronisation
With symmetric clipping, a 1% token can only reach 1.2% per update.

DAPO's dynamic sampling:

  1. Changes the temperature per prompt
  2. Discards all-correct and all-wrong groups and keeps sampling until the batch has enough informative groups
  3. Samples fewer responses for hard prompts
  4. Uses a draft model
It keeps the effective batch size from shrinking as accuracy rises.

Why do truncated (over-length) responses need special handling?

  1. They cannot be tokenised
  2. Labelling them wrong penalises reasoning that may have been sound but unfinished, adding reward noise
  3. They break the KV cache
  4. They are always correct
DAPO masks them or applies a soft length penalty near the limit.

A token-level loss (averaging over all tokens in the batch) means:

  1. Short responses dominate the gradient
  2. Each token has equal weight, so longer responses contribute proportionally more
  3. Only the last token matters
  4. The KL term is removed
It fixes the length bias of per-response averaging.

A process reward model differs from an outcome reward by:

  1. Using human preferences
  2. Scoring each intermediate step rather than only the final answer
  3. Being a program
  4. Ignoring the answer
Dense credit, at the cost of a learned, exploitable judge.

Math-Shepherd labels a solution step automatically by:

  1. Asking humans
  2. Rolling out completions from that step and measuring how often they reach the correct answer
  3. Checking its syntax
  4. Its length
A Monte Carlo estimate of the step's value.

Why did DeepSeek-R1 use outcome rewards rather than PRMs?

  1. PRMs did not exist
  2. PRMs reintroduce a learned, hackable judge, steps are ill-defined, and scoring every step is costly; their attempts did not pay off at scale
  3. Outcome rewards are dense
  4. PRMs need a critic
The R1 paper lists PRMs and MCTS among unsuccessful attempts.

During R1-Zero's RL training, average response length:

  1. Stayed constant
  2. Grew from hundreds to thousands of tokens without a length reward
  3. Shrank
  4. Was fixed by a cap at 512
The model learned to think longer; Dr. GRPO argued part of the growth is a normalisation artefact.

The R1 paper found that, for a 32B model, the stronger reasoner came from:

  1. Large-scale RL on the 32B model
  2. Fine-tuning it on samples from R1 (distillation)
  3. Prompting with chain of thought
  4. A PRM
Reasoning discovered by RL in a large model transfers cheaply by SFT.

Yue et al. (2025) found that, compared with their base models, RLVR-trained models:

  1. Were better at every \(k\)
  2. Were better at small \(k\) but often matched or were overtaken by the base model at large \(k\)
  3. Were worse at pass@1
  4. Solved entirely new problems
Interpreted as sharpening the distribution rather than adding new reasoning paths.

Why is entropy collapse harmful in RLVR?

  1. It increases memory use
  2. Samples in a group become nearly identical, groups stop being informative, and learning stalls
  3. It slows decoding
  4. It breaks the verifier
Clip-higher, dynamic sampling, temperature and entropy bonuses counter it.

In synchronous RLVR, why is GPU utilisation during generation often below 50%?

  1. The verifier is slow
  2. Response lengths vary widely, so batches empty and GPUs spend the end of the phase decoding a few long stragglers
  3. Prefill dominates
  4. The KV cache is too small
A few rollouts hitting the length cap set the phase's duration.

Partial rollouts (as in Kimi k1.5):

  1. Truncate responses and mark them wrong
  2. Cap tokens generated per step and continue unfinished responses in the next step with updated weights
  3. Generate only the answer
  4. Skip verification
They bound the step time without discarding long reasoning.

The cost of asynchronous RL is that:

  1. The trainer is idle
  2. Rollouts come from a policy several updates old, so the gradient is off-policy and must be corrected
  3. It needs more verifiers
  4. It cannot use GRPO
Clipped ratios and truncated importance weights handle small staleness.

In the 8B, 64-GPU worked example, roughly what fraction of the RLVR step is generation?

  1. 10%
  2. 33%
  3. 67%
  4. 95%
About 200 s of generation (much of it tail) against about 105 s of training.

Warm-up What is RLVR, and how does it differ from RLHF?

Reinforcement learning with verifiable rewards trains a model on problems whose outputs can be checked by a program: maths answers against references, code against unit tests, instructions against parsers. RLHF uses a reward model learned from human preferences, which is noisy (around 70% agreement) and exploitable, so it needs a KL leash and careful early stopping. RLVR's reward is binary, low-noise and sparse. There is no reward model and usually no critic (GRPO, RLOO), and optimisation can push much further, which is how reasoning models such as o1 and R1 were trained. The new failure mode is unsound checkers, and the cost is dominated by generating many long samples per prompt.

Core Derive GRPO's advantage and relate it to RLOO.

Start from REINFORCE with a baseline: any baseline independent of the sampled response is unbiased, and the ideal is the policy's expected reward on the prompt. Sample a group of \(n_s\) responses. RLOO uses the leave-one-out mean, \(\hat A_i=\mathcal R_i-\frac1{n_s-1}\sum_{j\ne i}\mathcal R_j\): exactly unbiased. GRPO uses \((\mathcal R_i-\bar{\mathcal R})/\operatorname{std}\). Algebra: \(\mathcal R_i-\bar{\mathcal R}=\frac{n_s-1}{n_s}\hat A_i^{\text{RLOO}}\), so the numerator is unbiased up to scale. The standard-deviation division reweights prompts (more weight when samples nearly agree), which biases the gradient. GRPO broadcasts \(\hat A_i\) to all tokens and uses PPO's clipped ratio with a \(k_3\) KL term in the loss.

Core Why does GRPO not need a critic, and what does it give up?

The critic in PPO supplies a baseline \(V(s)\). GRPO instead estimates the prompt-level baseline from the other samples in the group, which, for a binary reward and a group of 8–64, is a decent estimate of the pass rate. That removes a network the size of the policy (16N bytes of state), the hard problem of learning values over text prefixes, and the bias a bad critic introduces. It gives up per-token credit assignment: every token of a response gets the same advantage, so the model is not told which steps mattered, only which responses were better. It also requires multiple samples per prompt, which is acceptable because informative groups need them anyway and an inference engine shares the prompt's KV cache.

Deep-dive Explain the two biases Dr. GRPO identified and their effects.

Length bias: GRPO averages each response's token losses by \(1/n_{y,i}\), so every response has equal total weight. For negative advantages, a long wrong response is penalised no more in total than a short one, and less per token. For positive advantages, short correct responses get larger per-token pushes. The net incentive is to lengthen wrong answers, which inflates response length beyond what better reasoning needs. Difficulty bias: dividing by the group's standard deviation gives large advantages to prompts where samples nearly agree (pass rates near 0 or 1), over-weighting very easy and very hard prompts relative to intermediate ones. Fix: use mean-subtracted rewards without std normalisation, and sum token losses with a constant normaliser. They reported similar accuracy with shorter responses (better token efficiency).

Core Describe DAPO's four changes and why each helps.

Clip-higher: asymmetric clipping (\(\epsilon_{\text{low}}=0.2\), \(\epsilon_{\text{high}}=0.28\)) lets low-probability tokens with positive advantage grow more per update, countering entropy collapse and preserving exploration. Dynamic sampling: drop groups with all-correct or all-wrong outcomes (zero advantage) and resample to keep the batch full of informative groups, so the gradient's effective batch size does not shrink as accuracy rises. Token-level policy-gradient loss: average over all tokens in the batch, removing the length bias of per-sample averaging. Overlong reward shaping: mask or softly penalise truncated responses instead of marking them wrong, removing reward noise from the cap. It also removed the KL penalty for verifiable rewards. Result: 50 on AIME 2024 from Qwen2.5-32B base in half the steps of the R1-Zero-style baseline.

Core When does a group of samples provide learning signal? How would you build an RLVR dataset?

With binary rewards, only groups with both successes and failures have non-zero advantages. If the prompt's pass rate is \(p\), a group of \(n\) is informative with probability \(1-p^n-(1-p)^n\): near 1 for \(p\) in the middle, small near 0 or 1 (for \(p=0.02,n=8\), about 15%). Dataset design: estimate each prompt's pass rate with the current model (e.g. 8–16 samples), keep a middle band (say 10–90%), balance domains, deduplicate, and verify that references and tests are sound. During training, refresh the pool as the model improves (a curriculum), use dynamic sampling to replace uninformative groups, and use larger groups or SFT warm-up for valuable hard prompts.

Core Outcome versus process rewards: trade-offs, and what large runs used.

Outcome rewards check only the final answer: sound, cheap and hard to hack, but sparse, giving no indication of which steps were good. Process reward models score each step: dense credit (Lightman et al.: a PRM chose correct solutions more often than an outcome model, 78% versus 72% on a MATH subset). They need step labels (human, as in PRM800K, or Monte Carlo, as in Math-Shepherd), are learned and therefore exploitable, depend on an ill-defined segmentation into steps, and add inference cost. DeepSeek-R1 found PRMs did not pay off at scale and used outcome rewards. PRMs remain useful for best-of-\(n\) selection, search and diagnosis. A Monte Carlo step value is the RL value function estimated by rollouts.

Design Estimate the time of one RLVR step for an 8B model with 512 prompts, 16 samples each, mean length 4k, cap 16k, on 64 H100s. Where would you optimise?

Tokens: 8,192 × 4,000 ≈ 33M. Each GPU decodes 128 sequences; at an average context of 2.5k a step reads about 58 GB, 22 ms, so about 5,900 tokens/s per GPU and 87 s if always full. But about 1.7% of rollouts hit the 16k cap, so most GPUs run 16k sequential steps at falling batch, about 200 s: under 45% utilisation. Training: \((2N+8N)\times33\text{M}\approx2.6\times10^{18}\) FLOPs, about 105 s at 40% MFU. Step about 300 s, two thirds generation. Optimise the tail first: length curriculum (start at 8k), over-sample and stop early, partial rollouts, or asynchronous generation. Then per-token decode cost: FP8 weights and KV, CUDA graphs, larger batches, speculative decoding. Then colocate or overlap training with generation.

Deep-dive Does RLVR teach models new reasoning? Discuss the pass@k evidence.

Yue et al. (2025) compared base and RLVR-trained models by pass@\(k\). RL models win at small \(k\), but base models catch up or overtake at large \(k\) (hundreds of samples), and the problems RL models solve are mostly ones the base model already solved occasionally. Interpretation: RLVR mostly sharpens, moving probability to successful paths the base model already contains. Entropy collapse may even shrink the set of solvable problems at large \(k\). Counterpoints: pass@1 and token efficiency are what users experience; long RL runs with exploration-preserving tricks (clip-higher, entropy control) and bigger budgets report gains at larger \(k\); and RL elicits behaviours (self-verification, backtracking) that make long reasoning usable. Distillation from a stronger teacher can add capabilities a student lacks, which is why small reasoning models are distilled rather than trained by RL.

Design Design a rollout system for RLVR on a 70B model at large scale.

Generators: a fleet of inference engines (vLLM or SGLang) with TP within nodes, continuous batching, prefix sharing across each group, FP8 weights and KV if the logprob mismatch is acceptable, and CUDA graphs. Trainer: FSDP or Megatron on a separate pool, or colocated with resharding between the layouts. Weight sync: a broadcast tree or NCCL from trainer to generators after each update (hundreds of GB, which must take seconds, not minutes). Tail control: length curriculum, over-sampling with early termination, partial rollouts that carry unfinished responses forward, or fully asynchronous generation with bounded staleness (1–4 steps) and truncated importance weights. Verification: a horizontally scaled CPU sandbox service with timeouts and isolation, plus caching of results. Data: online pass-rate estimation and dynamic sampling. Monitoring: generation throughput, tail lengths, uninformative-group fraction, entropy, logprob mismatch and reward-hacking audits.

Core What is entropy collapse in RL fine-tuning, and how is it mitigated?

RL sharpens the policy on successful paths, so token-level entropy drops quickly early in training. Once collapsed, the samples in a group are near-duplicates, all right or all wrong, advantages vanish and exploration stops: learning plateaus and pass@\(k\) at large \(k\) can fall. Mitigations: clip-higher (let rising low-probability tokens grow more), dynamic sampling (train only on informative groups), sampling temperature adjustments (keeping the gradient's sampling assumptions consistent), entropy bonuses or entropy-targeting regularisers, KL to a reference (which also restrains sharpening), diverse prompt pools, and avoiding too many updates per batch.

Warm-up Why are truncated responses a problem in RLVR, and how are they handled?

A response cut off at the maximum length has no final answer, so a naive verifier marks it wrong, penalising reasoning that may have been on track and confusing "too long" with "wrong". This adds reward noise and pushes the model toward shorter, possibly worse reasoning, or, under GRPO's length bias, toward unhelpful patterns. Handling: mask truncated responses from the loss (overlong filtering), apply a soft penalty that grows as length nears the cap (overlong shaping), raise the cap over training (curriculum), or use partial rollouts that let a response continue in a later step.

Core Summarise the DeepSeek-R1 training pipeline and what R1-Zero showed.

R1-Zero: GRPO directly on the DeepSeek-V3 base model with accuracy and format rewards only, no SFT. AIME 2024 pass@1 rose from 15.6% to 71.0% (86.7% with majority voting over 64 samples); response length grew to thousands of tokens on its own, and reflective behaviour emerged. But outputs were hard to read and mixed languages. R1: a cold-start SFT on a small set of readable long chains of thought; reasoning-focused RL (with a language-consistency reward); rejection-sampling SFT on about 800k samples (reasoning plus general data); then RL across all scenarios (verifiable rewards for reasoning, preference rewards for helpfulness and harmlessness). Distilled models (Qwen and Llama, 1.5–70B) fine-tuned on R1 samples outperformed RL applied directly to models of their size.

Deep-dive Synchronous versus asynchronous RL: what is the statistical cost of asynchrony, and how is it controlled?

Synchronous RL generates with the current weights, then trains: on-policy, but GPUs idle during the tail and during training if pools are separate. Asynchronous RL generates continuously with weights \(n_{\text{stale}}\) updates old: the samples come from \(p_{\theta_{k-n_{\text{stale}}}}\) while the gradient is for \(p_{\theta_k}\), so it is off-policy. Corrections: compute the PPO ratio against the generating policy's log-probs (recomputed in the trainer), clip it, and apply truncated per-token importance weights for the remaining mismatch. Variance and bias grow with staleness and with how fast the policy changes (learning rate, updates per batch). Control: bound staleness (1–4 steps), interrupt and restart very long rollouts with new weights, monitor ratio statistics, and lower the learning rate if the clipping fraction rises.

Design How would you build a code-RL verifier service, and what can go wrong?

A pool of isolated sandboxes (containers or microVMs) with no network, CPU and memory limits, and timeouts. Each rollout's program is run against hidden unit tests, and the service returns the pass fraction or all-pass. Scale horizontally, since thousands of rollouts per step need thousands of CPU-seconds, and pipeline verification with generation so it never blocks the trainer. Cache results by program hash. Failure modes: reward hacking through weak tests (special-casing inputs, printing expected outputs), exploiting the harness (modifying tests, exiting with a success code, reading the test files), non-deterministic tests (flaky rewards), timeouts mislabelled as failures, and resource exhaustion. Mitigations: strong, hidden and randomised tests, a read-only harness, auditing high-reward samples, and penalties for detected tampering.

Core Compare the memory and compute of PPO, GRPO and RLOO for an 8B policy.

PPO: actor and critic trained (16N each), reference and reward model frozen (2N each): about \(36N\) = 289 GB, plus a critic forward and backward pass per step. GRPO: policy trained (16N) plus a frozen reference for the KL term (2N): \(18N\) = 145 GB, and none if the KL term is dropped (as in DAPO) or if LoRA makes the reference the base model. RLOO: the same models as GRPO, with a leave-one-out baseline and no standard-deviation normalisation. Both GRPO and RLOO need \(n_s\) samples per prompt, so generation per prompt is \(n_s\) times PPO's single sample, but that generation shares the prompt's prefill, and verifiable rewards need groups anyway. Training compute per generated token is lower without a critic: \(8N\) policy (with checkpointing) plus \(2N\) reference, against about \(20N\) for PPO (actor and critic at \(8N\) each, plus reference and reward-model passes).
